## User-visible outcome

A decision, with the elimination stated so a reader can refute it, on which of two live designs makes a reassociated pointwise chain checkable — so the largest non-reduction freedom site stops being unevaluable.

## Why this exists

**Fact — the grouping is already pinned, and the gap is on the other side.** [The freedom-sites enumeration](../docs/research/reference/plan-freedom-sites.md) Part 3.3 and Part 4 establish that `ScalarProgram::PointwiseF32(expression)` pins the emitted grouping exactly: `PointwiseF32Node::Add { lhs, rhs }` (`crates/tiler-ir/src/schedule/pointwise.rs:91`) is a binary node over dense topological ordinals, and `mint_elementwise` (`crates/tiler-compiler/src/request.rs:4697`) mints it as a faithful image of the possibly-reassociated semantic DAG. So the site is a witness. It is unevaluable.

**Fact — two designs are live and neither is correctness-dominant, which is why this is a decision and not research.**

1. **Retain the selected semantic candidate's program.** The reference already evaluates a `SemanticProgram` exactly (`ReferenceEvaluator::evaluate`, `crates/tiler-reference/src/evaluate.rs:178`). The rewritten program is discarded: it lives only in `SemanticCandidate.proposal` (`crates/tiler-compiler/src/pipeline.rs:328-333`), a private pipeline struct, and the retained `ProgramAlternative` (`pipeline.rs:247-271`) has no semantic-program field. Exact check: `grep -rn "pub fn .*SemanticProgram" crates/tiler-compiler/src/` returns nothing. Retaining it costs memory and a public accessor and needs no new evaluator.
2. **Write an exact evaluator for `PointwiseF32Expression`.** Costs a second evaluator and a new dependency edge — `grep -rn "ScalarProgram\|ReductionTopology\|VerifiedScheduledRegion\|PointwiseF32" crates/tiler-reference/` returns one line today, a doc comment in a test — but answers for the *physical* projection rather than for a semantic form the projection is trusted to mirror, which is the stronger claim.

**Inference — the difference is which artifact the oracle is evidence about**, and that is a genuine priority split rather than a cost trade: design 1 checks that the device matches the semantic program the compiler chose, design 2 checks that it matches the expression the compiler emitted. A projection defect is invisible to the first and caught by the second.

## What this ticket must produce

The elimination run explicitly against correctness, performance, and long-term maintainability, with the surviving design named; or, if both survive, one atomic question for Tom with a small worked tensor program, point, counterpoint, and a recommendation.

## Explicit non-goals

Implementing either design; accepting the witness surface, which is `accept-the-realization-witness-surface`.

## Closes when

One design survives with the derivation stated, or the fork reaches Tom as one atomic question.

## Outcome

**One design survives, and it is design 1 — retain the selected semantic candidate's program.** Recommended terminal state: `done`. The elimination is below; the same derivation lands in [the freedom-sites record's](../docs/research/reference/plan-freedom-sites.md) Part 7.3, which previously parked this fork. Nothing was implemented, no `crates/` file was touched, and the public boundary design 1 eventually needs is still Tom's.

**Fact — this ticket's own framing Inference is refuted at source, and the refutation is the elimination.** The body above states that "a projection defect is invisible to the first and caught by the second". The projection sits *between* the selected semantic program and the observed device bits, so the two designs' comparisons do not straddle it symmetrically. Write `P'` for the semantic candidate the portfolio selected, `E` for the `PointwiseF32Expression` `mint_elementwise` produced from it, and `z` for the candidate's observed output bits. Design 1 compares `z` against `ReferenceEvaluator::evaluate(P', inputs)` — across the projection, the kernel lowering, the emission, and the device. Design 2 compares `z` against an evaluation of `E` — across the lowering, the emission, and the device only, with its expected value read *out of* the artifact the projection produced. Coverage is strict containment, and in the opposite direction from the one the body asserts: a projection defect is caught by design 1 and invisible to design 2.

**Fact — the shape of the accepted parent derivation confirms the reading rather than depending on it.** [The permitted-divergence oracle](../docs/research/reference/permitted-divergence-oracle.md) Part 2.2 defines its surviving candidate O5 over `(P, C, W)` where `P` is the *semantic program* and `K` is "a compiled candidate with observed output bits `z`". Design 1 is exactly O5 with `W` = which candidate the portfolio selected. Design 2 is not O5 at another witness; it is an oracle over a different subject, and it fails the same test Part 2.3 uses to eliminate O4: "membership … accepts a strategy that produced some *other* legal grouping than the one it declared". Design 2 is weaker still than the candidate that argument eliminated — it admits an `E` that is not a legal grouping of `P'` at all, including one that drops a semantic operand, because the reference re-reads the compiler's own answer.

**Fact — the projection-defect class is unguarded, and it has fired.** Nothing in the workspace cross-checks the minted expression against the semantic DAG, by five reproducible checks:

1. `grep -rn "PointwiseF32Expression" crates/ --include='*.rs'` leaves exactly two non-test consumers outside the defining module: `verify_pointwise_f32` (`crates/tiler-ir/src/schedule/builder.rs:620-632`), which checks `expression.input_count()` against the read count and `expression.is_valid()` — structural only, no semantics — and `emit_pointwise` (`crates/tiler-ir/src/kernel/lower.rs:1632`), which lowers it.
2. The other copies are not independent derivations. The region's expression is `pointwise.expression.clone()` (`crates/tiler-compiler/src/physical.rs:820`, stored at `:957`) taken from the same `RecognizedElementwise` the request subject carries and encodes (`crates/tiler-compiler/src/request.rs:1289`, `:1412`, `encode_output_subject` at `:2268`). One `mint_elementwise` call is the common ancestor of every copy, so subject-versus-region agreement is self-consistency, not verification.
3. The one genuinely independent re-derivation in the tree does not reach it. `IndexRealizationLaw` (`crates/tiler-ir/src/index/law.rs:1-10`) "builds the expected canonical region" from the semantic operation's own attributes and requires exact canonical identity — but its subject is one occurrence's `VerifiedIndexRegion` emitted by the resolved lowering provider (`crates/tiler-compiler/src/lowering.rs:1-23`, `refine_index_region` at `crates/tiler-compiler/src/legality.rs:754`), never the fused `ScalarProgram::PointwiseF32`. It proves each occurrence is canonically realizable; it says nothing about which operands the fused expression's nodes consume, which is where a regrouping lives.
4. The whole-program numerical proof is unavailable exactly where the freedom is spent. `prove_fused_numerics` (`crates/tiler-compiler/src/fusion.rs:178-184`) returns `invalid(candidate, "strict-f32-proof")` whenever the contract's contraction or reassociation is anything but `Forbidden`, and its retained content is five fixed enum tags, so under `REASSOCIATE_F32` or `RELAXED_F32` it neither fires nor discriminates.
5. **It has fired.** `LeafRead`'s doc (`crates/tiler-compiler/src/request.rs:4206-4213`) records a shipped projection defect: keying leaves by value alone made the two reads of `a` in `a * permute(a)` one leaf, "so the region bound one access for both and `a * permute(a)` compiled as `permute(a) * permute(a)`". That is a wrong value produced inside `plan_elementwise`/`canonical_input_reads`. Design 1's comparison refuses it, because the reference evaluates `a * permute(a)` from the program. Design 2's admits it, because the expression *and* its read list both carry the collapsed leaf, so the reference reads the same wrong tensor the device does and agrees with it.

**Inference — so the reachability question resolves the fork instead of narrowing design 2.** The brief anticipated that an existing cross-check would narrow design 2's advantage; the finding is the reverse. No such check exists, so the projection genuinely needs oracle coverage — and design 2, whose expected value is downstream of the projection, is structurally incapable of providing it.

**Fact — design 2 additionally cannot be exact over the population it exists for, and the vocabulary says so at its own definition.** `PointwiseF32Node::Exp` (`crates/tiler-ir/src/schedule/pointwise.rs:117-124`) is "the one node in this vocabulary whose result is not a rational function of its operands, so it is the one whose admitted result set comes from a registered accuracy contract rather than from IEEE-754 alone", and `Rsqrt` (`:128-136`) states that its admitted result set "comes from the registered accuracy contract of the operation this expression realizes, never from IEEE-754 alone". The expression alone therefore does not determine a value at those nodes; the semantic operation does. **This is reachable rather than reserved:** `ElementwiseFamily::Silu` is a recognized production family (`request.rs:4307-4311`, `elementwise_family` at `:4330`), and `mint_elementwise` mints its body through `silu_point_body` (`crates/tiler-compiler/src/elementary.rs:125-135`) as `constant`/`multiply`/`exp`/`constant`/`add`/`divide` nodes directly into the same `PointwiseF32Expression` a reassociated chain carries. An exact evaluator over `E` would have to either refuse every expression containing `Exp` or `Rsqrt` — leaving part of its own population unevaluable, which is the gap it was written to close — or reconstruct the realized operation's accuracy contract, which `E` cannot supply: its nodes carry no member attribution, `PointwiseF32Expression` being `nodes` plus `root` (`pointwise.rs:150-153`) with the members kept beside it on `RecognizedElementwise`. Design 1 has no such problem: the operation is present, and `tiler::silu-f32@1`'s admitted set is what the reference registry already answers with (`crates/tiler-reference/src/silu.rs:26`, registered at `crates/tiler-reference/src/standard.rs:175`).

**Two independent correctness grounds, either sufficient. Design 2 is eliminated on correctness.** The remaining criteria are reported rather than decisive, because a correctness elimination that also happens to be the cheap option should be checked from the other side.

**Long-term maintainability.** Design 1 moves no reference-crate surface at all: `SemanticProgram` is a `tiler_ir::semantic` type `ReferenceEvaluator::evaluate` already takes, so the change is retention plus an accessor on the plan side. Design 2 adds a second evaluator plus the dependency edge the freedom-sites record names as its most consequential open item, and the obligation multiplies with the vocabulary rather than staying fixed: site 4.6 (`PointwiseBf16`, reserved) is a second expression vocabulary needing a second evaluator, whereas one semantic evaluator already spans both widths (`register_standard_bf16`, `crates/tiler-reference/src/standard.rs:202`). The parent derivation bounds O5's evaluator obligation by "the schedule's own reduction-topology vocabulary" and argues that an exact evaluator for a topology *is* that topology's definition; design 2 would extend that obligation to the scalar-program vocabulary, where the same argument does not hold — an expression's definition is IEEE-754 plus, at two nodes, a contract it does not carry.

**Performance eliminates nothing, and saying so is the honest form.** Design 1 costs one retained `SemanticProgram` per retained `ProgramAlternative`, beside the scheduled regions, verified kernels, `KernelProgram`, and artifact plan that structure already holds (`crates/tiler-compiler/src/pipeline.rs:247-271`). Design 2 costs one evaluation per point at test time. Neither is near any threshold, and no candidate here was discarded for being expensive.

**Fact — design 1 is not a new mechanism but the correct parameterization of the gate this repository already runs.** `crates/tiler-compiler/src/pipeline/conformance.rs:708-713` compares `interpret_fused(...)` against `ReferenceEvaluator::standard().evaluate(&program, …)` bitwise, and the shape repeats at `:889`, `:1458`, and throughout `pipeline/tests.rs`. That comparison is design 1 with `P' = P`, which is correct only because those fixtures compile under contracts where the selected candidate is the baseline. Design 1 makes the existing gate keep meaning what it says under a permissive contract; design 2 would stand a second, weaker mechanism beside it.

**Inference — design 1 closes two enumerated sites rather than one.** Site 4.7 (which semantic candidate was selected — undeclared) and site 4.5 (the expression DAG — witness, unevaluable) are one gap seen from two layers. `E` is a total deterministic function of `P'` and the declared inputs — `plan_elementwise` (`request.rs:4555`) walks the DAG, `canonical_input_reads` (`:4459`) fixes the leaf ordering from the declaration, and `mint_elementwise` (`:4697`) replays the steps — so retaining `P'` *declares* 4.7 and makes 4.5 evaluable in one change. Design 2 closes 4.5 alone and leaves 4.7 undeclared.

**Composition with the parked witness surface, stated as a consequence and not decided.** [`accept-the-realization-witness-surface`](accept-the-realization-witness-surface.md) is Tom's, and nothing here accepts, excludes, or reorders its items A, B, or C. What the elimination changes is one argument: that ticket records the plain-scalar alternative's disqualifier as "it cannot carry the pointwise expression at all", and under design 1 nothing needs it to — site 4.5's witness is the retained `SemanticProgram`, which `tiler-reference` already consumes, so the pointwise expression never has to reach that crate. Design 2 would have forced the opposite, making `tiler-reference` name a plan structure as a side effect of an evaluator rather than as Item C's explicit decision. The record's Item A accessor `pointwise_f32(&self) -> Option<&PointwiseF32Expression>` is correspondingly no longer load-bearing for this site; whether to keep it is part of the same parked acceptance and is not touched here.

**What design 1 does not close, so it is not overread.**

- It does not compose, by itself, with a plan that also spends reassociation at a physical reduction split. `ReferenceEvaluator::evaluate` dispatches a fold to the registry's strict left-fold capability and cannot be told a `ReductionTopology`, so a program that spends both freedoms needs the semantic evaluation and the declared-order reduction evaluator composed. Filed as [`compose-a-declared-reduction-topology-into-a-semantic-program-evaluation`](compose-a-declared-reduction-topology-into-a-semantic-program-evaluation.md).
- The canonical-form claim the freedom-sites record's Part 5 leaves untested is untested still. Design 1 does not rest on it for soundness — the reference computes from `P'` and never from `E` — only for the inference that `E` is redundant given `P'`.
- Retaining the program and exposing it is an ADR 0075 public boundary. This is a design decision, not its implementation, and the surface reaches Tom on its own ticket.

**Design 2 survives in a strictly weaker role, and typing it that way is what stops it becoming an oracle.** Given design 1, an evaluator over `E` is a *localizer*: when the reference and the device disagree, evaluating `E` attributes the difference to the projection or to everything below it. That is the same shape the parent derivation used to retain O3 as refutation-only and O4 as a refusal-population generator. It is not filed as work, because it has no caller until design 1 exists and a failure needs attributing.

**Measurement boundary.** Nothing was run: no build, no test, no device execution. Every claim is a source reading at base `9466f622`, with a file and line, and each absence claim carries the one-line command that reproduces it. The freedom-sites record's cited anchors were rechecked at this base and all hold; `mint_elementwise` is at `request.rs:4697`, `pipeline.rs:328-333` is `SemanticCandidate`, `ProgramAlternative` at `:247-271` still has no semantic-program field, `grep -rn "pub fn .*SemanticProgram" crates/tiler-compiler/src/` still returns nothing, and `grep -rn "ScalarProgram\|ReductionTopology\|VerifiedScheduledRegion\|PointwiseF32" crates/tiler-reference/` still returns exactly one line (`crates/tiler-reference/tests/index_region_oracle.rs:1414`).
