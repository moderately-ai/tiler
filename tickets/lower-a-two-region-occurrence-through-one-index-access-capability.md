## User-visible outcome

An operation whose realization needs more than one index region — a reduction that produces a shared intermediate, then an elementwise pass that consumes it — can resolve an index-access lowering capability, so that a normalization or a softmax is not held below R6 by the shape of the lowering vocabulary rather than by anything about the family.

## Why this is filed

**Fact.** `admit-the-rms-normalization-family` registered `tiler::rms-norm-f32@1` with a fusion role, a numerical capability row, structured-kernel constructs, and a Metal emission, and deliberately registered **no** `GovernedIndexAccess` row. The reason is structural rather than a deferral of effort.

**Inference — one region cannot express the occurrence.** `IndexAccessLoweringProvider::lower` emits one index region per occurrence, and a region evaluates one scalar expression per point of one iteration domain. RMS normalization is shape-preserving, so its output domain is the whole tensor, while its reduction's result is shared by every point of a normalized row. Emitting it as one region would re-evaluate the whole fold at every point: at the workload's extent of 1024 that is an unrolled expression of about 1024 nodes per output point and about 10⁶ nodes per row, which the index region's structural bounds refuse long before it becomes merely slow.

> **Correction (2026-08-05, from the dispatch that hit the discovery stop).** The paragraph above is true about the trait and false about the wall. It is retained rather than deleted because the *reasoning* is what the blocking ticket inherits — the occurrence genuinely needs two regions — but the attribution was wrong, and a reader acting on it would widen a surface that changes nothing. See the Outcome section.

**Fact — the two-region shape already exists elsewhere.** The physical planner's materialized serial-sum path plans exactly this: a reduction region writing an intermediate, then a pointwise region reading it. What is missing is a way for a *capability* to describe it, so an occurrence that needs two regions currently resolves nothing and fails closed.

> **Correction (2026-08-05).** The first sentence is true but names a different IR. That path is `KernelSubprogram` / `SubprogramStage` over `VerifiedScheduledRegion` (the physical/schedule IR, `crates/tiler-compiler/src/frontier.rs`); capabilities emit `tiler_ir::index::VerifiedIndexRegion` (the index-refinement IR). The second sentence's "what is missing" is therefore wrong: what is missing is upstream of the capability, in the realization law and receipt. Conflating the two IRs is precisely what made this ticket look reachable from `implementation/compiler`.

## Non-goals

Widening `select_supported_strategy`, which [`reach-a-verified-kernel-through-the-structural-families`](reach-a-verified-kernel-through-the-structural-families.md) owns; choosing between a fused and a materialized plan, which is selection's; and any new scalar key beyond what the two regions already emit.

## Closes when

1. A lowering capability can declare that it emits an ordered sequence of regions with a named intermediate between them, and the intermediate's shape, ownership, and lifetime are explicit physical contracts rather than implied by the order.
2. The capability's declared emitted-scalar set covers every region it emits, so the refinement containment check still sees the whole realization.
3. `tiler::rms-norm-f32@1` resolves a capability, and a deliberate perturbation — a capability declaring one region for a two-region occurrence — refuses with a typed reason rather than emitting a truncated realization.
4. The explain output names both regions and the intermediate, because a reader asking why an occurrence produced two dispatches must not have to infer it from the dispatch count.

## Outcome

Widening `IndexAccessLoweringProvider` to emit a region sequence would have been a surface with no consumer and no verifier — a type-system reservation shaped like implemented support. Parked at `blocked` behind [`admit-a-multi-region-index-realization-law`](admit-a-multi-region-index-realization-law.md), which owns the authority this ticket needs.

**Fact.** `crates/tiler-ir/src/semantic/registry.rs` registers an `IndexRealizationLaw` for exactly nine operations; the normalization and the softmax are deliberately absent, and the comment above the list says absence "fails closed later".

**Fact.** `refine_index_region` (`crates/tiler-compiler/src/legality.rs`) calls `realizations.resolve(subject)` *before* `emit_region`. For a lawless family `resolve` returns `IndexRefinementVerificationError::MissingRealizationLaw`, so the resolved provider is never driven.

**Measurement.** `crates/tiler-compiler/tests/two_region_occurrence_lowering_wall.rs`, four tests, run on this branch with `cargo nextest run -p tiler-compiler -E 'binary(two_region_occurrence_lowering_wall)'` → `4 tests run: 4 passed`. `refining_the_normalization_refuses_before_the_provider_is_driven` registers a normalization index-access capability whose provider increments an `AtomicUsize`, refines, and observes the error `IrVerifier(MissingRealizationLaw)` with a driven count of exactly `0`. The control `a_family_carrying_a_law_refines_through_the_identical_harness` refines `tiler::multiply-f32@1` through the same harness, so the refusal is attributable to the absent law rather than to the fixture.

**Measurement — the checks can say no.** Each assertion was perturbed and observed failing: resolving `multiply_subject()` instead of the normalization (the `expect_err` panics on `Ok`); pointing the recording provider at `tiler::multiply-f32@1` (observed `Emit(Occurrence { rule: "fixture-never-reached" })`, which also demonstrates that a family *with* a law does drive its provider); both driven-counter expectations flipped to `1` (observed `left: 0, right: 1`, proving the counters read a real zero rather than an absent value); the control pointed at the normalization (observed `IrVerifier(MissingRealizationLaw)`); and the resolved-operation assertion pointed at the multiply key.

A region sequence has no canonical identity that comparison can consume, and `IndexRefinementReceipt` binds one region's operands and results. So closes-when 1–4 above are all downstream of the law and receipt layer.

**Fact — what was deliberately not built.** No public boundary was changed. `crates/tiler-compiler/src/capability.rs` and `src/legality.rs` are untouched; the branch adds one integration test and ticket-graph edits. Identity-pin survey (`grep -rnoE '\b[0-9a-f]{16}\b'` and the `{64}` form over `crates/tiler-compiler`): 21 distinct 16-hex pins — 1 live at `explain.rs:4090` (`request=8e06e11fdc3a2889`) plus 20 historical values in its ledger comment — and 6 distinct 64-hex pins. None moved: the live pin hashes the request subject, and this branch adds no program shape to a request and no registry entry.

**Remaining reachable work in this scope.** None until the dependency lands. When it does, closes-when 1–4 are reachable from `implementation/compiler` as written, and the explain slot for closes-when 4 is already identified: the `capability.index-access-resolution.v1` record in `crates/tiler-compiler/src/pipeline/trace.rs` currently carries zero `ExplainFact`s, and `crates/tiler-compiler/src/pipeline/tests.rs` holds a rule census that a new record or changed count fails first.

## Outcome — 2026-08-06

**Why the shape is what it is.** A realization is now an ordered *sequence* everywhere the compiler touches it, because that is what the layer below settled: `ResolvedIndexRealization::verify` is `verify_sequence` over a one-stage chain, and a one-stage chain's identity is its region's identity byte for byte. Mirroring that upward is what makes the change identity-neutral — every governed family is one stage, and not one byte of its refinement content, occurrence binding, or explain output moved. The compiler-side surface is a **draft** consumer of a surface Tom has not yet accepted; the delta is appended to [`accept-the-multi-region-index-realization-surface`](accept-the-multi-region-index-realization-surface.md) rather than self-accepted.

**Fact — the provider vocabulary.** `IndexAccessLoweringProvider` gains a defaulted `lower_sequence(&self, &mut IndexAccessSequenceContext)`; `lower` is unchanged and still required. The default opens one stage sourced positionally, so all twenty existing provider implementations are untouched. A staged provider overrides `lower_sequence` and implements `lower` as an explicit refusal — which is not a stub but the same answer `IndexRealizationLaw::realize` gives for the same law, and it is asserted (`a_realization_of_the_wrong_stage_count_refuses_with_a_typed_reason`).

**Inference — why a defaulted method rather than one required sequence method.** Four shapes were tested against correctness, performance, and maintainability. *One required method taking the realization* unifies the vocabulary but writes the same three-line adapter into twenty providers, and the adapter is what the host can generate. *A second provider trait plus a second `register_*`* costs zero churn but permanently forks `GovernedIndexAccess`, `install_governed_index_access`, and the resolution surface for a distinction that is a property of the emission and not of the registration. *Sealing a stage from inside `IndexAccessLoweringContext`* costs zero churn too and was eliminated on correctness: the first stage's sources would be implied by position with no way to state them otherwise, which is precisely what closes-when 1 forbids. *A required single-region method beside a defaulted sequence one* survives all three, and it is the shape the law layer already has.

**Fact — the driven provider, which is the ticket's own measurement flipped.** `crates/tiler-compiler/tests/two_region_occurrence_lowering.rs` (renamed from `..._wall.rs`), six tests, `cargo nextest run -p tiler-compiler -E 'binary(two_region_occurrence_lowering)'` → `6 tests run: 6 passed`. `a_two_region_occurrence_refines_and_binds_every_stage` registers a staged operation carrying `StagedStrictSerialSumThenPointwiseF32`, resolves one index-access capability for it, and observes the counter that the parked measurement recorded as `0` now reading **`1`**. The refinement is complete: two stages, one rank-zero intermediate produced by stage 0 and consumed by stage 1, two *distinct* stage authorities (`[canonicalize-nan-f32]` and `[multiply-f32]`), operand bindings naming `(0, 0)` and `(1, 1)`, and the compiler's retained realization identity equal to the IR receipt's.

**Fact — closes-when 1 and 2.** The intermediate's shape, ownership, and lifetime are `StagedIntermediate`'s checked fields rather than the order's implication, and every stage's reached authority is checked against the capability's declared emitted set inside `verify_sequence`, so the containment check sees the whole realization. `RefinementContent` binds all of them: `realization_identity`, `stage_count`, and `scalar_authorities()`.

**Fact — closes-when 3.** Five typed refusals, each asserted at its exact value rather than as "some error": a truncated chain → `OperandInterface { position: 0 }`; a chain for a single-region law → `SemanticRealizationSequenceMismatch`; a stage whose region fails verification and whose provider *discards* the failure → `Build { stage: 1 }`; a provider that emits nothing, by either route → its own `Emit { stage: 0, source: Occurrence { .. } }` rather than the composition's `Realization { Empty }`; a chain past the governed ceiling → `Realization { TooManyStages { actual: 65, limit: 64 } }`.

**Inference — closes-when 4, and the boundary it stops at.** `pipeline::trace::with_realization_facts` adds `realization-stages`, one `realization-stage-{n}-region` per stage, and `realization-intermediate-{n}-{producer,consumer,elements}` to the `kernel.index-region-refinement.v1` record — **only when the realization is a chain**, so no governed compilation's explain output moves. The derivation is tested (`pipeline::tests::a_staged_realization_names_its_regions_and_its_handed_value`), including the perturbation that emitting for a one-stage realization is caught. **Its one-line call site in `record_refinement` is not exercised end to end, and cannot be**: reaching it needs a *recognized* program whose occurrence carries a staged law, and `normalize.rs` recognizes only the pointwise, serial-sum, and contraction families. That is a covered derivation plus an uncovered wiring statement, not a tested guarantee, and it is recorded as such.

**Fact — the boundary this ticket did not exceed.** `tiler::rms-norm-f32@1` still refuses, and the retained neighbour test says why: the family registers no realization law, because its fold is a sum of squares and its second stage a reciprocal square root, and no governed scalar operation spells either. Registering them is [`admit-the-rms-normalization-family`](admit-the-rms-normalization-family.md)'s work and crosses a semantic surface this ticket has no scope for. The evidence here therefore drives a **test-registered** capability through the staged template, exactly as the parked wall tests' harness did, and not the standard provider's registry. Closes-when 3's literal wording — "`tiler::rms-norm-f32@1` resolves a capability" — is satisfied only in its second half (it does resolve one; the counter proves resolution drives nothing), and the first half stays with the family ticket.

**Measurement — the checks can say no.** Each was perturbed and watched failing on this branch. Dropping the recorded-stage-failure guard in `emit_realization` → the swallowed failure becomes `OperandArity { region_inputs: 1, expanded_inputs: 2 }`, a true statement about a chain the provider never meant to emit, which is exactly the misdiagnosis the guard exists to prevent. Letting composition speak before the provider's own refusal → two failures, `Build { stage: 1 }` becoming `OperandArity` and the refusing provider's rule becoming `Realization { Empty }`. Writing a one-stage content identity under the staged tag → the unstaged-tag assertion fails. Emitting the realization facts for a one-stage realization → the empty-facts assertion fails. Flipping the driven counter to `0` → `left: 1, right: 0`. Changing the fold stage's scalar to the multiply → `SemanticRealizationSequenceMismatch`. Swapping the pass stage's two declared sources → `Realization { IntermediateInterface { stage: 1, slot: 0 } }`, which also demonstrates that variant is reachable. Moving the stage-ceiling guard off by one → the build counter reads `65` against `64`.

Two of these are worth stating for what they revealed rather than for firing. **A first attempt at the refusal-ordering perturbation passed**, and the reason is that a failure recorded through `stage()` is already prioritized inside `finish()`; the ordering is only observable for a provider that overrides `lower_sequence` and refuses *before* opening a stage, which no test then covered. That provider now exists (`RefusingSequenceProvider`) and the perturbation fires. **The stage-ceiling guard's typed refusal is unchanged by removing it** — `try_new` reports the same `TooManyStages` — so the guard is a resource bound, not a behaviour, and only the build counter separates them; the test asserts both and says which claim is whose. One perturbation *did not* fire and is recorded rather than hidden: swapping the fold stage's input and output boundary declaration order still refines, because the canonical region identity groups boundaries by role, so declaration interleaving is not part of it.

**Fact — identity survey.** `grep -rnoE '\b[0-9a-f]{16}\b'` and the `{64}` form over `crates/tiler-compiler`, run on the base commit `f7deede0` and on this branch and diffed: **26 distinct 16-hex pins and 6 distinct 64-hex pins on both, with an empty diff**. Nothing moved, and the reason is structural rather than lucky: the live explain qualifier `request=6dd42be71c6745fe` (`explain.rs:4149`) folds the request subject — the frozen semantic, scalar, and realization-law authorities and the lowering registry identity — and this branch registers no standard operation, no law row, and no governed capability, and changes no registry encoding. `cargo nextest run --workspace` → `2787 passed` on the branch.

**Fact — the accessor question, answered.** The law worker asked whether a staged receipt should expose a single-region accessor at all. It should, and the compiler's consumption is where that becomes concrete.

- *Remove them* is eliminated. The final stage is a real concept, not a truncation: its writes **are** the occurrence's results, `bind_results` is derived from it alone, and it is stored as a separate field precisely so "a realization has a final stage" is a type invariant rather than an `expect` at every read. Removing the accessor would push that `expect` back to every consumer.
- *Retain them unchanged* is also eliminated, and this ticket is the counterexample. `complete_pending_index_refinement` **did** consume `PendingIndexRefinementReceipt::region()` and hand it to content assembly as the whole realization, and `IndexRefinement::region()`'s documentation claimed the `tiler-reference` oracle could evaluate it against `operand_bindings` — a claim that is false for a chain, whose final stage reads a value no occurrence operand carries. Both were well-typed reads of the wrong thing.
- *Retain, but let the name state what it returns* survives. On the compiler side that is done here: `IndexRefinement`/`PendingIndexRefinement` carry the sequence, and the single-region view is `single_region() -> Option<&VerifiedIndexRegion>`, `None` for a chain — so the one honest consumer class, an evaluator that can run exactly one region, refuses a staged realization explicitly instead of evaluating a third of it and reporting the result as the occurrence's. On the IR side the equivalent step is a rename of `region()`/`scalar_authority()` to final-stage spellings, which is `implementation/ir` and therefore filed rather than taken: [`name-the-index-receipt-final-stage-accessors-for-what-they-return`](name-the-index-receipt-final-stage-accessors-for-what-they-return.md), deferred behind Tom's ruling on the acceptance node. **After this branch the compiler consumes no IR single-region accessor at all** — verified by `grep -rn 'receipt\.region()' crates/tiler-compiler`, which returns nothing — so the `const fn` constraint the node recorded no longer binds `region()`; only `scalar_authority()` is still reached, through `PendingIndexRefinement::scalar_authority`, itself a `pub const fn`.

**Fact — the public surface added, all draft.** In `tiler_compiler::capability`: `IndexAccessSequenceContext` (`occurrence`, `stage_count`, `stage`, `single_stage`), `IndexAccessStageFailure`, and `IndexAccessLoweringProvider::lower_sequence`. In `tiler_compiler::legality`: `IndexRefinement::{realization, single_region}`, `PendingIndexRefinement::{realization, single_region, scalar_authorities}`, `RefinementContent::{realization_identity, stage_count, scalar_authorities}`, and `RefinementError::{Emit { stage, source }, Build { stage, .. }, Realization { source }}`. Removed: `RefinementContent::region_identity`, `IndexRefinement::region`, `PendingIndexRefinement::region`, `impl From<LoweringEmitError> for RefinementError`. The delta is appended to the acceptance node; nothing here is self-accepted.
