Generalize typed physical boundary requirements, guarantees, satisfaction,
subsumption, child requirement derivation, dominance, identity, and explain for
layout, alignment, materialization, placement, memory domain, ordering, and
synchronization. This ticket defines properties only; executable transfers,
materializations, conversions, synchronization, and lifetime verification are
owned by `implement-boundary-property-enforcers`.

Any consequential public or cross-crate crate, module, trait, type, or call-site boundary remains a draft until Tom reviews and accepts the exact implementation commit. This ticket does not preselect that interface.

## Outcome

**Fact.** Added `crates/tiler-compiler/src/boundary.rs`, registered as a private `mod boundary;`. Every item is `pub(crate)` under ADR 0074 convention 7, so no always-ask surface under ADR 0075 is created: no new `pub mod`, no public trait, no `pub(crate)`-to-`pub` promotion, and no breaking change to an existing public signature.

**Fact — the dimension list is a stated reconciliation of two accepted sources that do not coincide.** `docs/compiler/optimizer.md` names five properties and introduces them with "Initial boundary contracts *include*"; ADR 0047 names an asymmetric pair of field lists for a requirement and a delivered placement. `BoundaryProperty` has eight variants: `StorageLayout`, `StorageEncoding`, `Alignment`, `Materialization`, `ExecutionAffinity`, `MemoryDomain`, `Availability`, `Visibility`. The module documentation derives each mapping and states the three deliberate exclusions with reasons — ADR 0047's *access mode* and *ownership* are the two sides' own qualifiers rather than dimensions and are carried beside the property sets; its *byte range* is an `AbiExpr` that ADR 0068 places in `tiler-ir`; its *value version* is a `KernelProgram`-scope product of an enforcer, so broadening to a mutating profile needs the dimension here and the version-producing step there together.

**Fact — the two sides have separate value spaces, and two of the asymmetries are load-bearing.** A memory-domain requirement is an `AdmittedMemoryDomains` set and a guarantee is one `MemoryDomainClass`, because ADR 0047 forbids inferring a total order from domain names and writes the requirement side as an "admitted" domain. A `VisibilityGuarantee` can name `RequiresExplicitCoherenceAction` — a state still owing a flush — which no requirement can ask for and which satisfies nothing. Where the two sides genuinely share a space they share a type: `StorageEncoding` and `ByteAlignment` are one type each, and the direction lives in the relation rather than the value.

**Fact — the four relations the accepted contract requires are implemented and tested.** *Satisfaction/subsumption*: `unsatisfied_properties` decides a requirement set against a guarantee set per dimension and returns every unmet requirement in canonical dimension order. A dimension the guarantee is silent on is `UnsatisfiedReason::NotGuaranteed`, never a pass. Alignment subsumption is divisibility (`16` satisfies `4`, not the converse) and rejects non-powers of two at construction, because divisibility is a partial order over powers of two and not over arbitrary integers. Encoding subsumption is equality within a family in both directions, per `decide-whether-storage-encoding-is-a-missing-boundary-property`. A dense row-major guarantee satisfies a unit-stride requirement on the last axis and no other. *Child-requirement derivation*: `derive_child_requirements` propagates only `ExecutionAffinity`, and only because ADR 0047's initial execution profile states that "Inputs must already be accessible, and all stages, temporaries, and outputs use that affinity"; every other dimension keeps the implementation's own value, because a goal constrains the value leaving a region and says nothing about the value entering it. A propagating dimension the two sides disagree on is a typed `ChildRequirementConflict`. *Dominance*: `RequiredProperties::is_no_stronger_than` and `GuaranteedProperties::is_at_least_as_strong_as` are partial orders, and a dimension only one side names is handled asymmetrically and correctly (an unnamed requirement is weaker; an unnamed guarantee is a gap). *Identity*: the sets encode domain-separated and length-prefixed through `tiler_ir::identity`, with every enum tagged by an exhaustive match written by an arm.

**Fact — the model is on the compile path, not a reservation beside it.** `frontier::BoundaryContract` now carries `RequiredProperties`/`GuaranteedProperties` derived from the verified region, replacing the two single-variant `BoundaryAvailability`/`BoundaryProduction` enums; each property's derivation source is stated in `derive_boundary_contract`'s documentation, and the memory domain is read from `ResourceRequirements::requires_device_memory` rather than assumed. `selection::satisfy_edge` reconciles each materialization edge through `unsatisfied_properties` instead of a hardcoded pair match, and `BoundaryDisagreement::UndischargedHandoff` now carries the typed `UnsatisfiedProperty` and delegates its reason code to it, so an explanation names which property failed and whether the producer offered the wrong value or none.

**Fact — a defect against the accepted contract, fixed.** `ImplementationFrontier::non_dominated` pruned on cost alone. The accepted relation requires that a dominating implementation's "boundary requirements are no stronger, its guarantees are at least as strong", and the same section requires that "interesting boundary properties such as useful unit-stride axes are retained on a bounded Pareto frontier even when they are not locally cheapest". `AdmittedImplementation::dominates` now checks boundary subsumption before cost. `BoundaryContract::subsumes` pairs the two contracts positionally and rejects the pairing unless the side-qualifier sequences agree entry for entry; matching by tensor role would mis-pair a region reading two `Input` boundaries and could report dominance where none holds.

**Fact — length framing consolidated.** `frontier.rs` and `selection.rs` each carried a private `encode_len`/`encode_bytes` pair, a sixth and seventh copy of the canonical framing that `crates/tiler-ir/src/identity.rs` owns. Both now use `push_len`/`push_slice`. The `length_framing_has_exactly_one_definition_in_this_crate` test does not reach them — it walks `tiler-ir` only — so this was found by reading rather than by the gate. Bytes are unchanged: the removed `encode_len` used `unwrap_or(u64::MAX)` where `push_len` uses a checked conversion, which differs only for a length above `u64::MAX`.

**Fact — a new ADR 0074 convention 5b site.** `tiler_ir::schedule::AccessMode` is now mapped totally onto an identity tag from outside `tiler-ir`, at `frontier::access_mode_tag` and `selection::access_mode_tag`. It carries no `#[non_exhaustive]` today and must not gain one. `docs/decisions/0074-*.md`'s enumeration of 5b sites is in `contracts/decisions` and was not entered.

**Measurement.** Base `06be974a5f35745548686bca077f9a93cc3ef854`, macOS arm64, toolchain `nightly-2026-07-19`. `uv run --locked python scripts/check_repository.py` passes ("complete repository validation passed"). `cargo nextest run -p tiler-compiler` runs 232 tests, 232 passed (23 new `boundary::tests`, one new `frontier::tests`, one new `selection::tests`). `git diff --check` clean. `ticketsplease guard` reports no scope escape.

**Measurement boundary.** Three relations cannot be produced end to end by the bounded profile and are exercised directly, which the tests say in their own comments: a child-requirement conflict needs a second symbolic affinity; a property-level handoff disagreement needs two regions whose derived contracts differ, and the profile derives one contract per region; and boundary-gated dominance needs two implementations of one region with different contracts, which cannot arise while the contract is a function of the region. This matches how `prototype-complete-physical-plan-selection` exercised its own disagreement guard, and is a bound on the tests rather than on the relations.

**Proposal (deferred, with what broadening requires).** The reserved property values reject explicitly rather than being approximated, and each names what would reach it: `MaterializationForm::{AliasView, OpaqueRuntimeValue}` need the frontier's reserved `View`/`OpaqueCall` bodies; `StorageEncoding::BitPacked` needs ADR 0028's sub-byte integers and an encoding-repacking enforcer; the four non-`Device` `MemoryDomainClass` variants and a second `ExecutionAffinity` need an execution profile beyond ADR 0047's initial one; `AvailabilityRequirement::AfterObservedHostCompletion` needs ADR 0033's observation boundary; and `VisibilityGuarantee::RequiresExplicitCoherenceAction` needs a coherence enforcer. Two derivations are pinned to the bounded profile by a missing IR field rather than by choice: alignment and encoding are derived as the natural `f32` values because `ScheduledRegion` carries no resolved element type, and a widened dtype vocabulary must derive both from the boundary value instead. `encode_property_identity` is the encoder the accepted "Possible memo contract" would key an optimization entry on; no memo exists, so nothing outside this module's tests calls it, and the property bytes on the compile path today reach identity through the implementation proposal instead.

**Proposal (contract follow-up, outside this ticket's scope).** `docs/compiler/optimizer.md`'s boundary-property list names five entries and does not name ordering or synchronization, which this ticket's own text and ADR 0047 both require. The list says "include" rather than "are", so nothing contradicts, but the contract should name `Availability` and `Visibility` beside the other six. That file is `contracts/optimizer` and was not entered.

**Proposal (draft public boundary — awaiting Tom's review of the exact commit).** New `pub(crate)` surface in `boundary.rs`: the `boundary` module; `BoundaryProperty` and `CANONICAL_PROPERTIES`; the value spaces `LayoutRequirement`, `LayoutGuarantee`, `StorageEncoding`, `ByteAlignment`, `MaterializationForm`, `ExecutionAffinity`, `MemoryDomainClass`, `AdmittedMemoryDomains`, `AvailabilityRequirement`, `AvailabilityGuarantee`, `VisibilityRequirement`, `VisibilityGuarantee`; the carriers `RequiredProperty`, `GuaranteedProperty`, `RequiredProperties`, `GuaranteedProperties`; the outcomes `BoundaryPropertyError`, `UnsatisfiedReason`, `UnsatisfiedProperty`, `ChildRequirementConflict`, `BoundaryPropertyIdentity`; and the relations `unsatisfied_properties`, `derive_child_requirements`, `encode_property_identity`. Changed `pub(crate)` surface in `frontier.rs`: `BoundaryAvailability` and `BoundaryProduction` are removed, `BoundaryOwnership` replaces the latter, `BoundaryRequirement`/`BoundaryGuarantee` carry property sets plus an access mode and an ownership, and `FrontierError` gains `UndeterminedBoundaryProperty`. Changed `pub(crate)` surface in `selection.rs`: `SatisfiedHandoff` carries an ownership and an access mode in place of a production and an availability, and `BoundaryDisagreement::UndischargedHandoff` carries an `UnsatisfiedProperty`.
