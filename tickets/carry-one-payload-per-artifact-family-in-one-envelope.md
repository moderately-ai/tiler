Tom decided on 2026-07-25 that one selection produces **one envelope carrying one payload per built family**, so the whole selection has one identity and a partial delivery is impossible by construction. `tiler_macros::delivery::DeliveryPlan` implements the emission half completely — positional outcomes in canonical family order, a total `#[cfg]` selector, one byte-string literal — and `tiler::RouteFacts::payload` is already the position it resolves to. The neutral artifact model cannot yet express the envelope those halves describe.

## Fact — the two rules close on each other

**Every declared payload must be realized by an executable entry.** `tiler_artifact::program::verify::payloads_are_referenced` requires it, `ArtifactDiagnostic::UnusedPayload` is the refusal, and `rejects_a_payload_no_entry_realizes` pins it.

**A variant's entries are exactly its program's stages.** `assemble_plan_artifact` calls `declare_entry` once per stage, and `push_variant` refuses any other count with `ArtifactBuildError::EntryCardinality`. Each entry names exactly one payload through `BackendEntryRef::payload`.

**So a second payload needs a second variant** — and `push_variant` refuses two variants packaging one program under one guard with `ArtifactBuildError::DuplicateVariant`, pinned by `rejects_a_duplicate_plan_variant`. A variant's guard is derived from the program's own applicability guard, so two variants over one plan always collide.

**Measurement.** `tiler_build`'s `a_second_artifact_family_cannot_yet_share_one_envelope` runs the production seam: one compilation, one selected plan, two emissions and two AOT compilations for `air64-apple-macos26.0` and `air64-apple-ios26.0`, both carried into one `assemble_plan_artifact` call. It refuses with exactly `[ArtifactDiagnostic::UnusedPayload]`. Dropping the second payload makes the same assembly succeed, which is what separates this refusal from an unrelated failure.

## Fact — the artifact family is not a compiler-profile axis, and that is what makes this tractable

The ledger's projection table records `MetalTargetFacts::platform` as backend-only, and the same test measures the consequence: two declarations differing *only* in platform share a profile key and a byte-identical canonical descriptor. So the two families are one compilation, one plan, one kernel program, and two compiled objects — not two target profiles. `ArtifactProgramBuilder::check_subject` would refuse two variants declaring different profiles with `TargetProfileMismatch`, but that is not the constraint that binds here.

Worth reconciling while doing this: `docs/artifact-abi.md:327` already states that a payload's `TargetProfileRef` is "the payload's contract, not the plan's", and that carrying it per payload "lets a program share one compiled object across variants declaring different profiles" — a sentence `check_subject` currently makes unreachable.

## What this has to decide

How an artifact expresses several backend objects that realize *the same* entries and are chosen by the consumer's build target rather than by the device. Today `tiler::route::select_embedded_route` only checks `RouteFacts::payload` for `None`; the index selects nothing, because there is nothing yet for it to select among. Whatever shape this takes has to keep the properties the current rules exist to protect: no unreferenced payload (which would give one artifact two byte identities — `docs/artifact-abi.md:188`), no ambiguous entry-to-payload mapping, and identity folding every carried payload so a two-family envelope and a one-family envelope are never one artifact.

## Closes when

One envelope carries one payload per built family with a cache subject covering the whole selection, the consumer's `#[cfg]`-selected position routes to that family's payload, a wrong-position payload is a build error rather than a wrong artifact, and `a_second_artifact_family_cannot_yet_share_one_envelope` is replaced by the positive test. It is only observable end-to-end once a second family has a measured declaration (`first-authoritative-ios-metal-compile-declaration`); the envelope work itself is exercisable before that through the `#[cfg(test)]` second-family fixture in `crates/tiler-build/src/metal_declaration.rs`.

The public artifact boundary is Tom's to accept.

## Outcome

**Implemented.** An executable entry is realized once per **delivery position** — the ordered slot a consumer's build target resolves to — so one selection produces one envelope carrying one payload per built family, with whole-selection identity and no partial delivery.

**The shape, and why the alternatives were eliminated.** `BackendEntryRef` names one `entry_key` and a `Vec<PayloadId>`, positional against the artifact's delivery positions: several backend objects realizing *the same* entries, chosen by the `#[cfg]` position rather than by the device. *Per-family variant guards* were eliminated on two grounds — a variant's guard is derived from its bound program since the `v6` identity step, so two variants over one program collide as `DuplicateVariant`, and a guard is evaluated against a live device, which cannot observe a consumer's build target (an `air64-apple-ios26.0` metallib loads and dispatches on the macOS host GPU without error). *N single-payload sub-envelopes* were eliminated because the outer container would need its own identity domain over sub-envelope identities, making a second identity authority over the artifact subject against ADR 0082, and would repeat the interface, the ABI arena, and the program section once per family. *A payload-selection table at the artifact level* — position → payload, entries naming only a key — was eliminated as a narrowing: it removes the per-entry payload freedom the model already admits, whereas the per-entry run recovers today's model exactly at one position.

**Identity moved: `tiler.artifact-program.v12` → `v13`, neutral manifest schema `10.0` → `11.0`.** The entry record writes a counted run of payload keys where it wrote exactly one, so the count *and* the order are folded in every entry: a one-family artifact, the two-family artifact carrying that object first, and the one carrying it second are three artifacts. Moved pins, all recomputed on this tree: `crates/tiler-build/src/metal_plan.rs`'s two goldens (`ARTIFACT_IDENTITY` `7a11d035…` → `cee402b8…`, `CACHE_SUBJECT` `58a71c54…` → `3f86db90…`); the restated domain separator in `crates/tiler/src/route/tests.rs`; the two codec assertions on the domain and `MANIFEST_SCHEMA`. No other golden, fixture, or recorded identity in the workspace names either version.

**Ledger step executed.** `docs/artifact-abi.md` gained the `v13` step with its reasoning, the three delivery obligations, the new required-feature row, and the corrected ledger paragraph; the stale sentence at the old line 327 — the payload compatibility contract letting "a program share one compiled object across variants declaring different profiles", which `check_subject` makes unreachable — is now labelled as having been unreachable and re-grounded on the case that *is* reachable. `docs/status.md`'s ledger bullet moved with it (`contracts/navigation`).

**New refusals, each watched failing.** `ArtifactBuildError::EmptyDelivery` and `ArtifactBuildError::DeliveryCardinality` at insertion; `ArtifactDiagnostic::AmbiguousPayloadDelivery` in whole-artifact verification and again in the codec; the codec's `check_delivery_positions` re-proving all three from bytes; the governed feature key `tiler.artifact.feature.multi-payload-delivery`; and `LoadRejection::UnknownDeliveryPosition` at `DecodedProgram::decode`. The existing `DuplicateBackendEntry` rule was found to already decide one new case — an entry naming one payload at two positions repeats `(payload, entry key)` — and both diagnostics are asserted together rather than only the first.

**The runtime takes the position at the decode.** `DecodedProgram::decode(bytes, delivery)`, once, where bytes become a program. It is deliberately not part of `ExecutionEnvironment`: that record is what a *device* reports through `RuntimeAdapter::bind_execution_context`, and a `#[cfg]` fact of the consumer's own compilation is not observable from a machine. There is no default position.

**Wrong-position payload is a build error, twice over.** Delivery order is folded into identity, so a carried run assembled the other way round is a *different artifact* and the cache seam refuses it as `ArtifactIdentity` before publication; a *pending* artifact whose payloads sit at the other family's positions is refused as `PayloadSubject { delivery: 0 }` before any compiler work. Both are pinned by `a_payload_at_another_familys_delivery_position_is_refused`. The per-position correspondence closure is watched separately: pointing it at `expected_metadata[0]` for every position makes the two-family test fail with `Correspondence { delivery: 1, Source }`.

**`a_second_artifact_family_cannot_yet_share_one_envelope` is replaced** by `one_envelope_carries_one_payload_per_artifact_family`, which drives the production seam over both families: two delivery positions, two payloads, each position resolving through the artifact's own entries to the object built for its own AOT triple, a cache subject that differs from the one-family selection's, and an artifact identity that differs from it. The reversed selection is asserted beside it, because the descriptor table is canonically ordered by content and does *not* move when delivery order does — which is what makes resolving through the entries a check rather than a coincidence. Perturbing that resolution to read the descriptor table positionally fails the test.
