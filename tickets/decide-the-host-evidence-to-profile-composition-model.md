## User-visible outcome

Tiler has one decided model for how measured evidence scoped to a single host composes into the profile identities consumers dispatch on — so profile keys encode claim scope (platform, GPU family, language version, fact family) while host attestation lives in per-row measurement provenance, and single-host evidence has a defined, fail-closed path toward (or a defined exclusion from) family-scoped claims.

## Why this exists

Filed 2026-08-18 from Tom's naming objection on the M3 Pro subgroup declaration: the delivered host-named profile key (`macos-m3pro-apple9`) was truthful pure-evidence discipline, but it coupled durable identity vocabulary to procurement. The current ledger convention (one execution environment per profile) is what forces per-host profiles; the candidate to beat is family-keyed profiles whose individual rows carry per-row execution provenance, with feasibility answering `Unknown` unless the querying context matches a row's scope. The standard-profile measurement deferral (`measure-thread-execution-width-on-the-standard-metal-profiles-own-host`) and the demotion carrier are both consumers of this decision.

## Closes when

A Pareto-complete packet (per the repository readiness gate) fixes the composition model — profile key scope, row provenance shape, the single-host-to-family rule, identity consequences — passes independent review, and Tom accepts one exact model.

## Grounding — what the encoders and consumers state at this base

Everything here is **Fact**, read from source at `741bc963`.

- **Per-row provenance over heterogeneous environments is already representable and identity-bearing.** The complete declaration descriptor (`crates/tiler-compiler/src/target.rs`, domain `tiler.target-profile.declaration.v11`) encodes the profile key, then a deduplicated source table under `tiler.target-profile.fact-sources.v4` — each source's canonical bytes include its measurement contexts, i.e. the compiler builds and all five execution-environment fields — then per-family row sections in which every measured row cites its source by index (anchor `every quantitative source was inserted into the source table`). A source holds up to 64 contexts (`MAX_MEASUREMENT_CONTEXTS_PER_SOURCE`, `crates/tiler-ir/src/numerics.rs`), a profile holds many sources, and the delivered perturbation `every_measurement_context_field_moves_the_descriptor` pins that hardware and OS-build fields each move the descriptor. Nothing in the encoders forces one execution environment per profile; that was a ledger convention.
- **The profile key is an opaque validated string, not a typed grammar.** `TargetProfileKey::new` admits lowercase/digit/`.`/`-`/`_` up to `MAX_TARGET_PROFILE_KEY_BYTES` (128) and imposes no segment structure. No consumer parses key internals: dispatch is exact equality on key then descriptor (`require_compiled_under`; artifact `TargetProfileRef` carries key plus descriptor digest per ADR 0043). "Keys encode claim scope" can therefore only be a documented naming convention enforced at review of the small closed population of public key mints — or a new typed grammar, which is enumerated and eliminated below.
- **A measured source cannot widen into a portable claim.** `TargetCompileProfileMeasurementSource::new` fixes `(CompileProfile, MeasuredProfile, MeasuredEnvironment)` by construction (anchor `FactValidityScope::MeasuredEnvironment`), and the read side reports validity beside authority because `exactly the mistake this scope prevents` is reading a measured fact as portable.
- **Compile-time feasibility carries no querying context, and the phases that do exist already own the host questions.** Resolution APIs take a subject and a phase only (`dtype_dispatchability`, `subgroup_realization`). The host enters at `LiveDevicePreflight` — the backend-owned applicability evaluation compares the observed OS family/version/build/architecture/device/GPU-family against a closed policy row field-exactly, refusing a mismatching host on its first failing predicate, and refuses even a fully matching host on the uninhabited translation authority (`crates/tiler-metal/src/applicability.rs`, `UnknownNativeTranslationAuthority`; ADR 0086 implementation boundary), so no observation earns a receipt — and at `PreparedKernelPreflight`, where the accepted prepared-width stage enforces per-entry `ObservedEqualsRequired` equality against the exact prepared pipeline (ADR 0094 decision 7; stage surface accepted 2026-08-18).
- **Four accepted decisions bound this one.** (i) The naming objection: no public identity from a hardware model name. (ii) The (R, R) remeasurement: one profile's rows will span two execution environments, each population in its own source, never folded. (iii) The compilation-selection surface (accepted 2026-08-18, carrier blocked): compile-profile contexts gain a required `compilation_selection` identity and `FACT_SOURCE_PROVENANCE_SCHEMA_VERSION` steps 3 → 4 — so a row's scope is becoming environment **plus** toolchain **plus** exact selection, not environment alone. (iv) ADR 0086 item 3: an exact environment row is a necessary validity scope and not a sufficient authority — Tom's recorded reason, `an opaque translator can change while the observed OS/build/device row remains identical`, is quoted twice in that record.

## Decision packet — 2026-08-18

### Options enumerated

1. **Status quo strict** — one execution environment per profile; per-host public profile keys when hosts differ.
2. **The relayed candidate, read literally (2a)** — family-keyed profiles, per-row provenance, and **compile-time feasibility** answering `Unknown` unless a querying context matches the row's scope.
3. **Claim-scoped keys + phase-gated scope matching (2b)** — family-keyed profiles, per-population measured provenance inside identity, a pre-registration rule for how single-host evidence enters a family key, and the scope match answered at the phases where a host exists. Stated exactly below.
4. **Claim-scoped keys + a separate host-attestation table (3)** — environments moved out of, or mirrored beside, descriptor identity.
5. **Per-host fixtures + explicit accepted promotion (4)** — light form: promotion = the protocol pre-named the beneficiary profile before the run; heavy form: every row addition is a separate Tom acceptance.
6. **A typed profile-key grammar** — parse and enforce scope segments at `TargetProfileKey::new`.
7. **Typed deferral (5).**

### Eliminated, each with the gate reason

- **Status quo strict.** Requires minting host-named public keys for evidence from any new host — revoked by Tom on 2026-08-18 and frozen pending this decision — and contradicts the accepted (R, R) disposition, which spans two environments under one key precisely to avoid folding or discarding the new-build evidence. Under it, every OS-build move mints a new key and retires every dependent artifact identity: durable identity coupled to procurement, which is the filing defect itself. Dominated on every dimension and disqualified by two accepted decisions.
- **2a — compile-time context-matched feasibility.** There is no querying context at `CompileProfile`: AOT compilation is host-free and consumer-agnostic, and a compile request names profiles, not hosts. A **required** context makes every production compile refuse (no truthful context exists to pass; copying a row's own environment in is self-certification) — the no-compiling-truthful-partition class the (R, R) packet already eliminated as "retain with a recorded gap". An **optional** context makes one profile answer differently depending on whether a caller passed one, and a caller wanting admission simply omits it — an unstated policy fork that guards nothing (gate rule 3). It would also duplicate, at a phase that lacks the data, the comparison ADR 0043/0086/0094 already place at the phases that have it.
- **3a — environments moved out of identity into a side table.** Steps the fact-sources grammar so two profiles measured on different hosts can share descriptor bytes; an artifact's `TargetProfileRef` could then no longer distinguish which evidence population assessed it — identity conflation (gate rule 3), and the exact property the delivered context-field perturbations exist to forbid.
- **3b — environments kept in identity and mirrored in a table.** A second authority over one fact. The 2026-08-18 ledger-mirror defect (`the_authority_ledger_mirrors_the_live_standard_metal_pins` holding superseded pins while the live pin was correct) is this repository's own demonstration that hand-mirrored values drift silently. Adds surface, prevents nothing 2b does not. Also wears ADR 0086's word "attestation" without its mechanism.
- **Retroactive promotion of the existing M3 record under any option.** Its frozen protocol pre-scoped it (`a *new* M3 Pro Apple9 compile-profile width claim over the frozen population only`; outcome anchors `does not source` / `not an Apple9-family guarantee`). A model — or a Tom decision — that attaches it to the standard profile anyway invents authority the record's own protocol withholds (gate rule 3). Every surviving option therefore leaves the fixture a fixture.
- **A typed profile-key grammar.** No consumer parses key internals and none is proposed; dispatch is exact key+descriptor equality. A parser plus a versioned segment vocabulary would exist for nothing that reads it, while every existing key (`tiler.prototype-target-neutral-baseline.v1`, the test keys) needs migration or grandfathering. The property that matters — no procurement identifiers in minted public keys — is a review-time property of a handful of `pub` declarations. Dominated on maintainability with zero correctness gain. Reversal: a consumer that must derive behaviour from key segments.
- **Typed deferral.** Every input to this decision is already in-repo; no experiment, measurement, or external fact is pending, so no reconsideration trigger can be written whose firing would supply information this packet lacks. Deferring leaves the reseat carrier without a stated model for its ledger presentation, the standard-profile deferral on a falsely narrow two-branch premise, the demoted spike without a disposition, and the freeze under which new-host evidence can become no profile at all. Deferral stays Tom's prerogative; it improves no option.

### Survivor comparison — 2b against 4-heavy

Both are top-tier on correctness and fail-closed strictness: neither admits an unevidenced row, inherits across environments, or self-certifies. They separate on process only. 4-heavy converts every row addition **and every reseat under an already-accepted disposition** into a fresh Tom acceptance; the population that gate would additionally guard — a row landed under a pre-registered protocol, with per-population provenance, descriptor identity moving, pins recomputed, and review — is not a failure class any recorded defect here exemplifies, while the classes that did fail (hand-mirrored pins, one source shared across differing selections) are construction and mirroring defects a queue gate does not touch. It also runs against Tom's standing measurement authorization (`never ask for permission again`) and the existing authority split, under which fact-family expansion on a public profile already reaches Tom through the decision-packet gate while row maintenance under accepted dispositions is worker-land. Equal on correctness, strictness, and host runtime; worse on maintainability and latency; better on nothing. **2b dominates**, so per gate rule 5 it is recommended rather than presented as a manufactured choice.

### The recommended model — six components, stated for verbatim lift into the ADR

1. **Profile keys name claim scope only.** A public compile-profile key names what its rows are claims about — backend, artifact/platform family, GPU family, language standard, stated content families, revision; `tiler.metal.macos-apple9.msl4-0.f32-bf16.v1` is already this shape — and never a procurement identifier: hardware model names, OS versions, OS builds, serial or registry identities are provenance vocabulary and may not appear in a minted public key. Enforced as a documented naming convention at review of public key mints, not as a typed grammar. A key revises when its own description would otherwise become false (the BF16 precedent, anchor `This is a new content key` in `metal_declaration.rs`: keeping `.f32` in a key for a profile that also states BF16 would make the key's own description false); every other change moves the descriptor, and ADR 0043 already makes the key alone insufficient.
2. **Rows carry exact measured provenance, per population, inside identity.** Every measured row cites a source whose contexts state the exact offline toolchain, execution environment, and — once the accepted selection carrier lands — the exact compilation selection. Rows from different measurement populations never share a source; environments are never folded; the descriptor's source table and per-row indices keep all of it identity-bearing, exactly as the encoders already do. One profile's rows may therefore span execution environments, each row scoped exactly; the reseated standard profile is the first instance.
3. **Single-host-to-family rule: pre-registered beneficiary, stated value, measured validity.** A measured row enters a family-keyed profile only when (a) the producing measurement's frozen protocol named that exact profile key as beneficiary **before the run**; (b) the declaring module transcribes only what the record states and refuses every other value by name (the `UnevidencedWidth` pattern); and (c) the row's validity is `MeasuredEnvironment` — the constructor already makes a wider claim unbuildable. A record whose protocol scoped it elsewhere composes into nothing else, ever. The retained M3 Pro width record stays a crate-private evidence fixture under this rule, permanently.
4. **A single-host row licenses planning, never portability; "matches" is answered where a host exists.** Compile-time feasibility keeps reading declared rows with no context parameter; silence stays `Unknown` and refuses. Whether a real host is inside a row's measured scope is answered in the owning backend's vocabulary (ADR 0092): at `LiveDevicePreflight` by the backend applicability evaluation, where **matches means byte-exact equality of every environment field against a measured context of the row's own population**, and even a full match stays necessary-not-sufficient because ADR 0086's authority requirement is untouched; and at `PreparedKernelPreflight` by per-entry `ObservedEqualsRequired` equality for prepared-phase facts (ADR 0094 decision 7). No device-model or family-level loosening: Tom's recorded ADR 0086 reason refutes looser rows a fortiori. The late-refusal shape is deliberate and fail-closed: a plan compiled against a width row on a mismatching future host refuses at prepared preflight, before routing commit — mispriced never, unexecutable until evidenced.
5. **Contradiction, not averaging, across a family.** If a second in-family measurement contradicts a declared whole-subject row (an Apple9 device preparing a width other than 32), the row cannot stand on the family profile: the builder's duplicate/contradiction refusals hold, and the disposition is withdrawal or a narrower claim subject — never per-host variants of one public key, never a vote.
6. **"Attestation" stays ADR 0086's word.** Per-row provenance carries host **identification** — the measured environment identity. Attestation remains the future mechanism ADR 0086 item 7 names; this model does not claim it, and the outcome wording of this ticket is corrected by this component rather than silently restated.

Forbidden, stated so the carrier can cite it: folding environments into one source, bumping the key for an OS-build move, and presenting the two execution environments as one table.
- **The M3 subgroup case**: the fixture stays a fixture (component 3). - **The standard-profile subgroup deferral**: its two-branch premise (restore `26A5388g`, or re-row the whole profile) is superseded — under the model a new width measurement runs on the current M4 Max under a new frozen protocol that pre-names `tiler.metal.macos-apple9.msl4-0.f32-bf16.v1` as beneficiary, and lands as a subgroup row with its own population source and environment; the standing measurement authorization covers the session. ### Identity consequences per option, derived from the encoders

- **2b (recommended): zero encoder change.** `tiler.target-profile.declaration.v11`, `fact-sources.v4`, the checked `descriptor.v10`, and every family domain stay; the independent accepted selection carrier steps `FACT_SOURCE_PROVENANCE_SCHEMA_VERSION` 3 → 4 and its owner domains on its own authority. Standard profile: key unchanged; descriptor, artifact identity, and cache pins move exactly once, at the reseat, as already accepted. M3 fixture: byte-identical. No key minted, none retired.
- **Status quo strict**: a growing host-named key population (forbidden); every OS-build move mints a key and retires dependent artifact identities.
- **2a**: a context parameter on every resolution API — public-surface churn — and either every production compile refuses (required) or policy forks (optional).
- **3a**: fact-sources grammar step, every profile descriptor moves, and host-conflated identity. **3b**: unchanged encoders plus a drift-prone mirror.
- **4-heavy**: zero encoder change; queue latency only. **Typed key grammar**: new versioned key schema plus migration of every existing key, read by nothing. **Deferral**: zero change; the freeze persists.

### Strongest counterargument, reversal evidence, negative controls

**Counterargument to 2b.** A family-scoped key over single-host rows reads like a family guarantee: `macos-apple9` will carry rows only one Apple9 device ever exhibited, and the key does not say so — the honesty lives in typed validity and provenance a casual consumer may never read. The late-refusal cost is also real (a subgroup plan can compile and only refuse at prepared preflight on a mismatching host). Mitigations, each already in force: no consumer derives anything from key text (dispatch is key+descriptor equality); per-row validity is `MeasuredEnvironment` and unwidenable by construction; host admission refuses under ADR 0086 anyway; the repository's maturity vocabulary separates an implemented row from a tested family guarantee.

**Reversal evidence.** A consumer shown to infer portability from key text alone; or an observed in-family contradiction (a prepared Apple9 pipeline reporting a width other than 32), which triggers component 5's withdrawal path and reopens whether family keys should carry whole-subject width rows at all; or an accepted attestation mechanism making per-host admission cheap enough that host-scoped public identity stops costing what it costs today.

**Negative controls** — definitional here (this ticket edits no production code); each is an obligation on the implementing carriers, with the refusal text to quote when it exists:

1. Source the standard profile from the M3 record → refused by component 3(a); the protocol line to quote is `a *new* M3 Pro Apple9 compile-profile width claim over the frozen population only`.
2. Mint any new host-named public key → review refusal citing the accepted model; the demote delivery's three compile-fail doctests remain the compile evidence for the existing one.
3. Fold a `26A5406e` population into the `26A5388g` source → the carrier's per-population construction must refuse; quote its environment-identity mismatch when it lands.
4. Declare a measured row at `PortableProfile` validity → unbuildable: `TargetCompileProfileMeasurementSource::new` fixes `FactValidityScope::MeasuredEnvironment`.
5. Loosen host applicability to device-model or family equality → refused by ADR 0086 item 3 and its recorded reason; the policy comparison stays field-exact.
6. Declare two contradicting in-family subgroup rows → the builder's existing duplicate/contradiction refusal; show its text when a second family measurement ever exists.
