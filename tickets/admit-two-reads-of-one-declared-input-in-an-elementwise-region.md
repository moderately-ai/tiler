## User-visible outcome

A program whose elementwise expression reads one declared input *both* densely and through a structural relation — `a * permute(a)` — compiles, instead of refusing at the request boundary under `structural-access-conflict`.

## Why this exists

**Fact — historical, at `912b6058` — the pre-widening path replaced a silently wrong result with a named refusal, then this ticket admitted the program.** At that commit, `out = a * permute(a)` over `a = [[1, 2], [4, 8]]` compiled and returned `[1, 16, 4, 64]`, which is `permute(a) * permute(a)`; the reference evaluator gives `[1, 8, 8, 64]`. The region bound one read per declared input and the expression's two `Input { ordinal: 0 }` nodes shared it, so the *mapped* relation served both leaves. `admit-elementwise-epilogues-over-a-materialized-intermediate` closed it fail-closed under `structural-access-conflict`; this ticket is the widening that admits the program instead (see Outcome).

**Correction — 2026-08-10.** Do not reproduce via a live `structural-access-conflict` row carrying `a * permute(a)`. That fixture moved to an *accepted* read-list assertion inside `every_refusal_names_its_unrecognized_property` (comment anchor `**Admitted, and this row moved here from the refusal inventory.**`); live `structural-access-conflict` rows are two structural relations on one input and staged `s * reverse(s)`. Observe admission with `cargo nextest run -p tiler-compiler -E 'test(one_input_read_densely_and_through_a_permutation_matches_the_reference_evaluator)'` (dense+permute bit-agrees with the reference and `assert_ne!` against `[1, 16, 4, 64]`) and the accepted-row half of `every_refusal_names_its_unrecognized_property`.

**Fact — historical problem statement — admitting it was a widening rather than a repair.** The region needed *two* reads binding one declared input, one dense and one mapped. Before this landing, `tiler_ir::schedule`'s `reads_bind_boundary_tensors_in_order` refused that by strict ascent of declared input ordinals (two reads of ordinal 0 failed), for the stated reason that two reads naming one input would bind one buffer twice while the leaf that meant another tensor went unbound. Relaxing it meant the region's read list and the program's declared interface would stop being the same list. After landing the rule admits a dense-then-mapped repeat of one ordinal (see Outcome and `reads_bind_boundary_tensors_in_order`).

**Inference — historical, pre-landing.** `plan_elementwise` keyed leaves by *value*, and an epilogue already numbered its leaves by access position rather than by declared ordinal, so a second read of one input was expressible in the recognizer's own vocabulary once schedule-side admission and assembly-side attribution landed (they did; see Outcome).

## Boundaries

- `crates/tiler-ir/**` for the read-list rule and whatever attributes a repeated ordinal; `crates/tiler-compiler/**` for the read list and the assembly binding.
- The *other* `structural-access-conflict` shape — one leaf carrying two *different* structural relations — is a separate question and may stay refused.

## Closes when

`a * permute(a)` compiles and bit-agrees with the reference evaluator; a region binding two reads of one input with no attribution still refuses by name, observed failing; and the fixture in `every_refusal_names_its_unrecognized_property` moves from the refusal inventory to an accepted row.

## Outcome

**Why the leaf, not the read list, was the thing to widen.** The defect was not that the region bound too few reads; it was that the *recognizer* had no way to say "two leaves, one tensor". `plan_elementwise` keyed leaves by `ValueId`, so `a` and `permute(a)` were one leaf carrying one relation, and every downstream list inherited that collapse. A leaf is now a `LeafRead { value, map }`: the relation is part of the leaf's identity, and two reads of one tensor under one relation still share a leaf, which is what keeps `(a * a) + b` one read of `a`. `ElementwisePlan::access_maps` disappeared — the map lives on the leaf it belongs to — and `NormalizedPointwise::access_maps` and `NormalizedSerialSum::prologue_access_maps` became `reads` and `prologue_reads`, per-read lists in access order, the shape `NormalizedEpilogue::reads` already had.

**Fact — the strict-ascent decision, with the elimination stated.** `reads_bind_boundary_tensors_in_order` now admits a repeated declared-input ordinal, and admits it in exactly one order: the dense read leads, the mapped read follows. Three candidates were tested and two discarded.

*Keep strict ascent and name the pair differently* — spell the second read as some other role, or renumber. Discarded on correctness: `TensorRole::Input`'s ordinal is program-scoped and `CoverAssembly::from_plan` resolves it against the declared interface, so any other spelling either binds the wrong buffer or invents a role with no interface behind it. The ordinal is not the problem; it is the only thing that *makes* the pair attributable, which is exactly why the same widening cannot extend to `TensorRole::Intermediate`.

*Relax to non-descending and require only that repeated reads carry distinct maps* — discarded on identity, not on cost. A region's reads and its expression's leaf ordinals are one correspondence, so swapping two reads of one ordinal and swapping the leaves that read them is a semantics-preserving renaming: two encodings of one region, two canonical identities, and the alpha-equivalence hazard the corpus names. Distinctness alone does not order the pair; ordering it needs a total order on `LogicalAccess`, which does not exist and whose addition would be a public-surface decision.

*Relax to non-descending with the pair's own canonical order — dense first, then mapped* — survives, and needs nothing new. There are at most two members, and "is this read `LinearIdentity`" totally orders them without ranking two relations against each other. This is what landed. Its corollary is derived rather than deferred: two *structural* relations on one ordinal stay refused because nothing orders them, which is the ticket's second Boundaries bullet reached from the rule instead of asserted beside it.

The rule's other two clauses are unchanged: at most one `TensorRole::Intermediate` read, and no read of a program output, each still refused by name rather than under a wildcard.

**Fact — one canonical spelling is preserved, and it is decided in the compiler, not left to the walk.** `canonical_input_reads` orders the read list by declared input, then dense-before-mapped within each input, because the two reads of `a` in `a * permute(a)` are popped in whichever order the operand stack produced. `recognize_epilogue` does the same after its staged read. Perturbing the intra-group order to mapped-first fails both `one_input_read_densely_and_through_a_permutation_matches_the_reference_evaluator` and `every_refusal_names_its_unrecognized_property`.

**Measurement — the defect's program compiles to the reference's answer.** `pipeline::tests::one_input_read_densely_and_through_a_permutation_matches_the_reference_evaluator` builds `out = a * permute(a)` over `a = [[1, 2], [4, 8]]`, asserts the region's three accesses are `Input{0}`/`LinearIdentity`, `Input{0}`/`ReindexBijection`, then the write, and asserts the kernel's output equals the reference bit for bit and equals `[1, 8, 8, 64]` — with `assert_ne!` against the measured wrong answer `[1, 16, 4, 64]` beside it, so a regression that reinstated the shared read fails on a value the test already knows the meaning of. The `structural-access-conflict` fixture in `every_refusal_names_its_unrecognized_property` moved from the refusal inventory to an accepted row asserting the derived read list, and its refusing neighbour is now the pair with no canonical order — two structural relations on one input.

**Fact — the second no-attribution refusal is the staged one, and it is reachable.** A staged value read both densely and through a relation would need two `TensorRole::Intermediate` accesses, and that role carries no ordinal, so nothing says which materialization edge each binds. `record_leaf` refuses it by name. `every_refusal_names_its_unrecognized_property` reaches it with `s * reverse(s)` where `s = sum(a, axis 1)`, against the accepted neighbour `s * s`. Its dense half is load-bearing for reachability: a *mapped-only* staged read is unreachable through the recognizer, because the epilogue boundary is discovered only when the walk meets the folded value as a direct operand, and `recognize_structural_read` refuses a structural occurrence over a computed value under `structural-operand` before that discovery happens. That was equally true before this ticket.

**Fact — the whole-program subject binding gained the check the widening made load-bearing.** `verify_region_output_binding`'s `Pointwise` arm and the serial-sum arm's prologue case compared expression, members, region id, shape, and element count — but not the read list, which was previously determined by the declared arity. It no longer is: a region reading input `0` twice and one reading inputs `0` and `1` carry the same three-leaf expression, and a dense read and a transposed one of the same tensor carry the same expression too. `elementwise_reads_match` compares the read list position by position, the way `epilogue_accesses_match` and `contraction_accesses_match` already did for their arms. `physical::tests::pointwise_schedule_requires_exact_expression_and_complete_ordered_coverage` forges an intrinsically well-formed region whose single read carries a whole-extent transposition; only this comparison refuses it, and stubbing the comparison to `true` fails that test alone.

**Measurement — an out-of-scope silent-wrongness defect found here and fixed rather than filed.** `fused_prologue_constants` recovered the affine constants from the prologue *expression* alone, and `fused_region` reads the declared input through a `LogicalAccess::ReductionContributor` relation with nowhere to put a structural one. So `sum(permute(a) * 2.0 + 1.0)` offered a fused single-region alternative that folded `a` where the program said `permute(a)`. Measured on this branch with the guard removed: the fused alternative returns `[8.0, 26.0]` where the reference gives `[12.0, 22.0]`, over `a = [[1, 2], [4, 8]]` folded on axis 1. It is not a defect this ticket introduced — the recognition of that program is unchanged by the widening (one non-dense read, no repeated ordinal), and the base's `fused_prologue_constants` is byte-identical to the perturbed form measured — and it returns an incorrect tensor, which the architectural contract does not admit deferring. The guard declines the candidate when any prologue read is non-dense, which loses a candidate and never a program: `pipeline::tests::an_affine_prologue_read_through_a_relation_declines_the_fused_fold` asserts no `Fused` alternative is retained and that the materialized pair agrees with the reference.

**Fact — identity: no domain and no sub-tag stepped *by this ticket*, and the argument is per-tag injectivity at the one encoding site.** `encode_access_maps` became `encode_elementwise_reads` and writes the *canonical sparse projection* of the read list: an ordinal whose only read is dense is written as nothing, and every other read is written as `(ordinal, relation)`. Three facts close it. (1) *No already-encodable subject's bytes move*: before this ticket a run held exactly the ordinals a structural occurrence interposed, which is what the projection still writes for a program with no repeated ordinal — verified at the construction site, `recognize_structural_read` being the only producer of a mapped read and building only `ReindexBijection` and `BroadcastReplication`. (2) *The widened domain is disjoint from the old one*: a repeated ordinal writes `LogicalAccess::LinearIdentity`'s tag `0x03`, which `encode_access_maps` could never emit. (3) *The projection is injective*: the declared input count is written earlier in the same arm, an absent ordinal has one dense read and an ordinal present `k` times has those `k` reads in run order, and the one ambiguous byte string — a lone entry writing `0x03` — is never emitted. So `pointwise-f32.v4` and `serial-sum-f32.v3` hold rather than step, under the forced-not-chosen standard: the cheaper option is available and its injectivity argument closes, so the step is not forced. `epilogue-f32.v1` holds trivially — its read-list encoder was already total over the widened domain and changed not at all. At landing time, `request-subject.v5` held and no arm's framing moved.

**Correction — 2026-08-10.** The enclosing request-subject domain has since stepped for unrelated work: live pin in `crates/tiler-compiler/src/domains.rs` is `tiler.compiler.request-subject.v6`. The arm sub-tags named above still appear; the claim that *this ticket forced no domain step* remains landing history, not a live `v5` reading.

**Measurement — no pin moved *by this ticket*, and the check that would have caught one was watched failing.** At landing, the explain qualifier `request=689c3aefc30f48d3` (`crates/tiler-compiler/src/explain.rs`) was *observed* green, not inherited: perturbing `encode_elementwise_reads` to write every read instead of the sparse projection fails `explain::tests::deterministic_trace_is_sealed_and_rendered_separately` and nothing else, so that test is exactly the sentinel for a subject-byte move and it says no when the bytes move. `grep -rnE '"[0-9a-f]{16}"|request=[0-9a-f]{16}' crates/ --include='*.rs'` returns that one site. The scheduled-region identity goldens (`STRICT_F32_REGION_IDENTITY_HEX`, `STRICT_F32_REGION_IDENTITY_HEX_V4`, the five `frontier.rs` rows) are unmoved: the IR change is an admission rule, not an encoding, and `tiler.schedule.v5` already encodes each access's role and map positionally. Zero pins moved on this landing.

**Correction — 2026-08-10.** Later tickets rebaselined the explain pin. The sole `tiler-explain-v7 request=` site in `crates/tiler-compiler/src/explain.rs` now pins `request=7ba3d77a66f04638`. The hex `689c3aefc30f48d3` is landing-time only; do not treat it as the live reading.

**Measurement — every new admitting and refusing path was watched failing, and the population is named.** Ten perturbations, each replacing exactly one site, run against the packages that must notice (`crates/tiler-ir/src/schedule/builder.rs`, `crates/tiler-compiler/src/request.rs`, `crates/tiler-compiler/src/physical.rs`; harness at `scratchpad/two-reads/perturb.py`, restoring each file from a sha256-compared copy). Restoring strict ascent fails `one_declared_input_may_be_read_densely_and_through_a_relation` and the end-to-end regression; admitting any repeated ordinal fails that test and `read_accesses_must_name_non_descending_declared_inputs`; admitting every read list fails those two and `a_pointwise_region_may_read_a_materialized_intermediate`; dropping the staged-attribution refusal, dropping the two-relations refusal, and refusing every repeated read each fail `every_refusal_names_its_unrecognized_property` (the last also failing the end-to-end regression); ordering the pair mapped-first fails both of those; stubbing `elementwise_reads_match` fails the forged-region test alone; dropping the fused guard fails the affine-prologue test alone; and writing every read into the subject fails the explain pin alone.

**The harness's own first run was wrong, and the correction is the reusable part.** Restoring with `shutil.copy2` carries the backup's mtime, which moves the file's timestamp *backwards*; cargo compares mtimes against its own build stamp, so a restored file looked fresh and every run after the first IR perturbation silently reused the binary built from that perturbation. The signature was a heterogeneous set of perturbations all failing one same unrelated test. The fix is `copyfile` plus `os.utime(source, None)`, and the clean tree was re-verified green (1543 tests) before the sweep was re-run.

**Unsupported cases, stated rather than approximated.** Two structural relations on one declared input refuse under `structural-access-conflict`; admitting them requires a canonical order between relations, which is a public-surface decision on `LogicalAccess`. A repeated read of a staged value refuses under the same rule and would need an ordinal on `TensorRole::Intermediate`. A dense read paired with a *broadcast* of the same value is unreachable rather than refused: a broadcast's operand is strictly smaller than the region domain and a dense leaf must be at the region domain, so the two cannot name one value — and were it ever reachable, `tiler_ir::program`'s `check_stage_accesses` would refuse it by element count, because both reads resolve to one whole-input view.

**Measurement boundary.** All evidence is `cargo nextest run` and `cargo test --doc` on this host under the pinned toolchain; no GPU execution and no timing. The end-to-end value comparisons run through the KIR interpreter and the reference evaluator, not through Metal.
