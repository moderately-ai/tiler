## User-visible outcome

A BF16 program encodes to an artifact and decodes back to the same program, with the dtype in its identity. A decoder meeting a BF16 tag it does not understand refuses rather than reading the bytes as `f32`, which at two versus four bytes per element would otherwise misread the whole buffer.

## Why the identity half is the risky half

**Fact, at `ef3c051`.** The artifact layer carries its own tag tables, separate from the IR's: `element_type_tag` / `element_type_from_tag` for `KernelType` and `storage_scalar_tag` / `storage_scalar_from_tag` for `StorageScalar` (`crates/tiler-artifact/src/program/model.rs`), plus `check_binding_access` in `codec/validate.rs`, which pairs a storage scalar with a kernel type in an exhaustive match.

**Fact.** `NumericalFacts` carries `canonical_arithmetic_nan_bits: u32` — a binary32-shaped field on the artifact's numerical record.

**Inference.** These tables are a second encoding of the same vocabulary, deliberately, so the artifact format does not move when the IR's internal representation does. That is why this is its own ticket rather than part of the IR one: a tag added in one place and not the other produces an artifact that encodes and fails to decode, and the failure is at the far end of the pipeline.

**Fact.** The canonical NaN field is `u32`-shaped and a BF16 canonical NaN is 16 bits. Whether it widens, becomes width-tagged, or moves into the realization record is a real design question, and `redesign-the-delivered-realization-record-from-typed-evidence` is already redesigning the record that owns delivered numerical evidence.

**Fact — the redesign has since landed, and the width question survived it unresolved (2026-08-06, read on `main` after the merge).** The record is now `EntryRealization` at artifact version 15 and manifest schema 13.0, and the field it projects from is unchanged: `NumericalRealization.canonical_arithmetic_nan_bits: u32` (`crates/tiler-ir/src/schedule/numerics.rs:237`), encoded big-endian into the artifact at `crates/tiler-artifact/src/program/model.rs:2245`. The dependency below is satisfied and the ordering concern it protected is discharged; the width question is now resolved against the landed record rather than coordinated with an in-flight redesign. Note the kernel IR already carries `CanonicalizeBf16Nan`, so a 16-bit canonical NaN value exists in the vocabulary this record describes.

## Implementation keys

- **The tag tables and `check_binding_access` are no longer this ticket's work** — they land in `admit-the-bf16-type-and-carrier-into-every-total-map`. **Measurement, 2026-08-02 at `3990f9d`, `cargo check --workspace --all-targets`.** `element_type_tag` (`program/model.rs:1737`), `storage_scalar_tag` (`:1758`), and `check_binding_access` (`codec/validate.rs:369`) are exhaustive matches over two deliberately non-`#[non_exhaustive]` vocabularies, so `crates/tiler-artifact` stops compiling the moment `KernelType::Bf16` and `StorageScalar::Bf16` exist. The tags therefore cannot wait for this ticket. On arrival, *verify* that both tables and their `*_from_tag` decoders already carry BF16 with every earlier tag value unchanged, rather than adding them a second time.
- What stays here is everything the tags are *for*: the round trip, the identity, and the refusals below. An artifact encoded before that widening must still decode to the identical program after it.
- The dtype participates in program identity, so a BF16 program and an otherwise identical F32 program have different identities. Assert this directly; it is the property a cache is wrong about if it does not hold.
- Resolve the `canonical_arithmetic_nan_bits` width question rather than widening the field by reflex, against the landed `EntryRealization` record rather than by introducing a second numerical record.
- Decoder refusal for an unknown tag stays a typed refusal at decode time, before any byte is interpreted.

## Required evidence

- Round trip: a BF16 program encodes, decodes, and compares equal, with its element count and byte length recorded.
- An artifact carrying a BF16 tag decoded by a build that does not know it is refused with a typed reason, not misread.
- A BF16 storage scalar paired with an F32 kernel type is refused by `check_binding_access`, observed failing.
- A BF16 program's identity differs from the same program at F32; both are recorded.
- Existing F32 artifacts decode byte-identically, pinned by the existing goldens.

## Closes when

A BF16 program survives the encode/decode round trip, the dtype is in the identity and shown to be, the unknown-tag and mismatched-binding refusals are observed failing, the canonical-NaN width question is resolved rather than deferred silently, F32 artifacts are unchanged, and the `ABI and materialization` cell for BF16 moves.

## Outcome

**The carrier is a tag, so nothing about the encoding moved — and that is the finding, not an absence of work.** The two questions this ticket existed to answer are whether a BF16 artifact survives its own codec and whether the carrier reaches identity. Both are answered affirmatively with no wire-format change, no `ARTIFACT_DOMAIN` step, and no `MANIFEST_SCHEMA` step, because a carrier occupies one tag byte inside a fixed-width row and both tables appended their BF16 value without disturbing an earlier one. The producer half of the outcome is not reachable at this layer and is now a filed ticket rather than a silent gap.

**Fact — the tag tables were verified, not re-added.** `element_type_tag`/`element_type_from_tag` carry `KernelType::Bf16` at `0x06` and `storage_scalar_tag`/`storage_scalar_from_tag` carry `StorageScalar::Bf16` at `0x03` (`crates/tiler-artifact/src/program/model.rs`), with `Bool`/`Index`/`F32`/`U8`/`I32` at `0x01`–`0x05` and `U8`/`F32` at `0x01`–`0x02` unchanged. `check_binding_access` (`crates/tiler-artifact/src/program/codec/validate.rs`) pairs `Bf16` with `KernelType::Bf16` by name, with no wildcard. `every_governed_tag_table_round_trips` pins every one of those values and its inverse, and its wildcard-free `match` over each vocabulary is what keeps the pinned list from covering one variant fewer than the vocabulary has. Nothing was added a second time.

**Fact — the canonical-NaN width question is resolved as no change, against the landed record.** `NumericalRealization.canonical_arithmetic_nan_bits` stays `u32`, zero-extended, and the artifact keeps projecting and encoding it verbatim big-endian; a `bf16` entry carries `0x0000_7fc0` and an `f32` entry `0x7fc0_0000`. The derivation, stated so it can be refuted rather than only read: (1) the shared IR already fixes this reading at `crates/tiler-ir/src/schedule/numerics.rs`, and `verify_pointwise_bf16` (`crates/tiler-ir/src/schedule/builder.rs`) *refuses* a `bf16` region whose declared payload is not `u32::from(CANONICAL_BF16_ARITHMETIC_NAN_BITS)` — so the reading is checked at the boundary that produces the region, not assumed at the one that emits it; (2) widening or width-tagging the artifact's field would make the artifact state a payload the record it projects cannot hold, which is a disagreement between two layers rather than added information; (3) it would move `ARTIFACT_DOMAIN`, the manifest schema, and every schedule and kernel identity to carry information no reader needs, since the arithmetic type that fixes how many bits are significant is already a total function of the region's scalar program; (4) zero-extension is injective across the two widths on its own terms, `0x0000_7fc0` and `0x7fc0_0000` being distinct `u32` values, so no `bf16` entry can collide with an `f32` one in identity. Moving the field into `EntryRealization` was rejected on that record's own stated grounds: it carries the *behaviours* the two records cross-check, and a NaN bit pattern is a value rather than a behaviour — which is exactly why it already excludes the profile key. **No `crates/tiler-ir` edit was required and none was made**, so stop condition 2 did not fire: the resolution is that the landed record is already right, and the artifact's job was to say so where a reader of the ABI will look.

**Measurement, at `55652b2b` + this branch, `cargo nextest run -p tiler-artifact`.** The single-variant fixture artifact with its program input on the `bf16` carrier encodes to **97,060 bytes** and decodes to an envelope equal to the model that produced it. Its input is the `[2, 3]` tensor, **6 elements**. The same artifact at `f32` also encodes to 97,060 bytes — the equality is the evidence that a carrier travels as a tag and not as a width the framing depends on — and the two byte strings differ at exactly forty positions: the thirty-two-byte manifest digest in the framing header (offsets 37–68), the interface component's carrier and access tags (3,194 and 3,196), the binding row's adjacent pair (25,148 and 25,149), and the copy of each pair inside the embedded artifact identity (28,854/28,856 and 73,648/73,649).

**Measurement — both identities, recorded by their difference rather than verbatim.** The two canonical identities are **48,584 bytes each** and differ at exactly **four** byte positions: `(3104, 0x02 → 0x03)` and `(3106, 0x03 → 0x06)`, the interface component's carrier and access tags separated by its storage-encoding byte, and `(47898, 0x02 → 0x03)` and `(47899, 0x03 → 0x06)`, the binding row's adjacent pair. Reproduced by encoding both envelopes and differencing `canonical_identity().as_bytes()`. They are recorded this way deliberately: a 48,584-byte hex string pinned in a test or a ticket is a pin the next identity step has to move, and it would carry no information this difference does not.

**Fact — both refusals are asserted as refusals, so each is observed failing by construction.** `an_unassigned_carrier_or_access_tag_is_refused_before_its_width_is_used` encodes a real BF16 artifact, locates the binding row through the encoder's own writers rather than through literals, and replaces the carrier tag with `0x04` and the access tag with `0x07` — each proven unassigned in the same test, so the day either is given a meaning the case fails rather than quietly stopping being about an unknown tag — resealing the manifest digest so what refuses is the tag table and not an integrity field a forger forgot. Both are refused as `UnknownTag` naming the subject and the rejected byte. This is the pre-BF16 reader's situation reproduced as exactly as it can be: that build cannot be run here, and a byte this build has not assigned takes the identical path `0x06` took through a reader written before `0x06` existed. `a_bf16_artifact_read_through_the_f32_access_type_is_refused` walks only the access type back on an artifact that really is `bf16` — the shape a partially updated producer emits — and gets `BindingAccessTypeMismatch`, `check_binding_access` running ahead of the component check. The pre-existing `a_bf16_carrier_is_refused_against_a_wider_access_type_and_admitted_against_its_own` stands unchanged and still passes.

**Fact — F32 artifacts are byte-identical and no pin moved.** No encoder, decoder, validator, or model file changed; the only source change is test code. `ARTIFACT_DOMAIN` holds at `tiler.artifact-program.v15` and `MANIFEST_SCHEMA` at `(13, 0)`. The exact check is `grep -rn "tiler.artifact-program.v1[45]\|MANIFEST_SCHEMA" --include="*.rs" crates/ prototypes/`, whose results are unchanged from the base commit, and `crates/tiler-artifact/src/proof/codec.rs`'s `MANIFEST_SCHEMA = (1, 0)` is the proof sidecar's and did not move. No golden, fixture, or recorded identity in `crates/tiler-build/src/metal_plan.rs`, `crates/tiler/src/route/tests.rs`, `crates/tiler-artifact/src/program/codec/tests.rs`, `docs/artifact-abi.md`, or `docs/status.md` was touched. **There was no identity-domain step**, so stop condition 1 did not fire, and the pins that lie outside these scopes were never at risk.

**Fact — the round trip is evidence about the encoding, and the producer half is a wall one layer down.** No producer in this workspace can assemble a BF16 artifact today, and the three reasons compose into one wall. `NumericalContractIdentity` (`crates/tiler-ir/src/index/refinement.rs`) is a newtype over `F32NumericalContractKey` with no route from the accepted `Bf16NumericalContractKey`, so a BF16 refinement subject is not expressible. `crates/tiler-ir/src/index/` contains no BF16 reference at all — the exact check is `grep -rln 'bf16\|Bf16' crates/tiler-ir/src/index/`, which returns nothing — so no BF16 scalar operation exists for a candidate region to apply. And the standard semantic provider's `register_index_realization_law` loop (`crates/tiler-ir/src/semantic/registry.rs`) registers laws for nine `f32` and quantization operations and none for the registered BF16 family, the comment beside it stating the absence is deliberate and fails closed later. **Inference.** So `CoveredOccurrence` is unobtainable for a BF16 occurrence, and a stage covering nothing is refused as `KernelProgramDiagnostic::UncoveringStage` at whole-program verification.

**Inference — why the BF16 envelope is assembled directly rather than built, and why that is the honest choice.** Two alternatives were eliminated. Waiting for the producer would leave the carrier's encoding untested until a layer this crate does not own lands, which is the wrong order: whether a BF16 artifact survives its own codec is answerable now and is this crate's to answer. Building a fixture with an `f32` semantic graph, `bf16` physical carriers, and a `PointwiseBf16` kernel is *structurally* admissible — `check_origin` pins a program input value's shape but not its carrier — and was rejected because it would assert a BF16 round trip for a program claiming to realize `tiler::multiply-f32@1` with `bf16` arithmetic. That is a fixture that passes while meaning something false, which is worse than a stated boundary. The forged envelope goes through the ordinary encoder and the ordinary decoder, so every check runs against production code; what it does not evidence is a producer, and the tests say so at the site.

### Verification

**Fact — a locator bug was found by the perturbation discipline and not by the passing suite.** The unknown-tag case's binding-row locator originally went through `manifest_offset`, which asserts the pattern occurs exactly once. It occurs *twice*: the manifest ends with the artifact identity, and the identity encoder restates a binding's carrier and access tags in the same order the entry row writes them. The case was failing on that assertion from the moment it was written and the first targeted run did not catch it, because the filter that run used matched on `bf16` and the case's name contains neither that nor the other term — the "a check that did not run reads as a check that passed" failure exactly. `manifest_occurrences` now returns every offset, the case asserts the count is two and says why, and it perturbs the manifest's own row, which a reader frames long before it reaches the identity to compare, so the refusal under test is the tag reader's rather than `ArtifactIdentityMismatch`.

**Measurement — five independent perturbations, each observed failing, each attributable.** Run singly against a restored tree, `cargo nextest run -p tiler-artifact -E 'test(bf16) or test(unassigned)' --no-fail-fast`, 4 tests in scope. (A) The binding never moves to the `bf16` carrier: 3 fail, and the pre-existing `a_bf16_carrier_is_refused_against_a_wider_access_type_and_admitted_against_its_own` still passes, because it forges its own envelope — correct isolation. (B) `UNASSIGNED_ACCESS` set to the assigned `0x06`: only the unknown-tag case fails, on its own `is_none` guard. (C) The access type is not walked back to `F32`: only `a_bf16_artifact_read_through_the_f32_access_type_is_refused` fails. (D) `encode_identity`'s component and binding writers stop folding the carrier and access tags (`crates/tiler-artifact/src/program/model.rs`): the round trip fails, which is the evidence that the identity inequality genuinely depends on those bytes rather than on something else that moved with them, and the unknown-tag case fails too because its locator then finds one occurrence instead of two — the asserted count doing its job. (E) `check_binding_access` maps `StorageScalar::Bf16` to `KernelType::F32`: all 4 fail, the refusal under test inverted. The tree was restored from backups after each and `git status` confirmed before committing.
