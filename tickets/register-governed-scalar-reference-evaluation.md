`FrozenScalarRegistry::standard()` now defines `tiler.scalar::constant-f32@1`, `multiply-f32@1`, and `add-f32@1`, and the governed index-access lowerings emit regions over them. No `tiler_reference::ScalarReferenceRegistryBuilder` registration exists for those keys, so the regions the compile path now refines cannot be executed by the independent `IndexRegionEvaluator` oracle.

That leaves a precise gap. Refinement binds structure and reached authority; it explicitly does not re-derive per-point arithmetic (`crates/tiler-compiler/src/legality.rs` module documentation). The governed lowerings are therefore proved to *realize the occurrence structurally* and are not yet checked to *compute it*. Two questions come with the registration and must be answered rather than assumed:

- Whether the governed scalar `add-f32` and `multiply-f32` canonicalize an arithmetic NaN result. `tiler_ir::kernel::lower` applies `ConvertOp::CanonicalizeF32Nan` after the biasing add and after every accumulation but not after the multiply, and `tiler_reference`'s `strict_sum` canonicalizes the reduction result. The scalar definitions' normative references currently name IEEE 754-2019 binary32 operations without stating a canonicalization rule.
- Whether the governed serial-sum lowering's seed-with-the-first-contributor fold reproduces `tiler_reference::strict_sum` exactly on the sign-of-zero and NaN vectors that distinguish it from a `+0.0`-seeded fold.

**Closing evidence.** A reference scalar registry for the three governed scalar keys, and an oracle test that executes each governed family's refined region on the conformance vectors already used by `pipeline::tests::structured_fused_body_interpreter_matches_reference_evaluator` and agrees bit for bit.

## Outcome

`tiler_reference::FrozenScalarReferenceRegistry::standard()` and `ScalarReferenceRegistryBuilder::standard()` now ship an executable oracle for the three governed scalar keys, bound to `FrozenScalarRegistry::standard()` and cached in a `OnceLock` exactly as its two sibling registries are. The regions the governed `f32` index-access lowerings emit are executable by `IndexRegionEvaluator` for the first time. Both open numerical questions are answered by measurement, and the second turned up a real oracle divergence.

**Question 1 — the governed `add`/`multiply` canonicalize an arithmetic NaN; `constant` does not.**

**Fact (inspected source).** `tiler_ir::semantic::registry.rs` gives `tiler::multiply-f32@1` and `tiler::add-f32@1` the `arithmetic_f32_facts()` record, whose second field is `canonical_f32_bits(CANONICAL_F32_ARITHMETIC_NAN_BITS)`. `tiler_reference::binary` implements it: every result passes through `canonicalize_arithmetic_f32`. `tiler::constant-f32@1` instead declares `"exact-binary32-bits"` and its normative reference is "exact IEEE-754 payload", and `F32ConstantReference` forwards the attribute bytes untouched. The scalar oracle matches both: `StandardScalarBinaryF32` canonicalizes, `StandardScalarConstantF32` does not. Canonicalizing the constant would make a region unable to materialize an exact binary32 pattern; propagating the host payload from an arithmetic result would make a refined region and the semantic evaluator disagree on the programs refinement exists to check.

**Measurement.** `governed::governed_scalar_arithmetic_canonicalizes_every_nan_result` drives both families over `0x7fc01234`, `0xffc00000`, `0x7f800001`, a NaN-pair, `INFINITY + NEG_INFINITY`, and `INFINITY * 0.0`; every NaN result is `0x7fc00000` and every case agrees with the tensor oracle. `governed_scalar_arithmetic_preserves_every_non_nan_payload` pins that nothing else is normalized — both signed zeros, the least subnormal, subnormal addition, and a signed infinity keep their exact bits. `the_governed_scalar_constant_reproduces_an_exact_payload` pins the opposite rule on six payloads including a signalling NaN.

**A contract gap this exposed, filed as `declare-governed-scalar-numerical-facts` (p1, `implementation/ir`).** `ScalarRegistryBuilder::standard` builds all three governed scalar contracts with `CanonicalValue::record([])` for both `facts` and `conformance`. So the canonicalization rule is stated by the *semantic* operation definitions and implemented by this oracle, but the scalar authority a third-party index-access lowering provider is written against declares none of it. That crate is `implementation/ir`, held by a live sibling, so this was filed rather than fixed.

**Question 2 — the fold matches `strict_sum` bit for bit everywhere it performs arithmetic, and diverges on exactly one case.**

**Measurement — agreement.** `governed::the_governed_serial_fold_matches_the_semantic_oracle_bit_for_bit` runs fourteen vectors: the `[2, 3]` conformance vector `structured_fused_body_interpreter_matches_reference_evaluator` already uses, four sign-of-zero vectors, five NaN-ordering vectors, three order-sensitive vectors whose sums differ under any reassociation, and a subnormal vector. All agree bit for bit. `a_positive_zero_seed_would_change_the_observable_result` shows the seeding rule is load-bearing rather than incidental: a `+0.0`-seeded fold over three negative zeros yields `+0.0` where the contract requires `-0.0`. `an_empty_reduced_domain_is_positive_zero_in_both_oracles` covers the vacuous case.

**Measured divergence — a single contributor whose payload is a non-canonical NaN. Filed as `reconcile-single-contributor-strict-sum-nan-canonicalization` (p0).** `tiler_reference::strict_sum` writes `canonicalize_arithmetic_f32(accumulator.unwrap_or(0.0))` unconditionally, so a fold that performed *zero* additions still reports `0x7fc00000`. `governed::GovernedStrictSerialSumF32` returns `seed` directly when `plan.reduced_points == 1`, and `tiler_ir::kernel::lower::emit_reduction` stores `seed` unchanged when `plan.contributors == 1` with a comment saying so. Two of the three implementations agree with each other and disagree with the normative oracle, on `0x7fc01234`, `0xffc00000`, and `0x7f800001`.

This is live in the compiled product: `physical.rs` builds a bare `ScalarProgram::StrictSerialSum` for the materialized alternative, and an extent-1 reduced axis is admissible — `pipeline`'s own `[4, 1]` fixture is one. No existing test catches it because that fixture's NaN is `f32::NAN`, which already *is* `CANONICAL_F32_ARITHMETIC_NAN_BITS`, and because its fused variant carries a scale/bias prologue whose `emit_scale_bias` canonicalizes the seed. Both sides are deliberate — `strict_sum_preserves_non_nan_singletons_and_canonicalizes_nan_results` pins one and a source comment pins the other — so this is a decision, not a defect to fix unilaterally. `governed::a_lone_non_canonical_nan_contributor_diverges_between_the_two_oracles` pins the disagreement so that a change to either side fails loudly instead of silently re-aligning the oracles at an unreviewed payload, and `a_single_contributor_agrees_on_every_payload_but_a_non_canonical_nan` bounds it to exactly that case.

**Two questions the ticket did not ask, checked because the same reasoning covers them.** Reduction *axis order* cannot diverge: `strict_sum` linearizes its reduced sub-shape in the order the axes appear in the attribute while `SumPlan` linearizes in ascending axis order, but the semantic inferencer rejects any non-strictly-ascending axis list with `sum.axes.canonical`, so no verified program can reach the difference. And `+0.0`-identity behaviour on the empty reduced domain agrees, because `SumPlan::fold_empty` emits the identity for exactly the case `strict_sum` returns `+0.0`.

**Scope boundary, and what it leaves open.** The closing evidence asked for the governed families' *refined* regions. `tiler-reference` depends only on `tiler-ir` and `tiler-compiler` dev-depends on `tiler-reference`, so `tiler-reference` cannot import `tiler_compiler::governed` (which is `pub(crate)` besides), and inverting that edge would put the reference oracle downstream of the compiler. The regions here are therefore hand-written mirrors, each written by reading `governed.rs` step for step and each naming which construct it mirrors. They answer the numerical questions completely; what they cannot catch is a mirror that has drifted from the emission. `execute-governed-refined-regions-against-the-oracle` (p1, `implementation/compiler`) closes that residue by running the emitted regions from the compiler crate, following the shape `legality::tests::refinement_output_is_checkable_against_the_reference_oracle` already uses.

**The tests live in the existing admitted target, not a new one.** `scripts/check_workspace.py` holds a closed `EXPECTED_TESTS` allowlist; a new `crates/tiler-reference/tests/governed_scalar_reference.rs` fails the workspace contract with `package.tiler-reference.targets: expected [...] got [...]`, verified by running `uv run --locked python scripts/check_workspace.py`. Amending the allowlist needs `implementation/workspace`, which this ticket does not hold. The ten cases are a `mod governed` inside `crates/tiler-reference/tests/index_region_oracle.rs`, which is already admitted and whose stated subject is exactly this. The module reuses that file's `f32_type`, `input_ids`, and `semantic_authority` and defines bit-exact helpers of its own: every fixture is built from `u32` bit patterns and never routed through an `f32` value, so a signalling NaN cannot be quietened in transit.

**Additive-public only.** `ScalarReferenceRegistryBuilder::standard`, `FrozenScalarReferenceRegistry::standard`, and two variants on the already-`#[non_exhaustive]` `ScalarReferenceRegistryError` (`ScalarRegistry`, `ReferenceRegistry`) plus a `From<ReferenceRegistryError>` conversion. No existing signature changed. Under ADR 0074 convention 5 the error enum stays 5a — no crate outside `tiler-reference` maps it totally — so `#[non_exhaustive]` is retained rather than reflexively removed. Convention 1 is why the two variants exist instead of an `.expect()` on `ReferenceSignature::new`: each preserves its own concrete cause through `source()`, mirroring the sibling `IndexRegionEvaluationError::ReferenceRegistry`. Convention 4's terminal is unchanged. `canonicalize_arithmetic_f32`, `f32_element`, and `decode_f32` were widened from module-private to `pub(crate)` so the scalar oracle shares the tensor oracle's exact arithmetic rather than restating it; the first gained a doc comment recording that it applies to an arithmetic *result* and not to a read or an exact constant.

**Verification.** `uv run --locked python scripts/check_repository.py` passes end to end ("complete repository validation passed"). `cargo nextest run --workspace`: 595 tests run, 595 passed. `git diff --check` clean. `tkt guard` and `tkt lint` verdicts recorded on the branch.
