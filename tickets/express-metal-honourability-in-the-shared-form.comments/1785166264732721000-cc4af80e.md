Blocked on `prototype-public-compiler-api`, verified by reading rather than inferred from the ticket text. Recording the derivation so the edge can be refuted rather than only the conclusion.

**Fact — every siting this ticket offers requires the declaration to cross from a Metal-side declarer into the compiler.** `tiler-compiler` depends on `tiler-ir` and `tiler-reference`; `tiler-metal` depends on `tiler-ir`, `tiler-artifact`, and `tiler-metal-aot`. Neither sees the other, and `AGENTS.md` forbids the compiler core depending on Metal. So whichever of the three sitings wins — `tiler-ir` owning the vocabulary, a checked adapter, or a third crate — something outside `tiler-compiler` must hand it a target-profile honourability declaration.

**Fact — no public boundary accepts one.** In `crates/tiler-compiler/src/lib.rs`, `feasibility`, `honourability`, and `request` are private `mod`s; only `capability`, `legality`, and `session` are `pub mod`. Every honourability type is `pub(crate)`. The governed declaration is a private `&'static [DeclaredBehaviour]` at `crates/tiler-compiler/src/request.rs:457` (`GOVERNED_TARGET_HONOURABILITY`). `capability` exposes `register_scalar_lowering` and `register_index_access`, which install *lowering providers*, not target profiles. `Compilation`'s `target_profile_key` and `target_profile_descriptor` are read accessors. The only public compile entry is `compile_governed(&program, contract)`, which takes no profile argument.

To refute in one line: find a `pub` item in `tiler-compiler` that accepts a target profile or an honourability declaration.

**Inference — the missing capability is exactly what `prototype-public-compiler-api` owns.** That ticket's stated outcome lists "target profiles" among the inputs an external frontend must be able to state through one checked boundary, and requires installing an authority "without an in-crate test hook". Until it lands, satisfying this ticket would mean either restating the Metal fact inside `tiler-compiler` — a second declaration of one target property, which this ticket names as the failure mode to avoid — or widening the compiler's private surface in a way `prototype-public-compiler-api` is about to redesign.

**What is not blocked.** The ownership decision itself can be researched now, and one candidate is already weakened: a third crate adds a graph node with no reachability property `tiler-ir` lacks, since `tiler-ir` is already the crate both sides depend on. Also worth carrying forward — `NumericalDimension` and `DimensionBehaviour` are near-restatements of `tiler-ir` vocabulary (`honourability.rs` says so on the type: they enumerate what `tiler_ir::schedule::NumericalRealization` carries, over `SubnormalMode` and `NumericalPermission`, which already live there). `HonouringMeans` is the genuinely new term and the one whose siting actually widens a remit. That suggests the split worth evaluating first is vocabulary in `tiler-ir` versus provenance discipline (`AvailabilityPhase`, `FactAuthority`, `FactValidityScope`) staying in `tiler-compiler`, rather than moving `DeclaredBehaviour` whole.
