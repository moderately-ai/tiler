## User-visible outcome

A semantic program declaring several ordered named outputs compiles, so the conformance gate's multi-output requirement is discharged by a program that compiles rather than by a test asserting the refusal.

## Why this exists

**Fact — two guards make single-output a boundary invariant.** `crates/tiler-compiler/src/request.rs:2491` opens `select_supported_strategy` with `if program.output_count() != 1`, and `crates/tiler-compiler/src/program.rs:1254` carries the same condition on the program-assembly path. A program with two ordered outputs is refused before a strategy is selected. (Both line numbers moved again between this ticket's second correction and its dispatch — `:2228` and `:1234` at the time of writing — so verify by reading rather than by seeking the line.)

*Corrected by [`admit-a-general-program-shape-recognizer-at-the-compiler-request-boundary`](admit-a-general-program-shape-recognizer-at-the-compiler-request-boundary.md).* This paragraph read "four guards" at `request.rs:2184`, `:2377`, and `:2581` — one per whole-program template. The general recognizer replaced those three templates with one occurrence walk, so the three per-template guards became the single program-wide one above, checked once before the output's producing occurrence is classified. The count changed; the invariant did not, and neither did this ticket's obligation.

**Fact — the conformance gate's multi-output row is therefore a permanent negative test.** `docs/correctness-and-testing.md:106-111` requires the optimizer conformance owner to exercise "non-isomorphic and fan-out or multi-output graphs" *before the public compiler facade is accepted*; `:117` records the consequence in the gate's own words — "Ordered multi-output programs are rejected explicitly rather than compiled, so the multi-output row of the requirement above is a negative test." The test is `ordered_multi_output_programs_reject_explicitly` at `crates/tiler-compiler/src/pipeline/conformance.rs:389`.

**Inference — the gap contradicts the architectural contract directly.** AGENTS.md requires modelling programs "as typed operations and values with ordered named outputs and multi-result support — not one SQL-like root or a single output tensor". A boundary refusing every multi-output program is the single-output root that clause forbids. [`admit-multi-input-elementwise-programs-at-the-compiler-boundary`](admit-multi-input-elementwise-programs-at-the-compiler-boundary.md) (`done`) is the precedent for how such a limit is located, measured, and lifted — and its outcome shows the wall is usually one layer below the guard, so this ticket's first obligation was to locate the multi-output wall before editing any guard.

## The wall was located, and it is not where the precedent predicted (2026-08-02)

**Fact — `tiler-ir` is not the wall.** The expectation on dispatch, from the multi-input precedent, was a missing schedule or artifact noun. There is none. `KernelProgramBuilder::push_output` (`crates/tiler-ir/src/program/builder.rs:714-765`) is general and bounded by `MAX_PROGRAM_OUTPUTS` (4096, `crates/tiler-ir/src/program/mod.rs:329`), not by one. `program::tests::storage_reuse_is_admitted_only_with_an_explicit_handoff` (`crates/tiler-ir/src/program/tests.rs:1706-1737`) builds and *verifies* a two-output program — `sum_a` and `sum_b` across four stages and five allocations — and asserts `outputs().len() == 2`. `program::tests::a_missing_named_output_is_rejected` (`:1756-1769`) already discharges this ticket's third required failure case, a plan naming fewer outputs than the program declares, as `KernelProgramDiagnostic::MissingNamedOutput`; `KernelProgramBuildError::DuplicateOutput` covers the collision case.

`TensorRole::Output` carrying no ordinal (`crates/tiler-ir/src/schedule/model.rs:54-55`, beside `Input { ordinal }` at `:48-51`) reads like the multi-input wall repeating and is not one. A region writes one owning tensor, several regions write several, and the program layer binds each stage's buffers to values positionally — which `ValueRole::fills` states outright at `crates/tiler-ir/src/program/model.rs:91-111` ("a stage binds its buffers to values positionally, so the ordinal is discharged by that position and this check owes only the class").

**Fact — the wall is this crate's planner.** `verify_artifact_refinements` matches the scheduled regions against exactly three fixed strategy shapes — `[single]`, `[_, _]`, `[_, _, _]` at `crates/tiler-compiler/src/program.rs:1228-1236` — which are the fused, materialized two-stage, and split-reduction forms of a **single-output** pipeline, and then reads the one output with `semantic.outputs().next()` at `:1244`. Nothing upstream produces a cover assigning regions to several ordered outputs.

**Fact — that widening is already owned by another ticket.** [`implement-general-dag-partitioning`](implement-general-dag-partitioning.md) (`todo`, p1) closing condition 2 is "Named and multi-result outputs are planned as ordered graph outputs, not reduced to a single root, and a plan naming fewer outputs than the program declares is rejected rather than accepted as a subset" — this ticket's obligation exactly. This ticket now depends on it. Relaxing `output-arity` first could only admit a program the planner cannot cover, failing mid-pipeline instead of refusing at the boundary, which is the outcome the multi-input precedent calls "strictly worse than refusing".

## The cover half landed, and the wall moved again (2026-08-04, general-pipeline audit)

**Fact — the dependency named above is `done` and its closing condition 2 is implemented.** `implement-general-dag-partitioning` landed 2026-08-04. `crates/tiler-compiler/src/cover.rs` collects the ordered named program outputs a cover must produce and `verify_cover` checks each is produced by **exactly one** region rather than merely retained by some region; `multi_result_outputs_are_retained_and_a_dropped_one_is_rejected` plans a two-output fixture with both outputs retained by every cover and refuses a cover naming fewer, and `the_named_output_and_observability_checks_can_say_no` proves those checks can fail. So the sentence in the paragraph above this section — "nothing upstream produces a cover assigning regions to several ordered outputs" — is no longer true, and neither is the identical sentence in `select_supported_strategy`'s doc comment at `crates/tiler-compiler/src/request.rs` (report it there; that file is another ticket's scope).

**Fact — the residual wall is two sites, both downstream of the cover.** Verified by reading the compile path at `c1110ea9`, and both are the ones `CoverPolicy::governed` already names as the reason duplication stays off the compile path (`crates/tiler-compiler/src/cover.rs`, the `governed` constructor's doc comment):

1. **Program assembly implements exactly three plan shapes.** `build_plan_program` in `crates/tiler-compiler/src/pipeline/planning.rs` matches the ordered scheduled regions against `[region]`, `[_, _]`, and `[_, _, _]` and returns `ProgramError::Structure { rule: "unsupported-plan-shape" }` for anything else; `verify_artifact_refinements` in `crates/tiler-compiler/src/program.rs` carries the same three-way match with `rule: "artifact-strategy-cardinality"`, and the `output_count() != 1` guard this ticket cites sits immediately below it under `rule: "semantic-output-coverage"`.
2. **The single installed physical provider proposes only for pre-computed member sets.** `GovernedPhysicalProvider::propose` in `crates/tiler-compiler/src/frontier.rs` compares a cover region's exact semantic member set against the member partitions the recognized strategy carries and returns an empty offer otherwise, so a cover the general search enumerates over any other region has no implementation and is dropped at complete-plan selection with no explain attribution — nothing rejected it, because nothing proposed for it.

**Inference — closing condition 1 needs restating, and this ticket is still correctly blocked.** Its first dependency is satisfied, its second (`carry-artifact-program-output-order-into-kernel-program-identity`) landed, and both sites above are now owned. **Updated 2026-08-04:** [`define-the-minimum-correct-physical-realization-profile`](define-the-minimum-correct-physical-realization-profile.md) defined the baseline both sites owe and filed one ticket each — [`assemble-a-kernel-program-from-an-arbitrary-cover`](assemble-a-kernel-program-from-an-arbitrary-cover.md) for site 1, which is now this ticket's fourth dependency, and [`derive-physical-proposals-from-the-cover-region-subject`](derive-physical-proposals-from-the-cover-region-subject.md) for site 2, which the assembly ticket in turn depends on. Site 2 remains not this ticket's work for the reason recorded here: a two-output program whose outputs are independent needs two regions the provider can propose for, which the reduction strategy's own partitions can supply, so site 2 bounds *which* multi-output programs compile rather than whether any does.

**Fact — half the ordering obligation already holds.** Output order is identity at the semantic layer: `crates/tiler-ir/src/semantic/identity.rs:128-132` encodes the output list in declaration order with no sort, and `canonical_traversal` (`:143-170`) seeds the canonical value numbering by visiting outputs in that order. The other half landed 2026-08-04: [`carry-artifact-program-output-order-into-kernel-program-identity`](carry-artifact-program-output-order-into-kernel-program-identity.md) (done) stepped the kernel-program domain to `tiler.kernel-program.v8` — the encoder now folds the ordered output list, and `verify_outputs` proves subject order, per-key contiguity, and declared component order, refusing `misordered-named-output`. This dependency is satisfied, and the ordering boundary this ticket must not violate is now enforced rather than merely owed.

**Fact — one cost the vocabulary imposes, recorded so the planner work does not rediscover it.** `ValueRole` is exclusive and `fills` refuses an `Output` value for a `TensorRole::Intermediate` buffer, enforced at `crates/tiler-ir/src/program/builder.rs:1130`. A program that both publishes an intermediate and consumes it therefore needs a copy stage reading `Intermediate` and writing `Output`. That is the shape `pipeline::conformance`'s own multi-output fixture has — it publishes `scaled` and reduces it into `reduced` — and building that copy stage is blocked by [`admit-elementwise-epilogues-over-a-materialized-intermediate`](admit-elementwise-epilogues-over-a-materialized-intermediate.md), since no elementwise region this profile builds reads a materialized intermediate. A multi-output program with *independent* outputs does not hit this.

**Evidence.** `crates/tiler-compiler/tests/multi_output_boundary.rs` is the executable form of everything above: the `output-arity` refusal against a compiling one-output control, the colliding-key case, the semantic-layer ordering guarantee, and the `fills` constraint pinned so a `ValueRole` widening reports itself. Each of its four assertions was observed failing under a deliberate perturbation before being trusted.

## The wall moved a third time, above everything the dependencies fixed (2026-08-05, dispatched implementation)

**Measurement — relaxing both guards admits nothing, so neither moved.** At base `3adc0689`, `select_supported_strategy`'s `output_count() != 1` and `verify_artifact_refinements`'s `semantic-output-coverage` arity check were relaxed together and two fixtures compiled through the ordinary entry point. An independent two-output program (`doubled = x * 2`, `tripled = x * 3`, built on `SemanticProgramBuilder::try_standard`) reached `phase: "strategy", rule: "operation-set"`. The reduction-epilogue fixture this ticket's conformance row uses — publishes `scaled`, reduces it into `reduced` — reached `phase: "program-assembly", rule: "cover-named-output-attribution"`, meaning recognition, cover enumeration, physical proposal, and complete-plan selection all *succeeded* for it. The perturbation was reverted and nothing of it is retained; reproduce by relaxing exactly those two conditions.

**Fact — the residual wall is the request-boundary recognition, one layer *above* everything the four dependencies fixed.** `select_supported_strategy` reads `program.outputs().next()`, classifies that one occurrence, and each recognizer below requires its walk to cover the program exactly — `recognize_pointwise` under `operation-set` when `recognized.members.len() != program.operation_count()`, `recognize_reduction` through `check_recognized_operation_cover`. `NormalizedProgram` therefore holds one expression, one output shape, one output key, and one member partition, and `crate::physical::spell_region` can spell only a cover region whose members equal one part of it.

**Inference — the admissible multi-output set is empty, structurally rather than by fixture survey.** A second declared output either has its producing occurrence inside the first output's walk or it does not. Outside, the walk covers less than the program and `operation-set` refuses. Inside, that value is consumed by another occurrence of the same walk, so its producing region either materializes for a consumer in another region — leaving its one owning write to serve both the edge and the publication — or contains that consumer and must publish two named outputs from one write. A region writes one owning tensor and `ValueRole` is exclusive, so both are refused a layer down. The dispatch brief's premise, that a program with *independent* outputs is the reachable compilation target, is refuted by the first branch: independence is exactly what puts the second producer outside the walk.

**Consequence — the guards stay, and this ticket is blocked on a new dependency.** Relaxing `output-arity` while nothing multi-output can compile trades a boundary refusal for a mid-pipeline one, which is what this ticket's own "Why this exists" section and the multi-input precedent call "strictly worse than refusing". [`recognize-several-ordered-named-outputs-at-the-compiler-request-boundary`](recognize-several-ordered-named-outputs-at-the-compiler-request-boundary.md) was filed for the widening and added to `dependencies`. The epilogue shape additionally needs [`admit-elementwise-epilogues-over-a-materialized-intermediate`](admit-elementwise-epilogues-over-a-materialized-intermediate.md), unchanged.

**The attribution elimination, run and recorded rather than implemented.** Closing condition 2's new obligation asks which route supplies the named-result attribution. Three candidates were tested:

- *Derive it from the cover region's members and the semantic graph* — for each declared output, find its producing operation and locate the region containing that member. **Eliminated on correctness.** It derives from a different fact than the one `verify_cover` proved. The cover's guarantee is stated over *retained named outputs*, and `DuplicationRefusal::NamedResultProducer` and `CoverRefusal::AmbiguousNamedOutput` exist precisely so that the day duplication admits a named-result producer, several regions contain the member while only one retains the output. Membership would then pick arbitrarily, and silently.
- *The assembly derivation reads the region formation outcome* — thread `&[RegionCandidate]` into `CoverAssembly::from_plan` and look each cover region's candidate up by occurrence identity. **Eliminated on maintainability.** `SelectedPlan` does not carry the candidates, so the second authority must be threaded through `build_alternative_for_origin`, `pipeline::verify`, and the `verify_artifact_refinements` re-derivation; and it contradicts `from_plan`'s own stated contract that the cover is consumed, never re-derived.
- *The cover retains the named result per region* — **survivor.** `CoverRegion` gains the named-output value ordinals its candidate retains with `named_result`, populated in `assemble_resolved_cover` from `candidate.retained_outputs()` and checked in `verify_cover` step 1 alongside members, content, and label. `from_plan` then attributes each declared output by value rather than by the execution-order `zip` it does today. **It is not folded into `encode_cover_identity`:** `RegionOccurrenceIdentity` already encodes the retained output sites and `RegionContentIdentity` already encodes their `named_result` flags, so the field is a projection of bytes cover identity already folds, and `verify_cover` proves the projection. Folding it again would move every cover identity — an identity-domain step for no information.

**Why the survivor was not implemented here.** Every refusal it introduces is unreachable while `output-arity` stands, and `from_plan` cannot be unit-driven for a multi-output plan: `CoverAssembly::stated` bypasses the attribution entirely, and building a real `SelectedPlan` needs a `VerifiedTargetRequest`, which needs the request boundary to admit the program. Landing checks that cannot be watched failing is what AGENTS.md forbids acting on, so the design is recorded here for the widening ticket to land *with* its tests rather than shipped as unreachable machinery now.

## The wall fell, and the last piece was a derivation rather than a guard (2026-08-05, round two)

**Measurement — with recognition widened, relaxing both guards reaches program assembly.** At base `23a3562d`, `select_supported_strategy`'s `output_count() != 1` and `verify_artifact_refinements`'s `semantic-output-coverage` arity check were relaxed together and nothing else changed. An independent two-output program (`product = a * b`, `sum = a + b`, standard registry) reached `phase: "program-assembly", rule: "cover-named-output-attribution"` — recognition, cover enumeration, physical proposal, and complete-plan selection all succeeded — where the same fixture at `3adc0689` had reached `strategy`/`operation-set`. The reduction-epilogue fixture reached `phase: "strategy", rule: "output-partition-overlap"`, which is [`recognize-several-ordered-named-outputs-at-the-compiler-request-boundary`](recognize-several-ordered-named-outputs-at-the-compiler-request-boundary.md)'s new partition rule rather than the assembly refusal it hit before recognition was widened. Both branches of the 2026-08-05 measurement therefore moved, and in the direction that ticket predicted.

**Fact — the attribution landed as recorded, and no identity moved.** `CoverRegion` gained `named_results`, the ascending named-result value ordinals its candidate retains, populated in `assemble_resolved_cover` from `candidate.retained_outputs()` through one derivation (`retained_named_results`) and checked in `verify_cover` step 1 beside members, content, and label. It is **not** folded into `encode_cover_identity`, for the reason the elimination recorded: the occurrence identity already encodes the retained output sites and the content identity already encodes their `named_result` flags. `CoverAssembly::from_plan` now calls `attribute_named_outputs`, which pairs each declared output with the region retaining its value ordinal and proves the pairing is a bijection onto the non-materializing regions.

**Measurement — the attribution is load-bearing on the compile path, not defensive.** Reverting `from_plan` to the execution-order pairing it replaced — `(0..regions.len()).filter(|p| !materializing[*p])` — makes `ordered_multi_output_programs_compile_through_the_ordinary_path` fail with `InvalidCompilerOutput(Program(CoreConstruction(StageElementCount { position: 2, .. })))`: the `[2]`-shaped fold's write bound to the `[2, 2]`-shaped published value. The gate fixture declares its two outputs at different domains in both declaration orders precisely so that one of them disagrees with the cover's canonical region order; execution order is not declaration order, and with one output the two agreed, which is why the guess was invisible. The perturbation was reverted.

**Fact — relaxing the guard surfaced no `sole_output` caller to convert, and that is worth recording rather than assuming.** [`recognize-several-ordered-named-outputs-at-the-compiler-request-boundary`](recognize-several-ordered-named-outputs-at-the-compiler-request-boundary.md) named `VerifiedTargetRequest::sole_output` so that its *removal* would be a compile error; removing the guard is a different event and produces none. Every compile-path per-region authority already resolves through `physical::spell_region` and `output_at`, and the only non-test callers left are `physical::build_scheduled_regions` and `build_fused_scheduled_region`, both `#[allow(dead_code)]` canonical constructors reached only from fixtures. The accessor stays, its doc comment corrected: its panic is now a reachable state and is the guarantee that a fixture growing a second output fails loudly.

**Fact — one refusal the widening made reachable for the first time, filed rather than absorbed.** `recognize_elementwise` requires each output's walk to read *every* declared input (`elementwise-reads`), because the region it builds binds one buffer per declared program input. With one declared output that could never fire — a frozen program drops an input no output reaches — and with two, outputs can split the input set. `doubled = a + a` and `squared = b * b` over two declared inputs refuses under `elementwise-reads` while `product = a * b` / `sum = a + b` compiles, so the refusal is about the subset rather than the second output. [`admit-an-elementwise-region-reading-a-subset-of-the-declared-inputs`](admit-an-elementwise-region-reading-a-subset-of-the-declared-inputs.md) owns it and the case is pinned in `multi_output_boundary.rs`.

**Fact — one stale doc comment corrected along the way.** `named_output_positions` in `crates/tiler-compiler/src/cover.rs` stated that its ascending-value-ordinal rank "is the program's own declaration order for the values its interface exports". It is not: the reduction-epilogue fixture declares `reduced` before `scaled` while `scaled` holds the smaller value ordinal. The coordinate reaches only `CoverRefusal::AmbiguousNamedOutput`'s explain text and nothing decides by it, so the behaviour is unchanged and the comment now says what it is.

**Scopes added.** `contracts/optimizer` and `research/program-planning`, because `docs/compiler/optimizer.md`, `docs/research/program-planning/minimum-correct-physical-realization-profile.md`, and `docs/research/program-planning/complete-model-ingestion-and-execution.md` each asserted the `output-arity` refusal as standing. Each carries a dated correction naming what moved; no product outcome was expanded.

## Boundaries

- Recognizer generalization *within one output's expression* is [`admit-a-general-program-shape-recognizer-at-the-compiler-request-boundary`](admit-a-general-program-shape-recognizer-at-the-compiler-request-boundary.md)'s and is this ticket's dependency; do not widen templates here. Generalization *across several ordered outputs* is the separate dependency filed 2026-08-05 above.
- Output *order* is identity, not presentation. A widening that admits two outputs but leaves them interchangeable would satisfy the guard and violate the contract. Ordering enters the schedule and artifact identity encodings exhaustively, with no previously encodable program's bytes moving.
- If the wall proves to be in the scheduled-region or artifact vocabulary rather than in `tiler-compiler`, file that widening as its own ticket and depend on it — do not widen a compiler guard onto a physical layer that cannot express the result. *Resolved 2026-08-02: the vocabulary was not the wall; the planner was. Both dependencies below were filed or added on that finding.*

## Required failure-path evidence

Each run against a case that must fail and observed failing, against an accepted neighbour: two declared outputs colliding on one semantic value; a program declaring more outputs than the plan names; a plan naming fewer outputs than the program declares (the same rule [`implement-general-dag-partitioning`](implement-general-dag-partitioning.md) states as its closing condition 2); and two programs differing only in output order yielding distinct identities.

Status of each after the 2026-08-02 wall survey, all in `crates/tiler-compiler/tests/multi_output_boundary.rs` unless noted. Colliding outputs: **done**, `two_output_keys_publishing_one_value_refuse_under_output_arity`. A plan naming fewer outputs than the program declares: **already discharged one layer down**, by `tiler-ir`'s `a_missing_named_output_is_rejected` against `KernelProgramDiagnostic::MissingNamedOutput`; re-asserting it here needs a compiler-built multi-output plan and so waits on the planner. Two programs differing only in output order yielding distinct identities: **done at the semantic layer**, `two_programs_differing_only_in_output_order_have_distinct_identities`; **open at the artifact layer**, which is the dependency filed below. A program declaring more outputs than the plan names: **waits on the planner**, for the same reason as its converse.
