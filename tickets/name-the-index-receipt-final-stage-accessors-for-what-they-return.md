## User-visible outcome

`IndexRefinementReceipt::region`/`scalar_authority` and `PendingIndexRefinementReceipt::region`/`scalar_authority` are named for the stage they answer, so a consumer reading one cannot mistake the final stage of a chain for the whole realization.

## Why this is filed

**Fact.** [`admit-a-multi-region-index-realization-law`](admit-a-multi-region-index-realization-law.md) made a realization an ordered `VerifiedIndexRegionSequence` and retained the two single-region accessors on both receipts, re-documented to answer *the final stage*. Its acceptance node names the open question directly: "should a staged receipt expose a single-region accessor at all?" and records that removal was not available to it, because `tiler-compiler` reached the accessors from `const fn`.

**Fact — the misread is observed, not hypothesized.** [`lower-a-two-region-occurrence-through-one-index-access-capability`](lower-a-two-region-occurrence-through-one-index-access-capability.md) answered the question from the consuming side and found two sites that had already read the accessor as the realization: `complete_pending_index_refinement` handed `PendingIndexRefinementReceipt::region()` to content assembly as the whole realization, and `IndexRefinement::region()`'s documentation claimed the `tiler-reference` oracle could evaluate it against `operand_bindings` — false for a chain, whose final stage reads a value no occurrence operand carries. Both were well-typed reads of the wrong thing, and both are fixed compiler-side.

**Inference — retention survives, the spelling does not.** The final stage is a real concept rather than a truncation: its writes are the occurrence's results, `bind_results` derives from it alone, and it is a separate field so that "a realization has a final stage" is a type invariant. Removing the accessor pushes that invariant back to every consumer as an `expect`. What does not survive is a name that says `region` while answering one stage of several.

## Proposed shape

Rename to `final_stage()` and `final_scalar_authority()` on both receipts, keeping `regions()`/`realization()`/`scalar_authorities()` beside them unchanged. Consider an `Option`-returning `single_region()` mirroring the compiler-side spelling `lower-a-two-region-occurrence-through-one-index-access-capability` landed, so a consumer that can evaluate exactly one region refuses a chain explicitly rather than truncating it.

## Non-goals

Changing what any accessor returns, any identity encoding, or any verification behaviour. This is a naming change over an accepted surface; if the acceptance ruling changes the surface itself, this ticket is superseded rather than layered on top.

## Closes when

Both receipts' accessors are renamed, every call site in the workspace is updated, and `cargo doc` describes the final-stage semantics at the new names.

`regions()`, `realization()`, `scalar_authorities()`, and `staged_obligations()` are untouched beside them, and the private fields keep their names — the field `region` sits beside `leading_regions` where the split is what the adjacent comment already explains.

Absence check after the fact: `grep -rn 'receipt\.region()\|receipt\.scalar_authority()\|Receipt::region\|Receipt::scalar_authority' crates prototypes spikes docs` returns nothing.

**Inference — why an `Option`-returning `single_region()` was considered and not added.** The Proposed shape invited it, mirroring the compiler-side spelling. It is eliminated. On `IndexRefinementReceipt` it would return an identity, and no consumer in or out of the tree wants a conditional identity. On `PendingIndexRefinementReceipt` it would have exactly one plausible consumer — `PendingIndexRefinement::single_region`, which already derives the same answer in one line from `realization()` — so it buys no correctness and removes no `expect`. Decisively: adding a method *is* a new public boundary, and the acceptance note anticipated a rename, not an addition; landing an addition under a ruling that did not cover it is precisely the unmarked partial acceptance the process forbids. Retaining the rename as a pure rename is also what keeps the identity survey below a statement about bytes rather than an argument.

**Fact — the doc-truth corrections.** Every doc claim about the four accessors now states chain behaviour rather than leaving it to be inferred from the one-stage case:

- The `IndexRefinementReceipt` type doc names the two accessors and says they answer the last stage alone and never the realization, directing a whole-chain reader to `regions()`, `scalar_authorities()`, or `realization()` — and says *why* the names changed, because the one-stage realization every registered law produces makes stage and realization indistinguishable at the only place a reader normally meets them.
- `IndexRefinementReceipt::final_stage` states the concrete failure mode: for a chain, the leading stages leave no trace in this identity, so two chains that merely end alike agree here; compare `realization()` to compare realizations.
- `IndexRefinementReceipt::final_scalar_authority` and `PendingIndexRefinementReceipt::final_scalar_authority` state that stages carry their own reached vocabularies and need not overlap, citing the governed staged template whose fold reaches the add and whose pass reaches the multiply — which is the same fact the file's own `a_staged_occurrence_verifies_and_binds_every_region` asserts with `assert_ne!` on the two stage authorities.
- `PendingIndexRefinementReceipt::final_stage` carries the counterexample that forced the compiler side: for a chain, at least one input boundary reads the value the preceding stage handed on, which no operand named by `operand_bindings` carries, so a consumer that can run exactly one region must establish `realization()` has exactly one stage before running this one — otherwise it runs part of a realization and reports the result as the occurrence's. That claim is exact rather than hedged, and the exactness is checked: `VerifiedIndexRegionSequence::try_new` refuses `IntermediateNeverRead` unless every non-final stage's single output is consumed by the stage immediately after it, so a chain's final stage always reads an intermediate.

The IR carries no oracle-evaluability claim of its own to correct — `grep -rn 'oracle\|tiler.reference' crates/tiler-ir/src/index/{refinement,sequence,mod}.rs` returns nothing. The false claim the counterexample named lived on `IndexRefinement::region()` in `tiler-compiler` and was fixed there.

Both renamed methods stay `const fn`, so the constraint is satisfied by the new names and constrained nothing about the old ones. No code comment anywhere states the constraint — `grep -rn 'const fn' crates/tiler-ir/src/index/*.rs` finds no doc or line comment carrying it — so the note lived only in the ticket graph, and this paragraph is its update.
