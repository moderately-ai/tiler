## Exactly three production call sites, named by the compiler

- **`pipeline.rs:921`** — `enumerate_covers(semantic, budgets, contract)`. The easiest and the most telling: `enumerate_complete_plans` **already receives `formation` as a parameter**, so this re-derived a value one line out of scope. Pass `formation`.
- **`selection.rs:841`** in `select_physical_plans`, inside `for source in sources` — so once per cover.
- **`selection.rs:905`** in `verify_selected_plan` — once per retained plan, called from `verify_portfolio` at `selection.rs:938`.

Both `selection.rs` functions need `outcome: &RegionFormationOutcome` threaded in and can drop the `budgets`/`contract` parameters they only forwarded. Their callers reach back to the authoritative formation at `pipeline.rs:770`.

`verify_equivalence` (`pipeline.rs:2573`) forms its own at `:2579` and should take one too.

## Test call sites

Roughly fifteen, all mechanical: `cover.rs` (~8), `selection.rs` (~6), plus `pipeline.rs`'s `plan_portfolio` helper at `:4204`, which already forms one and can pass it. Several test modules already call `form_region_candidates` themselves, so they hold the value and only need to pass it.

## Why the compiler is the right enforcement here

Every one of these sites is a type error after the signature change, so none can be missed. That is the maintainability half of this ticket: after it, "the formation is derived once per target compile" is a property of the signatures rather than a convention a new call site could quietly break by calling `form_region_candidates` again.

## Guard to land with it

`the_request_subject_rebuild_count_does_not_regress` in `hot_path.rs` is the pattern. Add a `region formation` counter to `crate::workcount`, record it in `form_region_candidates`, and assert one per compile. The ratchet in that file should be tightened in the same change if the count moves.
