Two corrections from the infrastructure performance investigation, and a reframing. Recorded here rather than edited into the body so the original reasoning stays legible.

**Correction — the manifest figure is stale.** This ticket cites "the 25,000-byte manifest interior". Measured directly on the fixture: the envelope is 26,126 bytes, of which the header is 69, the **manifest is 17,970**, and the sections are 8,087. `crates/tiler-artifact/src/program/codec/tests.rs:499` repeats the same stale figure in its docstring and should be corrected with it.

**Correction — the corruption sweep is not a throughput measurement, and now there is one.** This ticket already says so. The numbers: one decode of that 26,126-byte envelope is **548 µs release / 2.88 ms dev**, roughly 49 MB/s, and it is digest-dominated.

**Reframing — the algorithm is not where most of the time goes.** The implementation is block-at-a-time and streaming, and `digest_parts` streams its parts through one state without concatenating, so the obvious inefficiency is ruled out. What the measurement found instead:

- Every hashed byte is hashed **twice per decode**, because `decode.rs:113` re-encodes the whole envelope — 50% of decode time. On a cache hit the subject is hashed three times and the envelope three times.
- The artifact identity embeds whole section bodies (`program/model.rs:1604`) and is then embedded in the manifest and hashed, so payload bytes pass through the hash twice inside a single encode. That is why the manifest is ~18 KB for an 8 KB payload.
- `working.rotate_right(1)` (`digest.rs:378`) resolves to the *generic slice rotation*, 64 calls per block, on the innermost loop of every hash in the workspace.

So "how many times do we hash the same bytes" dominates "which SHA-256", and `stop-recomputing-pure-derivations-in-the-codec`, `decide-whether-the-canonicity-re-encode-is-redundant`, `encode-abi-expression-identity-in-linear-space`, and `fix-the-sha-256-inner-loop-and-encoder-presizing` now own those separately.

**What this ticket should still decide, sharpened.** The comparison it exists to make has a term it does not currently name: an audited crate buys SHA-NI / ARMv8 crypto-extension intrinsics, which this crate **cannot** have under the workspace's `unsafe_code = "forbid"`. On an Apple M4 Max that is roughly an order of magnitude on the compression function. That — not implementation quality — is the real in-crate-versus-dependency trade, and it should be measured against a fixed inner loop rather than the current one.
