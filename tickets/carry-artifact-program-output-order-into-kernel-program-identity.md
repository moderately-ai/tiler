## User-visible outcome

Two verified kernel programs that publish the same named outputs in different orders carry different canonical identities, so an artifact's ordered output interface is part of what its identity means rather than something a consumer must re-derive.

## Why this exists

**Fact — the artifact identity encoder sorts its output records.** `crates/tiler-ir/src/program/model.rs:1778-1792` builds one `Vec<u8>` per output holding the output key and the canonical id of the published value, calls `outputs.sort_unstable()`, and folds the sorted list. Two `KernelProgram`s differing only in the order of their `push_output` calls hold the same key set bound to the same values, so they produce the same sorted list and the same `CanonicalKernelProgramIdentity` bytes — while `KernelProgram::outputs()` (`:816-822`) still yields them in the two different declared orders.

**Fact — nothing else recovers the order.** `verify_outputs` (`crates/tiler-ir/src/program/verify.rs:584-608`) checks coverage as a *set* in both directions: every semantic interface output must be published by some record, and every `ValueRole::Output` value must be named by some record. It never relates the published order to `SemanticSubject::outputs`, which `interface_output_shapes` (`crates/tiler-ir/src/program/builder.rs:1315-1332`) reads from the semantic program *in order*. So the declared order is observable through `outputs()`, unconstrained by verification, and absent from identity.

**Fact — the semantic layer treats output order as identity, which is the asymmetry.** `crates/tiler-ir/src/semantic/identity.rs:128-132` encodes the output list in declaration order with no sort, and `canonical_traversal` (`:143-170`) *seeds* the canonical value numbering by visiting outputs in declaration order, so order reaches the graph identity twice over. `crates/tiler-compiler/tests/multi_output_boundary.rs::two_programs_differing_only_in_output_order_have_distinct_identities` pins that behaviour. The artifact layer discarding what the semantic layer preserves is the defect: a lowering that permuted an artifact's output interface would be invisible to the identity that is supposed to name it.

**Inference — latent today, live the moment multi-output lands.** `crates/tiler-compiler/src/program.rs:1254-1261` refuses any program whose `core.outputs().len() != 1`, and a one-element list sorts to itself, so no program the compiler currently produces can exhibit the collision. `tiler-ir` is a library and does not carry that restriction: `program::tests::storage_reuse_is_admitted_only_with_an_explicit_handoff` already builds and verifies a two-output program through the public builder. The collision is therefore reachable through `tiler-ir`'s own surface now, and becomes reachable through the compiler as soon as [`implement-general-dag-partitioning`](implement-general-dag-partitioning.md) can plan ordered multi-output covers.

## Boundaries

- Decide and state which of the two readings is the contract, because the current code is neither: either the declared publication order is meaningful, and identity plus `outputs()` must both carry it, or it is incidental, and `verify_outputs` must pin the published order to `SemanticSubject::outputs` so `outputs()`'s "ordered" claim is true. Do not leave order observable, unconstrained, and unencoded.
- The sort is not obviously wrong in isolation — the sibling `edges` and `splits` lists above it are sorted deliberately, each with a comment saying the entity "names entities rather than being named by one, so its declaration position carries no meaning identity should preserve". Establish why an output record is different (it *is* named, positionally, by the caller's interface) rather than deleting a sort that its neighbours justify.

## Identity domain consequence

This is an identity-domain step and must be executed completely or not at all. The subject is `PROGRAM_DOMAIN` in `crates/tiler-ir/src/program/model.rs` — **`tiler.kernel-program.v6` was already stale when this was filed**: `canonicalize-index-refinement-occurrence-ordinals` stepped it to `v7`, and this ticket's step therefore runs `v7` → `v8`; `crates/tiler-ir/src/program/mod.rs:44` is the ledger paragraph recording each prior step and must move in the same commit, as must `CanonicalKernelProgramIdentity`'s own step list.

Note the appends-only claim is **false** here and should not be asserted: a one-output program's bytes do not move, but `tiler-ir`'s existing two-output fixtures do, so the version steps. Recompute every pinned identity on the tree the step lands into and enumerate each moved pin in the report.

## Required failure-path evidence

Each observed failing against an accepted neighbour: two programs differing only in `push_output` order yield distinct identities, and re-declaring one of them in its original order reproduces its identity byte for byte; a one-output program's identity is unchanged by everything except the domain step itself; and whichever ordering rule is chosen, a program violating it is rejected by `verify_outputs` with a named diagnostic rather than silently accepted.

## Closes when

The chosen contract is stated in the program module's own documentation, identity distinguishes two publication orders (or verification forbids the second order from existing), the domain version and both ledger sites moved together in one commit with every moved pin enumerated, and `make full` passes.

## Outcome

**Decision — the published order is the semantic subject's, and identity carries it.** The two readings the Boundaries pose were tested rather than picked, and only one survived. A "meaningful and free" order — the producer choosing a publication order that identity then folds — admits a verified program whose ordered interface contradicts the semantic program it claims to realize, with nothing rejecting it: a consumer zipping `program.outputs()` against `semantic.outputs()` gets silently permuted results, which is a defect rather than an alternative. It also makes identity sensitive to what is, at the builder, indistinguishable from insertion order, contradicting the documented exclusion of transient ordinals and costing a cache miss between two programs that differ in nothing. Both grounds eliminate it. What remains is that the ordered output interface belongs to the unforgeable semantic subject — `KernelProgramBuilder::new` takes it from a verified `SemanticProgram` rather than from the producer — so a program realizes that order and does not restate it. `verify_outputs` now proves the published records carry the subject's keys in the subject's declared order, each key's records contiguous, and within one key the records in the encoded contract's declared component order; anything else is `KernelProgramDiagnostic::MisorderedNamedOutput` (`misordered-named-output`), carrying the declared position of the first record that leaves the order. The contract is stated in `crates/tiler-ir/src/program/mod.rs` under "The published output order is the semantic subject's".

**Why an output record differs from its sorted neighbours.** The edges and splits above it are sorted because each *names* entities and is named by none, so its declaration position carries no meaning identity should preserve. An output record **is** named — positionally, by the caller's interface — which is why sorting it discarded exactly the fact the semantic layer treats as identity: `semantic/identity.rs` writes the output list in declaration order and seeds canonical value numbering from it, so order reaches graph identity twice over. The nearest precedent in the same encoder is the routing-commit lifecycle, folded in lifecycle order with the comment that verification proves the declared sequence is content rather than insertion order; the published outputs are now the second member of that class. The order adds no bits the identity did not already determine — the folded `SemanticGraphIdentity` fixes the interface order and verification pins publication to it — and is folded anyway so that completeness of the fact does not rest on the verifier staying exactly as strict as it is today.

**Identity-domain step, executed completely.** `PROGRAM_DOMAIN` moves `tiler.kernel-program.v7` → `tiler.kernel-program.v8` (`crates/tiler-ir/src/program/model.rs`). Ledger sites moved in the same commit: the `PROGRAM_DOMAIN` step list (whose summary line also said "bumped to `v5`" against a `v7` constant, corrected), `CanonicalKernelProgramIdentity`'s own doc, the module ledger paragraph in `program/mod.rs`, `docs/artifact-abi.md` (current-ledger sentence, the ABI-uses sentence, the "(`v7` now)" parenthetical, and a new step paragraph), `crates/tiler-artifact/src/program/mod.rs`, `docs/research/program-planning/abi-expression-ownership.md`, and ADR 0072's implementation-status ledger.

**The appends-only claim is false here and is not asserted.** Each record's own bytes and framing are unchanged, so a one-output program's payload does not move; a program publishing several outputs in any order other than ascending record content encodes a different sequence. That is a reinterpretation of retained bytes, which is what the tag step buys. Per-tag injectivity holds at the changed site: the section is a framed count followed by that many length-framed records, each a framed key then a fixed-width canonical value id, so a reader recovers the exact *ordered* list from these bytes alone. No other domain is forced to move — the artifact, stage-key, envelope, and manifest domains fold the complete program identity with its separator, so their values move without their grammars changing.

**Pins recomputed on this tree, enumerated.** Exactly two, both in `crates/tiler-build/src/metal_plan.rs::the_standard_metal_path_publishes_its_recorded_identities`: `ARTIFACT_IDENTITY` `1249813…ba25bd` → `2b15415053d8f688de094d7f4490b90fa001463717affc686ee1fe3692786a81`, and `CACHE_SUBJECT` `94dfde3…3e6370` → `b0803f2a48f41aa03baed4a136f7e44ddb3dbafac39bc560673c2bb7f8801ae9`. Both are also recorded in that test's doc comment, which moved with them and gained the step's paragraph. The full workspace run is the enumeration: 2500 tests, one failure before the rebaseline and none after. The ticket predicted `tiler-ir`'s two-output fixtures would move; they did **not** — `sum_a`/`sum_b` sort into their own declared order — and the fixture whose bytes actually move is `tiler-artifact`'s `dual_output_program`, which publishes `result` then `copy` where the sort produced `copy` then `result`. No test pins those bytes (the artifact layer's identity assertions are relational), so nothing there needed rebaselining.

**Failure-path evidence, each observed failing.** Restoring the content sort in `encode_identity` fails `published_output_interface_order_reaches_program_identity` at its named assertion ("the output section holds the sorted order, not the interface order"). Disabling the misorder branch reports position 1 instead of 0 from the trailing-record branch; disabling *both* order branches makes the permuted program verify, failing `publishing_the_outputs_out_of_interface_order_is_rejected` with "verification must fail" — so the rejection is the check's and not a neighbour's. `verify_component_order` is exercised directly against a contract whose declared component order is deliberately *descending* by role id, so the accepted and rejected orders cannot be confused with a sort by role; the omission case is asserted `Ok` because that report belongs to `verify_components`. The re-declaration case reproduces identity byte for byte. The one-output invariance is carried by `the_program_domain_separator_is_what_distinguishes_the_reinterpreting_steps`, which asserts the fixture publishes exactly one output — a one-element list is invariant under any permutation, so its payload is unchanged across v6, v7, and v8 and only the separator distinguishes them.

**Scopes added autonomously, with reasons.** `implementation/build` — the two moved pins live there and an identity step recomputes every pinned identity on the tree it lands into. `implementation/compiler` — `tests/multi_output_boundary.rs` located this defect, named this ticket as its owner, and asserted in prose that the artifact layer does not carry output order; that claim is now false. `implementation/artifact` — the domain ledger in `program/mod.rs`, and the interface-projection comment in `program/builder.rs` that said the order is "which the kernel program does not retain". `research/program-planning` and `contracts/decisions` — the ABI-ownership record and ADR 0072 each state the current domain in a ledger sentence.

**Unsupported and unexercised.** No kernel in this profile writes a compound *output*, so no constructible fixture publishes several component records under one key; the component-order rule is proven against a contract directly rather than through a built program, and that boundary is stated at `verify_component_order`. Whether a future consumer should read its ordered interface from the program instead of the semantic program is a separate question this ticket does not decide: `tiler-artifact`'s projection still reads the semantic interface, and only its comment changed.

**One adjacent doc defect corrected in the same block.** `CanonicalKernelProgramIdentity`'s doc still described the ABI arena as folded "by canonical content key", which the v3 encoding step replaced with a written-once arena and canonical positions. The sentence sits in the doc block this change rewrites and is corrected there.
