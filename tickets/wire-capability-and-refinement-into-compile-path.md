Wire `capability` (lowering-capability resolution) and `legality` (checked index-region refinement) into the ordinary `compile()` path, so an externally registered *lowering* provider — not only an externally registered *semantic* provider — drives compilation end to end.

`prototype-optimizer-conformance-gate` wired `cover`, `frontier`, `selection`, and `fusion_legality` into `compile()` and proved an externally registered semantic operation set through the ordinary path. It did not wire `capability`/`legality`, and left `request::CompilerCapabilitySnapshot` as two named `LoweringProviderIdentity` fields (`materialized_serial_sum`, `fused_serial_sum`) that the artifact plan reads directly. That two-field snapshot is the last proof-only candidate list on the compile path: lowering provenance is a compile-time constant rather than a registry resolution.

**What this ticket must produce**

1. Replace `CompilerCapabilitySnapshot`'s two named fields with a frozen `capability::FrozenLoweringCapabilityRegistry` plus the `tiler_ir::index::FrozenScalarRegistry` it was registered against, carried on `CompilationRequest`. `VerifiedRequestSubject` retains the registry's `CanonicalLoweringRegistryIdentity` (it is `Eq + Ord`; the registry itself is not).
2. Resolve an index-access lowering capability per recognized semantic occurrence through `FrozenLoweringCapabilityRegistry::resolve_index_access`, failing closed on `MissingCapability`/`AmbiguousCapability` with a typed compile error and a `CapabilityResolution`-stage explain record.
3. Derive `ArtifactConstructionPlan::lowering_providers` from the resolved capabilities' `ProviderIdentity`/`LoweringCapabilityRevision` instead of the snapshot constants. `LoweringProviderIdentity { key: &'static str, revision: u32 }` must become an owned identity, and `explain::ProviderRef::lowering` must follow.
4. Run `legality::refine_index_region` per occurrence and retain the resulting `IndexRefinement` as occurrence-bound evidence, with a `KernelRefinement`-stage explain record carrying the refinement identity and the selected provider.
5. Ship a governed lowering-capability registry: a `tiler_ir::index::ScalarRegistryBuilder` populated with the scalar operations the four governed families emit, plus one `IndexAccessLoweringProvider` per family (`tiler.constant-f32`, `tiler.multiply-f32`, `tiler.add-f32`, `tiler.strict-serial-sum-f32`). No such governed scalar registry exists today: every consumer (`tiler-ir` tests, `tiler-compiler::capability` tests, `tiler-reference` tests) builds its own ad-hoc one.

**The measured blocker that shapes the design**

**Fact (inspected source, `crates/tiler-ir/src/index/mod.rs:76` at `b1c3e9b`).** `MAX_EXHAUSTIVE_PROOF_CELLS = 1_048_576`. `IndexRegionBuilder::build` proves bounds and write ownership by exhaustive enumeration over the domain, so a region whose iteration domain exceeds ~1M points fails closed with `IndexRegionDiagnostic::ProofResourceLimit { resource: ProofResource::Cells, .. }`.

**Inference.** Index-region refinement therefore cannot be an unconditional gate on the compile path. The existing conformance fixtures already cross the bound: `pipeline::tests::infeasible_baseline_does_not_suppress_a_feasible_fused_plan` compiles a `[70_000, 2]` program (140,000 points) and `no_feasible_plan_retains_a_typed_terminal_failure_trace` a `[70_000, 70_000]` one (4.9e9 points). Making refinement mandatory would convert a target-feasibility rejection — and, for the first fixture, a *successful* compilation — into a proof-budget rejection, which is exactly the confusion between hard feasibility and an exhausted analysis budget that `AGENTS.md` forbids.

**Required design consequence.** Capability *resolution* is unconditional and fails closed; index-region *refinement* is exhaustive finite evidence attached when the proof budget affords it, and a `BudgetStop` explain record at `ExplainStage::KernelRefinement` naming `ProofResource::Cells`, its limit, and the required cell count when it does not. The absence of refinement must be a recorded `Unknown`-class gap, never a silent pass and never a rejection of an otherwise valid plan. Preserve `SoundProof`, exhaustive finite evidence, and `Unknown` as distinct classes.

**Closing evidence.** The ticket closes when `compile()` resolves every recognized occurrence's lowering capability from a registry supplied on the request; a conformance test registers its *own* out-of-crate `IndexAccessLoweringProvider` and observes its `ProviderIdentity` in the artifact plan's `lowering_providers`; a missing and an ambiguous capability each produce a distinct typed error with an explain record; and a large-domain fixture records a typed proof-budget stop instead of failing.

## Outcome

All five products are implemented and wired. The branch is a concrete draft rather than a merge candidate: two breaking public signature changes need Tom's review under ADR 0075, and `accept-occurrence-aware-index-access-lowering` holds that decision.

**1 — the registry replaces the two-field snapshot.** `request::CompilerCapabilitySnapshot` now carries a `capability::FrozenLoweringCapabilityRegistry` and the `tiler_ir::index::FrozenScalarRegistry` it was registered against; `materialized_serial_sum` and `fused_serial_sum` are gone, and so are the `tiler.prototype.*` provider constants. `VerifiedRequestSubject` retains the registry's `CanonicalLoweringRegistryIdentity` and the capability schema version, which is what the explain subject and every receipt bind. `verify_request` no longer requires the registry to equal a governed one — an out-of-crate registry is exactly what the boundary admits — but does require the request to pair the registry with the scalar authority its capabilities were admitted against, rejecting a mismatch as `UnsupportedCapability { phase: "capability", rule: "scalar-authority-pairing" }`. Two snapshots compare equal exactly when their canonical registry identity and scalar snapshot agree, which is documented as a deliberate consequence: a provider whose emitted lowering changes must raise its capability revision, and that revision is inside the identity.

**2 — resolution is unconditional and fails closed.** The new crate-internal `lowering` module runs before cover enumeration in `pipeline::enumerate_complete_plans`, projecting each recognized member into a `legality::SemanticOccurrence` and resolving it through `FrozenLoweringCapabilityRegistry::resolve_index_access`. Success emits a `Check` at `ExplainStage::CapabilityResolution` attributed to the resolved provider at its capability revision. A missing capability is a `DeferredCapability` record and a contended one a disproved `Check`, and both terminate compilation with a distinct typed `UnsupportedCapability { phase: "lowering", rule: … }`. `explain::ExplainEvent::validate` was relaxed to admit a `Check` at that stage, with the reasoning recorded beside it: the three stages that stay excluded each own a richer typed event that a checked predicate would lose, and capability resolution has no such event for its admitted and disproved cases.

**3 — lowering provenance is resolved, not constant.** `LoweringProviderIdentity` is now an owned `{ ProviderIdentity, LoweringCapabilityRevision }` record, and `explain::ProviderRef::lowering` takes it by reference and delegates to `ProviderRef::registered`, which is the single place that decides a `ProviderRef` carries the provider's revision and not the capability's. `ArtifactConstructionPlan::lowering_providers` is the canonical distinct set of resolved identities, and `program::build_artifact_plan` re-derives it from the request's own registry instead of comparing against a stage-count table, so a receipt naming a provider the registry never resolved fails closed. Both plan shapes now name the same providers, because both cover the same occurrences: the alternatives differ in their cover, not in who lowers each operation. `ExplainWriter::new` takes its allowed providers from the registry, and `fusion::FusionNumericalProof` dropped its `materialized_reference_provider` field — the request subject it already binds carries the whole installed authority.

**4 — refinement is attached evidence with a recorded gap.** `legality::refine_index_region` runs per occurrence. Success is retained as an `IndexRefinement` and recorded as a `Check` with `EvidenceBasis::ExhaustiveFinite` at `ExplainStage::KernelRefinement`, carrying a refinement-identity fact and attributed to the selected provider. A build failure whose diagnostics are *only* `ProofResourceLimit` is a proof-budget stop, not a rejection: it emits a `BudgetStop` naming the resource key, its limit, and the required amount, plus a `Check` with the new `PredicateAssessment::unknown` and `EvidenceBasis::Unknown`. A `ProofResourceLimit` beside any other diagnostic is a genuine rejection, because the region was independently refused and reporting the pair as a gap would hide that. Any other refinement refusal fails closed at `ExplainStage::KernelRefinement`.

**5 — a governed registry, and a corrected budget claim.** `tiler_ir::index` gained `FrozenScalarRegistry::standard()` over `tiler.scalar::constant-f32@1`, `multiply-f32@1`, and `add-f32@1`, plus `FrozenScalarRegistry::semantic_authority()` so a composed lowering registry cannot drift from the semantic snapshot its scalars were typed against. The new `governed` module ships one `IndexAccessLoweringProvider` per governed family. All four are shape- and attribute-driven from the occurrence facts, so one registration covers every program shape.

**Corrected: the measured blocker is narrower than this ticket stated.** The ticket inferred that a region over more than ~1M points fails closed with `ProofResourceLimit`. Reading `crates/tiler-ir/src/index/builder.rs::verify_accesses` shows the budget is charged only for accesses that *need* the exhaustive path — where the interval proof fails, or a write is not a proved coordinate permutation — at `points × plan_len` cells. The governed lowerings emit interval-provable reads and permutation writes, so they charge nothing at any size, which `pipeline::conformance::governed_lowerings_never_charge_the_exhaustive_proof_budget` pins on the `[70_000, 2]` fixture. Refinement is therefore attempted for every occurrence rather than gated on size. The budget stop is still real and still required, because an external provider need not emit an interval-provable region: `a_refinement_the_proof_budget_cannot_afford_is_recorded_not_rejected` registers one whose write coordinate is a sixteen-deep modulo chain over a 65_535-point domain, needs 1_179_630 cells against the 1_048_576 limit, and compiles successfully with the stop and the unknown assessment recorded while the other four occurrences keep their exhaustive finite evidence.

**One conformance rule was corrected as a consequence.** `legality::check_authority_conformance` required the region's reached scalar authority to *equal* the capability's declared one. That is unsatisfiable for a shape-general provider: the governed serial sum reaches `add` when it folds, only the identity `constant` over an empty reduced domain, and nothing at all for a single contributor, yet one capability lowers all three. The rule is now containment — a region must reach nothing beyond what its capability declared it may emit — which is the property that was actually load-bearing. `tiler_ir::index::ScalarAuthorityEvidence::reached_operations` was added so the check compares key sets instead of opaque projections. `legality::tests::a_region_reaching_an_undeclared_scalar_authority_is_rejected` still rejects.

**Requires Tom's approval before merge (ADR 0075).** `capability::IndexAccessLoweringContext::new` gained a `&LoweredOccurrence` parameter and `legality::SemanticOccurrence::new` gained an `attributes` parameter. Both are breaking changes to existing public signatures. Without them a provider is shape- and attribute-blind, so the standard fixture's two `tiler.constant-f32` occurrences with different bits cannot both be lowered: two providers registered for one key are an `AmbiguousCapability`, not two lowerings. `accept-occurrence-aware-index-access-lowering` states the alternatives.

**Additive-internal, no approval needed.** `LoweringProviderIdentity` and `ProviderRef::lowering` are `pub(crate)`. Additive public items in `tiler-ir` — `OperationAttributes::canonical_encoding`, `CanonicalOperationAttributes`, `FrozenScalarRegistry::standard`/`semantic_authority`, `ScalarAuthorityEvidence::reached_operations`, the three governed scalar key helpers — are new items in existing public modules, none of which is a new namespace, a new trait, a breaking signature change, or a promotion. `capability` gained `LoweredOccurrence`, `OccurrenceBoundary`, registry accessors, and one variant each on two `#[non_exhaustive]` error enums.

**Neither `capability` nor `legality` carried a module-level `#![allow(dead_code)]`**, so none could be removed. `explain` and `feasibility` still need theirs; removing `explain`'s was tried and produces 26 dead-code warnings, so its reason is unchanged and still accurate.
