`MetalSubnormalArithmetic::FlushesToZero` is stated once, with no dtype, and `MetalTargetFacts::new` requires a caller to supply it. Every measurement behind it was `f32`, and finding 21 of [the Apple numerical-behaviour record](../docs/research/apple-targets/numerical-behaviour.md) now measures the same hardware **not** flushing in `f16`: a subnormal `half` operand comes back exactly doubled from a witnessed `fmul`, and the same holds for the result direction, for a bare add, and for a surviving `fdiv`, in all three math modes, on both compilation paths and both dispatchable families. The emitted modules are indistinguishable — `air.compile.denorms_disable` is declared for both dtypes — so nothing on the compile side would have caught this.

A single dtype-free declaration is therefore false for one of the two dtypes whichever way it is set. The type has to carry the dtype, or name the dtype its fact applies to and reject a query about any other; what it must not keep doing is answer a question it was not measured for.

**Which direction the error runs, so the fix is not over-scoped.** Reading the `f32` fact for an `f16` kernel says a subnormal is flushed when it is carried exactly. On the plan side that over-rejects — a spurious `MetalNumericalGap::SubnormalFlushInArithmetic`, or a feasibility rejection for a plan that is correct. It becomes a wrong tensor only where a *reference* evaluation flushes to match a device that does not, so the reference-side reading is the one to check first.

ADR 0076's re-verification and its subnormal-flush Measurement are stated without a dtype for the same reason and are consequently under-scoped. No conclusion of ADR 0076 moves: a module declaring `denorms_disable` while delivering preserved subnormals is a *stronger* case for its central argument that numerical honourability must be a stated versioned target fact rather than inferred from a compiled kernel.

**What closes this.** The declared fact distinguishes the dtypes it was measured for, an unmeasured dtype is rejected explicitly rather than defaulted to either behaviour, the measurement comment on the type cites finding 21 with its environment row, and ADR 0076's two dtype-free sentences say which dtype they hold for.

## Outcome

**Fact — the fact now carries the dtype as a key, not as a field.** `MetalTargetFacts::subnormal_arithmetic` is a `MetalSubnormalArithmeticFacts`: an entry per `MetalFloatArithmeticType` (`F32`, `F16`, `#[non_exhaustive]`, with `ALL`, `COUNT`, and a wildcard-free `index`), each entry an `Option<MetalSubnormalArithmetic>`. `MetalSubnormalArithmetic` is unchanged in shape and lost the `f32` from its own prose, because the dtype is now the key rather than something the behaviour asserts. The record is built from `unmeasured()` through `stating(type, behaviour)`, which asserts the type is not already stated — restating is a dropped measurement, so it is a panic (a compile error in a `const` context) rather than last-wins. The two Apple measurements live on the record: the `f32` flush rows and the `f16` preservation rows from finding 21, each with its environment, its math-mode/path/family coverage, and the execution witness that separates `preserved` from an optimized-away kernel.

**Fact — a consumer that needs a dtype it has no fact for fails closed.** `MetalSubnormalArithmeticFacts::behaviour(type)` returns `Result<MetalSubnormalArithmetic, MetalUnstatedSubnormalArithmetic>`; there is no accessor that yields a behaviour for an unstated type and no `From`, `Default`, or fallback that could manufacture one. `KernelEmitter::record_subnormal_obligation` takes the arithmetic type of the statement it was called for — derived from the operation vocabulary, `BinaryOp::F32Add`/`F32Multiply` — and on `Err` records the type in a new set instead of comparing against anything. `MetalTranslationUnit::unstated_subnormal_arithmetic()` exposes it, the provenance header writes it, and `require_declared_realization` rejects it as `MetalEmitError::UnstatedSubnormalArithmetic` (rule `unstated-subnormal-arithmetic`).

**Inference — the unstated set is checked *before* the gap set, and that ordering is the correctness content.** Gaps are only computed for types the target states a fact for, so a unit whose arithmetic reached an unstated type has an *incomplete* gap list, not merely a shorter one: `numerical_gaps()` can be empty while conformance is unknown. Reporting a gap from an incomplete comparison would present a partial answer as a total one, so the unknown is reported first and `numerical_gaps()`'s own documentation now says an empty slice is not on its own a conformance claim. `Unknown` is kept a third class throughout — it is not a `MetalNumericalGap` variant, because a gap means the target *cannot* honour the obligation and this means nothing says whether it can.

**Fact — the emitted text carries all three.** The header replaced its single `// f32 arithmetic subnormals: …` line with one line per arithmetic type, including `not stated` for types the target is silent about, and appends either `// Arithmetic types used with no stated subnormal fact: none.` or the list plus `// The obligations above are therefore incomplete.` The four golden fixtures were rebaselined for the header only — no body, symbol, or identity byte moved, and all four still compile and link through `tiler-metal-aot` on the local toolchain.

**Fact — the answer to "is any consumer generalizing today", which is no in the reachable sense and yes in one name.** No consumer can currently emit non-`f32` floating-point arithmetic: `grep -rniE '\bf16\b|bfloat|binary16' crates/ --include='*.rs'` returns nothing, `tiler_ir::kernel::KernelType` resolves `Bool | Index | F32`, and `BinaryOp`'s only floating-point members are `F32Add` and `F32Multiply`. So no code path reads an `f32` fact for an `f16` operation, and there is no live wrong tensor. One name did generalize: `tiler_metal_aot::input::NumericalRealization::preserves_subnormals()` returned `false` unconditionally from a dtype-free signature, with `f32` appearing only in its prose. It is renamed `preserves_f32_subnormals()` and its documentation states that the `f32` is load-bearing, that the same hardware preserves in `f16`, and that no dtype-free predicate is offered. Its only callers were its own tests.

**Fact — the reference side, which the ticket asked to check first, cannot produce the wrong-tensor case.** `grep -rniE 'flush|denorm' crates/tiler-reference/src/ crates/tiler-reference/tests/` returns nothing: the reference evaluates `f32` arithmetic with host IEEE-754 semantics and implements no flush-to-zero mode at all, so there is no reference evaluation that could flush to match a device that does not. The dangerous direction is therefore still only reachable in the future, once a flush-accepting reference exists — and that reference will have to be keyed by dtype for the same reason this record is.

**Fact — the contracts that named the old shape.** ADR 0076 gained an evidence refresh scoping its whole re-verification to `f32`, with the `f16` counter-measurement, the module-declaration point, and the explicit statement that two dtypes establish dependence and not which dtypes flush; its subnormal-flush Measurement heading names `f32`; its `Measured evidence` bullet records that the measurements it rests on are `f32` ones; its central Inference is *strengthened* rather than moved, because a module declaring `denorms_disable` while delivering preserved subnormals is a second independent case of a compiled artifact not reporting what the hardware does. Boundary item 3 gained an inherited constraint: a per-dimension honourability declaration alone cannot express the measured row, since `InputSubnormals` is `SupportedExactly` for `f16` and `Unsupported` for `f32` on one profile, so the shared form must carry the arithmetic type beside the dimension or restrict itself to one dtype and say which. `docs/backends/metal.md`'s "the Metal subnormal behavior is declared exactly once" is now "exactly once per floating-point arithmetic type", with the reason a single value cannot be right, and the strict-row measurement section gained the `f16` Measurement and the `Unknown`-rejects Inference.

**Fact — scopes added, and why each was forced.** `implementation/metal-aot` and `implementation/runtime` because `MetalTargetFacts::new`'s fifth parameter changed type and four construction sites live in `prototypes/serial-sum-compile` and `prototypes/serial-sum-run`, both workspace members the gate compiles; `contracts/artifacts` because `docs/backends/metal.md` stated the old shape as a normative Fact. None was avoidable without leaving a stale claim or a red gate.

**Deliberately not done, with what would close each.**

- **The gap variants do not name the arithmetic type they arose in.** `MetalNumericalGap` stays fieldless, and a unit performing arithmetic in two types that mismatched differently would record both gaps without saying which produced which. That is a loss of explanation and never a wrong verdict — each gap is still derived from its own type's fact — and it is unreachable while the structured kernel IR resolves one floating-point element type. It is the same limitation ADR 0076 already records for the two subnormal *dimensions*, and it should be closed with that one rather than separately. Stated on `MetalNumericalGap`.
- **`bf16` is unmeasured and is the discriminating case.** Finding 21 leaves two mechanisms open — native `f16` subnormal support, or evaluation at a wider internal precision in which every `f16` subnormal is a normal. **Inference:** those two predict *different* `bf16` behaviour, because `bf16` shares `f32`'s exponent range and its subnormals are `f32` subnormals rather than `f32` normals, so the wider-precision explanation would have `bf16` flush while `f16` preserves. Nothing here depends on the answer: `bf16` is simply absent from `MetalFloatArithmeticType`, which is `#[non_exhaustive]`, and adding it is a build error at `index` and `ALL` rather than a silent inheritance. `measure-the-apple-subnormal-flush-for-the-remaining-mature-dtypes` closes it.
- **No `f16` arithmetic can be emitted, so the `f16` entry is stated and never read.** The tests, the goldens, and both prototypes state the measured `f16` fact because it is the honest copy of the row, but only the `f32` entry is ever consulted. The unstated path is exercised by stating `f16` alone and emitting an `f32` kernel, which is a real reachable configuration, not a mock. `widen-the-f16-operation-vocabulary-to-contraction-and-reassociation` and the IR-side widening are what would make the `f16` entry load-bearing.
