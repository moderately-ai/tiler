`docs/architecture.md` has two gaps about `tiler-metal-aot` that a reader hits together, both found while deciding `choose-one-owner-for-apple-target-vocabulary`. Neither is in that ticket's scope (`implementation/metal`, `implementation/metal-aot`), so they are routed here.

**Fact — the accepted prototype packaging profile omits the crate entirely.** The "Accepted prototype packaging profile" section says "The prototype uses five reusable libraries and two non-published proof executables" and lists `tiler-ir`, `tiler-reference`, `tiler-artifact`, `tiler-compiler`, and `tiler-metal`. `Cargo.toml` has had six library members since `tiler-metal-aot` landed, and `scripts/check_workspace.py` pins it in `EXPECTED_MEMBERS`, `EXPECTED_WORKSPACE_DEPENDENCIES`, and `EXPECTED_DEPENDENCIES` with an empty dependency list. The profile block should name it, record `tiler-metal-aot -> []`, and record the development-only `tiler-metal` → `tiler-metal-aot` edge that `compile-golden-msl-through-the-aot-driver-in-the-gate` added and justified. Check whether the count sentence and ADR 0065's own text need the same correction, or whether the ADR is correct as of its acceptance and only this document is stale.

**Fact — the Component ownership table reads as if one crate owns all Metal target metadata.** The `tiler-metal` row says "Pure structured-kernel-to-MSL translation and Metal target metadata". `choose-one-owner-for-apple-target-vocabulary` decided that the MSL language version, Apple artifact family, and deployment minimum stay owned by *both* crates: `tiler-metal` owns what emitted source declares, `tiler-metal-aot` owns what a compiler invocation selects, and neither record subsumes the other. The table as written is the sentence a future reader would cite while "fixing" the duplication into a shared crate or into a dependency edge that destroys the driver's empty dependency closure — which is the failure mode that ticket exists to prevent. Distinguish the two rows' target-metadata ownership, and state that the correspondence between the two vocabularies is enforced by a total map in `crates/tiler-metal/src/target_correspondence.rs` rather than by a shared type.

**One decision this ticket owns: whether the ownership split needs an ADR.** `choose-one-owner-for-apple-target-vocabulary` deliberately did not write one. It changed no public surface — nothing moved, no signature changed, no namespace opened — so ADR 0075's always-ask categories do not reach it, and the reasoning is recorded on the types themselves plus three tickets. The case *for* an ADR is that the decision fixes a crate-ownership and dependency-direction boundary, which is the genre of ADR 0065 and ADR 0070, and that the alternative it rejects (a shared crate for three enums) is exactly what a future worker will propose again. The case *against* is that an ADR whose whole content is "these three types stay duplicated, here is the enforced correspondence" adds a fourth place the reasoning lives. Decide it here: either add `contracts/decisions` and draft the ADR for Tom's acceptance, or record in the Outcome why the contract update plus the type-level record is the complete answer. Do not leave it implicit.

**What closes this ticket.** Both edits landed in `docs/architecture.md`, the ADR question answered either way, `uv run --locked python scripts/docs.py render` rerun, and the complete gate green. Do not restate the vocabulary decision's full reasoning here; it lives on the types in `crates/tiler-metal/src/target.rs` and `crates/tiler-metal-aot/src/input.rs`, and duplicating it would create the second authority the documentation contract exists to prevent.

## Outcome

Both gaps are closed in `docs/architecture.md`, the ADR question is answered explicitly, and two follow-ups are filed for what this ticket's scope could not reach.

**Fact — ADR 0065 needed no superseding note; only this document was stale. That is the case.** ADR 0065's Decision reads "Add a fifth reusable target-independent crate: `tiler-reference -> tiler-ir`". That is an ordinal statement about the crate it adds — `tiler-reference` was and remains the fifth reusable crate admitted — not an enumeration of the workspace and not a cap on it. Its normative content is that `tiler-reference` owns host reference values, input bindings, evaluator traversal, evaluation diagnostics, and the separately frozen reference-capability registry, and that compiler, artifact, backend, and runtime production crates do not depend on it. A sixth crate with an empty dependency closure neither reverses nor narrows any of that. The "reusable-crate count" its status line claims from ADR 0056 is ADR 0056's enumeration of four, corrected to five; it is a correction, not a standing cardinality. What was stale is this document's own standing enumeration — "The prototype uses five reusable libraries and two non-published proof executables" followed by a five-entry block — which is false against `Cargo.toml`'s six library members and `scripts/check_workspace.py`'s `EXPECTED_MEMBERS`, and which sat in the same document as a Component ownership table that has listed all six crates for some time.

**Fact — an ADR gap is real, but it belongs to ADR 0056 and ADR 0070, and it is now filed rather than silently papered over.** ADR 0056 (`decision_status: superseded`) states "MSL emission and AOT invocation remain modules in `tiler-metal`" and "No frontend, proc-macro, Candle, generalized cache, or reusable Metal-runtime crate is created for the first proof". Its status line supersedes it only for the reusable-crate count, the reference-evaluator placement, the compiler-to-artifact edge, and the lockstep artifact/IR consequence, and says "the remaining packaging boundaries are retained". The AOT-invocation clause is therefore a retained boundary that the workspace departed from with no explicit superseding decision — the failure `AGENTS.md` names. ADR 0070's Decision block ("The dependency direction is:") lists five crates and no development edges; every edge it does list is still correct, so it is incomplete rather than wrong. `prototype-apple-aot-driver` held `implementation/metal-aot` and `implementation/workspace` and never `contracts/decisions`, so it could not have written the ADR when it admitted the crate. Until that ADR lands, this document says so in the packaging profile itself rather than presenting six libraries as an accepted decision.

**Decision — the Apple target-vocabulary ownership split gets no standalone ADR. For that split, the contract update plus the type-level record is the complete answer.** Three reasons. It changes no public surface — nothing moved, no signature changed, no namespace opened — so none of ADR 0075's always-ask categories reaches it, which `choose-one-owner-for-apple-target-vocabulary` established and which re-checking ADR 0075 confirms. The failure mode an ADR would prevent is a future reader consolidating the duplication, and the sentence leading that reader there was in this document; the second edit removes it and puts the enforcement mechanism in its place, so the contract now argues against the consolidation at the exact point of contact. And `docs/decisions/README.md` defines an ADR as recording a choice that "constrain[s] several components or would be expensive to reverse": this one constrains two crates and is reversible by whichever component first orchestrates emission and compilation together, an obligation `prototype-metal-bundle-assembly` already carries. A standalone ADR would be a fourth copy of reasoning that `crates/tiler-metal/src/target.rs`, `crates/tiler-metal-aot/src/input.rs`, and `crates/tiler-metal/src/target_correspondence.rs` already state in full, with no normative content of its own. `contracts/decisions` was therefore not added and no ADR was drafted here.

**The split does belong in the indexed decision record — as a consequence clause of the crate-admission ADR, not as its subject.** The argument that actually decided it is the driver's empty dependency closure, and that closure is precisely the property `record-an-adr-for-the-metal-aot-crate-admission` must establish. One or two Consequences sentences there, naming `target_correspondence.rs` as the enforcement, put the split into the ADR record without creating a standalone authority; that ticket carries the instruction, including the requirement to reference the types rather than restate them. This is a routed "no", not a dropped question.

**Fact — edit one, the packaging profile.** The count sentence now reads "The workspace carries six reusable libraries and two non-published proof executables, whose intra-workspace edges — normal, plus development where marked — are:", the block gains `tiler-metal-aot -> []` and marks both development edges (`tiler-compiler` + development `[tiler-reference]`, `tiler-metal` + development `[tiler-metal-aot]`), and three paragraphs follow it: that `scripts/check_workspace.py` pins the member set, the `[workspace.dependencies]` table, and every package's complete normal and development dependency list, so the edges are checked rather than described; that the driver's empty dependency closure is a decided property because the crate spawns `xcrun metal`/`xcrun metallib` and its value is an invocation auditable without the lowering stack behind it; that the `tiler-metal` → `tiler-metal-aot` edge is development-only for the two reasons `compile-golden-msl-through-the-aot-driver-in-the-gate` established, namely that `tiler-metal` must not acquire Apple tool discovery in a consumer's build graph and that Cargo permits a cycle through a development dependency while rejecting one through a normal dependency, so the edge preserves the eventual `tiler-metal-aot` → `tiler-metal` production direction; and that no accepted ADR yet records the admission, naming the follow-up.

**Fact — edit two, the Component ownership table, with a later refinement.** This ticket originally placed launch-index realization among `tiler-metal` target facts. `separate-metal-launch-index-from-index-and-address-width` later established from MSL 4.0 Table 5.8 that the selected declaration is an emission choice, not a fixed target capability, and moved it into `MetalEmissionRealization`. The current architecture table therefore gives `tiler-metal` the target facts emitted source declares—language standard, artifact family, deployment minimum, subnormal arithmetic, and buffer binding capacity—and separately names selected backend ABI realizations such as the launch-index declaration. The `tiler-metal-aot` row owns the target facts a compiler invocation selects: Apple SDK, language standard, artifact family, and deployment minimum. Neither row subsumes the other, and the total map in `crates/tiler-metal/src/target_correspondence.rs` keeps their genuine overlap exhaustive.

**Fact — three further statements in this document were stale, wrong, or ambiguous.** Two were fixed here because they sit inside the block being rewritten. The profile named `prototype-compile` and `prototype-run`, which are not package names: `prototypes/serial-sum-compile/Cargo.toml` and `prototypes/serial-sum-run/Cargo.toml` declare `tiler-prototype-compile` and `tiler-prototype-run`, so the block mixed exact package names with informal ones. And `prototype-run -> [tiler-artifact, platform Metal bindings]` claimed an edge that does not exist: `tiler-prototype-run` depends on `tiler-artifact` alone and `prototypes/serial-sum-run/src/main.rs` is a five-line stub printing "serial-Sum runtime prototype is not implemented yet", so the entry now reads `+ planned platform Metal bindings` with a sentence saying the runner is still a stub. The third was not fixed: the "Dependency direction" diagram mixes Cargo-edge arrows (`frontend integrations ─► tiler-ir ◄─ tiler-compiler`) with data-flow arrows (`backend emitters` above `target AOT tools`), and read as a Cargo edge the emitter/AOT pair points opposite to the production direction this document now reserves. Choosing what the arrows denote is an interpretive change to an accepted contract's illustration that this ticket did not scope, and a one-line "this diagram is data flow" note would have been false of its first row. `disambiguate-the-architecture-dependency-direction-diagram` owns it.

**Follow-ups filed.** [`record-an-adr-for-the-metal-aot-crate-admission`](record-an-adr-for-the-metal-aot-crate-admission.md) — `contracts/decisions`, `contracts/navigation`, `contracts/foundation` — owns the crate-admission ADR, superseding ADR 0056's retained AOT-invocation clause, restating ADR 0070's block with six crates and both development edges, and carrying the vocabulary split as a consequence clause. It needs `contracts/navigation` because `scripts/docs.py render` regenerates the `ADR TOPICS` and `ADR CHRONOLOGY` blocks in `docs/decisions/README.md` and `scripts/check_repository.py` runs `scripts/docs.py validate`, which calls `render(check=True)` and fails on a stale block; a new ADR therefore cannot land without that file, and `scope-einsum-contraction-support` held that scope exclusively while this ticket ran. [`disambiguate-the-architecture-dependency-direction-diagram`](disambiguate-the-architecture-dependency-direction-diagram.md) — `contracts/foundation` — owns the diagram.

**Scope.** No scope was added. All edits are inside the declared `contracts/foundation` (`docs/architecture.md`) and shared `project/tickets` (this ticket and the two new ones).
