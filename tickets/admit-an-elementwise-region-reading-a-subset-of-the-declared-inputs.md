## User-visible outcome

A program declaring several ordered named outputs whose recognition walks read *different* subsets of the declared input tensors compiles, so an output's region binds the inputs its own expression reads rather than every input the program declares.

## Why this exists

**Fact — the check is whole-program and the region it protects is per-output.** `recognize_elementwise` (`crates/tiler-compiler/src/request.rs`) is handed `declared`, the program's *entire* declared input list, and ends with `if reads.len() != declared.len() { return mismatch("elementwise-reads"); }`. `recognize_pointwise` and `recognize_reduction` both build that list as `program.inputs().map(|input| input.value()).collect()`, and `NormalizedPointwise::input_keys` is likewise every declared input key. So an output whose expression reads two of three declared inputs is refused, under a rule whose own comment states the property it is protecting: "Every declared input must be read. One that is not would bind a buffer the kernel never loads, and the expression's own dense-ordinal rule would refuse the assembled expression anyway".

**Inference — the rule was correct while a program had one output, and multi-output admission is what made it wrong.** With one declared output, an input no output reaches is dropped by `SemanticProgramBuilder` before the program is frozen — `request::tests::every_refusal_names_its_unrecognized_property` records exactly that for the `input-arity` row ("a frozen program drops the unused declaration"). So the whole-program input list and the single output's read set always agreed, and no fixture could distinguish them. [`admit-ordered-multi-output-programs-at-the-compiler-request-boundary`](admit-ordered-multi-output-programs-at-the-compiler-request-boundary.md) relaxed both arity guards, and two outputs can now split the declared inputs between them while every input is still read by *some* output.

**Measurement (2026-08-05, at the multi-output landing).** `crates/tiler-compiler/tests/multi_output_boundary.rs`'s `two_outputs_reading_disjoint_declared_inputs_refuse_for_their_unread_buffers` compiles `doubled = a + a` and `squared = b * b` over two declared `[4]` inputs, under every stated numerical contract, and observes `phase: "strategy", rule: "elementwise-reads"`. Its accepted neighbour is `two_output_region` in the same file — `product = a * b` and `sum = a + b`, the same two inputs, the same two families, the same independence — which compiles, so the refusal is about the *subset* and not about the second output.

## Boundaries

- This is about which inputs one output's region binds, not about input arity. [`admit-multi-input-elementwise-programs-at-the-compiler-boundary`](admit-multi-input-elementwise-programs-at-the-compiler-boundary.md) landed the general multi-input expression and is not to be re-opened.
- **`TensorRole::Input { ordinal }` is program-scoped, and must stay so.** `CoverAssembly::from_plan` checks `ordinal < semantic.input_count()` and binds `AssemblyBinding::Input(ordinal)` against the program's declared interface, so a region reading inputs 0 and 2 should carry those ordinals rather than a region-local renumbering. A renumbering would make the same expression at two sites carry different bytes and would have to be undone at assembly.
- What has to move together is the *expression's* leaf numbering and the region's bound input list: `PointwiseF32Expression` uses dense `InputOrdinal`s from zero, so the projection needs a stated map from the expression's leaf ordinals to the program's input ordinals, and that map is part of what the region's identity must fold. Decide whether it belongs on `NormalizedPointwise`/`NormalizedSerialSum` or on the built region before editing either.
- Whether the whole-program obligation "every declared input is read by *some* output" survives is a separate question from this one, and it should: an input no output reaches is a buffer the caller binds and no kernel loads. If it survives, it belongs beside `check_output_cover` in `select_supported_strategy`, which is where the other whole-program obligations moved.

## Required failure-path evidence

Each observed failing against an accepted neighbour: the disjoint-input two-output program above must compile rather than refuse under `elementwise-reads`; a program declaring an input *no* output's walk reads must still refuse, so the obligation is relocated rather than deleted; a region built for an output reading a subset must bind the program input ordinals its expression actually reads, checked against a fixture where those ordinals are not `0..n`; and two programs whose outputs read different subsets must keep distinct region identities.

## An unrecorded `tiler-ir` prerequisite, discharged 2026-08-06

**Fact — this ticket was filed dispatchable over a wall a crate down, and that wall is now gone.** Closes-when item 1 requires the region built for an output to bind exactly the program input ordinals its expression reads, and item 4's failure evidence names "a fixture where those ordinals are not `0..n`". `tiler_ir::schedule`'s `verify_pointwise_region` refused precisely that: it required read access `i` to be `TensorRole::Input { ordinal: i }` at every position, so a region binding inputs `0` and `2` was rejected by the intrinsic verifier no matter what the recognizer produced. [`admit-a-materialized-intermediate-read-in-the-scheduled-region-vocabulary`](admit-a-materialized-intermediate-read-in-the-scheduled-region-vocabulary.md) separated the access position from the declared input the role names, for the epilogue's sake, and the rule is now that the reads name *strictly ascending* declared inputs — a gap between ordinals is admitted, a repeat or a descent is not.

**Inference — the second Boundaries bullet is now enforced by the verifier rather than only asserted here.** That bullet states `TensorRole::Input { ordinal }` is program-scoped and a region-local renumbering would have to be undone at assembly. The widening reached the same conclusion from the other direction and `crates/tiler-ir/src/schedule/builder.rs`'s `reads_bind_boundary_tensors_in_order` records the derivation; `read_accesses_must_name_strictly_ascending_declared_inputs` pins the non-prefix admission with a region reading declared inputs `0`, `1`, and `7`.

What this does *not* discharge is anything in this ticket's own scope: `recognize_elementwise` still requires `reads.len() == declared.len()`, `NormalizedPointwise::input_keys` is still every declared input key, and the leaf-ordinal-to-input-ordinal map item 1 asks for still has to be carried and folded into identity. The wall this ticket would have hit *after* doing that work is what moved.

## Closes when

1. Each recognized output carries the declared inputs its own walk reads, with an explicit map from the expression's dense leaf ordinals to the program's input ordinals, and the region built from it binds exactly those.
2. The whole-program obligation is relocated rather than removed, with the removal-shaped perturbation observed failing.
3. `two_outputs_reading_disjoint_declared_inputs_refuse_for_their_unread_buffers` is flipped from a refusal to a compilation, and `crates/tiler-compiler/tests/multi_output_boundary.rs`'s header paragraph naming this wall is rewritten to record what moved.
4. Any identity consequence of the ordinal map is executed as a complete step at its owning layer, with every moved pin enumerated — or shown by recomputation not to move.

## Outcome

**Why the read list was already the map, and nothing new had to be carried for the elementwise half.** Closes-when item 1 asks for "an explicit map from the expression's dense leaf ordinals to the program's input ordinals". `admit-two-reads-of-one-declared-input-in-an-elementwise-region` had already built it without needing it: `mint_elementwise` numbers a leaf by its position in the canonical read order and `resolve_elementwise` builds `reads` from that same order, so `reads[i]` *is* "leaf `i` binds declared input `reads[i].0` under relation `reads[i].1`". What that ticket left was a correspondence that happened to be the identity on `0..declared`, and all this one had to do was stop requiring it to be. The Boundaries bullet asking where the map belongs — `NormalizedPointwise`/`NormalizedSerialSum` or the built region — is answered by neither: it was on `NormalizedPointwise::reads` already, `crate::physical::pointwise_region` already built the region's accesses from it, and `elementwise_reads_match` already bound it position by position. `TensorRole::Input { ordinal }` stayed program-scoped, so nothing renumbers and nothing is undone at assembly.

**Fact — the admission is one deleted clause, and the obligation it carried moved rather than went.** `canonical_input_reads` walked the declared inputs, ordered each one's reads dense-first, and refused when a group came out empty. The group loop is unchanged; the refusal is gone. What it protected — a declared input the caller binds, the ABI declares, and no kernel loads — is now `check_output_cover`'s third obligation, `input-set`, stated over the outputs together beside `operation-set` and `output-partition-overlap`. It is derived through a new exhaustive `NormalizedOutput::reads_declared_input`, which reads each recognized shape's own record of the fact: an elementwise region's read list, a fold's prologue read list *or* its own contributor ordinal, a contraction's operand count, and both halves of a chain.

**Fact — the relocated obligation is defence in depth, and the derivation says so rather than the check implying otherwise.** `SemanticProgramBuilder` freezes only output-reachable values, so a retained declared input is an operand of some retained occurrence; `operation-set` claims every retained occurrence for some walk; and every way `plan_elementwise` consumes an operand — an elementwise node, a structural occurrence, a constant, a fold's contributor, a contraction's operand — records a read of it. No program the public builder can construct reaches `input-set`, and `tiler_ir::program`'s `verify_usage` refuses the same shape a layer down under `unused-value`. It is stated at the boundary so the refusal names the caller's program rather than a provider. Its removal-shaped perturbation is therefore driven against a *forged* recognition — a recognized program with one read entry removed — and its unforged neighbour is asserted to pass in the same test.

**Fact — a silent-wrongness site the widening created, found by reading and closed before it could fire.** `crate::physical::contributor_tensor` derived a prologue-less fold's contributor read as `Input { ordinal: 0 }` from `prologue.is_none()`, and `subject_contributor_tensor` did the same on the subject. That was right only because a prologue-less fold's walk reads exactly one tensor, so under the old completeness rule the program declared exactly one input. With subsets admitted, `folded = sum(b)` beside an independent `doubled = a + a` would have folded `a` — an intrinsically valid region binding the wrong caller tensor. The fact is now recognized rather than inferred: `NormalizedSerialSum::contributor_input: Option<u32>` is `Some` exactly when there is no prologue, `NormalizedSerialSumSubject` carries it, and both derivations route through one `declared_contributor_tensor`. The same hazard exists one step over in the *fused* region, which reads the tensor its prologue read; `fused_contributor_tensor` is the single derivation both the builder and the subject binding now ask, and it subsumes the dense-read guard `fused_prologue_constants` already had.

**Fact — a `tiler-ir` wall behind that fix, converted into structure rather than pushed through.** `crates/tiler-ir/src/schedule/builder.rs` spends `const FIRST_INPUT` in five places that decide a fold's contributor: `ContributorTensor::DeclaredDomain::admits`, the `FusedMultiplyAddSerialSum`/`SquaredSerialSum`/`StrictSerialMaximum` arms of `verify_access_and_semantics`, and both parallel topologies' `Exactly(FIRST_INPUT)`. **Measured on this branch at base `c2607938`:** with the recognizer admitting it and no compiler-side guard, `sum(b)` beside `a * a` over two declared `[2, 2]` inputs reaches `InvalidCompilerOutput(Frontier(MalformedProposal { provider: tiler::prototype-serial-sum-physical@1, source: Intrinsic { rule: "numerical-or-access-refinement", region: RegionId(1) } }))` — every request and planning stage succeeds and only the intrinsic region verifier refuses. `crates/tiler-ir/**` maps to `implementation/ir`, which this ticket does not hold, and widening another layer's admission vocabulary is the shape the board files separately (the `admit-a-materialized-intermediate-read-in-the-scheduled-region-vocabulary` precedent). So the recognizer refuses it by name under `sum-contributor-ordinal`, the fused alternative is *withheld* rather than proposed and rejected (losing a candidate, never a program — the materialized prologue-and-fold pair realizes it and reads declared input `1` happily), and [`admit-a-fold-over-any-declared-input-in-the-scheduled-region-vocabulary`](admit-a-fold-over-any-declared-input-in-the-scheduled-region-vocabulary.md) is filed at `todo` carrying the five sites, the measurement, the identity expectation, and the four compiler-side deletions that land with it.

**Fact — identity: no domain and no sub-tag stepped, and the step was eliminated rather than skipped.** The read run's recovery rule is "an ordinal absent from the run has one dense read", and its *premise* was the very completeness rule this ticket lifted. Without repair the projection is no longer injective: over three declared inputs, two dense reads encode identically whether the pair is `{0, 1}`, `{0, 2}`, or `{1, 2}` — one arm, one byte string, three programs — and separating them by the enclosing subject's graph identity is exactly the unstated invariant the `pointwise-f32.v4` comment forbids resting on. Two repairs were tested.

*Write every read positionally, as `epilogue-f32.v1` does.* Injective, and it moves the bytes of every subject already encodable: an all-dense complete read list writes an empty run today and would write one entry per declared input. That costs `pointwise-f32.v4` and `serial-sum-f32.v3` a version each and every governed compilation its request qualifier. Discarded because the cheaper option's argument closes.

*Write an explicit entry for each declared input no leaf reads.* Survives. The entry occupies the run's relation slot under `UNREAD_DECLARED_INPUT_TAG = 0x04`, and `encode_access_relation` writes `0x00`, `0x01`, `0x02`, or `0x03` and nothing else — so no run encodable before can carry that byte, per-tag injectivity closes over the widened domain, and a program reading every declared input emits no marker at all and encodes exactly what it did. Both sub-tags hold and `request-subject.v5` holds. The reciprocal obligation is recorded at both sites: a relation added to `encode_access_relation` takes the wildcard or a tag above `0x04`, never `0x04`.

The serial-sum arm reaches the same run through the fold's own contributor read when there is no prologue region to describe one, which is what makes `sum(a)` and `sum(b)` distinct subjects once the wall above lifts. Its bytes are unmoved for every fold encodable before: a prologue-less fold declared one input, so the lone dense read is omitted and no ordinal is left unread — the framed zero it already wrote.

**Measurement — no pin moved, and the check that would have caught one was observed failing.** The explain qualifier `request=689c3aefc30f48d3` (`crates/tiler-compiler/src/explain.rs:4174`) is *observed* green, not inherited: perturbing `encode_elementwise_reads` to write every read positionally — the step this avoided — fails `explain::tests::deterministic_trace_is_sealed_and_rendered_separately` and one encoder test, and nothing else, so that test is exactly the sentinel for a subject-byte move and it says no when the bytes move. Dropping the markers instead fails only the encoder test and *not* the pin, which is the direct evidence that no already-encodable subject's bytes moved. `grep -rnE '"[0-9a-f]{16}"|request=[0-9a-f]{16}' crates/ --include='*.rs'` returns that one site. The two request-subject-derived artifact identities in `crates/tiler-build/src/metal_plan.rs` (`e3ac0aee…`, `14cbccad…`) are unmoved and green in the full workspace run, as are the `tiler-ir` schedule goldens — no encoder outside `encode_elementwise_reads` was touched, and its widened branch is unreachable for any program those fixtures compile. Zero pins moved.

**Measurement — every new admitting and refusing path was watched failing, and the population is named.** Eight perturbations, each replacing exactly one site, run against the whole `tiler-compiler` suite (685 tests); harness at `scratchpad/subset-reads/perturb.py`, restoring each file from a `sha256`-compared copy with `copyfile` plus `os.utime` for the reason the two-reads landing records. Restoring the completeness rule fails five tests (the conformance row, the multi-output row, and all three recognizer rows); dropping `input-set` fails `a_declared_input_no_output_reads_is_refused_at_program_scope` alone; dropping the `sum-contributor-ordinal` refusal fails `a_fold_over_a_later_declared_input_refuses_by_name` alone; dropping the unread markers fails `the_read_run_marks_unread_declared_inputs_and_leaves_a_complete_list_empty` alone; writing every read fails that test and the explain pin; deriving the fold contributor from the arity again fails `a_folds_contributor_tensor_is_its_recognized_declared_ordinal`; dropping the fused first-input gate fails that derivation's own test and the conformance row; and renumbering a region's reads densely fails the conformance row, the multi-output row, and the existing `one_input_read_densely_and_through_a_permutation_matches_the_reference_evaluator`. The clean tree was verified green before the sweep and again after restoration.

**One site could not say no until a test was written for it, and that is recorded rather than hidden.** `declared_contributor_tensor`'s general arm is unreachable past `Some(0)` while `sum-contributor-ordinal` stands, so the sixth perturbation — replacing that arm with `InputOrdinal::FIRST` — initially left the whole suite green. That is a uniform pass over a site the sweep should have discriminated, so `physical::tests::a_folds_contributor_tensor_is_its_recognized_declared_ordinal` drives the derivation directly and the perturbation now fails it. The general arm is **implemented and walled**, which is a different maturity claim from tested end to end, and the test's own comment says so.

**Measurement — bit agreement per output, at the ordinals each output reads.** `pipeline::conformance::outputs_reading_input_subsets_compile_and_bind_the_inputs_they_read` compiles three declared `[2, 2]` inputs into `product = a * c` and `folded = sum(b * 2.0 + 1.0)`: three cover regions, one materialization edge, three dispatches, and read lists asserted as `[Input{0}, Input{2}]`, `[Input{1}]`, and `[Intermediate]`. Both published outputs are compared against `ReferenceEvaluator::standard().evaluate` bit for bit, and stated independently of the oracle with the wrong-tensor answer named beside the right one — `folded` is `[98, 386]` and a prologue that had stayed at the first declared input would give `[8, 26]`. The payloads are chosen so no two elements and no two row sums coincide. The same fixture is the evidence that the fused alternative is withheld rather than offered and rejected. `multi_output_boundary::two_outputs_reading_disjoint_declared_inputs_compile_binding_only_what_they_read` is the caller-visible half: `doubled = a + a` and `squared = b * b` compile at every stated contract beside their `two_output_region` neighbour, and the assembled kernel program's two stages bind the input keys `a` and `b` — read through `MaterializedOrigin::ProgramInput` rather than asserted from the recognizer.

**The gate row's wording, for whoever holds `contracts/numerics`.** `docs/correctness-and-testing.md` is not in this branch's scopes. The span to replace is the sentence beginning **"What the row still does not cover."** through **"…owns."** in the multi-output paragraph. Proposed replacement for exactly that span:

> **The row now covers outputs reading different subsets of the declared inputs.** Two independent outputs reading *disjoint* subsets refused under `elementwise-reads` until 2026-08-06, because every elementwise walk had to read every declared input — the same requirement as "the program's inputs are all read" while a program declared one output, and a different one once two outputs can split the declaration.
