`reconcile-the-transfer-taxonomy-convertdtype-label-with-the-enforcer-definition` checked every `PlacementEnforcer` variant in `docs/research/transfers/transfer-synchronization-and-resource-lifetime.md` against the accepted definition in `docs/compiler/optimizer.md` — that an enforcer "may change only how a boundary value is stored, addressed, placed, or delivered, never which values that boundary carries". Eight of the nine settled immediately. `Recompute(RecomputeStage)` did not, and it is the one variant the memo's "Enforcer and mechanism taxonomy" table never describes at all.

Every other enforcer moves, aliases, migrates, re-lays-out, or repacks an authoritative value version that already exists; its value preservation is discharged by the mechanism. Recomputation does not move a version, it re-derives one. Whether the re-derived value is the same value is a numerical question, not a placement one: a recomputation whose reduction order, contraction, or subnormal treatment differs from the original produces a different value, and under the very same ADR 0001 argument the definition rests on, one semantic program would then mean different things under two plans that differ only in whether a value was recomputed or kept.

ADR 0047 accepted recomputation as an enforcer and that acceptance is preserved — this is not a proposal to remove the variant. What is missing is the obligation that makes it legitimate. Decide and record:

- what `RecomputeStage` must carry so a verifier can prove the re-derived value equals the retained one under the effective numerical contract, and whether that is bit-identity or a stated weaker relation the boundary's requester declared acceptable;
- whether the obligation is discharged structurally — the recomputation is the same `ScheduledRegion` identity with the same numerical realization, which would make it checkable without a value model — or whether it needs a numerical proof of the kind `FusionNumericalProof` already carries;
- whether a recomputation that cannot discharge it is a typed feasibility rejection rather than a cost, per the repository's rule that hard feasibility is never hidden behind an infinite cost; and
- a row in the taxonomy table for `Recompute`, since its absence is why the gap survived a table that exists to make exactly this comparison.

The memo is a proposal that no accepted ADR and no normative contract has incorporated, so this is a gap to close before incorporation rather than a defect in an accepted contract.

Closes when the taxonomy table describes `Recompute`, its value-preservation obligation is stated, and `uv run --locked python scripts/check_repository.py` passes.

## Outcome

**The obligation is bit-identity, discharged structurally, but at one identity layer above the one this ticket proposed.** All four questions resolved, none of them to a choice needing Tom.

**1. The relation is bit-identity with the version the enforcer stands in for, and the weaker option this ticket offered is eliminated rather than declined.** A relation the boundary's requester declared acceptable fails three independent checks. It makes two plans of one program deliver different values by construction, which is the conclusion ADR 0001's argument exists to forbid rather than a parameter of it. It is a second numerical authority scoped below the program, which ADR 0076 item 5's consequence forbids in terms — a caller's resolved contract "does not become a per-region choice, and two regions of one program never honour different contracts". And it prices meaning: a planner reaches `Recompute` by comparing it against a transfer on cost, so a tolerance makes the cheaper plan cheaper partly because it delivers a different value. The future region/output accuracy layer does not rescue it, because that layer must identify an observable output and a recompute boundary is an internal placement obligation.

**2. Structural — and "the same `ScheduledRegion` identity with the same numerical realization" is not sufficient. The case that breaks it is this enforcer's ordinary case.** `docs/ir.md`'s identity layering puts the selected numerical realization/provider in `RegionImplementation`, one layer *above* `ScheduledRegion`, and puts output-affecting backend/compiler configuration and selected target identity in artifact identity; `IndexRegion` identity excludes targets outright. A recomputation exists to run where the retained version is not, so it is selected against the destination's requirements and a different implementation over the same scheduled region is the expected outcome. Two implementations refining one declared realization need not agree bit for bit — the optimizer contract itself admits that "A stronger implementation may satisfy a weaker requested result set", and an ADR 0042 accuracy envelope is satisfied by more than one bit pattern. Committing only to the scheduled region admits exactly that pair, silently.

The discharge is four conditions, all decidable from identities and stated facts: equal `RegionImplementation` identity; equal delivered numerical realization, which under ADR 0076 items 3 and 4 carries the compiler build and execution environment with it; the plan-deterministic guarantee at the executing scope, which `docs/numerical-semantics.md` already defines and already requires the physical plan to hold by rejecting timing-dependent atomics; and operand closure, recursively, since the first three prove only that the same function was applied.

Condition 1 must be identity and not conformance-equivalence, on the fail-closed test. The weaker rule's correctness depends on the effective permissions leaving no freedom, so a contract moving reassociation from forbidden to permitted would convert a discharging recomputation into a non-discharging one with no build error and no gate signal — the projection hazard `docs/ir.md` already states as a rule.

**A numerical proof is not the alternative, because nothing could supply one.** `FusionNumericalProof` is not a precedent: it binds a rederived candidate, the request subject, and the forbidden-transform permissions, and asserts that the fusion removed no observable boundary and consumed no forbidden transform. It is a structural proof about one transformation, not a value model comparing two programs. Proving two *different* implementations bit-equal is a universal claim over an unbounded input domain, and the only available evidence for it is empirical agreement over samples, a strictly weaker class. So a cross-implementation recomputation is inadmissible rather than provable, which is what makes conditions 1 and 2 requirements rather than a conservative shortcut.

**3. A typed pre-commit rejection, never a cost.** `MechanismPreflight`/`RecomputeValuePreservationUnproved`, naming which condition failed. It is reachable only at preflight, because every condition is a property of stated identities and stated target facts rather than of an executed stage, so it preserves fallback authority exactly as `NotApplicable` and `UnsupportedCapability` do and the planner selects another complete enforcer. Two rules close this independently: hard feasibility is separate from estimated cost; and a plan whose delivered values differ from the boundary's is not a cheaper plan but a wrong one. The first alone would still permit ranking; the second is what makes it unconditional.

**4. The row exists — and the missing row was only half the reason the gap survived.** `Recompute` is the one enforcer with no `source: TransferEndpoint`. The verifier's structural items 1–8 are all written over a source/destination pair, so none of them was *false* about a recomputation; each had no subject. A row alone would not have closed it, so the verifier gained structural item 9 and the runtime items renumbered to 10–16.

**What landed** in `docs/research/transfers/transfer-synchronization-and-resource-lifetime.md`: a `Recompute` row in the value-preserving enforcer table; the `RecomputeStage`, `RecomputeValuePreservation`, and `OperandDelivery` shapes; a new "The recompute obligation" section carrying the whole derivation, labelled Fact, Inference, Proposal, and Measurement throughout; structural verifier item 9 with the runtime items renumbered; `RecomputeValuePreservationUnproved` in the typed failure vocabulary with the fallback-preserving sentence extended; a "Recomputation instead of a transfer" worked profile; and a deferred question with its trigger. The memo's proposal status is unchanged and is restated where the derivation could be mistaken for a normative contract.

**What the Apple measurement does and does not show, since the dispatch overstated it.** Findings 21 and 22 of `docs/research/apple-targets/numerical-behaviour.md` measure `f16` preserving subnormals that `f32` flushes from modules declaring the identical `air.compile_options` set. That pair differs in *dtype*, so it is not an instance of "the same operation, recompiled, carrying a different numerical realization" — the two kernels are different kernels. What it establishes is the premise condition 2 rests on: a compile-side declaration is not a report of delivered arithmetic, so equality of declarations is not equality of deliveries. The nearer evidence for the recompile axis is findings 8 and 9 — the offline and runtime compilers on one host are separately built (`32023.883` and `32023.921`), their forty macOS cases agree bit for bit, and the record states the boundary itself: the agreement "does not make the offline build's declared realization *transferable* to a runtime-compiled kernel; it makes the two happen to coincide here".

**Bounded experiment.** `spikes/transfers/transfer_contract.rs` gained `Mechanism::Recompute`, a `recompute_operands` endpoint list, three typed rejections, and four tests; seventeen tests became twenty-one. The model takes the four conditions as stated booleans rather than deriving them, because deriving them needs an implementation-identity encoding, a delivered-realization record, and a determinism level that live in `tiler-ir`, `tiler-artifact`, and the physical planner. What it establishes is that the structural item is expressible over the same plan shape as the other mechanisms, that a recomputation is checked against its operands rather than a source version, and that a missing condition fails closed as one typed rejection.

**Left open, with its trigger.** How condition 2 is checked across two execution sites that do not share a delivered-realization record. ADR 0076 item 4 requires the artifact to carry that record and its ticket `record-delivered-numerical-realization` is `todo`, so the memo states the condition and not its check. The trigger is whichever comes first: that ticket landing, or a second symbolic affinity becoming executable. Until then ADR 0047's one-affinity profile makes the comparison vacuous and a recomputation to any other site fails condition 2 closed.
