# Dtype support maturity

**Status:** proposed visibility ledger

This ledger answers one question: for each recognized or deliberately excluded dtype family, what has Tiler actually built at each layer? The [mature dtype taxonomy](research/numerics/mature-dtype-taxonomy.md) owns the semantic universe, [Numerical semantics](numerical-semantics.md) owns meaning and legality, [Dtype-family research tracks](research/numerics/dtype-family-research-tracks.md) owns which ticket holds each family's next step, and this document owns delivered maturity. Listing a family authorizes no implementation.

Each **Trigger** below names its track's owner. A track ticket is filed `deferred` while its trigger has not fired, so the scheduler never offers one as work; naming it here is how a reader reaches the trigger's own statement without this document acquiring a second job.

The matrices are deliberately non-monotone. A target measurement can exist before a semantic identity is registered; a physical carrier can exist without tensor arithmetic; and a tested reference evaluator does not imply runtime dispatch. Read a cell only for its named family and layer.

## Cell vocabulary

Every cell uses exactly one maturity claim:

- **absent/unsupported** — no family-specific authority exists at this layer, or the family is deliberately outside this axis.
- **type-system reservation** — a generic type can represent the shape of the concept, but does not fix this family's meaning.
- **architectural seam** — an accepted decision or normative contract fixes family-specific obligations, but no mechanism at this layer implements them.
- **implemented mechanism** — family-specific production code exists, but this document cites no checked guarantee for the complete claim in this cell.
- **tested guarantee** — checked evidence exercises the linked claim within the boundary stated in the family notes.

An implemented generic provider, opaque canonical byte carrier, enum variant, or target measurement is evidence about that mechanism only. It never promotes an unregistered family.

## Evidence and triggers

### Logical bool

**Fact.** [ADR 0028](decisions/0028-recognize-sub-byte-integers.md) recognizes logical `bool` as two-valued and distinct from integer `i1`, while leaving bit-, byte-, and ABI-sized storage independent. [the governed dtype catalog](../crates/tiler-ir/src/semantic/catalog.rs) registers `tiler::bool@1` with a descriptor that states its two-valued cardinality and deliberately no logical width, and checked tests assert that `tiler::i1@1` has no authority and that no registered operation admits a `bool` operand at any arity. `KernelType::Bool` in [structured kernel IR](../crates/tiler-ir/src/kernel/model.rs) and `AbiType::Boolean` in the host ABI are control predicates, not logical bool tensor values, and registration did not change that.

**Trigger.** Admit the first exact vertical only for a named `Select`, comparison, logical reduction, or frontend workload, with semantic operations, speculation rules, storage and ABI, runtime validation, target facts, and conformance named together. Owned by [`scope-the-predicate-tensor-vertical`](../tickets/scope-the-predicate-tensor-vertical.md), which records that the trigger has not fired because the first attention program vertical binds a host-built **additive** `f32` causal mask rather than a predicate tensor, and which must close together with the operation axis's `RQ-OP-03` — the [operation taxonomy](research/semantic-graph/mature-operation-and-signature-taxonomy.md) states that the same missing decision gates five operation families and that neither side may be closed alone.

### Signed and unsigned integers

**Fact.** [ADR 0028](decisions/0028-recognize-sub-byte-integers.md) recognizes signed and unsigned widths 2, 4, 8, 16, 32, and 64. [ADR 0039](decisions/0039-explicit-integer-overflow-operations.md) and [ADR 0040](decisions/0040-specialize-integer-division-families.md) make overflow-specialized arithmetic and division/remainder families explicit; no general integer evaluator, optimizer, or backend vertical implements them. [the governed dtype catalog](../crates/tiler-ir/src/semantic/catalog.rs) registers all twelve widths as nominal identities carrying a signedness class and a logical width, and the reference provider tests U4's and U8's exact code domains, but the only governed operation signatures use U4 and U8 as strict-affine code and zero-point roles. The catalog's descriptors state no packing, and the code domain is deliberately derived from class and width rather than stored. That tested recognition and code-domain contract do not establish integer arithmetic, target honourability, physical ABI, or dispatch. `KernelType::Index`, `KernelType::U8`, and `KernelType::I32` remain address, carrier, and widened-subtract machinery rather than tensor arithmetic support.

**Trigger.** A named tensor workload must select an exact width, operation family, overflow/division/conversion behavior, storage, target, and corpus. Quantized codes alone do not trigger an integer arithmetic vertical. The numerical and reference half is owned by [`define-the-integer-numerical-contract-and-honourability-subject`](../tickets/define-the-integer-numerical-contract-and-honourability-subject.md), whose named gap is a honourability *subject* rather than an operation contract: ADRs 0039 and 0040 already fix the overflow and division families, while [Numerical semantics](numerical-semantics.md) states that the honourability subject vocabulary "covers floating-point scalar arithmetic", so the measured Apple code-domain integer evidence has nowhere to be declared. The storage half for one operand shape is owned separately and is live: [`admit-a-storage-carrier-for-integer-program-inputs`](../tickets/admit-a-storage-carrier-for-integer-program-inputs.md) states the carrier question as a public boundary for Tom and selects no arithmetic family. Packing for the sub-byte widths is [`generalize-the-sub-byte-storage-encoding-contract`](../tickets/generalize-the-sub-byte-storage-encoding-contract.md)'s, not this row's.

### IEEE f32

**Fact.** [Standard semantics](../crates/tiler-ir/src/semantic/registry.rs) registers F32 plus constant, multiply, add, and strict serial sum; [standard reference evaluation](../crates/tiler-reference/src/standard.rs) implements them; [compiler request normalization](../crates/tiler-compiler/src/request.rs) and governed fusion roles implement the narrow F32 profile; [structured kernel lowering](../crates/tiler-ir/src/kernel/lower.rs), program construction, artifact construction, and [Metal emission](../crates/tiler-metal/src/emit.rs) preserve its storage and numerical requirements. Checked tests cover exact bits, separate rounding, contributor order, NaN canonicalization, subnormals, signed zero, overflow, ABI identity, deterministic source, typed numerical refusal, and the target-neutral pipeline.

**Measurement.** The retained [runtime proof](../prototypes/serial-sum-run/src/proof.rs) executed the bounded F32 program under its explicitly selected flush-to-zero contract (`NumericalContract::FLUSH_SUBNORMALS_TO_ZERO_F32`) on one Apple M4 Max host and compared thirty cases bit-for-bit. That is a tested guarantee for that exact contract, host, toolchain, program shape, and corpus, not production runtime support or portable Apple-family dispatchability. Strict subnormal-preserving arithmetic remains rejected by the governed Metal profile where the measured target cannot honour it.

[the governed dtype catalog](../crates/tiler-ir/src/semantic/catalog.rs) registers all six, each with its sign/exponent/significand widths, its exponent bias as the vendored `mlir-builtin-types-llvmorg-22.1.8` record states it, and an explicit Boolean for every special member; E8M0FNU's descriptor states unsigned exponent-only data with NaN and no zero, sign, infinity, or subnormals. Nothing beyond identity is registered: no operation signature admits one. E8M0FNU is unsigned exponent-only scale data in compound formats, not an ordinary signed arithmetic dtype. FNUZ, alternate-bias, and vendor variants are not aliases without exact equivalence evidence.

**Trigger.** A selected model or kernel must name the exact format, operations, conversion and accumulation policy, physical representation, runtime refusal rules, target dispatchability, and conformance corpus. Owned by [`scope-the-ocp-reduced-precision-float-vertical`](../tickets/scope-the-ocp-reduced-precision-float-vertical.md), which covers exactly the six identities registered here. The five FNUZ, alternate-bias, and IEEE-convention FP8 spellings the taxonomy also catalogs — `f8E3M4`, `f8E4M3`, `f8E4M3FNUZ`, `f8E5M2FNUZ`, and `f8E4M3B11FNUZ` — are external owner-namespaced candidates whose row is [External and vendor formats](#external-and-vendor-formats), not this one; the catalog-size check below is the one-line way to confirm none of them is registered.

### Decimal, complex, and other reserved numeric families

**Fact.** [ADR 0035](decisions/0035-recognize-ieee-decimal-floating-formats.md) recognizes decimal32/64/128 and keeps DPD and BID as physical encodings of the same logical dtype. [ADR 0037](decisions/0037-parameterize-complex-dtype-identity.md) recognizes `tiler::complex@1<ComponentTypeKey>` initially over f16/f32/f64 and keeps planar versus interleaved storage physical. Both families are now registered as identities by [the governed dtype catalog](../crates/tiler-ir/src/semantic/catalog.rs): the three decimal formats carry their interchange width and coefficient precision, and the complex constructor carries its ordered real-then-imaginary component contract with exactly the f16/f32/f64 components ADR 0037 admits — every other component, including `complex<bf16>` and nested complex, is refused by typed reason. Neither family is evaluated, and no operation signature admits either. Wide `i128/u128`, bounded `iN/uN`, fixed-point, UNORM/SNORM, posit, and other numeric candidates remain extensions or reservations under the [dtype taxonomy](research/numerics/mature-dtype-taxonomy.md), not accepted built-ins.

**Trigger.** Decimal, fixed-point, and normalized formats require a named frontend or accelerator consumer. Complex requires a named operation and component type plus branch-cut, exceptional-value, accuracy, storage, ABI, target, and conformance choices. Other reservations require an exact producer and consumer before architectural work. Three owners, because the three clauses share no obligation: [`scope-the-ieee-decimal-vertical`](../tickets/scope-the-ieee-decimal-vertical.md) carries decimal32/64/128 and the DPD-versus-BID storage distinction a bit-preserving ABI must not conflate; [`scope-the-complex-arithmetic-vertical`](../tickets/scope-the-complex-arithmetic-vertical.md) carries the parameterized complex family, whose first requiring consumer on the operation axis is F-40 spectral transforms; and [`route-the-reserved-numeric-families-through-the-extension-boundary`](../tickets/route-the-reserved-numeric-families-through-the-extension-boundary.md) carries wide and arbitrary-width integers, fixed-point, decimal fixed-point, UNORM/SNORM, and posit, which are one track because the admission policy gives all of them the same single route.

### Strict-affine U4/F32

**Fact.** [Quantization semantics](../crates/tiler-ir/src/semantic/quantization.rs) registers U4, the strict-affine U4/F32 scheme, and the exact `AssembleStrictAffine`, `QuantizeStrictAffine`, and `DequantizeStrictAffine` operation families; [quantization reference evaluation](../crates/tiler-reference/src/quantization.rs) tests compound roles and shapes, positive **normal** scale (the admitted domain — subnormal, zero, negative, infinite, and NaN scales are each refused by class), zero-point range, nearest-even rounding, infinity saturation, NaN refusal, widened subtraction, F32 multiply, and positive zero; since 2026-08-04 the reference validators derive those obligations through `tiler_ir::semantic::check_bound_value` from the resolved type rather than a hand-rolled walk, and an assembled result's scale route is covered by the same authority. [Schedule and kernel IR](../crates/tiler-ir/src/kernel/model.rs) implement the exact whole-component packed-U4 LSB-first, zero-tail dequantization path, and program/artifact tests preserve component roles and structural ABI.

**Fact.** The compiler has no quantized candidate and explicitly refuses this scalar program during region-subject verification. Metal mechanically emits the structured U4 dequantization vocabulary, but a checked honourability test rejects the strict profile because its required F32 subnormal preservation is unavailable. The runtime binding site does not yet enforce semantic value preconditions or encoded payload validity — the host reference path does, since 2026-08-04, enforcing bound-value conformance derived from the resolved type — and no dispatchability row exists for this scheme. **Corrected 2026-08-06 as to the last clause only, and it narrowed rather than moved this row's cells.** A dtype dispatchability axis now exists at both ends — `dtype_dispatchability` on the compile profile and `ExecutionEnvironment::classify_dtype` in the loader, described under [IEEE `f32`](#ieee-f32) — but it is keyed by `ArithmeticType`, which names no quantized scheme, so nothing about this compound family is declarable through it and no cell of this row moves. Semantic value precondition enforcement, which is what this row's runtime gap actually is, remains absent everywhere and is still owned by [runtime semantic enforcement](../tickets/implement-first-runtime-semantic-value-precondition-enforcement.md).

**Fact — this profile was measured against a real workload and eliminated (2026-07-31).** [The first quantized language-model profile](research/numerics/first-quantized-lm-profile.md) round-tripped the pinned `Qwen/Qwen3-0.6B-Base` weights through per-tensor strict-affine U4 and re-ran the workload's own C1 conformance row: the model agrees with its F32 baseline's greedy token at **0 of 18 positions** and emits a different sequence. It is the only quantized profile with a delivered target-neutral vertical, and it is not the selected one. Nothing about this cell changes — the delivered vertical is still a tested guarantee for what it tests — but no backend work will consume it.

**Trigger.** The selected backend must structurally depend on [runtime semantic enforcement](../tickets/implement-first-runtime-semantic-value-precondition-enforcement.md), a target-family dispatchability authority, the exact selected grouping/map and physical-widening tickets, and calibrated costs before making a device-optimal claim. **The dispatchability link named here was `admit-a-dtype-dispatchability-capability-axis`, which is closed as superseded**; [`admit-a-caller-declared-target-profile`](../tickets/admit-a-caller-declared-target-profile.md) owns canonical resolved-type dispatchability facts, and it is `done` — so what a selected backend now owes is a measured `(target family, dtype)` row through that boundary rather than a new axis.

### Strict-affine U8/F32

**Fact.** U8/F32 has the same registered operations and tested reference semantics as U4/F32 in [quantization semantics](../crates/tiler-ir/src/semantic/quantization.rs) and [quantization reference evaluation](../crates/tiler-reference/src/quantization.rs), including the full byte code domain. It has no schedule, kernel, program, artifact, Metal, runtime, or dispatchability vertical. The U8 carrier spellings used internally by the U4 path do not implement this compound value.

**Fact — the trigger below fired on 2026-07-31, and no cell moved.** [The first quantized language-model profile](research/numerics/first-quantized-lm-profile.md) selected **per-output-channel** strict-affine U8/F32 over the pinned workload's 196 weighted projections, and named the U8 physical representation (unpacked `StorageScalar::U8`, no packed encoding), the component ABI, the fused-decode candidate, the analytical cost with its measurement boundary, the qualified `apple9-f32-unified-msl4-macos26` target, the runtime predicates including a strengthened positive-*normal* scale, and the exact-bits conformance criterion. That is a selection, not an implementation: the registered scheme validator still admits only the two **per-tensor** contracts, so the selected per-channel form is not yet a statable contract and every physical cell in the row above stays absent. Seven delivery tickets carry it, headed by [`implement-workload-selected-quantized-parameter-maps`](../tickets/implement-workload-selected-quantized-parameter-maps.md) and [`implement-first-quantized-backend-profile`](../tickets/implement-first-quantized-backend-profile.md).

**Trigger.** A selected workload must name the U8 physical representation, component ABI, candidate, cost, target, runtime predicates, and conformance corpus independently of U4 — done, above. What remains before a cell moves is that the parameter map, the physical vocabulary, the fused schedule, and a device measurement each land and test what they claim.

### Other affine and OCP MX schemes

**Fact.** [ADRs 0029 through 0033](decisions/0029-affine-quantization-parameter-maps.md) establish parameter maps, first-class encoded values, strict affine semantics, and the semantic-validation/physical-enforcement split. Generic encoded-numeric identity, compound reference tensors, and bit-packed structural records are reservations, not support for per-axis, per-block, alternate widths, alternate expressed types, `Requantize`, or integer `Rescale`. [ADR 0038](decisions/0038-recognize-ocp-mx-schemes.md) recognizes six OCP MX 1.0 32-element compound scheme identities. [the governed dtype catalog](../crates/tiler-ir/src/semantic/catalog.rs) registers all six *scheme identities* with their constituent element and E8M0 scale types, block size 32, and scale-selection contract, and a checked test asserts that every static contract offered to one is refused with `microscaling.unsupported-contract` while an unregistered scheme spelling still fails as missing authority. **No MX value can be constructed.** The only parameter-index map that exists is per-tensor, which is the wrong association for a 32-element block, so admitting a contract would put a false numerical claim into durable identity; the conversion, rounding, saturation, and block-wide special-value rules also stay with the pinned `ocp-mx-v1.0` record, whose bytes are metadata-only and are not restated in the descriptor. Recognition here therefore buys one thing: an MX identity is refused as unsupported rather than reported as unknown.

**Fact — the affine half of the trigger below fired on 2026-07-31; the MX half did not.** [The first quantized language-model profile](research/numerics/first-quantized-lm-profile.md) names all eleven fields for a **per-axis** map over the weight's output-feature axis, so generalized affine work has its named producer and consumer and starts at [`implement-workload-selected-quantized-parameter-maps`](../tickets/implement-workload-selected-quantized-parameter-maps.md). Two of its findings belong here rather than only there. **Per-block and per-group maps were eliminated on legality, not on accuracy**: a scale that varies along the contracted axis makes a fused contraction partition that axis into contiguous intervals merged in order, which is exactly the reduction topology [the contraction realization record](research/scheduling/first-metal-contraction-realizations.md) attributed to `contiguous_split` and admitted only under reassociation — a permission no contract registered for that workload grants. Their measured accuracy was the *best* of any candidate, which is why the ground has to be stated: a caller granting reassociation reopens them. **MX remains not a candidate at all**, and for the reason this section already gives — no MX value can be constructed, so there is nothing to measure or lower; a non-per-tensor map is a prerequisite for MX rather than a substitute for it, and the per-axis map selected above is not a 32-element block map.

**Trigger.** Generalized affine work starts only when a selected profile names its exact code/expressed/scale/compute types, parameter map, grouping, storage, ABI, runtime predicates, target, cost, and corpus — done, above, for the per-axis form only. MX requires a selected model format and exact constituent scheme; it is not a scalar-dtype widening ticket and it is not reached by implementing a per-axis map. The affine half's live owners are named in the paragraph above; the MX and vendor block-scaled half is owned by [`scope-the-block-scaled-compound-value-vertical`](../tickets/scope-the-block-scaled-compound-value-vertical.md), which carries NVFP4 and the project block codecs alongside the six OCP schemes and records the third reopening route this section states — a caller granting reassociation, since per-block and per-group maps were eliminated on legality rather than accuracy.

### External and vendor formats

**Fact.** The [semantic registry](../crates/tiler-ir/src/semantic/registry.rs), [reference registry](../crates/tiler-reference/src/registry.rs), compiler capability registries, and opaque artifact type bytes implement provider seams. No bundled external or vendor format is supported. Test-only external F8 and U8 fixtures prove provider identity or transport, not arithmetic, physical ABI, runtime validation, or dispatch.

**Trigger.** A real consumer must publish a stable owner-namespaced identity, immutable descriptor, normative reference, encode/decode vectors, operation set, storage and ABI, runtime refusal rules, target evidence, and versioned conformance. Similar spelling or bit width is never equivalence. Owned by [`govern-external-dtype-namespace-registration-and-equivalence`](../tickets/govern-external-dtype-namespace-registration-and-equivalence.md), which separates the settled half from the open one: [ADR 0034](decisions/0034-tiler-governed-built-in-dtype-keys.md) fixes the ownership direction, and the [admission policy](research/numerics/dtype-identity-admission-policy.md) records that "namespace registration and collision governance for external providers remain an API-design task". That remainder is a public boundary under [ADR 0075](decisions/0075-scope-public-boundary-approval-by-change-category.md), and the same-format owner check ADR 0034 requires is vacuous while no external identity exists to collide with, which is the second reason the track waits.

### Execution-only formats

**Fact.** The [dtype taxonomy](research/numerics/mature-dtype-taxonomy.md) keeps TF32, PTX scale encodings, `x86_fp80`, and `ppc_fp128` out of logical built-in identity when they describe an execution mode, target register/ABI format, or interchange spelling rather than an ordinary tensor element contract. Typed target profiles and kernel vocabularies can reserve such facts without exposing them as semantic dtypes.

**Trigger.** Add a physical fact only when a selected backend operation needs it and can state conversion boundaries, delivered numerical behavior, target detection, artifact identity, and refusal. Promote nothing into logical identity without a separate semantic decision. Owned by [`place-execution-only-numeric-formats-in-the-physical-layers`](../tickets/place-execution-only-numeric-formats-in-the-physical-layers.md), whose whole content is where such a fact would live rather than what its element semantics would be — these formats have none.

### Nonnumeric and non-tensor domains

**Fact.** String/bytes, temporal, categorical/dictionary, structured/record, object, and variant values are potential tensor element domains, not numeric kernel scalars. Generic nominal identities reserve representation without defining their operations, storage, lifetime, ABI, verifier, or runtime behavior.

**Trigger.** A named frontend or product workload must require the exact domain and define its operation and lifetime contracts. Numeric dtype breadth does not trigger it. Owned by [`scope-the-nonnumeric-tensor-element-domain-vertical`](../tickets/scope-the-nonnumeric-tensor-element-domain-vertical.md), which carries string and bytes, object and variant, temporal, structured and record, and categorical or dictionary as one track because each needs offsets, buffers, lifetimes, and its own operation family before any of them is a tensor element at all.

### Sparse, ragged, and non-tensor values

**Fact.** Sparse and ragged describe container, shape, layout, or value representation, not scalar dtype identity. Tokens, resources, handles, PRNG keys, shapes, indices, tuples, futures, and control values are graph value kinds rather than tensor dtypes. They therefore remain explicitly outside this ledger's dtype axis instead of occupying misleading reservation cells.

**Trigger.** A workload whose representation cannot be expressed by current shape/layout/value contracts requires a separate container or graph-value design; it does not widen the dtype catalog. These families have owners, and they are on other axes: [Dtype-family research tracks](research/numerics/dtype-family-research-tracks.md) `## Families routed off the dtype axis` names Q-SEM-011 for effects, resources, and tokens, Q-SEM-012 for tuples and control constructs, the operation taxonomy's F-43 for typed PRNG keys, and `RQ-OP-10` with Q-SHAPE-004 and Q-SHAPE-005 for data-dependent extents. No dtype ticket is filed for any of them, which is the point of routing them.

## Reproducible negative checks

Run these from the repository root and read the named construction site before changing a cell:

```sh
# Standard semantic construction. The accepted built-in identity catalog is registered from the one
# table in catalog.rs; every other registration in these three files is an operation signature or a
# Rust marker binding. Read the sites before changing a cell: registering an identity is what the
# recognized-identity column reports, and `register_operation` is what the next column reports. Only
# F32, U4, U8, and the two strict-affine contracts carry a marker, and only F32 and strict-affine
# reach an operation signature.
rg -n 'register_marked_value_type::<|register_value_type\(|bind_marker::<|register_operation\(' crates/tiler-ir/src/semantic/{registry.rs,quantization.rs,catalog.rs}

# The registered identities are 27 nominal scalars, the complex constructor, six OCP MX schemes, and
# the strict-affine scheme. This asserts that set against a list transcribed from the accepted ADRs
# rather than from the catalog table, so a table typo fails rather than confirming itself.
cargo nextest run -p tiler-ir -E 'test(the_registered_catalog_is_exactly_the_accepted_names)'

# Shipped reference construction: F32, BF16, and strict-affine U4/U8 are the only family-specific
# providers. The BF16 file joined this population on 2026-08-01; a reference registration outside
# these three files would be a family this ledger does not account for.
rg -n 'registrar\.register(_value_type)?\(' crates/tiler-reference/src/{standard.rs,quantization.rs,bf16.rs}

# Search reduced float, decimal, complex, MX, sparse, and ragged spellings case-insensitively in the physical/reference construction areas. This stopped being an absence check for BF16 on 2026-08-05, in two steps. The carrier landing put `KernelType::Bf16` and `StorageScalar::Bf16` into kernel/model.rs and program/model.rs with their tags, their two-byte widths, and the access-type pairing between them, and put the BF16 spelling refusal into emit.rs beside its `MetalFloatArithmeticType` numerical mapping. The vocabulary landing then added schedule/pointwise_bf16.rs whole, plus `ScalarProgram::PointwiseBf16` and its node encoder in schedule/model.rs, `KernelConstant::Bf16Bits`, `BinaryOp::{Bf16Add,Bf16Multiply}`, and `ConvertOp::CanonicalizeBf16Nan` in kernel/model.rs, and their lowering and signature derivation in kernel/lower.rs and kernel/verify.rs. The remaining matches are the BF16 reference registration in standard.rs, F16 and decimal comments in emit.rs, and a "ragged" partition comment in schedule/model.rs. Read every match before preserving an absence claim: BF16's whole target-neutral vertical is present, and no other family named in this pattern is.
rg -ni 'f16|bf16|f64|fp8|fp6|fp4|e8m0|decimal|complex|mx|sparse|ragged' crates/tiler-ir/src/kernel crates/tiler-ir/src/program crates/tiler-ir/src/schedule/model.rs crates/tiler-reference/src/{standard.rs,quantization.rs} crates/tiler-metal/src/emit.rs

# No strict-affine U8 physical vertical exists in compiler, schedule, kernel, program, artifact, or Metal construction.
rg -n 'StrictAffineU8|U8::resolved_type' crates/tiler-ir/src/{schedule,kernel,program} crates/tiler-artifact/src/program crates/tiler-metal/src crates/tiler-compiler/src

# The dtype dispatchability axis, at both ends. This stopped being an absence check twice over, and
# its first path stopped resolving at all: `crates/tiler-compiler/src/feasibility.rs` moved under
# `target/` when the target-description authorities were gathered under one module root, and `rg`
# reports a missing path on stderr while still searching the rest — so the check read as empty for
# the wrong reason before it read as non-empty for the right one. The population is now the compile
# profile's own resolution (`target.rs`, `target/feasibility.rs`), the request boundary that refuses
# on it (`request.rs`, `RequestError::DTypeNotDispatchable`), and the loader that resolves a host's

rg -n 'DType|dtype.*dispatch|dispatch.*dtype' crates/tiler-compiler/src/target.rs crates/tiler-compiler/src/target crates/tiler-compiler/src/request.rs crates/tiler-runtime/src
```

Each check was run over the named population and its construction sites were read. The expected-empty ones were fault-proved by substituting a known-present spelling before relying on the empty result. **Two of them are expected-empty today** — the strict-affine U8 physical search and the semantic-precondition search, both re-run empty on 2026-08-06 — and the other two intentionally report and identify their current matches: the case-insensitive search since the BF16 carrier landed on 2026-08-05, and the dispatchability search since the runtime began resolving a host's stated dtype row on 2026-08-06. A check whose label still said "no such axis exists" would be read as an absence claim by a reader who did not run it, which is why each states what it now finds. The first two checks changed when the accepted catalog was registered: the semantic-construction search now spans `catalog.rs`, and the identity set it prints is asserted independently rather than being read back out of the table that produced it.

## Dtype-addition recipe

Thirteen rungs, in the order a dtype has to climb them. It is derived from the completed U4/F32 vertical and from [the BF16 second-dtype spike](../spikes/numerics/bf16-second-dtype/README.md), which walked rungs 1 to 4 and 11 out of tree and read the rest from source.

**Start from a named workload, never from a format.** Rung 0 is not on the list because it is not Tiler's work: a producer and a consumer must select the exact dtype, the operations, the target, and the accuracy the workload actually needs. A recipe entered without one produces a format nobody can retire.

**Each rung names four things**, because a rung reported as "done" without them is not checkable: its **authority** (who owns the answer), its **typed unsupported state** (what a program hitting the gap gets instead of a wrong tensor), its **evidence class** (what would make the rung's claim true), and its **identity consequence** (what durable bytes move, because those are what a cache or artifact can be wrong about later).

| # | Rung | Authority | Typed unsupported state | Evidence class | Identity consequence |
| --- | --- | --- | --- | --- | --- |
| 1 | **Recognition** — a canonical key and immutable descriptor | `crates/tiler-ir/src/semantic/catalog.rs`, under ADR 0034 | unknown identity, distinct from unsupported | primary-source synthesis against a pinned normative reference | a new registered identity; the registry's authority closure |
| 2 | **Descriptor adequacy** — the fields downstream consumers parameterize on | the same catalog row | an absent field, which means "evidence does not fix this", never a default | primary-source synthesis | descriptor bytes enter every identity that names the type |
| 3 | **Accuracy-metric compatibility** — is adjacent-value behaviour derivable? | `ULP_FORMAT_RULES` in `semantic/accuracy/metric.rs` | `accuracy.metric.incompatible-dtype`, a refusal rather than a guess | exhaustive-finite over the format | a new class rule, cited by every accuracy contract over the dtype |
| 4 | **Reference semantics** — the exact value set and the operations over it | `crates/tiler-reference`, registered per operation key | an unregistered operation key; evaluation refuses | exhaustive-finite plus a hand-derived witness corpus | the reference registry identity |
| 5 | **Semantic operation signatures** — one registered key per operation | `SemanticRegistryProvider::register_operation` | an operation the graph cannot name; construction refuses | executable model with a failing negative | new operation keys and their canonical facts |
| 6 | **Numerical policy** — rounding, subnormals, exceptional values, and their honourability subject | `docs/numerical-semantics.md`; `ScalarArithmetic` and the contract presets | `Unknown` in ADR 0043's sense, which fails closed | bounded measurement per target family | a new contract key; the profile descriptor |
| 7 | **Computation and accumulator types** — stated independently of the value type | the operation's own registered facts | no implicit promotion exists; a mixed program needs an explicit conversion that does not yet exist | executable model | the operation's facts, hence its identity |
| 8 | **Optimizer legality** — which rewrites preserve meaning at this width | `crates/tiler-compiler` fusion and rewrite legality | a candidate refused with a named rule | executable model with a rejected-rewrite explain record | rewrite-rule identities |
| 9 | **Physical carrier** — storage scalar, width, alignment, packing | `StorageScalar` and the boundary alignment derivation | a binding the translator cannot bind | executable model | storage tags in the artifact encoding |
| 10 | **ABI and artifact identity** — binding, transport, and the delivered realization record | `crates/tiler-artifact` | a decode-time refusal on an unknown tag | executable model plus fail-closed probes | artifact tags; every cached program identity |
| 11 | **Target dispatchability** — can this family run this dtype at all? | the caller-declared target profile, per `decide-per-dtype-dispatchability-as-a-target-capability` | `Unsupported` or `Unknown`, resolved **before** the routing commit | bounded measurement per `(family, dtype)` | the profile descriptor |
| 12 | **Backend lowering and execution** — the kernel type, its spelling, and a dispatched result | `crates/tiler-metal` and its peers | an emission gap naming the unstated fact | bounded measurement with an execution witness | kernel-type tags; emitted source identity |
| 13 | **Conformance** — the corpus that would catch a regression | `docs/correctness-and-testing.md` | a red test | exhaustive-finite where the format allows it, else a stated bounded profile | the conformance corpus itself |

**The rungs are not a total order, and the ledger is deliberately non-monotone.** U4/F32 has a tested physical carrier and no optimizer legality; BF16 reached a dispatched result at rung 12 on 2026-08-07, through a run that crosses neither rung 10's artifact envelope nor the routing commit above it, while its rung-8 legality landed the same day *derived* over a vocabulary carrying no fold rather than measured. Its tested rung-11 refusal at the routing boundary remains a guarantee about what will *not* run, and the dispatch at rung 12 did not come through it. Rungs 1 to 4 do gate everything after them, because an identity nothing recognizes cannot be validated and a semantics nothing states cannot be checked against.

| 13 Conformance | reuses for F16 (65,536 encodings); **F64 and F128 are not exhaustively enumerable** and need a stated bounded profile | reuses, and is cheaper | **different**: the corpus is over blocks | unknown |

**What the dry runs establish.** Only rung 11 reuses unchanged across all four families. Rungs 1 and 9 through 10 reuse for scalar families and break for compound ones, because a compound value is more than one buffer. Rung 6 fails outright for both non-float families, and that is a *stated* boundary rather than a discovered one — `docs/numerical-semantics.md` already says the scalar-arithmetic contract does not generalize. The vendor column is mostly `unknown`, which is the honest answer: the missing piece is a namespace and equivalence policy, not a lowering.

**What would make this recipe wrong.** It assumes a logical value is a scalar with an ordered value set (rung 3 breaks otherwise), that one logical value has one physical buffer (rung 9 breaks otherwise), and that the built-in catalog owns the identity (rung 1 breaks otherwise). All three assumptions are named here rather than buried, and the MX and vendor columns are where each fails first.

## Graph policy

A cell becomes an implementation ticket only when a named producer and consumer select the exact dtype or scheme, operation set, workload, target, physical layout, numerical contract, runtime predicates, cost boundary, and conformance corpus. Do not file a generic “support all dtypes” ticket.

Every family nonetheless has an owner, because a family with no ticket is indistinguishable from one nobody considered. [Dtype-family research tracks](research/numerics/dtype-family-research-tracks.md) partitions the taxonomy into fifteen tracks, maps every catalog row to one, and assigns each a live ticket or a `deferred` one carrying a trigger stated as a checkable state of the corpus rather than a judgement. A `deferred` track is not offered by the scheduler, so naming an owner here creates no dispatchable work and no implicit authorization; twelve of the fifteen are deferred today, and in five cases the trigger's non-firing is a recorded elimination — the additive causal mask, the unpacked U8 selection, the per-block legality elimination, the quantized-codes exclusion, and decimal's weak GPU adoption — rather than an absence of interest. One cross-cutting track has no row of its own: sub-byte and packed storage encodings are a column here and an owner there, because bit order, cross-byte layout, tail, alignment, unaligned access, neighbour-safe writes, and repacking are the same question for `bool`, the sub-byte integers, and the FP4 and FP6 carriers.

The accepted built-in catalog, dtype dispatchability, runtime semantic enforcement, selected quantized profile, compound grouping/map, exact physical vocabulary, backend candidate, and cost calibration remain separate authorities. A selected backend profile must make its actual prerequisites structural in the ticket graph; a prose list is not a dependency.
