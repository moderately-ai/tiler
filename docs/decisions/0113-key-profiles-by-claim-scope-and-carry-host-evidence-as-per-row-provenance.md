# 0113: Key profiles by claim scope and carry host evidence as per-row provenance

**Status:** accepted by Tom on 2026-08-19 in the live coordination session with the orchestrator, relayed first-hand by the coordinator, as item 25 of the decision queue, presented in explain-then-recommend form immediately beforehand. The accepted model is **2b, components 1–6 exactly as stated in the packet** on [`decide-the-host-evidence-to-profile-composition-model`](../../tickets/decide-the-host-evidence-to-profile-composition-model.md) — packet authored at `6236feef`, independently reviewed at `427b2080`, both merged at `1578c113`, acceptance recorded there under *Accepted decision — 2026-08-19*. Applied on 2026-08-19 by [`apply-the-accepted-host-evidence-composition-model`](../../tickets/apply-the-accepted-host-evidence-composition-model.md).

## Context

Measured target facts are scoped to the exact environment that produced them, and Tiler's profile keys are the durable vocabulary consumers dispatch on. On 2026-08-18 Tom rejected the delivered host-named key `tiler.metal.macos-m3pro-apple9.msl4-0.subgroup-f32.v1` on that collision: it was truthful pure-evidence discipline, but it codified a hardware model name into durable public identity. The declaration was demoted to a crate-private fixture and no further host-named public key could be minted until this question was decided.

Two forces made a decision unavoidable rather than optional. The ledger convention of one execution environment per profile is a not-yet-reworked implementation, and the accepted (R, R) disposition on [`resolve-the-retained-metal-profile-measurement-invocation-authority`](../../tickets/resolve-the-retained-metal-profile-measurement-invocation-authority.md) already commits the standard profile's measured rows to span two execution environments on one device, each population in its own source. Meanwhile the encoders already represent exactly that: the complete declaration descriptor writes the profile key, then a deduplicated source table whose canonical bytes include every measurement context — the compiler builds and all five execution-environment fields — then per-family row sections in which every measured row cites its source by index. Nothing in the encoders forced one environment per profile; only the convention did. What was undecided was the rule: how single-host evidence may enter a family-scoped key, and where "does this host match" is answered.

[ADR 0086](0086-require-attributable-or-attested-native-translation.md) item 3 bounds the answer from the other side: an exact environment row is a necessary validity scope and not a sufficient authority, because *an opaque translator can change while the observed OS/build/device row remains identical*.

## Decision

The six components below are the accepted model.

1. **Profile keys name claim scope only.** A public compile-profile key names what its rows are claims about — backend, artifact/platform family, GPU family, language standard, stated content families, revision; `tiler.metal.macos-apple9.msl4-0.f32-bf16.v1` is already this shape — and never a procurement identifier: hardware model names, OS versions, OS builds, serial or registry identities are provenance vocabulary and may not appear in a minted public key. Enforced as a documented naming convention at review of public key mints, not as a typed grammar. A key revises when its own description would otherwise become false (the BF16 precedent, `crates/tiler-build/src/metal_declaration.rs "This is a new content key"`: keeping `.f32` in a key for a profile that also states BF16 would make the key's own description false); every other change moves the descriptor, and [ADR 0043](0043-use-typed-phased-target-feasibility.md) already makes the key alone insufficient.

2. **Rows carry exact measured provenance, per population, inside identity.** Every measured row cites a source whose contexts state the exact offline toolchain, execution environment, and — once the accepted selection carrier lands — the exact compilation selection. Rows from different measurement populations never share a source; environments are never folded; the descriptor's source table and per-row indices keep all of it identity-bearing, exactly as the encoders already do. One profile's rows may therefore span execution environments, each row scoped exactly; the reseated standard profile is the first instance.

3. **Single-host-to-family rule: pre-registered beneficiary, stated value, measured validity.** A measured row enters a family-keyed profile only when (a) the producing measurement's frozen protocol named that exact profile key as beneficiary **before the run**; (b) the declaring module transcribes only what the record states and refuses every other value by name (the `UnevidencedWidth` pattern); and (c) the row's validity is `MeasuredEnvironment` — the constructor already makes a wider claim unbuildable. A record whose protocol scoped it elsewhere composes into nothing else, ever. The retained M3 Pro width record stays a crate-private evidence fixture under this rule, permanently.

4. **A single-host row licenses planning, never portability; "matches" is answered where a host exists.** Compile-time feasibility keeps reading declared rows with no context parameter; silence stays `Unknown` and refuses. Whether a real host is inside a row's measured scope is answered in the owning backend's vocabulary ([ADR 0092](0092-answer-backend-scoped-route-requirements-in-the-owning-backends-vocabulary.md)): at `LiveDevicePreflight` by the backend applicability evaluation, where **matches means byte-exact equality of every environment field against a measured context of the row's own population**, and even a full match stays necessary-not-sufficient because [ADR 0086](0086-require-attributable-or-attested-native-translation.md)'s authority requirement is untouched; and at `PreparedKernelPreflight` by per-entry `ObservedEqualsRequired` equality for prepared-phase facts ([ADR 0094](0094-bind-a-subgroup-combine-to-a-register-transfer-tree.md) decision 7). No device-model or family-level loosening: Tom's recorded ADR 0086 reason refutes looser rows a fortiori. The late-refusal shape is deliberate and fail-closed: a plan compiled against a width row on a mismatching future host refuses at prepared preflight, before routing commit — mispriced never, unexecutable until evidenced.

5. **Contradiction, not averaging, across a family.** If a second in-family measurement contradicts a declared whole-subject row (an Apple9 device preparing a width other than 32), the row cannot stand on the family profile: the builder's duplicate/contradiction refusals hold, and the disposition is withdrawal or a narrower claim subject — never per-host variants of one public key, never a vote.

6. **"Attestation" stays ADR 0086's word.** Per-row provenance carries host **identification** — the measured environment identity. Attestation remains the future mechanism [ADR 0086](0086-require-attributable-or-attested-native-translation.md) item 7 names; this model does not claim it, and the outcome wording of the deciding ticket is corrected by this component rather than silently restated.

## Identity consequences

The model itself is a **zero encoder change**: `tiler.target-profile.declaration.v11`, `tiler.target-profile.fact-sources.v4`, the checked target-profile descriptor domain, and every family domain stay as they are; no key is minted and none retired. The standard profile's key does not move; its descriptor, artifact identity, and cache pins move exactly once, at the reseat, as already accepted under the (R, R) disposition — a count that holds because that plan folds the selection step, the per-population sources, the row reseating, and the pin recomputation into one merged tree, so a coordinator splitting those landings would make it two moves and deviate from the accepted plan. The M3 Pro fixture stays byte-identical.

## Consequences

Tom accepted the model with these three stated consequences.

- **The M3 Pro width record permanently stays a crate-private evidence fixture.** Its frozen protocol pre-scoped it before a single width was read — `tickets/measure-metal-thread-execution-width-across-prepared-pipelines.md "a *new* M3 Pro Apple9 compile-profile width claim over the frozen population only"` — so component 3 forbids attaching it to any other profile, permanently and under every option the packet enumerated.
- **The demoted spike's rerun-from-`586c508a` exception becomes the permanent disposition.** The spike's tip-of-`main` build path is **not** restored, because the only restoration routes — a feature-gated re-export, or a second copy of the rows — were already found inadmissible in the demote delivery: the first undoes the demotion, the second mints a second authority over one retained measurement.
- **The standard profile's subgroup path is a new pre-registered measurement on the current host.** A new width measurement runs on the current M4 Max under a new frozen protocol that pre-names `tiler.metal.macos-apple9.msl4-0.f32-bf16.v1` as beneficiary, and lands as a subgroup row with its own population source and environment; the standing measurement authorization covers the session. Adding the subgroup fact family to the flagship public profile remains a Tom-facing packet under existing rules, because it moves the profile's stated content, descriptor, and every pin.

Two further consumer positions follow from the components.

- **The reseat carrier** ([`reseat-the-grid-and-cost-profile-rows-on-the-re-measured-records`](../../tickets/reseat-the-grid-and-cost-profile-rows-on-the-re-measured-records.md), first consumer): the standard key does not move; grid and cost rows reseat onto per-population sources carrying the `26A5406e` environment and the request-derived selection; the ledger gains third-environment tables presented **per population**; every moved pin is recomputed on one tree. Forbidden, stated so the carrier can cite it: folding environments into one source, bumping the key for an OS-build move, and presenting the two execution environments as one table.
- **Host applicability**: unchanged today — no host earns a receipt: a mismatching host is refused on its first failing environment predicate, and even a fully matching one is refused on the uninhabited translation authority (`crates/tiler-metal/src/applicability.rs "UnknownNativeTranslationAuthority"`). The single-row policy shape versus a multi-environment profile is a real mapping question that goes live only under an ADR 0086 item-7 trigger; it is owned by [`define-host-applicability-for-profiles-whose-rows-span-environments`](../../tickets/define-host-applicability-for-profiles-whose-rows-span-environments.md), deferred with a trigger check log.

The counterargument the packet records against the accepted model, kept here rather than left in the ticket: a family-scoped key over single-host rows reads like a family guarantee — `macos-apple9` will carry rows only one Apple9 device ever exhibited, and the key does not say so, so the honesty lives in typed validity and provenance a casual consumer may never read; the late-refusal cost is real too. The mitigations are all already in force: no consumer derives anything from key text (dispatch is key plus descriptor equality), per-row validity is `MeasuredEnvironment` and unwidenable by construction, host admission refuses under ADR 0086 anyway, and the repository's maturity vocabulary separates an implemented row from a tested family guarantee. The evidence that would reverse it: a consumer shown to infer portability from key text alone; an observed in-family contradiction, which triggers component 5's withdrawal path and reopens whether family keys should carry whole-subject rows at all; or an accepted attestation mechanism making per-host admission cheap enough that host-scoped public identity stops costing what it costs today.

## Alternatives considered

The packet's Pareto frontier retained two survivors, both top-tier on correctness and fail-closed strictness: this model, and per-row Tom-gated promotion of every measured row ("4-heavy"). They separate on process only, and 4-heavy was not recommended: the population it would additionally guard — a row landed under a pre-registered protocol, with per-population provenance, moved descriptor, recomputed pins, and review — is not a failure class any recorded defect here exemplifies, while the classes that did fail were construction and mirroring defects a queue gate does not touch. Equal on correctness, strictness, and host runtime; worse on maintainability and latency; better on nothing.

Eliminated before ranking, each on a stated gate reason: the status quo of one execution environment per profile with per-host public keys, which is revoked by the naming objection and contradicted by the accepted (R, R) disposition; compile-time context-matched feasibility, because no querying context exists at `CompileProfile`, so a required context refuses every production compile and an optional one is a caller-selectable policy fork; moving environments out of descriptor identity into a side table, which conflates identity; mirroring them beside it, which creates a second drift-prone authority over one fact; retroactive promotion of the existing M3 record under any option, which its own frozen protocol forbids; a typed profile-key grammar, since no consumer parses key internals and every existing key would need migration or grandfathering to serve no reader; and deferral, since every input is in-repo and no reconsideration trigger could supply information the packet lacks. The light form of per-host fixtures with explicit promotion is not a separate survivor: it is exactly component 3, absorbed rather than eliminated. The complete enumeration, eliminations, identity-consequence table, negative controls, and the independent review that attacked them live in the accepted packet.
