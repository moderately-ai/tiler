One refinement landed on 2026-07-25: item 3's provenance discipline now names what a validity scope must identify — the compiler build and execution environment a declared behaviour was measured on — and item 4 records that its artifact record inherits that requirement rather than adding one. ## Context

### Re-verification of the forcing measurement

**Measurement — environment.** Apple M4 Max, macOS 27.0, `Apple metal version 32023.883 (metalfe-32023.883)`, `xcrun --sdk macosx metal -target air64-apple-macos13.0 -std=metal3.1`. Offline compilation through `xcrun metal` then `xcrun metallib`; dispatch through a hand-written Objective-C host (`MTLCreateSystemDefaultDevice`, `newLibraryWithURL:`, one thread per output, `MTLResourceStorageModeShared`, bit patterns in and out). This reproduces the environment of `prototype-metal-numerical-realization` on the same toolchain build; it is one host and one toolchain row, not a portable guarantee about Metal. The [numerical behaviour record](../research/apple-targets/numerical-behaviour.md) reproduces this same row through a checked-in harness the repository gate runs; it is the authority for every value below, and the two places where it refines this re-verification are marked where they occur.

**Measurement — `-fmetal-math-mode=safe` still disables denormals.** Compiling `crates/tiler-metal/goldens/pointwise_scale_bias.metal` with `-S -emit-llvm` emits the named metadata `!"air.compile.denorms_disable"` under `safe`, `relaxed`, and `fast` alike. Under `safe` it appears alongside `!"air.compile.fast_math_disable"` and, at `-ffp-contract=off` and `=on`, every emitted `fmul`/`fadd` carries no fast-math flag; under `relaxed` each carries `reassoc nsz arcp afn` and under `fast` each carries `reassoc nnan ninf nsz arcp afn`. At `-ffp-contract=fast` the same three modes carry `contract`, `reassoc nsz arcp contract afn`, and `fast` respectively. The strictest mode the driver offers therefore disables denormals while simultaneously declaring fast math disabled.

**Refinement — the spellings are contraction-dependent, and this record originally stated them without a contraction setting.** It recorded only "under `relaxed` each carries `reassoc nsz arcp contract afn`; under `fast` each carries `fast`", which is the `-ffp-contract=fast` column alone. Finding 1 of the [numerical behaviour record](../research/apple-targets/numerical-behaviour.md) gives all nine cells and is the authority for the corrected text above. Nothing in this record's argument depends on the exact spelling: what is load-bearing is that `relaxed` and `fast` apply fast-math licences at all while the module still declares fast math disabled, and that holds in every cell. This therefore refines the recorded values rather than unsettling a conclusion, and it is recorded because a reader comparing a future toolchain against an unqualified spelling would otherwise see a spurious difference.

**Measurement — arithmetic flushes both subnormal operands and subnormal results, and the two are separable.** An emitted `x * 2.0f` returns `0x00000000` for the operand `0x00400000`, where preserving the operand would produce the *normal* value `0x00800000`; because the correct result is not itself subnormal, this isolates **input** flushing. An emitted `x * 0.5f` returns `0x00000000` for the normal operand `0x00800000`, where the correct result is the subnormal `0x00400000`; because the operand is normal, this isolates **result** flushing. Both hold at `-O0` and `-O2` and under `safe` and `fast` without variation. An emitted `x + 0x00800000` returns `0x00800000` for the operand `0x80400000`, where preserving the operand would produce the subnormal `0x00400000`, confirming input flushing on the additive path — the one observation this record carried as unreproduced by the harness, now re-established by the evidence refresh immediately below.

**Evidence refresh 2026-07-25 — the additive-path observation is re-established with an execution witness, and the caveat this record stated twice is retired.** Until this refresh, both the `Measured evidence` bullet above and the sentence immediately preceding recorded that this one observation was outside the checked-in harness's kernel set: every probe kernel that added did so after a multiply, so no add took a subnormal operand straight from the buffer, and a multiplicative flush could not be assumed to carry to the additive path. That was accurate about the harness and is no longer accurate about it. `extend-the-numerical-probe-to-an-additive-path-kernel` added `add_smallest_normal` — a single `x + 2**-126` with no multiply before it — and finding 20 of the [numerical behaviour record](../research/apple-targets/numerical-behaviour.md) owns the result. It returns `00800000` for the operand `80400000`, where preserving that operand would give the subnormal `00400000`, at `-O0` and `-O2`, under `safe`, `relaxed`, and `fast`, on both the offline and the runtime compilation path, and for both dispatchable families. That is twenty-four dispatched configurations agreeing on one result vector, in the covering and the exhaustive retained records alike, on the same environment row the re-verification above names.

**Fact — what is flushed here is an addend and not the whole result, which is why this row had to be measured rather than inherited.** The flushed subnormal stands beside a nonzero bias rather than becoming the result, so the returned value is *normal* and the observation is invisible to a reading in which a flush shows up as a returned zero. The probe derives its flushing candidate from the kernel by exact arithmetic under the substitution hypothesis instead of assuming a zero, which is what makes the case expressible at all. A third outcome is kept distinct rather than folded into either candidate: `00000000` would mean the operand survived the add and the subnormal *result* was flushed instead, a different mechanism from the one this probe isolates.

**Fact — this is the only witnessed additive observation available under the relaxed modes, and it satisfies both guard layers rather than being admitted despite one.** Adding a nonzero constant is an identity on no operand, so the `fadd` cannot be deleted the way the trap kernel's arithmetic is: it survives into the emitted module in all six offline configurations per family, and the execution witness `00800000 → 01000000` reports `executed` in every offline and runtime configuration. The `scale 1.0, bias +0.0` kernel that the trap measurement below rests on retains zero floating-point operations under exactly `relaxed` and `fast`, so it can supply no additive observation there. This kernel therefore reaches the modes that are least trustworthy, which is where an unwitnessed observation would have been worth least.

**Measurement — the flush preserves the sign of zero.** `0x80400000 * 2.0f` returns `0x80000000`, not `0x00000000`. This detail is new to the record and is load-bearing for the vocabulary below: a flush-to-zero mode that does not state which zero it produces is under-specified against measured hardware.

**Measurement — materialization is unaffected.** A load-then-store kernel with no arithmetic returns `00000001`, `00400000`, `007fffff`, `80400000` unchanged under every mode. The limit is a property of arithmetic, not of materialization.

**Measurement — math mode changes a conforming result.** For the emitter's `MultiplyThenAdd { scale 1.0, bias +0.0 }` shape, the operand `0x80000000` returns `0x00000000` under `safe` and `0x80000000` under `relaxed` and `fast`. IEEE-754 round-to-nearest requires the former, since `(-0.0) + (+0.0) = +0.0`.

**Measurement — contraction changes a conforming result.** A multiply and an add written as two separate statements over `scale = 1.5`, `bias = 1.0` return the separately rounded `0x3fc58f9e` for the operand `0x3eb97ef9` under `-ffp-contract=off` and `-ffp-contract=on`, and the fused `0x3fc58f9d` under `-ffp-contract=fast`.

**Measurement — a relaxed mode can appear to honour a strict contract by deleting the arithmetic.** In that same `scale 1.0, bias +0.0` kernel, subnormal operands are returned *unchanged* under `relaxed` and `fast`, and flushed under `safe`. At `-O2`, counting floating-point operations in the emitted LLVM IR explains it: `x * 1.0` is folded to a copy under every mode, so `subnormal_mul_one` retains zero floating-point operations; the kernel retains exactly one under `safe` — the `fadd` of `+0.0`, which cannot be removed without `nsz` — and zero under `relaxed`, where `nsz` removes it. The surviving `fadd` is what flushes. So the identical licence that breaks signed zero also deletes the operation that would have flushed, and the *same* mechanism produces both observations.

**Measurement — the operation count is necessary and not sufficient, and the gap strengthens the inference below.** The account above is complete at `-O2` and incomplete at `-O0`. The [numerical behaviour record](../research/apple-targets/numerical-behaviour.md) measures the same kernel at `-O0` under `relaxed` and `fast`: **two** floating-point operations survive into the emitted LLVM IR, and the GPU still returns every operand unchanged, negative zero included. A stage below the IR this record can read — the AIR-to-ISA compilation the driver performs at pipeline-state creation — removed them. Counting the emitted operations is therefore one layer of a guard that needs two: the emitted module must contain floating-point arithmetic, **and** the dispatched kernel must return an execution witness, a designated non-subnormal operand whose result differs from the operand exactly when the arithmetic ran. The harness encodes both and refuses to classify any observation that fails either, naming the precise reason rather than collapsing it into a boolean.

**Inference — honourability must be a stated target fact, never a value observed from a kernel.** Because a relaxation can delete the arithmetic — and because it can do so below any IR the toolchain will show, so that even a correct operation count does not establish that the operation executes — observing preserved subnormals from a compiled kernel is not evidence that the target preserves them; it may be evidence that no arithmetic executed, and no readable artifact the compiler emits will say which. Any design that derived a target's numerical honourability by measuring a probe kernel would infer the wrong fact under exactly the modes that are least trustworthy. `MetalTargetFacts::subnormal_arithmetic` already takes the opposite approach — a required caller-stated fact with the measurement recorded on the type — and this record generalizes that choice rather than replacing it.

### The design already names the vocabulary; the implemented subset does not

**Fact.** The originating ticket frames the finding as a vocabulary gap: "a vocabulary that cannot describe real hardware forces every real target to be non-conformant." That is accurate about the code and inaccurate about the design, and the distinction changes what this record may do. ADR 0019 is accepted and states that "every applicable floating-point operation resolves subnormal input handling and subnormal result handling independently. Each dimension initially supports preservation or an explicit flush-to-zero behavior." `docs/numerical-semantics.md` spells the same two-dimensional shape as `SubnormalContract { inputs: Preserve | FlushToZero, results: Preserve | FlushToZero }` and states that "some targets expose only a coupled mode or cannot realize every combination; that is reported as native, emulated, relaxed-only, or unsupported backend feasibility rather than collapsing the semantic dimensions." The conformance matrix already requires "all four input/result preserve/flush combinations" as adversarial coverage. ADR 0011 decides the selection model — a program ceiling intersected with per-operation restrictions and operation capabilities. ADR 0043 decides that supported operations are hard feasibility, not cost.

**Inference.** This record must therefore not invent a vocabulary. Doing so would create a second authority over the same terms, which the documentation contract forbids. What it must do is bind the implemented subset to the vocabulary that is already accepted, and decide the mechanism questions those accepted records leave open.

**Fact — what the implemented subset is, at `6555119`.** `tiler_ir::schedule::NumericalRealization` already carries `input_subnormals` and `result_subnormals` as two independent fields, so the struct shape matches ADR 0019; what is missing is a second variant, since `SubnormalMode` has only `Preserve` and `NumericalPermission` has only `Forbidden`. Two realizations therefore cannot differ on any subnormal dimension. `StrictF32NumericalContract` in `crates/tiler-compiler/src/request.rs` is `pub(crate)`, its only constructor `governed()` is a constant, its only assembly site `CompilationRequest::governed` is `#[cfg(test)]`, and `pipeline::compile` is itself `pub(crate)` — so there is no non-test path by which any caller states a numerical contract at all, and `verify_request` rejects any contract that is not the constant with `compile.unsupported.numerics.strict-f32`.

**Fact — the target's declaration is one boolean, and it does not carry the subnormal obligation, at `6555119`.** `PrototypeTargetProfile::supports_strict_f32: bool` is bridged by `physical::checked_target_profile` into a single `CapabilityAxis::StrictF32Arithmetic` fact, whose `Relation::Implies` admits only `0` or `1`. The requirement side comes from `tiler_ir::schedule::model::derive_requirements`, which computes `requires_strict_f32: !permits_reassociation() && !permits_contraction()` — reading contraction and reassociation and **ignoring both subnormal fields entirely**. Two consequences follow and neither is currently observable, because one variant per enum makes every realization identical. First, the boolean cannot name which dimension was unhonourable, so a rejection could only report `strict-f32: required 1, available 0`. Second, once the vocabulary widens, a subnormal-preserving contract that permits contraction and reassociation derives `requires_strict_f32 == false` and would be *admitted* on a target declaring no strict-`f32` support, because the obligation it needs was never in the predicate.

**Evidence refresh 2026-07-24 — the second consequence stopped being conditional, and item 1's ticket repaired it in the same change.** `1f78223` widened the vocabulary and, in the same commit, stopped `derive_requirements` deriving any summary bit at all: `ResourceRequirements` now carries `input_subnormals`, `result_subnormals`, `contraction`, and `reassociation` forward per dimension. The interim `CapabilityAxis::StrictF32Arithmetic` still needs one boolean, so the summary moved to `tiler_compiler::physical::requires_strict_f32`, where it is computed as a **disjunction** over four exhaustively matched dimensions — any one strict dimension is enough — rather than as the conjunction over contraction and reassociation that ignored both subnormal fields. It sits in the compiler because the collapse is a property of that axis and not of the region. The first consequence is untouched: `PrototypeTargetProfile::supports_strict_f32` and the axis still exist and still cannot name a dimension, and item 3 owns retiring them.

**Fact — two accepted four-outcome vocabularies exist and nothing states how they compose.** ADR 0043's outcomes are `Proven`, `Deferred`, `Rejected`, and `Unknown`, and they classify *how well a predicate is known* across five availability phases. `docs/numerical-semantics.md`'s backend numerical outcomes are `SupportedExactly`, `SupportedWithExactEmulation`, `SupportedOnlyUnderDeclaredRelaxation`, and `Unsupported`, and they classify *by what means an obligation is honoured*. These are orthogonal — an emulated realization is fully `Proven` at `CompileProfile` — and conflating them would lose the emulation outcome, which is the only one that changes the emitted program rather than the verdict. This is the genuine unresolved question behind the ticket, and it is the substance of the decision below.

**Fact — the two sibling identity encodings disagree, and only one fails closed on a widened enum, at `6555119`.** `tiler_ir::kernel::model::push_numerical` encodes the profile key, the canonical NaN bits, both subnormal modes, and both permissions, through `push_subnormal` and `push_permission` whose `match` arms are exhaustive over non-`#[non_exhaustive]` enums — so adding a variant is a build error there. `tiler_ir::schedule::model::push_numerical` encodes the profile key, the NaN bits, and the two `permits_*` booleans, and encodes **neither subnormal field**; because those accessors are `!matches!(…)` expressions rather than matches, adding a variant compiles silently and two realizations that differ only in subnormal treatment would receive the same `CanonicalScheduledRegionIdentity`. `crates/tiler-metal/src/emit.rs` guards itself a third way, with irrefutable `let SubnormalMode::Preserve = mode;` bindings at `realization_requirements` and `record_subnormal_obligation` that become compile errors on widening. Today the omission is masked, because `profile_key` is encoded and every distinct contract has so far carried a distinct key — but relying on a key to stand in for the field values it names is an unstated invariant, and the scheduled-region layer is the one place that does not enforce it.

**Evidence refresh 2026-07-24 — the disagreement is resolved, and the masking invariant is now stated as forbidden.** `1f78223` gave `crates/tiler-ir/src/schedule/model.rs` its own `push_subnormal` and `push_permission`, so `schedule::model::push_numerical` encodes every field of the realization — both subnormal dimensions and both permissions — each through an exhaustive match over a vocabulary that is deliberately not `#[non_exhaustive]`, matching the kernel encoder tag for tag. The two derived `permits_*` booleans it used to write are gone: a boolean is a projection of the permission, and a projection cannot fail closed when its source grows. `crates/tiler-metal/src/emit.rs` no longer needs the irrefutable `let SubnormalMode::Preserve = mode;` form, because the enum has more than one variant; `realization_requirements` matches each dimension exhaustively instead. `CanonicalScheduledRegionIdentity` moved from 192 to 194 bytes and the affected fixtures were rebaselined deliberately. What replaces the unstated invariant is a normative sentence rather than a repaired encoder alone — see item 6.

**Fact — the interim Metal behaviour this record supersedes.** `MetalNumericalGap::SubnormalFlushInArithmetic` records the unhonourable obligation, is written into the generated MSL provenance header, and is enforced by `MetalTranslationUnit::require_declared_realization`, which fails closed with `MetalEmitError::UnrealizableNumericalObligation`. That is correct as far as it reaches, and it is deliberately backend-local: it is one gap variant that cannot distinguish input flushing from result flushing, it names no target-profile identity, emission still succeeds so a caller that never asks for conformance never sees the rejection, and nothing above `tiler-metal` can select a contract the target would honour instead.

**Evidence refresh 2026-07-24 — the gap vocabulary grew to three variants and the limitation this Fact names survives all three.** Widening the contract made two more mismatches expressible, so `crates/tiler-metal/src/record.rs` now carries `SubnormalPreservationInArithmetic` — a declared flush on a preserving target, a gap for the same honesty reason, since emitting an explicit flush would be emulation this backend does not express — and `UndeclaredFlushedZeroSign`, because `MetalSubnormalArithmetic::FlushesToZero` states *that* the target flushes and not which zero it produces, while the measured Apple flush is sign-preserving. All three are still recorded per region rather than per dimension: `record_subnormal_obligation` compares the input and the result dimension against the same target fact and inserts the result into one set, so a gap on either dimension yields the same variant and the record still cannot say which dimension failed. Nothing else in this Fact moved, and items 3 and 5 still subsume the whole vocabulary. The ticket's own outcome record proposed widening `SubnormalMode` as the honest resolution and correctly declined to do it out of scope.

**Inference — "feasibility selects a conformant contract" is the wrong verb, and the ticket's own architectural line is why.** The ticket asks that a profile declare its realizations "so feasibility can *select* a conformant contract rather than only reject an unsatisfiable one." If any planning authority chooses which numerical contract to compile under, then a target's limitation has redefined what the program means, which is precisely the line the same ticket says to preserve. `docs/artifact-abi.md` already forbids the neighbouring case: "all variants in one program have the same semantic and numerical contract … routing never chooses between different accuracy meanings. Variants may use different realizations only when each independently refines the same contract." Feasibility *assesses*; it never chooses meaning. What turns a permanent refusal into a choice is not moving the decision into feasibility, but making the contract a stated caller input that has more than one expressible value — so that a caller who is willing to accept flushing can say so, in advance, as part of what the program means. The decision below is written that way, and the correction is deliberate rather than a paraphrase.

## Decision

### 0. Scope: one general model, with subnormals as the worked case

**Proposal.** This record states a general model over every dimension of the resolved numerical contract — subnormal input and result handling, contraction, reassociation and operand permutation, NaN result and payload behaviour, signed zero, infinity assumptions, reciprocal and approximate-intrinsic envelopes — and not a subnormal-specific mechanism.

Three reasons, in decreasing order of force. First, every mechanism question below has the same answer in every dimension: where the caller states the contract, what happens when the caller states nothing, how a profile declares honourability, what the artifact records, and what a rejection must name do not vary by dimension, so a subnormal-only mechanism would be generalized on its first reuse and the generalization would be a second migration through the same four crates. Second, the measured evidence already spans more than one dimension: the same session that measured the subnormal flush measured a signed-zero divergence between `safe` and `relaxed` and a contraction divergence between `-ffp-contract=on` and `fast`, so a record scoped to subnormals would fail to cover evidence already in hand. Third, ADR 0011's ceiling and ADR 0019's independence are already general, so a dimension-specific mechanism would be narrower than the decisions it implements.

**What is deliberately *not* general.** Only the subnormal dimension has a measured target that cannot honour the strict reading at all. Contraction and reassociation are honourable on the measured Apple row, which makes each a `MetalNumericalRequirement` and not a gap — but neither is honourable through a stated compiler selection *alone*, and the refinement below records what each additionally requires. So this record generalizes the *mechanism* and claims measured unhonourability for exactly one dimension on exactly one target row. Widening either claim requires its own measurement.

**Refinement 2026-07-25 — a compiler selection is necessary and not sufficient for either dimension, and this record originally stated it as sufficient.** The paragraph above previously attributed the honourability of contraction and reassociation to a stated compiler selection with no further condition. Two measurements added by `broaden-the-apple-numerical-probe-matrix` narrow that, and neither unsettles the surrounding claim: both dimensions remain honourable on this row, and the subnormal dimension remains the only one with no honourable selection at all.

**Refinement — contraction. A contraction setting governs what the emitter writes separately; it does not unfuse what the emitter writes fused.** Finding 16 measures a source-level `fma` carrying this record's own contraction constants emitted as `air.fma.f32` and returning the fused `3fc58f9d` at `-ffp-contract=off`, `=on`, and `=fast` alike, and on the runtime path as well, where the two-statement pair returns the separately rounded `3fc58f9e` at `off` and `on`. The contraction measurement recorded below is therefore exactly as scoped as its own wording says — a multiply and an add written as two separate statements — and is measured to be no defence at all against a fused operation the source asked for. Contraction honourability on this row rests jointly on the compiler selection and on an emission discipline: an emitter that lowered a `MultiplyThenAdd` to a source-level `fma()` would deliver a contracted result under every contraction setting, and no flag in the measured matrix would report it. That makes the per-statement emission rule a correctness requirement rather than a stylistic one, and it is a requirement a target-fact declaration under item 3 cannot carry on its own, because a profile declaring contraction honourable would be declaring something true only of an emitter that behaves. Stating it belongs to the numerical-semantics and Metal backend contracts, neither of which this record owns.

**Refinement — reassociation. It is honourable by selecting `safe` and measurably unhonourable under the relaxed modes, which "a stated compiler selection" left implicit.** Finding 17 measures a two-add chain chosen so that association order moves the value by one ulp: under `safe` the emitted module keeps two `fadd`s and the device returns the as-written `3f800000`, and under `relaxed` and `fast` it keeps one `fadd` carrying `reassoc` and the device returns the reassociated `3f800001`, with the runtime path agreeing at both optimization levels. The earlier three-fixture negative result that found no counterexample is bounded by this rather than contradicted — it is evidence that those three fixtures did not discriminate. The consequence for item 3 is a bound on what a per-dimension declaration may report: a profile admitting `relaxed` or `fast` cannot declare a reduction order honoured on this row, and whether that is a feasibility rejection or a declared gap belongs to the numerical contract's owner.

### 1. Vocabulary: bind the implemented enums to ADR 0019; add no new terms

**Proposal.** `tiler_ir::schedule::SubnormalMode` grows to the two behaviours ADR 0019 already accepted, and the two independent fields `NumericalRealization` already carries stay independent — coupling them is forbidden even when a target couples them, which is ADR 0019's operative sentence. `NumericalPermission` likewise grows to express a permitted transform, since `Forbidden` alone cannot state a relaxed contract. No dimension gains a coupled "fast" spelling, and no dimension is expressed as a single boolean.

**Proposal — a flush behaviour must state its zero.** The measurement above shows the Apple flush preserving the sign of the flushed value, and `docs/numerical-semantics.md` already requires that "the zero sign follows the resolved signed-zero and subnormal contract rather than an ambient target mode." A flush-to-zero behaviour that does not state which zero it produces cannot be checked against that hardware and cannot be reference-evaluated. Whether the sign is carried as a field of the flush behaviour or resolved from the contract's signed-zero dimension is an implementation choice for the IR ticket; leaving it unstated is not.

**Consequence — widening is a semantic change to identity, not only to a vocabulary.** Because `SubnormalMode` had one variant when this record was accepted, the identity encodings and the feasibility predicate could omit or collapse it without observable loss. Adding the second variant makes every omission observable at once. Item 6 states the obligation that falls out of this, and the two landed together in `1f78223` for exactly this reason.

### 2. Selection: the resolved contract is a required compile input with no default

**Proposal.** The resolved numerical contract is a required, typed input at the compilation-request boundary. It has no `Default`, no ambient fallback, and no implicit strictest reading. A request that does not state it does not compile, and the diagnostic says the contract is unstated rather than naming a dimension.

**Why refusal rather than a strict default.** A strict default is the safe direction for results, and it is the wrong direction for this contract, for a reason the measurements make concrete: on the measured Apple row a strict default is *unhonourable*, so defaulting to it would make every Apple compilation fail with a rejection the caller never asked for, and the fix a caller would reach for is to discover the contract knob by reading a rejection. That is the same failure the whole numerical contract is written against — `docs/numerical-semantics.md` avoids an overlapping `fast_math` boolean, refuses ambient promotion tables, and states that "no conversion inherits ambient frontend, compiler, or device defaults." A required input makes the caller's numerical intent visible in the request, which is where an explain trace and an artifact record can attribute it. `MetalTargetFacts` sets the in-repo precedent and documents its reasoning: it "deliberately provides no `Default`: a caller states the language standard, artifact family, deployment minimum, launch-index realization, and binding capacity it is emitting for."

**What a caller may state.** One resolved contract, or an explicitly ordered preference list of contracts the caller declares equally acceptable. When a list is given, resolution is by the caller's stated order and the first honourable entry wins; it is deterministic, recorded, and never cost-ranked. A single-entry list and a bare contract behave identically, so the list is an additive generalization rather than a second mechanism. **This is the only place where anything resembling selection occurs, and the choice is the caller's, stated before compilation, not the planner's.**

**Fact — this shapes a surface that does not exist yet.** `CompilationRequest` and `pipeline::compile` are both `pub(crate)` with a `#[cfg(test)]` constructor, so this decides the shape of a boundary before it is public rather than changing a published one. Under ADR 0075 that boundary is Tom's to review when it is promoted; this record states what it should express, not that it may be promoted.

### 3. Target capability declaration: a per-dimension honourability report, not a boolean axis

**Proposal.** A target profile declares, for each dimension of the numerical contract it can be asked about, which behaviours it honours and *by what means*, using the four outcomes `docs/numerical-semantics.md` already names: honoured exactly by the target's own arithmetic; honoured by exact emulation the backend emits; honoured only under a relaxation the contract has already authorized; or unhonourable. The declaration is a stated, versioned profile fact with the same provenance discipline `CapabilityFact` already carries — an availability phase, a validity scope, an authority, and the declaring profile's identity — so a rejection can name where the fact came from. The validity scope must additionally identify **which compiler build and which execution environment** the declared behaviour was measured on. One Apple host resolves an offline compiler from the Xcode toolchain asset and a separate runtime compiler per execution environment — three distinct builds on the one machine the [numerical behaviour record](../research/apple-targets/numerical-behaviour.md) qualifies, which owns the measurement — and they version independently, the runtime one with the OS build or the simulator runtime and the offline one with Xcode. A target fact that names only "Metal on Apple silicon" therefore names no compiler at all, and a profile that declares honourability without naming one has not stated a versioned fact.

**Proposal — this is a distinct authority from `CapabilityAxis`, and it composes into ADR 0043 rather than joining it.** `CapabilityAxis` is a quantitative space: a `u64` bound, a `Quantity` unit, and an `AtMost`/`Exact`/`Implies` relation. Numerical honourability is not a quantity, and the decisive point is that `SupportedWithExactEmulation` has no representation as a bound comparison — emulation is honoured by *emitting different operations*, so it changes the program rather than the verdict, and any encoding as a satisfied `Implies` predicate discards exactly the outcome that carries work. The composition is stated rather than left implicit: a dimension honoured exactly or by emulation contributes a satisfied hard predicate; a dimension honourable only under a relaxation the caller's stated contract does not authorize contributes a *disproved* predicate, not a deferred or unknown one, because the caller's authorization is known at `CompileProfile` and cannot arrive later; a dimension the profile declares unhonourable contributes a disproved predicate; and a dimension the profile does not speak to at all contributes `Unknown` in ADR 0043's exact sense — no admissible proof path — and therefore may appear in search and explain state but never in an executable frontier. That last clause is what makes an unenumerated dimension fail closed instead of defaulting to honoured.

**Proposal — retire the boolean.** `supports_strict_f32` and `CapabilityAxis::StrictF32Arithmetic` are replaced rather than extended. A boolean cannot say which dimension failed, cannot express emulation, and — as established above — is today wired to a requirement predicate that omits the subnormal dimensions entirely, so extending it would preserve a defect. The requirement side (`derive_requirements`) stops deriving one summary bit and instead carries the region's declared realization forward per dimension.

**What this buys, stated plainly.** A profile that declares `f32` arithmetic flush-to-zero as its honoured behaviour, and preservation as unhonourable, makes a flush-tolerant contract *compile* on that target with a positive conformance claim, and makes a preserving contract reject with a named cause. Both outcomes are the feasibility authority working correctly. The change is not that feasibility became permissive; it is that the caller can now express a contract the target honours, which is what was missing.

### 4. Artifact record: the delivered realization is recorded, never inferred

**Proposal.** A produced artifact carries a first-class record of the numerical realization actually delivered: the resolved contract, complete over every dimension, with each dimension's means of honouring it, together with the target facts relied on and the identity of the profile that declared them. A consumer comparing generated output against a CPU reference reads this record. It does not reconstruct it from the request, from the selected compiler flags, or from the target's name.

**Proposal — the record inherits item 3's compiler-and-environment requirement.** The target facts this record carries are the ones item 3 governs, so each arrives already naming the compiler build and execution environment it was measured on, and the artifact record carries that identification rather than discarding it. This is not an additional obligation but the consequence of the one item 3 states: a record naming a delivered realization without naming the compiler that produced it is not *readable* in the sense this item requires, because a reader cannot tell whether the realization it names was established on the compiler that actually built these bytes.

**Measurement — why flags cannot substitute.** Under `-fmetal-math-mode=relaxed` the emitted module records `!"air.compile.fast_math_disable"` while every floating-point operation in it carries a fast-math licence set — `reassoc nsz arcp afn` at `-ffp-contract=off` and `=on`, and `reassoc nsz arcp contract afn` at `=fast`. Only `fast` emits `air.compile.fast_math_enable`, so the divergence is `relaxed`'s and it is present at every contraction setting. The module-level flag is therefore not a faithful summary of the licences actually applied, and an artifact-side reader that inferred the delivered realization from it would read the opposite of the truth. `docs/artifact-abi.md` already puts the numerical contract and the exact flags into artifact *identity*, which is what makes two artifacts distinguishable; this record adds the separate obligation that the realization be *readable*, because a digest a consumer can compare is not a statement a consumer can act on.

**Consequence — the record's content is fixed by the honesty rule.** Because item 5 forbids delivering anything other than the declared contract, the delivered realization always equals the declared one for any artifact that exists. The record is therefore not a channel for reporting a downgrade — there are none — but the evidence that no downgrade occurred, together with the means by which each dimension was honoured, which the caller cannot derive and which changes what a reference comparison should expect from an emulated dimension.

### 5. The honesty rule, stated in both directions

**Proposal.** `docs/numerical-semantics.md` already states one direction: "target defaults such as TF32 input precision, reduced-precision accumulation, floating-point contraction, flush-to-zero, or conversion rounding cannot expand the program's permissions." The converse is not stated anywhere and is added here: **no authority may narrow, weaken, or substitute the caller's stated numerical contract in order to make a target feasible.** When no contract the caller stated is honourable on a target, compilation rejects with a typed, explainable error naming the dimension, the required behaviour, the behaviour the target declares, the means the profile offers if any, and the declaring profile's versioned identity. It never emits a program under a different contract, never falls back to a target default, and never reports the difference as a cost.

**Consequence — the numerical contract is not a search dimension.** Cost-based selection ranks implementations of one contract. It may never rank contracts against each other, because doing so would price meaning. This follows from ADR 0043's separation of hard feasibility from estimated cost and from `docs/artifact-abi.md`'s existing rule that routing never chooses between different accuracy meanings; it is stated here because the neighbouring temptation — treating a flush-tolerant plan as a cheaper alternative to a preserving one — is exactly the mistake a "select a conformant contract" reading invites.

**Consequence — one contract per program, as today.** A caller's ordered preference list resolves to exactly one contract before planning begins. It does not become a per-region choice, and two regions of one program never honour different contracts.

### 6. Identity: the realization's encoding must be complete and must fail closed

**Proposal.** The numerical realization's canonical identity encoding is complete over its fields at every layer that commits to it, and each field is encoded by an exhaustive match over a non-`#[non_exhaustive]` enum so that widening the vocabulary is a build error rather than a silent identity collision. No layer may rely on `profile_key` standing in for the field values it names.

**Fact — the contract does not say the realization is part of that identity, which is why the encoder can omit it, at `6555119`.** `docs/ir.md` states that "`IndexRegion` identity commits only to the canonical structural program: iteration and reduction domains, typed tensor boundaries, access maps, scalar operations and values, constraints, and ordered outputs", and its layered summary reads "`IndexRegion` commits to canonical iteration/scalar/access content." The numerical realization appears in neither enumeration, even though the implemented `IndexRegion` carries a `numerical: NumericalRealization` field and its encoder partially encodes it — and even though `ScalarProgram`'s own variants separately carry the canonical NaN bits and a contraction flag, so part of the realization is inside "scalar content" while the region-level declaration is outside it. The contract and the implementation therefore disagree about where the realization sits in the identity layering, and the scheduled-region encoder's incompleteness is what that disagreement looks like in code. Item 6 requires the IR contract to state the answer, not only the encoder to be repaired.

**Evidence refresh 2026-07-24 — the contract states the answer, so both quotations above are of superseded text.** `1f78223` extended `docs/ir.md`'s enumeration to "constraints, ordered outputs, and the region's declared numerical realization", and its layered summary to "`IndexRegion` commits to canonical iteration/scalar/access content and to its declared numerical realization, complete over every dimension." The contract now also states why the realization is *inside* the structural program rather than beside it — it says what the region's scalar operations mean, so two regions differing only in subnormal, contraction, or reassociation resolution compute different values and must not share identity — that the encoding is complete over every dimension and exhaustive per dimension, and, in the words item 6 asked for, that "no layer may encode the realization's contract key in place of the field values that key names, and no layer may substitute a derived predicate for the field it was derived from; a key and a predicate are both projections, and a projection cannot fail closed when its source grows." It further records that a scalar operation's own numerical fields are a refinement the structural verifier requires to agree with the region-level declaration, so encoding both is one authority checked rather than two.

**Why this is in the decision and not left to the implementer.** Widening `SubnormalMode` is the single change that converts this omission from unobservable to a correctness defect, so the two must land together. A widened enum with the current scheduled-region encoder would give two semantically different regions one identity, which is a cache-and-artifact correctness failure of exactly the class `AGENTS.md` singles out for special scrutiny, and it would compile without a warning. Deciding it later would mean deciding it after a cache had already been populated under the ambiguous encoding.

## Consequences

- A real target becomes conformant by declaring what it honours, and a caller reaches it by stating a contract that matches. Neither party gains the ability to change what the other meant.
- A rejection stops being `strict-f32: required 1, available 0` and becomes a named dimension, a named required behaviour, a named target behaviour, and a declaring profile identity. That is the explainability `AGENTS.md` requires of a rejected feasibility decision and it is not available from a boolean axis.
- The reference-comparison rule in `docs/correctness-and-testing.md` needs no change. It says the comparison "follows the declared numerical contract and conformance level", and item 5 guarantees that any artifact which exists honours its declared contract, so declared and delivered never diverge and the oracle rule stands as written. This is the reason that contract is not in `applies_to`.
- An unenumerated dimension fails closed as `Unknown` rather than defaulting to honoured, so adding a dimension to the contract cannot silently admit plans on profiles that have not been updated to speak about it.
- Emulation becomes expressible, which means a dimension a target lacks natively can still be honoured by emitted operations at a cost the cost model may price. The cost is priced; the contract is not.
- The measured Apple row gains a positive conformance story for the first time: a flush-tolerant `f32` contract compiles and conforms, and a preserving one rejects with a cause. The current backend-local `MetalNumericalGap` is subsumed by the profile declaration and the typed rejection, and the four goldens can carry a contract the hardware actually honours instead of one it cannot.
- Four crates change and none of the changes is independently shippable, because widening the vocabulary without the identity encoding is a correctness defect and widening it without the profile declaration leaves the new variant unreachable. The follow-up tickets are ordered, not parallel.
- Nothing here makes the compiler more permissive about *unknown* numerical behaviour. Every added expressiveness is a stated behaviour with a stated means and a stated declarer.

## Implementation boundary

**This record changed nothing operative when it was accepted, and one of its four tickets has since landed.** `implementation_status` is `partial`, and it describes the decided behaviour rather than this document: the vocabulary expresses more than one behaviour per dimension, the scheduled-region identity encoding is complete and exhaustive, and `docs/ir.md` states item 6's rule normatively — while items 2, 3, 4, and 5 are stated in no governed contract, no target profile declares per-dimension honourability, no artifact records a delivered realization, and the request boundary is still crate-private. The four tickets follow acceptance in dependency order, so each inherits a concrete answer rather than re-deriving one.

1. **`tiler-ir` — vocabulary and identity, together. Done 2026-07-24 in `1f78223` (`widen-numerical-vocabulary-and-complete-identity`).** Widen `SubnormalMode` and `NumericalPermission` to the behaviours ADR 0019 and ADR 0011 accept; keep `NumericalRealization`'s input and result fields independent; decide and state where the flushed zero's sign lives. In the same change, make `schedule::model::push_numerical` complete over every field and exhaustive per field, matching `kernel::model::push_numerical`, and update whatever scheduled-region identity fixtures that shifts. Also stop `derive_requirements` from collapsing the realization into one `requires_strict_f32` bit. Items 1 and 6. **As landed:** `SubnormalMode` is `Preserve | FlushToZero { zero_sign }` over `FlushedZeroSign::{PreservesSign, AlwaysPositive}` and `NumericalPermission` is `Forbidden | Permitted`; the two subnormal dimensions stayed independent; and the open sign question was settled the first of the two ways this item allowed — the sign is a field of the flush behaviour, not a resolution against the contract's signed-zero dimension, on the reasoning that a permission may leave a zero's sign unspecified and an unspecified flush result is exactly the under-specification item 1 forbids, so every `SubnormalMode` value answers "which zero" alone. That placement is a divergence from ADR 0019's sentence that "zero-sign behavior is resolved with the signed-zero contract"; this record refines ADR 0019 and item 1 authorized either placement, but ADR 0019 has not been updated to record which one was taken, and `reconcile-adr-0019-zero-sign-placement-with-the-landed-flush` owns closing that. **Deliberately not done here:** the `StrictF32Arithmetic` axis survives, with its summary boolean moved to `tiler_compiler::physical::requires_strict_f32` as an exhaustively matched disjunction, because retiring the axis is ticket 2's.
2. **`tiler-compiler` — selection and the composed feasibility decision.** Make the resolved contract a required typed request input with no `Default` and a distinct unstated-contract diagnostic; accept an ordered caller preference list resolved deterministically by stated order; add the per-dimension honourability authority as a peer of `feasibility::CheckedTargetProfile` rather than as new `CapabilityAxis` variants; implement the stated composition into `Proven`/`Rejected`/`Unknown`, including the unenumerated-dimension `Unknown` path; retire `PrototypeTargetProfile::supports_strict_f32` and `CapabilityAxis::StrictF32Arithmetic`; and give `explain` the rejection shape item 5 requires. Items 2, 3, and 5.
3. **`tiler-metal` — the profile declaration.** Express `MetalSubnormalArithmetic` as a per-dimension honourability declaration in the shared form rather than a backend-local target fact, so the compiler can assess it before emission; retire `MetalNumericalGap` and `require_declared_realization` in favour of the typed rejection, or state precisely why a backend-local conformance step survives alongside it. Keep the measurements recorded on the declaring types. Item 3.
4. **`tiler-artifact` — the delivered-realization record.** The crate is a four-line shell at `6555119`, so this ticket creates the first content in it and its public surface is a new namespace under ADR 0075 and therefore Tom's to review. It owns the readable delivered-realization record: the contract complete over its dimensions, each dimension's means, the target facts relied on, and the declaring profile identity. Item 4. **Evidence refresh 2026-07-24 — the crate is no longer a shell, and this ticket's remit narrowed accordingly.** `tiler-artifact` now carries an artifact-program model and a bounded neutral envelope codec, and that codec already encodes the resolved contract complete over its dimensions — `NumericalFacts` and `ResourceRequirements` both write all four dimensions through exhaustive tag maps. What item 4 still owns is everything the contract's *values* do not supply: each dimension's means of being honoured, the target facts relied on, and the declaring profile's identity. None of that exists, because none of it can before ticket 3 declares it.

## Open questions

These are recorded unresolved on purpose. None is settled by this record.

- **Whether `applies_to` names the right destinations for items 3 and 4.** `tiler.contract.numerical-semantics` is unambiguous: items 1, 2, 5, and the honourability vocabulary all change what it states. `tiler.contract.ir` is unambiguous for item 6, though for the opposite reason to the obvious one — that contract's identity enumerations omit the numerical realization entirely, so item 6 requires it to gain a sentence rather than to have one corrected. The other two are weaker edges and are stated as such. `tiler.contract.metal-backend` currently records the strict flag row and says the compatibility probe "did not observe the numerical behavior these flags request"; this record's measurement closes that gap in one direction, so the contract must record that the strict row does not deliver subnormal preservation — but whether the profile *declaration* mechanism belongs in that document or in the architecture contract is not settled. `tiler.contract.artifact-abi` already puts the numerical contract into artifact identity, and item 4 adds a readable record; whether that record's schema is an envelope concern or belongs with the ABI is likewise not settled. Neither weak edge should be read as a claim that the named document will state the whole item.
- **Whether a caller's ordered preference list is the right shape, or one contract plus an explicit retry is.** The list keeps resolution inside one compilation and makes the caller's ranking part of the request, which is what an explain trace and an artifact record can attribute. The alternative — one contract per request, with the caller re-requesting on rejection — is strictly simpler and keeps the boundary smaller, at the price of making the caller's fallback intent invisible to the compiler and unrecorded in the artifact. This record chooses the list because the intent is worth recording, but the alternative has not been rejected on evidence and the choice is reversible before the boundary is public.
- **Whether `SupportedOnlyUnderDeclaredRelaxation` earns its place in the implemented subset.** It is one of the four outcomes `docs/numerical-semantics.md` names, and the composition above maps it to a disproved predicate whenever the caller has not authorized the relaxation — which makes it behave identically to `Unsupported` for every unauthorized case and identically to `SupportedExactly` for every authorized one. Whether it therefore needs to be a distinct outcome in the implemented profile, or whether the distinction is only an explain-trace refinement, is not settled.
- **Whether the measured "kernel performs `f32` arithmetic" condition is the right gate.** `record_subnormal_obligation` fires per emitted `f32` arithmetic statement, derived from the operation vocabulary. The measurement above shows that the compiler may fold that arithmetic away — `x * 1.0` retains zero floating-point operations at `-O2` under every math mode — so a source-level arithmetic predicate over-reports the flush relative to what executes. Over-reporting is the fail-closed direction and is the right default. Whether an honourability model should ever be permitted to reason about post-optimization arithmetic, and what evidence class such reasoning would have, is unowned. The `-O0` refinement above sharpens what that evidence class would have to be rather than supplying it: the emitted IR is not a sufficient basis, because arithmetic that survives into it may still not execute, so any such reasoning would need a dispatched execution witness on the exact toolchain row — evidence a plan-time authority cannot obtain by asking the compiler. That makes the question harder, not closer to settled. **Added 2026-07-25:** folding is not the only way the executed operation departs from the written one, and the second way is not fail-closed in the same direction. Findings 15 and 16 measure the driver rewriting a written power-of-two division into a single `fmul` under the strictest offline selection, and emitting a written `fma` fused at every contraction setting. For the subnormal dimension the over-reporting direction survives both, because a substituted operation is still `f32` arithmetic that flushes. For a dimension whose obligation is operation-specific it does not, since a predicate over the written vocabulary would classify a substituted operation by a form the device never executed. Any post-optimization reasoning would therefore have to establish *which operation ran*, not only that some arithmetic ran.
- **Whether coupled target modes need an expressible declaration.** `docs/numerical-semantics.md` observes that "some targets expose only a coupled mode", and ADR 0019 forbids a coupled backend switch from coupling Tiler's semantic permissions. Item 1 keeps the semantic dimensions independent, but a profile declaring a target whose two subnormal dimensions cannot be set independently has no way to say so beyond declaring each dimension's honoured behaviour separately, which happens to express the coupling correctly for the measured Apple row (both flush) and would not for a target that couples them at a settable value. No such target is measured.

## Alternatives considered

**Scope the record to subnormals only.** Defensible, and rejected on the three grounds in item 0. The strongest form of the argument for it is that only subnormals have a measured unhonourable target, so a general mechanism is partly unevidenced. The answer is that the mechanism questions are dimension-independent while only the *claim* of unhonourability is dimension-specific, and item 0 draws that line explicitly rather than letting generality imply measured coverage.

**Add per-dimension boolean `CapabilityAxis` variants instead of a separate authority.** This is the smallest change that would let a rejection name the dimension, and it reuses machinery that is already wired, canonical, and tested. It is rejected because it cannot express `SupportedWithExactEmulation`: an emulated dimension would encode as a satisfied `Implies` predicate indistinguishable from native support, discarding the fact that the backend must emit different operations. A boolean axis space can report *whether* an obligation is met and not *by what means*, and the means is what the artifact record and the cost model both need. This alternative would be right if emulation were dropped from the model, which would mean superseding a sentence of `docs/numerical-semantics.md` rather than implementing it.

**Default the contract to the strictest reading when a caller states nothing.** Rejected in item 2. It is the safe direction for results and the wrong direction here, because on the measured Apple row the strictest reading is unhonourable, so the default would make the common case fail and would teach callers about the contract through rejections.

**Let the planner choose the strongest contract the target honours.** This is the reading the originating ticket's "feasibility selects" wording most naturally supports, and it is the most attractive alternative because it makes every target work with no caller change. It is rejected because it makes a target's limitation redefine what the program means, which contradicts the ticket's own stated architectural line, `docs/artifact-abi.md`'s existing rule that routing never chooses between accuracy meanings, and the separation of hard feasibility from cost. It also silently changes results between targets for one unchanged program, which is the failure mode the whole numerical contract exists to prevent.

**Keep the backend-local gap and reject at the Metal conformance step.** This is the implemented interim behaviour and it is honest as far as it reaches: the gap is in the typed record, in the generated source header, and in the crate documentation, and `require_declared_realization` fails closed. It is insufficient as a durable answer because no caller can express a contract the target honours, so the only reachable outcomes on Apple are a refused conformance claim or a caller that never asks; the gap names no profile identity and cannot distinguish input from result flushing; and the decision belongs to the numerical contract rather than to one backend, which the ticket that implemented it said explicitly.

**Record the delivered realization only in artifact identity, as today.** `docs/artifact-abi.md` already puts the numerical contract and the exact flags into the identity digest, which is enough to distinguish two artifacts. It is not enough for a consumer deciding what a reference comparison should expect, because a digest is comparable and not readable, and the measured `relaxed` case shows that the nearest readable proxy — the module's own fast-math flag — states the opposite of the licences actually applied.
