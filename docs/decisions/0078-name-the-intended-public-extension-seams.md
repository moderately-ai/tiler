**Status:** accepted on 2026-07-25. The decision is unchanged from the proposed text and nothing was amended at acceptance. ## Decision

### 1. A seam is a propose-then-re-verify boundary, and that is the whole of its trust model

**Proposal.** A Tiler extension seam lets a provider *propose* work and lets Tiler *re-derive* every fact the proposal would otherwise assert. A provider is trusted to be deterministic, side-effect-free, and in-process; it is never believed. Concretely, a seam must satisfy all four of the following, and a surface that cannot is not a seam:

- **The provider's output re-enters the ordinary checked path.** `frontier::enumerate_frontier` resubmits every `ProposalBody::ScheduledKernel` through `physical::verify_schedule_with_feasibility`, which runs whole-region intrinsic verification, the request-subject binding, and the hard-feasibility decision before admission. A lowering provider emits only through the canonical `IndexRegionBuilder` wrapped by `IndexAccessLoweringContext`, never receiving the raw builder or region finalization, and `legality::refine_index_region` then proves the emitted region realizes the occurrence.
- **The provider cannot stamp its own provenance.** A physical proposal declares a body, a target-applicability predicate, and a cost estimate, and nothing else. The frontier stamps provider identity from the calling provider, derives the exact resource requirements from the verified region, and derives the boundary contract from the region's accesses — so a proposal can neither forge another provider nor declare resources a verifier did not compute.
- **Its identity is versioned and separated per ADR 0072.** Every seam keys on a `ProviderIdentity` carrying a nonzero output-affecting revision, and provenance stays outside graph meaning.
- **Every disposition is explainable.** Admission, rejection, ambiguity, absence, and an exhausted proof budget are each distinct typed outcomes that reach the explain trace.

**Why this is the governing rule rather than a list of nice properties.** It is what makes a public seam affordable at all. A boundary whose claims Tiler re-derives can be opened to third parties without Tiler inheriting their correctness; a boundary whose claims Tiler must take on faith cannot, whatever its visibility keyword says.

### 3. What a seam is not

**Proposal.** The negative space below is normative. Each item is a property a seam must *keep*, not an accident of the bounded profile, and each is realized today.

**Offering nothing is a legitimate local result, not an error and not a licence to approximate.** `PhysicalImplementationProvider::propose` returning an empty vector means the provider offers no implementation for this region and target; `GovernedPhysicalProvider` does exactly that for any member set it does not recognize. `enumerate_frontier` then returns `Ok` with an empty admitted set, and a cover no provider can implement is reported by complete-plan selection as an unimplemented region. Three outcomes stay distinct: no offer, a typed rejection, and a `FrontierError` compiler fault. A provider that emits structurally invalid IR fails the whole enumeration closed, because malformed compiler output is a bug and must not be silently dropped into the empty-frontier case that looks just like it.

**A resolved provider's claim is re-derived, never inherited.** Resolution selects an authority; it establishes nothing about the work that authority emits. `capability`'s own module documentation draws this boundary — the registry "resolves available lowering knowledge" and "does not prove that a resolved provider's emitted index work actually refines the semantic occurrence". A well-formed region that does not realize its occurrence is a genuine rejection (`LoweringError::Refine`), precisely because the artifact plan names the resolved provider as the occurrence's lowering authority and that claim has to be true.

**An unenumerated capability fails closed as `Unknown`; it never defaults to supported.** `FusionNumericalCapabilities::classify` returns an `Option`, and an operation family with no registered fusion role yields `FusionLegality::Unknown` rather than an approximated accept. `FusionEvidenceClass` keeps `NormativeGuarantee`, `SoundProof`, `ExhaustiveFinite`, `Empirical`, and `Unknown` as five distinct classes that are never collapsed, with the last two carrying an explicit reservation note so a future finite-domain or measured discharge declares itself honestly.

**An absent capability and a contended one are different findings, and neither is a preference.** `LoweringError::is_missing` exists to keep them apart: absence says the installed authority was never extended to this occurrence, contention says two extensions contradict each other. `contended_lowering_capabilities_fail_closed_with_a_distinct_error` asserts that a contended occurrence records the resolution rule at `ExplainDisposition::RejectedIntrinsic` and — explicitly — *not* at `DeferredUnsupported`. There is no last-wins, no priority order, and no preferred provider.

**An exhausted analysis budget is an `Unknown` gap, not a rejection and not an admission.** When the exhaustive access proof cannot afford a region, `lowering::refine` records a typed `RefinementBudgetStop` naming the resource, its limit, and the required amount, and the plan stands: nothing about the emitted region was disproved, the analysis simply stopped. `proof_budget_stop` returns the stop only when it is the *sole* diagnostic, so a budget stop can never hide a real refusal behind an exhausted analysis.

**Correction — 2026-08-08, current evidence under ADR 0109's narrow supersession.** The retired `RefinementBudgetStop` and `proof_budget_stop` names above remain historical. At `a17884b0`, `fn proof_budget_stop` accepted a nonempty population whose rows were all `IndexRegionDiagnostic::ProofResourceLimit`, returned `None` when any row belonged to another diagnostic class, and retained the first stop when several resource-limit rows were present; the historical “sole diagnostic” wording therefore meant sole diagnostic class, not cardinality one. Current `pub fn complete` on `ResolvedIndexRealization` creates one `IndexDomainProofLedger` for the whole realization; `fn fill_unassessed` assigns an `IndexDomainUnknownReason::ResourceLimit` claim to obligations not reached after exhaustion, while `fn retain_complete_assessments` retains every produced assessment and selects an assessed `IndexDomainProofRefusalKind::Disproved` before `IndexDomainProofRefusalKind::Unknown`. The compiler's `pub(crate) fn discharge_pending_index_refinement` projects that complete refusal ledger without dropping assessments, `fn refine` in compiler lowering turns it into `LoweringError::SemanticDischarge`, and `pub(super) fn enumerate_complete_plans` returns `lowering_failure` before `enumerate_covers`: `Unknown` becomes `UnsupportedCapability` rather than invalid compiler output, and no executable coverage receipt is minted unless every obligation is proved. The historical diagnostic-class rule does not describe the current atomic ledger: a later unassessed obligation whose domain might contain a counterexample remains `Unknown` rather than being called disproved, but an assessed `Disproved` claim elsewhere in the same ledger takes precedence. `RegionBudgetStop` and `ExplainEvent::BudgetStop` are separate region-formation vocabulary, not index-domain proof claims or executable-refinement receipts. [`repair-adr-0078s-budget-stop-and-unknown-gap-evidence`](../../tickets/repair-adr-0078s-budget-stop-and-unknown-gap-evidence.md) records the complete source audit. **The rule this item states is preserved exactly: proof-budget ResourceLimit is an `Unknown` gap, neither disproof nor admission; ADR 0109 changes the executable boundary, not that classification.**

**Superseded — 2026-08-08, only on the historical `Ok` and “the plan stands” requirement above.** Tom accepted [ADR 0109](0109-fail-closed-before-executable-planning-when-index-domain-proof-is-unknown.md), which preserves ResourceLimit as `Unknown`, neither disproof nor admission, and makes the current proof-bound executable boundary normative: an Unknown refuses before cover enumeration and mints no executable coverage. Completion retains every produced assessment and chooses an assessed `Disproved` claim before any ResourceLimit Unknown. The historical paragraph remains as the rule that exposed the conflict, and the correction records the replacement's current evidence; ADR 0109 supersedes neither this item's Unknown classification nor any other part of this record.

**A provider's revision is provenance, not a version negotiation.** ADR 0072 places provider revisions in admission and selected-plan provenance rather than in graph meaning, and this seam model adds no negotiation on top. **Fact.** `LoweringCapabilityKey` is `{family, operation, signature, provider}`, `ProviderIdentity` is `{namespace, name, revision}` with derived `Eq` and `Ord`, and `FrozenLoweringCapabilityRegistry::resolve` filters candidates on family, operation, and signature only. **Inference.** Two revisions of one provider are therefore two distinct keys that both register successfully and both match one selector, so they resolve as an `AmbiguousCapability` — the same contradiction as two unrelated providers claiming the occurrence. Registering the identical `(family, operation, signature, provider)` twice is a `DuplicateCapability` collision. Neither path lets a newer revision supersede an older one; a capability additionally carries its own `LoweringCapabilityRevision`, distinct from the admitting provider's revision, covering the exact lowering it emits. **Measurement — 2026-07-27.** The two-revision case is now pinned by `capability::tests::two_revisions_of_one_provider_resolve_to_an_ambiguity`, and it measured the inference above rather than restating it: both registrations succeed, resolution returns `AmbiguousCapability`, and the candidates are both identities in canonical ascending order, in either registration order. The test's own coverage claim was also checked — simulating a newer-wins rule inside `resolve` leaves the two sibling ambiguity tests green and fails only this one, so it closes a gap rather than duplicating them.

**The same input can be a contradiction at one seam and an alternative at another, and that asymmetry is deliberate.** Two providers claiming one occurrence is an unresolvable ambiguity in the lowering registry, because exactly one authority may define how an occurrence lowers. Two providers proposing an implementation of one region is an additive alternative in the frontier, retained side by side and separated by their folded provenance in `ImplementationProposalIdentity`, because a region may legitimately have several correct implementations that later selection chooses between on cost. A reader must not generalize either rule to the other seam.

**A reservation is not a capability.** `ProposalBody`'s `KernelSubprogram`, `OpaqueCall`, and `View` variants carry a `ReservedProposalSeam` holding an uninterpreted `&'static str` that is echoed into the rejection diagnostic and read nowhere else. They exist so an unsupported body rejects explicitly as `FrontierRejection::UnsupportedVariant` instead of being approximated by the nearest thing the bounded profile can emit. The real opaque-call contract — typed ABI, effect, aliasing, placement, and evidence boundaries — is owned by [`implement-opaque-physical-call-providers`](../../tickets/implement-opaque-physical-call-providers.md) and does not exist. Describing these variants as opaque-call support would be the single most likely misreading of the frontier, and it is wrong.

**Correction — 2026-07-31.** Two of those three variants are no longer reservations, and the paragraph is corrected rather than rewritten because the rule it states is what generalizes and the inventory is what dated. `View` is the only body still carrying a `ReservedProposalSeam` and rejecting as `UnsupportedVariant`. [`enumerate-the-split-reduction-on-the-planning-frontier`](../../tickets/enumerate-the-split-reduction-on-the-planning-frontier.md) gave `KernelSubprogram` an ordered chain of stages, each re-entering the same checked verification a single scheduled kernel does, because a scheduled kernel is one region and therefore one dispatch and a split reduction had no spelling on the frontier at all. ### 6. What is permanently internal

**Proposal.** These are authorities Tiler owns outright, free to change shape without a participation story: region formation, cover enumeration, fusion legality *derivation*, plan selection, feasibility assessment, normalization, request verification, the pipeline itself, and the governed provider set. Each decides something about a program that no provider is positioned to know, and none of them takes a proposal.

Two qualifications keep this from over-claiming. **Explain** is internal as an authority and public as an obligation: nobody registers an explain provider, and ADR 0073 nonetheless makes typed explain output a contract every stage must speak, including the seams above. **Feasibility** is internal as a decision procedure, but the target profiles it consumes are typed data whose ownership is exactly the open data-versus-code question in item 5 — so this record classifies the procedure and deliberately not the data.

## Consequences

- Promotion becomes a scheduled act with a written intent behind it. A ticket that promotes a surface named in item 2 is applying this record; a ticket that promotes anything in item 6 is contradicting it and needs a superseding decision.
- The four rungs stop being rhetorical. "The seam exists" and "an external provider drove it through `compile()`" are now different claims about different rows of one table, and item 4 shows they can differ for the two halves of a single surface.
- Item 3 is the part a future change is most likely to erode, because each of its properties looks like a small conservatism until the case arrives. A default provider, a priority order between contending capabilities, a supported-by-default fallback for an unregistered operation, and a rejection dressed up as a budget stop are each individually reasonable-sounding and each break the guardrail this record is built on.
- Nothing here rests on compatibility, and none of these consequences changes when a surface is later reshaped. They change when Tiler acquires an external consumer, which is the trigger ADR 0075 already names.
- **Historical consequence, since narrowed by ADR 0090.** At acceptance this record deliberately left two seams unassigned, because both turned on evidence no landed component had produced. ADR 0090 later supplied and resolved the physical-provider half; only the mature per-operation fusion capability remains unclassified, under the explicit evidence triggers below.

## Open questions

These questions are retained with their later disposition rather than deleted: the first two were settled by ADR 0090 and the fourth by ADR 0105, while the third remains open with an evaluable trigger.

- **Whether target-specific scheduling knowledge is typed target-profile data or code in backend crates.** This is prior to, and decides, `frontier::PhysicalImplementationProvider`'s visibility. Current evidence leans toward data: caller-authored target profiles now feed feasibility, the bounded Metal numerical adaptation is data projected through `tiler-build`, and `tiler-metal` remains pure structured-KIR-to-MSL lowering downstream of scheduling. That evidence exercises target *facts*, not a backend contribution of scheduling knowledge or an out-of-compiler physical provider, so it does not choose between the two mature participation models. Close the question on the sharpened trigger in item 5 or when a backend first contributes target-specific scheduling knowledge. **This is Tom's.** **Evidence refresh 2026-07-31 — the evidence this question was waiting on now exists, and the question does not close.** Two spikes exercised the architecture from opposite ends: a forkless custom Metal physical provider showed a real specialization that no declared axis expresses, and a bounded scalar CPU vertical carried a second backend end to end wanting profile data and no provider code at all. [ADR 0090](0090-compose-backends-per-responsibility-rather-than-per-backend.md) reads that pair as eliminating both pure positions and decides a checked combination split at feasibility. **Closed 2026-07-31: Tom accepted that record in full**, so this question is answered — profiles declare what a target can do, providers propose what to do with it, the host performs every comparison — and the physical-provider classification proceeds under it. Item 6's permanently-internal feasibility rule is unchanged and is load-bearing in the accepted split.
- **Whether the sharpened trigger in item 5 restates Tom's intent or narrows it.** One sentence from him settles it, and the answer decides whether the physical-provider classification is ripe now or still waiting. **This is Tom's.** **Evidence refresh 2026-07-31, and closure the same day.** [ADR 0090](0090-compose-backends-per-responsibility-rather-than-per-backend.md) carried this question to Tom as one of its three acceptance items, and he answered it at that record's acceptance: the trigger reads as evidence-based rather than literal — the literal wording could only fire after the seam it gates ships — and the two spikes satisfy it, so item 5's deferral is lifted and the classification is ripe. The literal fact stands unchanged for the record: at acceptance, no out-of-crate physical provider had driven `compile()`, because installation did not yet exist.
- **Whether the mature per-operation fusion numerical capability is a registered third-party capability or a projection of the semantic definition.** [The operation-extension contract](../operation-extensions.md) already lists fusion participation among separately versioned optional capabilities, while `FusionNumericalCapabilities` is a compiler-owned table with no registration path and a `ProviderIdentity` used purely for attribution. The tension is real: an extension author genuinely knows whether their operation is an ordered reduction, and a provider *asserting* a numerical permission is a claim the host cannot verify, which is the class of claim ADR 0021 requires proof or runtime validation for. The recommendation, offered rather than adopted, is to derive the role from the reached semantic definition wherever it is derivable and to treat a declared-only role as `Unknown` until an evidence class stronger than a provider assertion supports it. Reconsider when the first registered third-party semantic definition reaches fusion and its numerical role cannot be derived from that definition, or when a stronger evidence class for a declared-only role is admitted; neither trigger has fired, so the recommendation remains unadopted rather than becoming policy by relocation.
- **Whether `ScalarLoweringProvider` should reach the compile path at all.** The family is registered, resolvable, and tested, and `lowering.rs` resolves only `IndexAccess` — an index-access provider emits its own per-point scalar work through the same context. **Answered 2026-08-06 — the affordance reading, and it is now an accepted decision rather than an open question.** [`resolve-or-retire-the-scalar-lowering-provider-seam`](../../tickets/resolve-or-retire-the-scalar-lowering-provider-seam.md) ran the elimination and found that the registered `IndexRealizationLaw` fixes the whole realization including its per-point scalar applications — `verify_sequence` refuses any candidate whose canonical identity differs, and `pipeline::conformance::a_lowering_cannot_replace_the_semantic_providers_realization_law` observes that on the ordinary path — so a scalar provider would have exactly one admissible output, decided elsewhere. It would also have nowhere checked to return it: `legality::refine_index_region` refuses the family by name and no `refine_scalar_*` authority exists, which item 1 of this record makes disqualifying rather than incidental. **This question is therefore closed as answered and reopened as a decision**: [ADR 0105](0105-retire-the-scalar-lowering-provider-seam.md) retires the family and supersedes this record's item-2 row, accepted by Tom on 2026-08-06. The elimination's own reservation is retained: the byte-for-byte law comparison is what makes the output set a singleton, so a future decision to admit semantically equivalent alternate realizations would reopen the question rather than leave it answered.

## Alternatives considered

**Leave the intent implicit, as it was at decision time.** This was the status quo the originating ticket was filed against: the classification would be made at promotion time by whoever held the change, from the sibling modules they happened to read. It is the same failure mode ADR 0074 was written to stop for API shape.

**Classify by the `pub` keyword.** Attractive because it is mechanical. Rejected because the tree contains all four combinations of visible-versus-intended, listed at the end of item 3, so the keyword and the obligation are simply different facts. The durable obligation comes from admitting a provider, not from a module declaration.

**Decide `PhysicalImplementationProvider` now.** Rejected by Tom on 2026-07-24, and the reasoning holds independently: the question that decides it is the data-versus-code architecture question, no backend has exercised that architecture, and guessing buys nothing that the Metal vertical will not supply as evidence.

**Write the negative space into the operation-extension contract instead of an ADR.** Rejected because that contract owns the trust, identity, registration, and diagnostic obligations of a provider — what a seam requires — and this record settles which surfaces *are* seams and at what maturity, which is a decision with alternatives rather than a contract clause. Splitting one classification across a contract and a decision record would create the duplicated authority the documentation contract exists to prevent, and acceptance is Tom's under ADR 0075's trait and namespace categories.

**Assign the two undecided seams by default — read a `pub(crate)` trait as permanently internal, or an extension-shaped trait as intended-public.** Rejected in both directions. The first would silently make ADR 0074's staging rule a classification, so every draft authority would acquire an intent it was never given. The second would commit Tiler to a participation model for a surface whose deciding question is still open, which is exactly the cost ADR 0075 records for a trait: each implementor written against it makes the model harder to see as a choice.
