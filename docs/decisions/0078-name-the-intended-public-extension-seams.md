# 0078: Name the intended public extension seams

**Status:** proposed. Tom accepts; nothing here is operative until he does. This record classifies surfaces and changes no visibility, no signature, and no behaviour. Promoting or demoting any surface named below is separate work that must satisfy [ADR 0074](0074-use-explicit-public-api-conventions.md) and [ADR 0075](0075-scope-public-boundary-approval-by-change-category.md).

## Context

The originating ticket asked which surfaces are *intended* to become public extension seams at maturity and which are permanently internal, because that intent was implicit and was therefore being settled case by case at promotion time — the most expensive moment to settle it. Since the ticket was filed the question stopped being hypothetical: four seams landed, and three of them are now exercised on the ordinary compile path. This record describes what exists rather than speculating about what might.

**Fact — the compile path now runs an extension seam unconditionally.** [`crates/tiler-compiler/src/lowering.rs`](../../crates/tiler-compiler/src/lowering.rs) resolves exactly one `LoweringFamily::IndexAccess` capability for every recognized occurrence through the frozen registry the request carries, and drives the resolved provider through `refine_index_region`. `pipeline::compile` calls it at `crates/tiler-compiler/src/pipeline.rs:827`; there is no shape-recognizer fallback and no default provider. `crates/tiler-compiler/src/governed.rs` registers Tiler's own four families — `tiler.constant-f32`, `tiler.multiply-f32`, `tiler.add-f32`, `tiler.strict-serial-sum-f32` — as ordinary `IndexAccessLoweringProvider` implementations through the same public `LoweringCapabilityRegistryBuilder` an external provider uses.

**Fact — the frontier is additive and Tiler registers through it like anyone else.** [`crates/tiler-compiler/src/frontier.rs`](../../crates/tiler-compiler/src/frontier.rs) enumerates proposals from a list of `PhysicalImplementationProvider`s, retaining several providers' implementations of one region side by side. `GovernedPhysicalProvider` in that same module is an ordinary implementor of the trait, and `pipeline.rs:924` supplies it as a one-element provider array.

**Fact — both halves of the seam were driven end to end by out-of-crate-shaped code.** The `#[cfg(test)] mod conformance` block at the end of `crates/tiler-compiler/src/pipeline.rs` defines `ExternalSemantics`, a `SemanticRegistryProvider` written entirely against `tiler-ir`'s public surface, and builds every fixture program from `SemanticProgramBuilder::try_new(registry.freeze())` rather than `try_standard`, so no governed semantic definition is in scope. `externally_registered_operations_compile_through_the_ordinary_path` compiles such a program through `compile()`. `ExternalMultiplyLowering` is an `IndexAccessLoweringProvider` composed through the public `capability` surface, and `an_externally_registered_lowering_provider_drives_the_compile_path` asserts the artifact plan records `acme/external-multiply-lowering` at provider revision 3 and capability revision 7 as the authority that lowered `tiler.multiply-f32`.

**Fact — the guardrail these seams already satisfy is written down.** `AGENTS.md` states that "extension mechanisms must preserve validation, reference semantics, feasibility, explainability, and versioned identity" and that "'extensible' does not mean unknown behavior is optimizable". Every seam above realizes it the same way, which is the observation this record turns into a rule rather than a coincidence.

**Fact — the live inconsistency the ticket named is still live, and is not a defect.** `crates/tiler-compiler/src/lib.rs` declares exactly two public modules, `capability` and `legality`, and keeps `cover`, `explain`, `feasibility`, `frontier`, `fusion`, `fusion_legality`, `governed`, `lowering`, `normalize`, `physical`, `pipeline`, `program`, `region`, `request`, and `selection` private. `frontier::PhysicalImplementationProvider` is `pub(crate)` while being, by construction, the shape a cross-crate provider implements. ADR 0074's convention 7 is why: an authority stays crate-private until Tom accepts its exact facade, so a `pub(crate)` trait is a staging state and not a statement of intent. What was missing is the statement of intent, which is this record.

## Decision

### 1. A seam is a propose-then-re-verify boundary, and that is the whole of its trust model

**Proposal.** A Tiler extension seam lets a provider *propose* work and lets Tiler *re-derive* every fact the proposal would otherwise assert. A provider is trusted to be deterministic, side-effect-free, and in-process; it is never believed. Concretely, a seam must satisfy all four of the following, and a surface that cannot is not a seam:

- **The provider's output re-enters the ordinary checked path.** `frontier::enumerate_frontier` resubmits every `ProposalBody::ScheduledKernel` through `physical::verify_schedule_with_feasibility`, which runs whole-region intrinsic verification, the request-subject binding, and the hard-feasibility decision before admission. A lowering provider emits only through the canonical `IndexRegionBuilder` wrapped by `IndexAccessLoweringContext`, never receiving the raw builder or region finalization, and `legality::refine_index_region` then proves the emitted region realizes the occurrence.
- **The provider cannot stamp its own provenance.** A physical proposal declares a body, a target-applicability predicate, and a cost estimate, and nothing else. The frontier stamps provider identity from the calling provider, derives the exact resource requirements from the verified region, and derives the boundary contract from the region's accesses — so a proposal can neither forge another provider nor declare resources a verifier did not compute.
- **Its identity is versioned and separated per ADR 0072.** Every seam keys on a `ProviderIdentity` carrying a nonzero output-affecting revision, and provenance stays outside graph meaning.
- **Every disposition is explainable.** Admission, rejection, ambiguity, absence, and an exhausted proof budget are each distinct typed outcomes that reach the explain trace.

**Why this is the governing rule rather than a list of nice properties.** It is what makes a public seam affordable at all. A boundary whose claims Tiler re-derives can be opened to third parties without Tiler inheriting their correctness; a boundary whose claims Tiler must take on faith cannot, whatever its visibility keyword says.

### 2. The seam inventory

**Proposal.** These are the surfaces Tiler intends as public extension seams, with the participation model each is intended to admit at maturity. The maturity rung uses the four claims `AGENTS.md` requires be kept apart — a *type-system reservation*, an *architectural seam*, *implemented support*, and a *tested guarantee* — and names the highest rung the surface has actually reached.

| Surface | Intended participation | Rung reached at `412ceae` |
| --- | --- | --- |
| `tiler_ir::semantic::SemanticRegistryProvider`, with `OperationInferencer` and `ValueTypeInstanceValidator` | Third-party | Tested guarantee: an external provider defines the whole operation set and compiles through `compile()` |
| `tiler_compiler::capability::IndexAccessLoweringProvider` | Third-party | Tested guarantee for emit-and-refine; architectural seam only for out-of-crate *installation* (see item 4) |
| `tiler_compiler::capability::ScalarLoweringProvider` | Third-party | Implemented support: registration and resolution exist and are tested in `capability.rs` and `legality.rs`, and no compile-path caller resolves the family |
| `tiler_reference::{ReferenceRegistryProvider, ReferenceOperation, ReferenceValueValidator}` and `oracle::ScalarReferenceOperation` | Third-party | Implemented support: no production compile-path consumer, because `crates/tiler-compiler/Cargo.toml` takes `tiler-reference` as a development dependency only |
| `tiler_ir::index::ScalarOperationInferencer` | Third-party | Implemented support |
| `frontier::PhysicalImplementationProvider` | Undecided; deliberately deferred (item 5) | Architectural seam: cross-crate-ready by design, `pub(crate)`, with one governed implementor and multi-provider additivity covered by in-module tests |
| Per-operation fusion numerical capability | Undecided (open question below) | Architectural seam: `fusion_legality::FusionNumericalCapabilities` is a compiler-owned keyed lookup with no registration path at all |

**Fact — the reference row's dependency claim.** `crates/tiler-compiler/Cargo.toml` declares `tiler-ir` under `[dependencies]` and `tiler-reference` under `[dev-dependencies]`, and nothing else. The reference seam is therefore reachable from tests and proof executables and from no production compiler stage.

**Fact — the scalar-lowering row's absence claim, stated so it can be refuted in one line.** `grep -rn "resolve_scalar_lowering" crates/` returns sites only in `crates/tiler-compiler/src/capability.rs` and its and `legality.rs`'s test modules; `crates/tiler-compiler/src/lowering.rs`, read in full, calls `resolve_index_access` and nothing else.

### 3. What a seam is not

**Proposal.** The negative space below is normative. Each item is a property a seam must *keep*, not an accident of the bounded profile, and each is realized today.

**Offering nothing is a legitimate local result, not an error and not a licence to approximate.** `PhysicalImplementationProvider::propose` returning an empty vector means the provider offers no implementation for this region and target; `GovernedPhysicalProvider` does exactly that for any member set it does not recognize. `enumerate_frontier` then returns `Ok` with an empty admitted set, and a cover no provider can implement is reported by complete-plan selection as an unimplemented region. Three outcomes stay distinct: no offer, a typed rejection, and a `FrontierError` compiler fault. A provider that emits structurally invalid IR fails the whole enumeration closed, because malformed compiler output is a bug and must not be silently dropped into the empty-frontier case that looks just like it.

**A resolved provider's claim is re-derived, never inherited.** Resolution selects an authority; it establishes nothing about the work that authority emits. `capability`'s own module documentation draws this boundary — the registry "resolves available lowering knowledge" and "does not prove that a resolved provider's emitted index work actually refines the semantic occurrence". A well-formed region that does not realize its occurrence is a genuine rejection (`LoweringError::Refine`), precisely because the artifact plan names the resolved provider as the occurrence's lowering authority and that claim has to be true.

**An unenumerated capability fails closed as `Unknown`; it never defaults to supported.** `FusionNumericalCapabilities::classify` returns an `Option`, and an operation family with no registered fusion role yields `FusionLegality::Unknown` rather than an approximated accept. `FusionEvidenceClass` keeps `NormativeGuarantee`, `SoundProof`, `ExhaustiveFinite`, `Empirical`, and `Unknown` as five distinct classes that are never collapsed, with the last two carrying an explicit reservation note so a future finite-domain or measured discharge declares itself honestly.

**An absent capability and a contended one are different findings, and neither is a preference.** `LoweringError::is_missing` exists to keep them apart: absence says the installed authority was never extended to this occurrence, contention says two extensions contradict each other. `contended_lowering_capabilities_fail_closed_with_a_distinct_error` asserts that a contended occurrence records the resolution rule at `ExplainDisposition::RejectedIntrinsic` and — explicitly — *not* at `DeferredUnsupported`. There is no last-wins, no priority order, and no preferred provider.

**An exhausted analysis budget is an `Unknown` gap, not a rejection and not an admission.** When the exhaustive access proof cannot afford a region, `lowering::refine` records a typed `RefinementBudgetStop` naming the resource, its limit, and the required amount, and the plan stands: nothing about the emitted region was disproved, the analysis simply stopped. `proof_budget_stop` returns the stop only when it is the *sole* diagnostic, so a budget stop can never hide a real refusal behind an exhausted analysis.

**A provider's revision is provenance, not a version negotiation.** ADR 0072 places provider revisions in admission and selected-plan provenance rather than in graph meaning, and this seam model adds no negotiation on top. **Fact.** `LoweringCapabilityKey` is `{family, operation, signature, provider}`, `ProviderIdentity` is `{namespace, name, revision}` with derived `Eq` and `Ord`, and `FrozenLoweringCapabilityRegistry::resolve` filters candidates on family, operation, and signature only. **Inference.** Two revisions of one provider are therefore two distinct keys that both register successfully and both match one selector, so they resolve as an `AmbiguousCapability` — the same contradiction as two unrelated providers claiming the occurrence. Registering the identical `(family, operation, signature, provider)` twice is a `DuplicateCapability` collision. Neither path lets a newer revision supersede an older one; a capability additionally carries its own `LoweringCapabilityRevision`, distinct from the admitting provider's revision, covering the exact lowering it emits. No test pins the two-revision case today; `test-two-revisions-of-one-provider-as-a-capability-ambiguity` owns closing that.

**The same input can be a contradiction at one seam and an alternative at another, and that asymmetry is deliberate.** Two providers claiming one occurrence is an unresolvable ambiguity in the lowering registry, because exactly one authority may define how an occurrence lowers. Two providers proposing an implementation of one region is an additive alternative in the frontier, retained side by side and separated by their folded provenance in `ImplementationProposalIdentity`, because a region may legitimately have several correct implementations that later selection chooses between on cost. A reader must not generalize either rule to the other seam.

**A reservation is not a capability.** `ProposalBody`'s `KernelSubprogram`, `OpaqueCall`, and `View` variants carry a `ReservedProposalSeam` holding an uninterpreted `&'static str` that is echoed into the rejection diagnostic and read nowhere else. They exist so an unsupported body rejects explicitly as `FrontierRejection::UnsupportedVariant` instead of being approximated by the nearest thing the bounded profile can emit. The real opaque-call contract — typed ABI, effect, aliasing, placement, and evidence boundaries — is owned by [`implement-opaque-physical-call-providers`](../../tickets/implement-opaque-physical-call-providers.md) and does not exist. Describing these variants as opaque-call support would be the single most likely misreading of the frontier, and it is wrong.

**A `pub` keyword is neither necessary nor sufficient.** The tree already contains all four combinations, which is why this record classifies by participation model instead. `tiler_compiler::capability` is `pub` while nothing public can install what it builds (item 4). `frontier::PhysicalImplementationProvider` is `pub(crate)` while being cross-crate-ready by design. `tiler_ir::semantic::ValueTypeMarker` is `pub` and openly implementable and confers no authority whatsoever — a frozen registry must separately bind the marker to an admitted resolved type. `tiler_ir::shape::ShapeEvidence` and `tiler_ir::semantic::ShapePredicate` are `pub` and *sealed*, so they cannot be implemented outside the crate at all.

### 4. The lowering seam's registration surface is public and its installation path is not

**Fact.** `crates/tiler-compiler/src/lib.rs` exports no entry point: it declares `pub mod capability` and `pub mod legality`, no `pub use`, and pins `pipeline::compile` behind a compile-time reachability assertion. `request::CompilerCapabilitySnapshot` and `request::CompilationRequest` are `pub(crate)`, as is the `capabilities` field the conformance gate assigns. `governed::governed_index_access_capabilities`, which the gate uses to compose a registry that substitutes one governed family, is likewise crate-private.

**Inference.** An out-of-crate consumer can today build a `FrozenLoweringCapabilityRegistry` through the public `capability` surface and has no public way to install it, to reach `compile`, or to reuse the governed capabilities it would compose beside. The seam is exercised through the ordinary compile path by a provider written against the public surface, from inside the crate. That is a real measurement boundary and this record states it rather than rounding the rung up.

**Proposal.** This asymmetry is convention 7 working as designed and is left as it is. It closes when [`prototype-public-compiler-api`](../../tickets/prototype-public-compiler-api.md) lands the reviewed compiler facade, which is the change that makes installation reachable; until then neither promoting the request path nor demoting `capability` is worth a churn. The open question below records the cost of leaving it.

### 5. The physical-implementation provider stays deferred, with a sharpened trigger

**Fact — this is Tom's decision, taken on 2026-07-24 and recorded in [the originating ticket](../../tickets/draft-public-extension-seam-ownership-adr.md).** He was asked directly about `frontier::PhysicalImplementationProvider` and chose to defer classifying it rather than assign it now. Visibility stays `pub(crate)`, and the design stays cross-crate-ready because it already is.

**The deferral rests on missing information, not on migration cost.** ADR 0075 records that Tiler has no external consumer, sets `version = "0.0.0"` and `publish = false`, and that Tom rejected the compatibility framing outright. There is no asymmetry between promoting and not promoting, so a reader must not reconstruct this deferral as reversibility caution.

**The prior question that actually decides it** is architectural rather than about who writes the code: does target-specific scheduling knowledge live as typed target-profile *data* consumed by in-compiler providers, or as *code* in backend crates? Rust visibility is per-crate, so even a first-party `tiler-metal` implementing providers would force `pub`. It is carried as an open question below rather than answered here.

**Proposal — the trigger, sharpened.** The ticket recorded the trigger as "the first time a backend genuinely needs to contribute a physical implementation, or when the optimizer conformance gate pushes a provider through the ordinary compile path — whichever comes first". **Fact.** The gate has since pushed an external *index-access lowering* provider through `compile()`, and `enumerate_frontier` is still called from exactly one site with exactly one in-crate `GovernedPhysicalProvider`. **Inference.** Read literally the second clause has fired; read against the question it exists to answer — the data-versus-code question above, which a lowering provider does not touch — it has not. This record therefore restates the clause as *a physical implementation provider defined outside `tiler-compiler` reaching `enumerate_frontier` through `compile()`*, which is a check anyone can run. That is a sharpening of Tom's decision, not a reversal of it; if he reads the original clause as already satisfied, the deferral is ripe now and the open question below is the one to answer.

### 6. What is permanently internal

**Proposal.** These are authorities Tiler owns outright, free to change shape without a participation story: region formation, cover enumeration, fusion legality *derivation*, plan selection, feasibility assessment, normalization, request verification, the pipeline itself, and the governed provider set. Each decides something about a program that no provider is positioned to know, and none of them takes a proposal.

Two qualifications keep this from over-claiming. **Explain** is internal as an authority and public as an obligation: nobody registers an explain provider, and ADR 0073 nonetheless makes typed explain output a contract every stage must speak, including the seams above. **Feasibility** is internal as a decision procedure, but the target profiles it consumes are typed data whose ownership is exactly the open data-versus-code question in item 5 — so this record classifies the procedure and deliberately not the data.

## Consequences

- Promotion becomes a scheduled act with a written intent behind it. A ticket that promotes a surface named in item 2 is applying this record; a ticket that promotes anything in item 6 is contradicting it and needs a superseding decision.
- The four rungs stop being rhetorical. "The seam exists" and "an external provider drove it through `compile()`" are now different claims about different rows of one table, and item 4 shows they can differ for the two halves of a single surface.
- Item 3 is the part a future change is most likely to erode, because each of its properties looks like a small conservatism until the case arrives. A default provider, a priority order between contending capabilities, a supported-by-default fallback for an unregistered operation, and a rejection dressed up as a budget stop are each individually reasonable-sounding and each break the guardrail this record is built on.
- Nothing here rests on compatibility, and none of these consequences changes when a surface is later reshaped. They change when Tiler acquires an external consumer, which is the trigger ADR 0075 already names.
- The record deliberately leaves two seams unassigned. That is a smaller claim than assigning them, and it is the honest one: both turn on evidence no landed component has produced.

## Implementation boundary

**This record retrofits nothing.** No visibility changes, no signature changes, no behaviour changes. `implementation_status` is `partial` and describes the decided behaviour rather than this document: the governing principle in item 1 is realized without exception by every seam in item 2, while the classification itself is stated in no governed contract, and items 4 and 5 name two surfaces whose posture is recorded as unresolved rather than implemented.

Propagating an accepted classification into [the operation-extension contract](../operation-extensions.md) and [the architecture contract](../architecture.md) is deliberate follow-up work owned by [`propagate-extension-seam-classification-into-governed-contracts`](../../tickets/propagate-extension-seam-classification-into-governed-contracts.md), conditional on acceptance, so that a proposed ADR never becomes the operative rule by default. That contract already owns the public capability surface and the provider trust, identity, registration, and diagnostic obligations; this record adds the classification and the negative space, and must not restate what that contract states.

## Open questions

These are recorded unresolved on purpose. None is settled here.

- **Whether target-specific scheduling knowledge is typed target-profile data or code in backend crates.** This is prior to, and decides, `frontier::PhysicalImplementationProvider`'s visibility. Current evidence leans toward data — target profiles are already typed data feeding feasibility and the frontier, and `tiler-metal` is scoped as pure structured-KIR-to-MSL lowering, downstream of scheduling — but that is an inference from an architecture no backend has ever exercised, which is why it is not decided. Close it on the sharpened trigger in item 5, or when the Metal vertical answers it empirically. **This is Tom's.**
- **Whether the sharpened trigger in item 5 restates Tom's intent or narrows it.** One sentence from him settles it, and the answer decides whether the physical-provider classification is ripe now or still waiting. **This is Tom's.**
- **Whether the mature per-operation fusion numerical capability is a registered third-party capability or a projection of the semantic definition.** [The operation-extension contract](../operation-extensions.md) already lists fusion participation among separately versioned optional capabilities, while `FusionNumericalCapabilities` is a compiler-owned table with no registration path and a `ProviderIdentity` used purely for attribution. The tension is real: an extension author genuinely knows whether their operation is an ordered reduction, and a provider *asserting* a numerical permission is a claim the host cannot verify, which is the class of claim ADR 0021 requires proof or runtime validation for. The recommendation, offered rather than adopted, is to derive the role from the reached semantic definition wherever it is derivable and to treat a declared-only role as `Unknown` until an evidence class stronger than a provider assertion supports it. No owner is assigned.
- **Whether `capability` should stay `pub` while nothing public can install what it builds.** Item 4 leaves it, on the ground that the asymmetry is temporary and that removing it costs a reviewed boundary for no gain while Tiler is pre-alpha. The cost of leaving it is that a reader of `pub mod capability` would reasonably conclude the seam is usable out of crate, and it is not. Close it when [`prototype-public-compiler-api`](../../tickets/prototype-public-compiler-api.md) lands, which either makes the conclusion true or makes the question moot.
- **Whether `ScalarLoweringProvider` should reach the compile path at all.** The family is registered, resolvable, and tested, and `lowering.rs` resolves only `IndexAccess` — an index-access provider emits its own per-point scalar work through the same context. Whether the scalar family is a second seam a program reaches, or a decomposition affordance an index-access provider may delegate to, is not decided by its existence. No owner is assigned.

## Alternatives considered

**Leave the intent implicit, as today.** This is the status quo and it is what the originating ticket was filed against: the classification then gets made at promotion time by whoever is holding the change, from the sibling modules they happened to read. It is the same failure mode ADR 0074 was written to stop for API shape.

**Classify by the `pub` keyword.** Attractive because it is mechanical. Rejected because the tree contains all four combinations of visible-versus-intended, listed at the end of item 3, so the keyword and the obligation are simply different facts. The durable obligation comes from admitting a provider, not from a module declaration.

**Decide `PhysicalImplementationProvider` now.** Rejected by Tom on 2026-07-24, and the reasoning holds independently: the question that decides it is the data-versus-code architecture question, no backend has exercised that architecture, and guessing buys nothing that the Metal vertical will not supply as evidence.

**Write the negative space into the operation-extension contract instead of an ADR.** Rejected because that contract owns the trust, identity, registration, and diagnostic obligations of a provider — what a seam requires — and this record settles which surfaces *are* seams and at what maturity, which is a decision with alternatives rather than a contract clause. Splitting one classification across a contract and a decision record would create the duplicated authority the documentation contract exists to prevent, and acceptance is Tom's under ADR 0075's trait and namespace categories.

**Assign the two undecided seams by default — read a `pub(crate)` trait as permanently internal, or an extension-shaped trait as intended-public.** Rejected in both directions. The first would silently make ADR 0074's staging rule a classification, so every draft authority would acquire an intent it was never given. The second would commit Tiler to a participation model for a surface whose deciding question is still open, which is exactly the cost ADR 0075 records for a trait: each implementor written against it makes the model harder to see as a choice.
