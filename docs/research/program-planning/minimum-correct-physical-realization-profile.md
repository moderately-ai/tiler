# Minimum correct physical realization profile

- **Status:** research complete; nothing here is accepted, and no row registers or schedules anything.
- **Ticket:** [`define-the-minimum-correct-physical-realization-profile`](../../../tickets/define-the-minimum-correct-physical-realization-profile.md).
- **Research date:** 2026-08-04, against the tree at `57474a09`.
- **Evidence boundary:** every `Fact` below is inspected source at that revision, with the exact check stated so a reader can refute it in one line. No measurement was taken, no program was compiled for this record, and no claim here is evidence that any component behaves as specified — the specification is what a component must guarantee, not a report that one does.

## What this record is for

The compiler has two independent kinds of physical competence, and the project has been building the second without ever writing down the first. The second is *optimization*: fusion, tiling, split and tree reductions, cover search, cost-based selection. The first is the one every optimization is measured against — **a deliberately simple, valid physical route that exists for any program the semantic layer admits, so that a program without a fast path still compiles rather than failing.** This record defines that first competence: what it must cover, what it may refuse, and what each stage of the pipeline owes it.

The distinction matters because the two fail differently. A missing optimization costs performance and is visible as a slower program. A missing baseline costs *compilation*, and today it costs it silently: a cover the general search legitimately enumerated is dropped because nothing proposed an implementation for it, and the trace a caller reads records an absence rather than a reason. The profile below is what turns that absence into either a plan or an explained refusal.

**Scope boundary.** This record specifies obligations and files the work that discharges them. It designs no optimizer, chooses no cost model, proposes no public type, and claims no fallback for an operation whose numerical contract is undefined. Where an obligation would cross a public boundary or an identity domain, it says so and leaves the crossing to the ticket that owns it.

## The profile, stated as one property

> **P.** For every semantic program the request boundary admits, and every target profile whose declared facts satisfy the program's numerical contract, the compiler either emits a verified executable program, or refuses with a typed failure class naming the exact subject and the exact missing authority. It never drops a legal cover without a recorded reason, never reports a coverage gap as malformed input, and never approximates an unimplementable region into a neighbouring one.

Everything below is P decomposed into obligations that can be checked individually. P is deliberately *weaker* than "every admitted program compiles": a program containing an occurrence no installed lowering capability covers must refuse, and that refusal is the correct outcome. What P forbids is the third state — neither a plan nor a reason.

### The five things the profile is composed of

1. **Deterministic topological partitioning.** A cover exists for every acyclic program: the fully-materialized singleton cover, one region per recognized occurrence, with a materialization edge at every consumed value. **Fact.** `CoverEnumeration::fully_materialized_cover` (`crates/tiler-compiler/src/cover.rs`) already names this cover, and the general DAG partition search enumerates it among the others. The profile's claim on it is that it is never removed by a budget: [the optimizer contract](../../compiler/optimizer.md#bounded-hierarchical-search) already states that hitting a search budget "never removes singleton/unfused coverage", and the profile is what makes that sentence load-bearing rather than decorative.
2. **Ordered multi-output preservation.** The cover's regions produce every declared program output, each by exactly one region, in declaration order. **Fact.** `verify_cover` checks each ordered named output is produced by exactly one region rather than merely retained by some region (`crates/tiler-compiler/src/cover.rs`), and `carry-artifact-program-output-order-into-kernel-program-identity` made output order part of kernel-program identity at `tiler.kernel-program.v8`. The profile adds no new obligation here; it depends on this one and states that a baseline that reduced several outputs to one root would violate the architectural contract rather than merely underperform.
3. **Conservative materialization with explicit buffers.** Every cross-region value is a materialized buffer with a stated element count, a unique writing region, and a data dependency from producer to consumer. No profile region reads a value another region computed without that edge. **Fact.** `MaterializationEdge` (`crates/tiler-compiler/src/cover.rs`) already carries the value, producer position, result position, element count, producer occurrence, and consumer occurrences — the complete set the profile needs, held by the authority that decided the materialization.
4. **Serial or direct kernels wherever legal.** Each region is realized by the simplest schedule its occurrence admits: a linear one-invocation-per-output elementwise pass, a strict serial fold for a reduction, a direct nested loop for a contraction. No parallel topology, tiling, or cooperative staging is required for a plan to exist; each is an additive alternative beside the serial one. **Fact.** This is already the shape of the governed provider's offer — `GovernedPhysicalProvider::propose` (`crates/tiler-compiler/src/frontier.rs`) offers the serial alternative unconditionally and adds the split and the workgroup tree beside it, never in place of it. The profile generalizes the *unconditional serial offer* from three member sets to every region, and generalizes nothing else.
5. **Fail-closed refusal with a reason, where no legal realization exists.** A region with no admitted implementation, a cover with no complete plan, and a program with no feasible cover each produce a typed failure naming the subject and the missing authority, distinguished from each other and from a target rejection.

### What the profile explicitly does not include

- **No host or reference fallback.** **Fact — this is mechanically enforced rather than merely unimplemented.** `crates/tiler-compiler/Cargo.toml` lists `tiler-reference` under `[dev-dependencies]` and not `[dependencies]`; the exact check is `grep -n -A 25 '^\[dependencies\]' crates/tiler-compiler/Cargo.toml`, which shows `num-bigint`, `num-integer`, `num-traits`, and `tiler-ir` and nothing else. A compiled program therefore cannot route work to the reference evaluator, because the crate is not linked into a non-test build. **Fact.** The reference evaluator's own role record states it "defines semantic results independently of fusion, scheduling, device execution, and physical storage" and is "deliberately slow and bit-oriented" ([normative reference slice](../reference/normative-reference-slice.md)) — it is the oracle a plan is compared against, not a plan. **Fact.** The one "fallback" [the architecture contract](../../architecture.md) names is a *consumer-side* one: "If no variant's preflight guards hold, the Tensor-level integration invokes a defined fallback rather than entering an unsafe custom operation." That is the Candle adapter declining to dispatch, not the compiler substituting a host route. **Inference.** The ticket's condition — "reference/host fallback only if the architecture explicitly permits it" — resolves to *not permitted*, and the resolution is stronger than a policy: the dependency direction makes it unrepresentable. The profile's "fallback" is therefore always a device kernel under the ordinary schedule vocabulary, and where no such kernel exists the profile refuses.
- **No fallback for an operation with no defined reference or numerical contract.** Stated as a rule in [Which operations the profile can cover](#which-operations-the-profile-can-cover) and derived from the operation taxonomy's own D7 column.
- **No cost model, no memo, no calibration, no boundary-property enforcer, no shared-work duplication.** Each of those improves a baseline; none is required for one to exist. [The general compilation boundary](general-compilation-boundary.md#the-critical-path-to-a-naive-but-general-compiled-mimo-program) states the same ordering and this record does not restate its derivation.
- **No relaxation of any numerical, feasibility, or verification gate.** A baseline that compiled more programs by checking fewer things would be the substitution [ADR 0043](../../decisions/0043-use-typed-phased-target-feasibility.md) and [ADR 0076](../../decisions/0076-declare-target-honourable-numerical-realizations.md) forbid. The profile is *simpler*, never *laxer*.

## Where the current tree stops, verified by reading

[The optimizer contract](../../compiler/optimizer.md#what-each-stage-is-general-over-today) records the general-pipeline audit's per-stage result and names stages 8 and 11 as the two walls. This section adds what the audit did not have to carry: the exact shape each wall takes, and one correction to the audit's account of the explain consequence.

### Wall 1 — stage 8 proposes for pre-computed member sets

**Discharged 2026-08-04** by [`derive-physical-proposals-from-the-cover-region-subject`](../../../tickets/derive-physical-proposals-from-the-cover-region-subject.md). The two Facts below remain the record of the tree at `57474a09` and are what the ticket was derived from; they are no longer true of the working tree. `GovernedPhysicalProvider::propose` now spells the subject through `crate::physical::spell_region` and converts every unspellable region into a typed `StrategyDeclineCause::UnspellableRegion`, `pointwise_region` takes the written tensor role the cover assigned, and all three explain defects below closed with it. What did *not* change is the covered set: the three region-vocabulary walls are refusals with named causes rather than offers, and each still waits on its own widening ticket.

**Fact.** `GovernedPhysicalProvider::propose` in `crates/tiler-compiler/src/frontier.rs` reads `context.subject().semantic_members()` and compares it, by exact equality, against member sets the *request-level recognizer* pre-computed: `request.pointwise().members`, `request.contraction().members`, and the serial-sum strategy's `members.pointwise()`, `members.reduction()`, and `members.all()`. Every other member set reaches a final `else` returning `ProviderOffer::default()` — no proposal and, critically, no decline.

**Fact — the region builders are keyed on the request, not on the subject.** `crate::physical::pointwise_region(request)` takes only the `VerifiedTargetRequest` and reads `request.pointwise()` or `request.serial_sum()` for its iteration shape, element count, input arity, scalar expression, members, and even the *role of the tensor it writes* (`TensorRole::Output` for a whole-program pointwise region, `TensorRole::Intermediate` for a reduction prologue). `reduction_region`, `contraction_region`, and `fused_region` have the same signature and the same source of truth. So the member-set comparison is not an accident of the provider; it is the only way to select among builders that cannot be asked about an arbitrary region in the first place.

**Inference.** Generalizing the provider is therefore two changes that must land together: a region constructor that derives its iteration domain, accesses, ownership proof, scalar program, and written tensor role from *the cover region it is handed and the occurrences that region names*, and a provider that calls it and converts an unspellable region into a typed decline instead of silence.

### Wall 2 — stage 11 implements three plan shapes

**Discharged 2026-08-05** by [`assemble-a-kernel-program-from-an-arbitrary-cover`](../../../tickets/assemble-a-kernel-program-from-an-arbitrary-cover.md). The two Facts below remain the record of the tree at `57474a09` and are what the ticket was derived from; they are no longer true of the working tree. `build_plan_program` takes one `CoverAssembly` and has no match; `CoverAssembly::from_plan` derives every structural quantity from the cover and the semantic program; `verify_artifact_refinements` re-derives through the same call; and both retired rules are gone, with an unassemblable cover reaching a caller as `RequestError::UnsupportedCapability { phase: "program-assembly" }` naming the region.

**Correction — the ordering inference below was right about the dependency and wrong about what discharging it would unlock.** Wall 1 falling did not make a four-region cover retainable, because it widened nothing: `verify_region_subject_binding` (`crates/tiler-compiler/src/physical.rs`) admits a verified region only when its `semantic_members` equal one of the recognizer's pre-computed partitions — `normalized.members`, `members().pointwise()`, `members().reduction()`, `members().all()` — or are empty for a split's combining pass. So the assembler's N-region paths are an architectural seam with their obligations proven, not a tested guarantee over four-region programs, and the three region-vocabulary walls are what unlocks the latter. The exact check is `grep -n 'semantic_members ==' crates/tiler-compiler/src/physical.rs`, which returns one comparison per recognized partition and none against anything else.

**Fact.** `build_plan_program` in `crates/tiler-compiler/src/pipeline/planning.rs` matches `(kind, scheduled)` against exactly `(Fused, [region])`, `(Materialized, [_, _])`, and `(Materialized, [_, _, _])`, and returns `ProgramError::Structure { rule: "unsupported-plan-shape" }` otherwise. `verify_artifact_refinements` in `crates/tiler-compiler/src/program.rs` carries the same three-way match over `scheduled` with `rule: "artifact-strategy-cardinality"`, and immediately below it requires `semantic.output_count() == 1` and `program.core.outputs().len() == 1` under `rule: "semantic-output-coverage"`.

**Fact — the assemblers read the recognizer's subject, not the cover.** `build_materialized_core` and `build_split_core` (`crates/tiler-compiler/src/program.rs`) open with `let subject = request.serial_sum();` and derive from it the input keys and their count, the input shape and element count, the output key, shape, and element count, and the member partitions each stage is recorded as covering. Buffers are minted positionally against that subject: one external allocation per declared input, one program allocation for the temporary, one for the output, plus one for the staged partials in the split case.

**Inference.** The failure class is worse than the provider's. A four-region cover does not merely fail to be assembled; it is classified as **invalid compiler output** — the class [the optimizer contract](../../compiler/optimizer.md#compilation-boundary-and-failure-classes) reserves for a compiler-produced value failing its own verifier. A deterministic topological partition of any program with more than three occurrences produces exactly that shape immediately, so the first thing the profile's own partitioning would do is trip a compiler-fault path.

### The explain consequence, corrected

The general-pipeline audit recorded that a dropped cover reaches complete-plan selection "with *no* explain attribution: nothing rejected it, because nothing proposed for it, so a reader of the trace sees an absence rather than a reason." That is the right conclusion for the wrong reason, and the precise version is worth having because it changes what the fix must do.

**Fact — a rejection *is* constructed.** `select_physical_plans` (`crates/tiler-compiler/src/selection.rs`) walks each cover's bound frontiers and, for every region whose admitted set is empty, inserts a `PlanRejection::RegionUnimplemented { role, cover }` into the portfolio's rejection map, deduplicated by role within a cover. Its own comment records the scale: "the governed program records 38 of these per compile, every one of them the role `unrecognized`."

**Fact — no production code ever reads it.** `SelectedPortfolio::rejections()` has three call sites in `crates/tiler-compiler/src/selection.rs` at lines 2429, 2473, and 2676, all of which are inside the `#[cfg(test)]` module that begins at line 1705. The exact check is `grep -rn '\.rejections()' crates/ --include='*.rs'`, which returns seven sites: those three, one `ImplementationFrontier::rejections()` in a `frontier.rs` test, two `ImplementationFrontier::rejections()` uses on the compile path in `pipeline/`, and two unrelated `refusals` in `session.rs` and `tiler-build`. `record_plan_selection` (`crates/tiler-compiler/src/pipeline/trace.rs`) records the plan count, the analytical component costs, and the budget stops — and does not touch `portfolio.rejections()`.

**Fact — the frontier record that does reach the trace is keyed by role, and the role collapses.** `record_frontier` (`crates/tiler-compiler/src/pipeline/trace.rs`) writes its subject key as `region:{role}`, and `pipeline/planning.rs` calls it only on the first sighting of each role (`let first_sighting = !recorded_roles.contains_key(role);`). `region_role` (`crates/tiler-compiler/src/pipeline.rs`) returns one of `whole-program`, `pointwise`, `reduction`, or `unrecognized`, decided by exact member-set equality against the same pre-computed partitions the provider uses. The planner's own comment records the consequence: "the governed five-operation program enumerates 48 times over 17 distinct subjects" and "Fourteen of those seventeen subjects share the role `unrecognized` while covering different occurrences."

**Inference — three separate defects, not one.** (a) Fourteen distinct region subjects share one explain subject key, so a reader cannot tell which region a record is about. (b) Thirteen of them emit no record at all, because only the first sighting of a role is recorded. (c) The one authority that *did* name the coverage gap per cover is retained in a struct nothing reads. A profile that "fails closed with an explainable reason" has to fix all three; fixing only the provider would leave a compiled-away reason, and fixing only the trace would leave a reason with no subject to attach to.

Nothing else on the path needs to change, and in particular nothing in `tiler-ir` does — its program layer already carries variable-length stages and buffers bounded by `MAX_PROGRAM_OUTPUTS` rather than by one, and builds and verifies a two-output four-stage program in its own tests.

## Hard feasibility, cost, and target availability are three separations the profile must not blur

The ticket asks for two separations and the audit's evidence shows they are really three. Each is stated as what the profile may and may not do, because the profile is exactly where a shortcut would be tempting.

**Feasibility versus cost.** A region the target cannot realize is refused by `crates/tiler-compiler/src/target/feasibility.rs` with the fact that refused it, and never by an infinite or arbitrary cost. The profile adds no exception: a serial kernel that exceeds a declared resource limit is infeasible on that target, and the correct outcome is a refusal naming the axis, the required amount, and the available amount — not a cheaper-looking plan. **Fact.** The separation is enforced by absent conversions rather than by a rule: the feasibility authority has no cost input, and `crates/tiler-compiler/src/estimate.rs` offers no conversion from an estimate into anything feasibility consults.

**Semantic correctness versus target availability.** A program whose occurrence no installed capability lowers is a *missing compilation capability* — the program is valid and the authority is absent. A program whose serial kernel no target profile admits is an *infeasible plan* — the authority is present and refused. These reach a caller as different failure classes and must not be merged; merging them would tell a frontend author to change their program when they need to change their target, or the reverse.

**Absent proposal versus refused proposal.** This is the third, and it is the one the current tree does not have. A provider that returns an empty offer is saying "I recognize nothing here", which is a legitimate local result and *not* a coverage claim — the trait's own doc comment says so. A provider that declines a named strategy is saying "this strategy applied and this request did not admit it", which is a much stronger statement with a typed cause. **Inference.** The profile requires that for a region a *legal cover placed*, the first answer is inadmissible: the compiler installed one provider, that provider is the whole of the physical authority for this build, and its silence is therefore indistinguishable from a coverage gap it should have named. The generalized provider must convert every "any other member set" path into a decline whose cause names what it could not spell.

## Which operations the profile can cover

The [mature operation and signature taxonomy](../semantic-graph/mature-operation-and-signature-taxonomy.md) carries, per family, a **D7 Reference realization and physical fallback** cell — "the minimum correct host oracle, and the minimum physical route that is not a fast path". That is precisely this profile's per-family input, and this section consumes it as the record's own join table intends rather than re-deriving anything.

**The admission rule, derived from the taxonomy's own structure.** A family belongs to the profile's covered set only when *all three* hold: its D7 cell names a minimum physical route outright, rather than deferring to a declared carrier, a vendor library, a further contract, or an unrepresented mechanism; its D5 cell states a numerical and exceptional-value contract that a serial realization can refine; and no open `RQ-OP-nn` bears on *what that route is*. The third condition is deliberately narrower than "carries no open question": `RQ-OP-01` leaves a checked-overflow operation's result count open and does not change the route, which is a scalar kernel operation under either answer. `RQ-OP-04` was the same case for conversion's family decomposition and has since closed — answered 2026-08-05 and decided by [ADR 0102](../../decisions/0102-key-conversion-families-by-the-ordered-pair-and-derive-their-fields.md), which Tom accepted on 2026-08-06 — and the route moved on neither the answer nor the acceptance, exactly as the condition predicted: a family keyed by the ordered pair with a derived field set is still a scalar convert. `RQ-OP-03` is the opposite case — it decides whether a predicate tensor is a graph value at all, so until it closes there is nothing for a route to write into. Applied to all forty-seven families, the rule sorts them into four classes, and every family appears exactly once.

| Class | D7 shape in the taxonomy | The profile's obligation | Families |
| --- | --- | --- | --- |
| **Covered — direct scalar or map route** | "physical fallback is a scalar kernel op", an index or read-map change with no data movement, a copy, a guarded read, or an embedded or bound buffer | The profile must have a serial or direct kernel, and refusing one is a defect | F-01, F-02, F-03, F-05, F-06, F-08, F-09, F-10, F-15, F-18, F-19, F-21, F-22, F-23, F-25, F-26, F-27, F-43 |
| **Covered — direct fold or nested loop** | "physical fallback is a serial pass", "a direct triple loop", "a direct nested loop" | The profile must have the *serial* form; the tree, split, multi-pass, GEMM, im2col, and Winograd forms are alternatives beside it and never substitutes | F-28, F-29, F-31, F-32, F-33 |
| **Covered only under a stated precondition** | D7 names a route that exists only once something else is declared, decided, or proved | The profile covers the family *after* the precondition, and refuses by name before it | F-04 (a declared storage encoding), F-07 (a target that offers single rounding, which [ADR 0015](../../decisions/0015-fma-vs-contraction.md) makes non-negotiable), F-11 (a vendor bound that refines the declared accuracy contract), F-12 (the pinned formula rather than a mathematically equivalent one), F-20 (a packing and parameter-broadcast route), F-24 (a view where the ABI expresses the offset, a copy otherwise), F-30 (the stable formulation, which the naive composition is not), F-35 (proved unique write ownership or the separate atomic-combine contract), F-37 and F-38 (a stated float total order and tie-break), F-39 (a validated sortedness assumption), F-40 (the complex arithmetic that does not exist), F-41 (the gather its coordinates are read through) |
| **Not covered, and the refusal is the guarantee** | D7 is empty, names no route, or the family has no admissible numerical evidence | The profile must refuse by name and must never approximate | F-13, F-14, F-16, F-17 (gated together on `RQ-OP-03`'s predicate-tensor decision, which the [dtype support ledger](../../dtype-support.md)'s `Logical bool` trigger states from the other side), F-34 (needs the gather/scatter/indirection contract the [index model](../indexing/index-access-model.md) defers), F-36, F-44, F-46, F-47 (D7 is empty — no physical route exists to name), F-42 (a vendor decomposition publishes no accumulation order, so its evidence is `Unknown`), F-45 (declared per instance; a call declaring no numerical contract is inadmissible rather than unconstrained) |

**The rule that falls out, and it is the ticket's own non-goal restated with teeth.** *A family whose D7 cell names no minimum physical route, or whose D5 cell states no numerical contract, gets no fallback — it gets a typed refusal naming the missing authority.* F-42 is the sharpest case and is worth stating because it is the one where a "fallback" is most tempting: a vendor decomposition would run, and would produce numbers, and the profile still must not use it, because the optimizer requires every implementation candidate to advertise a machine-checkable numerical guarantee that refines the effective operation contract and an unpublished accumulation order cannot. Admitting it as a baseline would make the baseline the one plan whose correctness nothing checks.

**Two boundaries on this table that a reader must not overstate.** First, it is a classification of the taxonomy's *proposed* inventory, whose own disposition is `pending`; a family's presence in the covered column is a statement about what a minimum route would look like, not that the family is registered, admitted, or schedulable. The [operation-family support matrix](../../roadmap.md#operation-family-support-matrix) owns delivery and this table does not move a rung. Second, the profile's *currently reachable* covered set is far smaller than the covered column: it is the intersection of that column with what the schedule vocabulary spells, which today is the `f32` pointwise expression vocabulary, the strict serial sum, and the strict tensor contraction. The named region-vocabulary wall — no `ScalarProgram` spelling for the registered unary families — has its own owning ticket and *widens the covered set* without changing the profile's obligations. *Corrected 2026-08-06:* this sentence named three walls, and all three are now gone. [`admit-a-reduction-over-a-declared-input-tensor`](../../../tickets/admit-a-reduction-over-a-declared-input-tensor.md) widened the serial `StrictSerialSum` arm to the fold's declared contributor domain, so "no reduction directly over a declared input" stopped being true on the day this file's row 1 recorded it and this sentence was missed; [`admit-a-materialized-intermediate-read-in-the-scheduled-region-vocabulary`](../../../tickets/admit-a-materialized-intermediate-read-in-the-scheduled-region-vocabulary.md) then separated a pointwise read's access position from the declared input its `TensorRole` names, so an elementwise region may read one materialized intermediate and only the *producer* half of the reduction epilogue was still unspellable; [`admit-a-strict-serial-fold-that-writes-a-materialized-intermediate`](../../../tickets/admit-a-strict-serial-fold-that-writes-a-materialized-intermediate.md) then closed that half by replacing the `write.tensor == TensorRole::Output` literal at every *committing* fold pass — the four serial arms, the split's final pass, and the cooperative tile — with `CommittedTensor::CoverAssigned`, since where a fold's result goes is a property of the surrounding cover and not of the fold. **The reachable set named above moves with it**: the schedule vocabulary now spells a `prologue -> fold -> epilogue` chain end to end, so a reduction-with-epilogue program is bounded by the *recognizer* rather than by this profile's vocabulary. What the widening deliberately did not touch is the split's partial pass, which keeps `CommittedTensor::Exactly(Intermediate)` because a partial is an unfolded fragment and is no cover's declared output.

## What the region-general physical provider must guarantee

This is the specification [`derive-physical-proposals-from-the-cover-region-subject`](../../../tickets/derive-physical-proposals-from-the-cover-region-subject.md) implements. It is written as obligations rather than as a design, because the interface it lands on is a crate-private boundary the implementing ticket owns.

1. **The proposal is derived from the subject it is handed.** Its inputs are the cover region's exact semantic members, the presentation role, the intermediate element counts the cover stated, and the verified target request. Its output must be a function of those. A proposal derived instead from a whole-program recognition — the shape today's builders take — cannot be correct for a region that recognition did not name.
2. **Every region gets an answer, and the answer is never silence.** For a region whose occurrences the schedule vocabulary spells, at least one verified serial or direct proposal. For every other region, a `DeclinedStrategy` whose cause names the exact missing vocabulary — which occurrence, and which of the three region-vocabulary walls it hit. The existing `StrategyDeclineCause` variants (`NumericalPermissionRefused`, `NoAdmissibleShape`, `Unrepresentable`) do not spell this case; a new variant is required and must be added append-only, with each encoding tag proved injective at its own site rather than by the gate staying green.
3. **The write role is derived from the cover, not from the strategy.** A region writes a program output when the cover assigns it one, and an intermediate when a materialization edge names it as producer. Today `pointwise_region` picks between `TensorRole::Output` and `TensorRole::Intermediate` by asking whether the *request* was recognized as a whole-program pointwise or as a reduction prologue — a question about the program, answered where a question about the region belongs.
4. **Verification is unchanged and non-negotiable.** The host resubmits every body through `crate::physical::verify_schedule_with_feasibility`, and a generalized provider gets no shortcut through it. A generalized builder that emitted a region failing intrinsic verification is invalid compiler output, exactly as a specialized one would be.
5. **Existing proposals must not move.** The three recognized member sets must yield byte-identical proposals, identities, and costs after generalization, because their identities are folded into plan and artifact identity. This is the ticket's cheapest and strongest regression check, and it is stated here so the implementing ticket does not have to rediscover it.
6. **The additive-alternative discipline holds.** The serial proposal is offered unconditionally; the split and tree remain additive beside it for the regions that admit them. A generalization that made a parallel alternative a precondition for any offer would delete the baseline it was meant to guarantee.
7. **Nothing in enumeration, dominance, retention, or plan selection is touched.** [The optimizer contract](../../compiler/optimizer.md#the-review-obligation) makes a diff touching those a violation until justified. This work is a proposal generator and a typed decline; it has no business in a comparison.

## What the cover-general program assembly must guarantee

This is the specification [`assemble-a-kernel-program-from-an-arbitrary-cover`](../../../tickets/assemble-a-kernel-program-from-an-arbitrary-cover.md) implements. **Implemented 2026-08-05**; each numbered obligation below is discharged, with obligation 3's reclassification landing as a `RequestError::UnsupportedCapability { phase: "program-assembly" }` refusal that names the region, and obligation 7's byte-identity checked by recomputing every alternative's canonical kernel-program identity before and after the change.

1. **Every structural quantity comes from the cover or the semantic program, never from a recognized strategy subject.** Program inputs and their keys from the semantic program's declared inputs; one internal value and one program-owned allocation per materialization edge, sized by the edge's own element count; one output value per ordered named program output, in declaration order; one stage per scheduled region, ordered so producers precede consumers; one data dependency per materialization edge, from the producing stage to each consuming stage.
2. **Stage coverage is derived from the cover region's members.** Today the assemblers pass `subject.members.pointwise()` and `subject.members.reduction()` as the occurrences a stage covers. Generalized, a stage covers exactly its cover region's members — with the one documented exception that a subprogram's final pass covers nothing, because the partial pass already claims the occurrence the two of them realize.
3. **An unassemblable cover is a typed refusal, not invalid compiler output.** This is the failure-class correction the wall makes necessary. A cover the assembler cannot express must reach a caller as a missing-capability refusal naming the region and the reason, in the same class as any other coverage gap. `"unsupported-plan-shape"` and `"artifact-strategy-cardinality"` are the two rules to retire or reclassify.
4. **The whole-program verifier remains the authority and gains no exception.** Complete disjoint coverage of the semantic graph, a unique writer per materialized value, temporary initialization and lifetimes, aliasing, ABI and launch references, and named-output coverage are proven by `KernelProgramBuilder::build`, and a generalized assembler proves nothing itself. Its correctness argument is that it constructs the same obligations for N regions that it constructs for two.
5. **`verify_artifact_refinements` re-derives by the same route.** The receipt path and the build path must not acquire two independently maintained descriptions of what a cover assembles into, which is exactly the duplicate-derivation hazard the three-way match already embodies twice.
6. **The single-output guard is a separate obligation with a separate owner.** Relaxing the three-shape match does not relax `output_count() != 1`, and relaxing that guard here without the request boundary's would admit a program the other refuses. [`admit-ordered-multi-output-programs-at-the-compiler-request-boundary`](../../../tickets/admit-ordered-multi-output-programs-at-the-compiler-request-boundary.md) owns both guards and now depends on this ticket.
7. **Existing programs must not move.** The one-, two-, and three-region shapes must assemble to byte-identical programs and artifact plans, for the same identity reason the provider owes.

## What the explain trace must carry for a refused baseline

Stated separately because it is the obligation that turns P's second clause from a policy into something a caller can act on, and because the three defects it repairs are independent.

1. **One explain subject per region subject, not per role.** A key derived from the region's canonical occurrence identity distinguishes the fourteen subjects that share `unrecognized` today. The role remains a presentation label beside it.
2. **A record for every enumerated region subject.** The `first_sighting` guard is a deduplication over a key that is too coarse; with a per-subject key it becomes a correct deduplication instead of a lossy one.
3. **The coverage gap reaches the trace.** `PlanRejection::RegionUnimplemented` names the cover and the region that had no implementation, and is the only authority that states the gap *per cover*. It is currently read by tests alone; the profile requires it emitted, at the selection stage, caused by the frontier record for that subject.
4. **A decline and an absence stay different records.** After the provider generalization there should be no absences left for a region a legal cover placed, and the check that this is true is that a region with no admitted implementation always has a decline record naming why. That is a check that can say no, and the implementing ticket owes running it against a deliberately unspellable region and watching it fail before it passes.

## Ordering, and why it is a dependency rather than a preference

**Inference — the provider precedes the assembly, and the derivation is falsifiable.** Program assembly is reached only for a *retained plan*, and a plan is retained only when every one of its cover's regions has an admitted implementation. Before the provider generalizes, no cover with a region outside the three recognized member sets ever produces a plan, so a generalized assembler's new paths would be unreachable from the compile path and testable only through a fixture that constructs a plan the compiler cannot produce. That is the reverse of the discipline this repository applies elsewhere — a check that cannot fail on the real path is not evidence. If someone demonstrates a compile-path route that retains a four-region plan without a generalized provider, this ordering is refuted and the two become independent.

**Inference — both precede the multi-output relaxation and the duplication activation.** [`admit-ordered-multi-output-programs-at-the-compiler-request-boundary`](../../../tickets/admit-ordered-multi-output-programs-at-the-compiler-request-boundary.md) needs an assembler that does not assume one output pipeline of one, two, or three stages; [`activate-shared-work-duplication-on-the-compile-path`](../../../tickets/activate-shared-work-duplication-on-the-compile-path.md) names both walls as its own activation triggers, having derived independently that enabling the policy today "would enumerate every duplicating cover, find each region unimplementable, record a `RegionUnimplemented` rejection, and retain no additional plan". Two tickets reaching the same two walls from different directions is corroboration that the walls are where the audit placed them.

**What is deliberately *not* ordered before the profile.** The three region-vocabulary walls, the boundary-property enforcers, the retention budget, the calibrated cost model, and the memo. Each widens or improves the baseline; none is a precondition for one existing. Ordering any of them first would be building the second competence again.

## Conclusions

1. **The baseline is two changes away, not a research programme.** Stages 1 through 7, 9's join, and 10 already discharge every obligation P places on them. The gap is a provider that answers for the region it is handed, an assembler that reads the cover, and the trace that publishes the gap when there is one.
2. **The load-bearing one is the provider,** and the reason is that its silence is currently indistinguishable from a coverage gap. Everything downstream of it is either general already or unreachable until it moves.
3. **The stage-11 failure class is the sharper defect even though the stage-8 one is the blocker.** A four-region cover being classified as invalid compiler output means the first thing a correct baseline does looks like a compiler bug. **Both closed 2026-08-04 and 2026-08-05, and the closing revealed a third fact this record did not carry:** with both stages general, no four-region cover is retainable *at all*, because the region vocabulary refuses every member set outside the recognizer's three. The walls were real and are gone; what remains between here and a general compiled program is the covered set, which is [the three region-vocabulary widenings](#which-operations-the-profile-can-cover) and nothing on the pipeline.
4. **The explain gap is three defects and the audit found one of them.** A rejection is constructed, deduplicated, and never read; the subject key collapses fourteen regions into one; and thirteen of those emit no record at all.
5. **The profile permits no host or reference fallback, and the enforcement is structural** — `tiler-reference` is a dev-dependency of `tiler-compiler`, so a compiled program cannot contain a host route.
6. **The taxonomy's D7 column is directly consumable and sorts its forty-seven families into four classes,** of which one is "refuse by name" and is not a gap to be closed. The rule that decides it — no minimum physical route or no numerical contract means no fallback — is the ticket's non-goal turned into a test.
7. **Nothing here needs `tiler-ir` to change.** Every cardinality the profile requires is already variable-length in the program layer, and a two-output four-stage program already builds and verifies there.
