# The measured-feedback tuning loop

This record designs the seam through which on-device timing is allowed to affect what Tiler compiles: where a measurement may enter, what a store of measurements is and is not, when one shape's result may speak for another's, and what happens when no measurement is available. It decides four questions and defers two, each with its reasoning. It contains no implementation, proposes no crate, and collects no timing.

Every claim below is labelled **Fact**, **Inference**, **Proposal**, or **Measurement**. A **Fact** was read in the source named beside it — repository source at the commit this record was written against, or the exact byte stream digested in [the source record](sources/README.md). A **Measurement** is always someone else's; this record produced none.

## What this record decides, in one table

| Question | Decision | Section |
| --- | --- | --- |

| What the tuning store is | **An append-only log of immutable observations with a derived, replaceable verdict.** Three of the expansion cache's five properties transfer; two invert, and one of those inverts at the heart of the design. | [2](#2-the-tuning-stores-identity-discipline) |
| Transfer across shapes | **A measurement transfers only by fitting a parameter whose domain is the machine.** A per-shape winner table is refused. A declared validity region is the only admitted exception, and it is a miss outside its bounds, never a nearest neighbour. | [3](#3-the-transfer-model-across-shapes) |

## 0. The state this design starts from

The ticket asserted two facts about the tree and asked that they be verified rather than assumed. Both hold, and verifying them turned up a third that changes the design.

**Fact — the analytic cost authority exists.** `crates/tiler-compiler/src/component_cost.rs:76` declares `ANALYTICAL_MODEL_KEY: &str = "tiler.cost.analytical.v1"`, with `CostComponent`, `CostUnit`, `CostValue`, `ComponentCost`, and `AnalyticalPlanCost` beside it. Nine governed components are emitted for every retained plan in canonical order; seven are derived and two — `ResourcePressure` and `CompileTime` — evaluate to `CostValue::Unknown` in a single shared arm. The module header states the discipline this record inherits: an unmodelled component is `Unknown`, "not a zero and not an infinity", and `unknown_is_not_a_zero` asserts it.

**Fact — a measured selector exists and is consulted.** `crates/tiler-compiler/src/measured_cost.rs:119` declares `MEASURED_FOLD_STEP_MODEL_KEY: &str = "tiler.cost.measured-fold-steps.v1"`, and `crates/tiler-compiler/src/pipeline/planning.rs:1010-1030` (`measured_scores`) consults it during selection.

**Fact — and this is the one that matters — no measurement enters compilation.** What `measured_cost` consumes is a single `u64` read off the target profile through `TargetProfile::saturated_parallel_fold_steps` (`crates/tiler-compiler/src/target.rs:3758`). That number is a literal in a declaration: `crates/tiler-build/src/metal_declaration.rs "saturated_parallel_fold_steps: Some("`, declared through `declare_measured_saturated_parallel_fold_steps` (`target.rs:2968`). *(Corrected 2026-08-19 at the compilation-selection carrier's integration: this read `metal_declaration.rs:337 … Some(1_056)`, and both the line and the value had moved — the declared row is `Some(1_280)` since the accepted (R, R) re-measurement reseated the cost row onto the 2026-08-18 record. Re-anchored rather than renumbered, because the claim is about the literal's existence and not its position.)* Separately, `crates/tiler-compiler/src/estimate.rs:60` documents `EstimateProvenance::Measured` as reserved — "no measurement path reaches this module yet" — and `grep -rn 'EstimateProvenance::Measured' crates/ --include='*.rs'` returns only that declaration and its key mapping.

**Inference.** The word "measured" in the compiler today names *provenance of a constant*, not a loop. One human read one retained sweep, fitted one machine parameter, and typed it into a declaration. Nothing reads a device, nothing stores a result, nothing refutes anything. So this record is not refining an existing loop; it is deciding whether the constant-transcription path should ever become one, and what it would have to be if it did. The ticket's framing — "the design questions are now askable against something real" — is right, and what is real is a *calibrated parameter*, which is a much narrower thing than a tuning loop and, as [section 3](#3-the-transfer-model-across-shapes) argues, is also the right thing.

**Fact — the seam that would carry a measurement is already typed, and it fails closed.** `TargetCostRowResolution` resolves a cost row to `Declared { value }`, `Deferred { available_at }`, or `Unknown` (`target.rs:3765-3785`), against an `AvailabilityPhase` ladder whose five ordered variants are declared in `crates/tiler-ir/src/program/abi.rs:114-131` under [ADR 0043](../../decisions/0043-use-typed-phased-target-feasibility.md). `measured_scores` asks at `AvailabilityPhase::CompileProfile` and treats `Deferred` exactly as `Unknown`, with the reason stated in its own doc comment: "a compile cannot wait for it". `declare_saturated_parallel_fold_steps`'s doc comment states the other half — a cost row is "a **cost row, not a capability axis**", silence means "*no preference*", and a profile declaring nothing "selects exactly as it did before this row existed, byte for byte".

**Fact — a second cost-model key may not enter dominance.** `component_cost.rs`'s header records why: `PlanStructuralCost::dominates` returns `false` across differing keys, so "plans carrying different keys never dominate each other, so the non-dominated set would silently become the whole set and Pareto pruning would go dark with nothing reporting that it had". `frontier.rs:2140-2145` refuses a proposal whose declared key is not `tiler.cost.structural.v1` as `FrontierError::MalformedCostProvenance`, and `an_analytical_cost_key_is_refused_by_the_frontier` (`frontier.rs:4290`) drives that refusal against the analytical key by name.

**Inference.** Any tuning result therefore reaches selection the way the measured selector does — as a *ranking over already-retained valid plans*, outside dominance, outside feasibility, carrying its own key — or it does not reach selection at all. This is not a constraint the design chose; it is the shape of the only door that exists, and it is a good door: `planning.rs:1082-1089` records that hard feasibility is untouched because "there is no infeasible plan in the set to prefer".

## 1. Where measurement enters

Three sites were compared: **offline calibration** (measure before compiling, ship a fitted parameter), **in-loop tuning** (measure during compilation, search against the results), and **post-hoc refinement** (measure during execution, revise the plan afterwards or mid-flight).

### Decision: offline calibration, and only that, for now

**Proposal.** Measurement enters Tiler at exactly one place: a fitted parameter on a target profile, declared through the existing measured-fact constructors, resolved through the existing availability-phase ladder, consumed by a selector that ranks retained valid plans. Everything this record designs is a discipline *around that one site* — how the fit is evidenced, stored, scoped, and refuted — and not a second site.

**Why not in-loop tuning.** Three independent arguments, two measured by others and one structural.

*Measurement (Ansor, OSDI 2020, §7.1 and §7.4).* An operator-level tuner spends a budget that is counted in thousands of hardware executions: the evaluation gives each framework "up to 1, 000 measurement trials per test case", and for whole networks lets AutoTVM and Ansor run "to 1000 × n measurement trials on each DNN, where n is the number of subgraphs". The paper's own summary of the cost is that "it takes several hours for Ansor to generate fully-optimized programs for a DNN on a single machine", which it defends as "acceptable for inference applications because it is a one-shot effort before deployment".

*Fact (AGENTS.md, architectural guidance).* Tiler's stated product constraint is the opposite of a one-shot deployment step: "Preserve self-contained inline Rust AOT embedding: no required consumer `build.rs`, duplicated registry, source scan, Cargo subcommand, prepare step, or runtime JIT." An in-loop tuner is a prepare step by construction. It would have to run inside a proc-macro expansion, dispatch to a GPU thousands of times per invocation, and do so on every developer machine and every CI runner that builds the consumer. **Inference.** That is not a cost-benefit trade against a faster kernel; it is a different product, and the architectural guidance already decided against it.

*Measurement (Halide, 2016 and 2019 read together).* The two Halide autoschedulers are the only pair in this corpus where the analytic-only and measured-search poles are evaluated on one system. Mullapudi et al. 2016 state that their algorithm "does not require costly (and often impractical) auto-tuning" and "in seconds, generates schedules ... performance-competitive with, and often better than, schedules manually authored by expert Halide developers". Adams et al. 2019 report that their learned model "operates effectively with or without autotuning", producing schedules "almost twice as fast as the existing Halide autoscheduler without autotuning, or more than twice as fast with", and outperforming the 2016 scheduler "by 75% on average with no autotuning, and up to 135% on average with a few hours per application of autotuning". The same paper records what the fully-measured predecessor cost: the original Halide autotuner "relied entirely on ground-truth benchmarking to measure performance" and "finding schedules could take days for moderately-sized pipelines".

**Inference.** Read as a ratio rather than as a headline, 2019's numbers say that going from *no measurement at compile time* to *hours of measurement per application* bought roughly 1.34x (from 75% to 135% over a common baseline), while the model itself bought the 75%. For a project whose analytic model currently reports two of nine components as `Unknown` and has never been calibrated against a device on any axis but one, the model side is where the unclaimed factor is. Spending the design budget on an in-loop tuner would be optimizing the term that the one comparable measurement says is worth least, at the cost of the product constraint the project has already fixed.

**Trigger for reopening.** In-loop tuning becomes reconsiderable when *both* of these hold: (a) a target profile declares a cost row that the analytic model provably cannot derive — that is, a quantity that is not a function of the machine but of the (machine, program) pair — and (b) the repository has adopted an explicit build-time compilation mode that is already permitted to touch a device. Neither holds. Condition (b) in particular is a product expansion and Tom's to make.

**Why not post-hoc refinement.** *Fact (Kabra and DeWitt, SIGMOD 1998, §2).* The mechanism is an **annotated query execution plan**: "we modify the query optimizer so that these estimates are included in the query evaluation plan that it produces, and are sent to the database execution engine", carrying "sizes and cardinalities of intermediate results, selectivities of selection and join predicates, and estimates of the number of groups". At chosen points the engine collects statistics, and "the improved estimates are also used to determine whether the remainder of the query execution plan would benefit from re-optimization. If so, then the remainder of the query is re-optimized."

**Inference — the mechanism splits cleanly into a half Tiler can have and a half it cannot.** The *annotation* half is cheap and valuable: a plan that carries the compiler's own estimate of what it will cost is a plan whose estimate can later be compared against an observation, and without the annotation no observation can be attributed to a prediction at all. The *re-optimization* half requires that an alternative plan exist at the moment of the observation. Tiler AOT-compiles one selected plan into an immutable artifact; the alternatives are enumerated, reported in explain, and then discarded. There is nothing to switch to. Shipping several plans in one artifact and choosing among them at run time is precisely parametric query optimization (see [section 3](#3-the-transfer-model-across-shapes)), it is a genuine product expansion, and it is Tom's decision and not this record's.

**Proposal — the annotation half is adopted and re-scoped.** The compiler already computes, per retained plan, a nine-component analytical cost and (where a row is declared) a fold-step assessment retaining both sides of its `max`. **Proposal:** when an artifact is produced, the selected plan's cost record and the *reason it was selected over the named runner-up* are retained in the artifact's explain surface, so that any later measurement of that artifact — by a benchmark, a consumer, or a future calibration sweep — can be compared against a prediction rather than against nothing. This is a reporting obligation, not a loop; it is the necessary precondition for any future refinement and costs no device access. It is deliberately *not* specified further here, because the artifact explain surface is a public boundary.

## 2. The tuning store's identity discipline

This is the load-bearing section. A tuning store looks like the expansion cache and is not one, and the places where the resemblance fails are exactly the places where copying the cache would produce a silently wrong compiler.

**Fact — the expansion cache is specified by five properties**, stated together in `crates/tiler-cache/src/expansion.rs:3-57` and decided in [ADR 0050](../../decisions/0050-use-immutable-self-validating-expansion-cache-entries.md): complete cache identity, validation on every hit, immutable entries, atomic publication, and defined crash and race behaviour. ADR 0050's decision sentence is "The expansion cache stores one immutable self-validating bundle per complete compilation key."

They are taken one at a time. **Every row below is a Proposal about a store that does not exist**, argued against a Fact about the cache that does.

### 2.1 Complete cache identity — **transfers, and must be widened**

**Fact.** "A key that omits an input does not make a cache slower; it makes a validated hit return an artifact built from different inputs" (`expansion.rs:8-10`). The key is a digest, under a versioned domain separator `tiler.cache.expansion-key.v1\0` (`key.rs:14`), of a `ComposedSubject` that is "constructable only by naming every facet of the envelope a bundle carries". Two things are deliberately *outside* the key: the cache root, because [ADR 0089](../../decisions/0089-resolve-the-expansion-cache-root-from-an-override-or-the-user-cache.md) decided "a resolution is a pure function of the composed subject, so moving the root changes where entries live and never what they mean", and debug retention, because it does not change what was compiled (`expansion.rs:30-43`).

**Proposal — the property transfers unchanged in form and must be strictly widened in content, and the reason is a difference in kind.** *Compilation is a pure function of its inputs; execution is not.* The cache can afford to key on the compilation subject alone because running the compiler twice on one subject is guaranteed to produce one answer. Running a kernel twice on one device is guaranteed to produce a *distribution*, whose parameters depend on the device, the OS build, the driver, the thermal and power state, what else was resident, and the measurement protocol. A tuning key must therefore name all of that, and none of it appears in a compilation key.

The tuning key is a digest, under its own domain separator, of an ordered composition of exactly four facets:

1. **The subject** — the plan identity being timed, the target profile key, the numerical contract key, and the shape coordinates. This is the part that overlaps the compilation subject.
2. **The environment row** — the live device identity, the OS build, the execution toolchain provenance, and the declared power and thermal policy in force. This is the part the compilation key does not have and cannot borrow.
3. **The protocol descriptor** — warm-up count, timed repetition count, interleaving and rotation policy, encode-count amortization, and the timing instrument. See [section 5](#5-statistical-discipline-for-noisy-gpu-timings) for why this is identity rather than prose.
4. **The oracle** — what was checked, and how, before any timing was recorded.

**Proposal — reuse scope moves *into* the key, and this is an inversion of a stated non-property.** `key.rs:60-66` says of the cache, in so many words: "**A key does not carry a reuse scope, and this crate does not enforce one.** ... What no code here can check is that a configured cache root is host-local; a caller that points this cache at a shared volume defeats the producer's bound and this crate will not notice." For compiled artifacts that is a known, owned gap. For measurements it is fatal at the default, because a measurement's validity scope is *already* narrower than a compilation's by declaration: `declare_measured_saturated_parallel_fold_steps` takes a `TargetCompileProfileMeasurementSource` specifically so that its validity is "fixed at `TargetFactValidityScope::MeasuredEnvironment`" and cannot widen "into a portable claim" (`target.rs:2952-2974`). A tuning store that let one host read another's timings would defeat that by accident on the first shared build cache. So the environment row is not metadata beside the key; it *is* part of the key, and a differing environment is a different key and therefore a miss.

### 2.2 Validation on every hit — **the form transfers; the content splits and half of it inverts**

**Fact.** "`ExpansionCache::lookup` has no fast path. Every read decodes the whole bundle frame ... re-derives the key from the carried subject, and then hands the carried envelope to `decode_artifact` ... Nothing is returned before all of it passes" (`expansion.rs:18-24`). `CachedEntry`'s doc adds: "There is no way to construct one otherwise" (`store.rs:70-82`).

**Proposal — structural validation transfers verbatim.** A tuning entry carries its own subject bytes, a reader re-derives the key from them and refuses an entry that does not hash to the key it is filed under, every framed section is length- and digest-checked, and nothing is returned before all of it passes. There is no argument for weakening this and every argument for reusing the mechanism exactly.

**Proposal — semantic validation inverts, and this is the first of the two real inversions.** The cache's hit is *self-proving*: the entry claims "these bytes are the compilation of that subject", and re-deriving the key plus re-proving the digests establishes exactly that claim, completely, from the bytes alone. A tuning entry's claim is "on this machine, this plan is faster than that one" — a claim about the world. No amount of digest checking can establish it, because the bytes are not the evidence for it; they are a *report* of evidence that was destroyed when the run ended.

**Inference — so a validated tuning hit is not proven, it is unrefuted, and the two must not be spelled the same way.** Concretely: the cache may return a `CachedEntry` whose mere existence is the proof, and the compiler may consume it without further thought. A tuning store may not. What it returns is a *claim with its own statistics attached*, and the consumer is obliged to apply the separation test ([section 3, rule 3](#3-the-transfer-model-across-shapes)) before acting on it. **The test is a property of the consumer, not of the store**, because the store cannot know the tolerance the caller needs. A store that pre-applied the test and returned a bare winner would be exporting a judgement dressed as a fact, and that is the shape of every silently-wrong autotuner.

**Fact — the repository has already made this distinction once, in a different vocabulary.** `component_cost.rs` keeps `Exact`, `Bounded`, and `Unknown` apart precisely because "they are different evidence classes, not three confidences on one scale. Collapsing them into a number with an error bar would make an unmodelled component indistinguishable from one modelled imprecisely, and only the second is safe to calibrate against." **Inference.** A measured verdict is a fourth class, and it is not `Exact` even though it is a number. It is empirical evidence with a sample size, which is what the accepted maturity ladder in AGENTS.md already calls it.

### 2.3 Immutable entries — **inverts, and this is the design's centre**

**Fact.** "A final entry is never opened for writing, appended to, or edited in place. It is created by one `rename` and afterwards only read, replaced by another whole `rename`, or unlinked" (`expansion.rs:26-28`). The garbage collector holds the same line: "The collector never holds a writable descriptor to an entry" (`collect.rs:69-71`).

**Inference — why the cache can afford this.** A cache entry's *content is a function of its key*. Two derivations of one key must produce identical bytes, so mutating an entry could never make it more correct — it could only make it disagree with its own key. Immutability is not a durability convenience there; it is a consequence of determinism.

**Proposal — a measurement is a sample, not a function of its key, so the aggregate must be mutable.** Two runs of one tuning key legitimately produce different numbers. That is not corruption; it is the phenomenon. An entry that could never be revised would either freeze the first sample forever — making the store's answer a function of run order — or force a new key per run, which fragments the very population the statistics need. The ticket names this correctly: entries are **refutable** rather than immutable.

**Proposal — but immutability is preserved one level down, and that is what keeps the crash story.** The store holds two kinds of object with opposite disciplines:

- **An observation** is one measurement session's complete record: the protocol descriptor it was taken under, the environment row observed at the time, the raw sample vector, and the oracle result. An observation is **immutable, content-addressed, and published exactly as a cache entry is** — one `create_new` temporary, validated through a separate descriptor, one `rename`. Observations accumulate; none is ever edited; the set under a key is append-only.
- **A verdict** is the ordering derived from the observation set under a stated aggregation rule. A verdict is **derived, replaceable, and never authoritative on its own**: it names the exact observation set it was computed from, and publishing a new verdict is another whole-file `rename` over the old one, not an edit.

**Inference — the inversion is therefore narrower and sharper than "entries are mutable".** *Evidence is immutable; conclusions are not.* The cache never had to make that distinction because in a deterministic world the conclusion is the evidence. Making it explicitly is what lets a later sample overturn a stored preference without anyone having to decide whether they are allowed to delete a measurement — they are not, and they never need to.

**Proposal — a verdict states what would refute it.** A verdict that says "A beats B" and nothing else is unfalsifiable in practice, because the next reader has no way to know whether one more sample would matter. A verdict therefore carries the separation statistic it was decided on and the sample count that produced it, so "one more observation with these properties would overturn this" is answerable by arithmetic rather than by rerunning the sweep. This is the discipline `component_cost.rs` already applies to its own definitional choices — "**The weighting is a definitional choice, not a derivation, so it is stated here to be refuted**" — applied to a statistic instead of a formula.

### 2.4 Atomic publication — **transfers unchanged, and is load-bearing twice**

**Fact.** "One `rename` from a `create_new` temporary file on the same filesystem is the only operation that makes an entry visible. The temporary is validated through a *separate descriptor* first, so the bytes that are checked are the bytes on disk rather than the bytes in a buffer this process still owns" (`expansion.rs:45-49`). In code: `create_temporary` uses `create_new(true)` (`store.rs:1051-1078`), `validate_written` re-reads it (`store.rs:970-1007`), and `fs::rename` at `store.rs:919` is the publication point, after which "no later failure can retract it" (`store.rs:933-937`).

**Proposal — transfers unchanged, and the reason it is needed twice is worth stating.** Publishing a *verdict* is exactly the cache's case: one whole object replaces another, atomically. Appending an *observation* looks like a different problem and should not be solved as one. **Proposal:** an observation is stored as its own content-addressed file in a per-key shard, so appending to the set is *creating a new file*, which the existing `create_new`-plus-`rename` mechanism already makes atomic and crash-safe. Appending to a shared log would need a record-framing and torn-write story that this repository does not have and does not need to invent; the set is the directory listing. This costs one inode per observation and buys the entire crash protocol for free.

### 2.5 Defined crash and race behaviour — **the rule transfers; what it falls open *to* inverts**

**Fact.** The cache's lock "is deliberately *not* the correctness boundary: correctness comes from the four properties above, each of which holds against a writer that dies at any point" (`expansion.rs:51-57`). ADR 0050: "Cache I/O failures fall open to validated uncached compilation." And `lib.rs:20-24`: "Falling open is *not* silence. Every rejection this crate makes is a typed reason the caller receives inside a `CacheReport` ... There is no path through this crate that produces a miss without producing the reason for it."

**Proposal — the rule transfers verbatim: every failure is a typed miss and none is silent. What it means to fall open inverts.** A cache miss falls open to *doing the work again*, which is slower and identical. A tuning miss falls open to *a different authority* — the analytic model — which may rank differently. So a cache miss changes only latency, while a tuning miss can change the selected plan and therefore the artifact. **Inference — that is why a tuning miss must be louder than a cache miss, not quieter.** A cache reports its miss for diagnostics. A tuning store must report its miss because the compiler's *output identity* depends on which authority answered, and explain must name that authority for the selected plan and for every rejected alternative. This is the same obligation `frontier.rs` already discharges for rejections — the whole reason `DeclinedStrategy` exists is that otherwise "the split's absence is unexplainable — which is the one thing an explainable frontier may not be".

### 2.6 Two properties the cache does not have, which the store needs

**Proposal — negative results are first-class and must be stored.** The cache stores no negatives; a failed compilation produces an error, not an entry. A tuning store must store "this plan was measured under this protocol and was slow" with exactly the status of "this plan was measured and was fast", because the expensive thing is the measurement and not the outcome. *Fact (Ansor, §7.4)* records the same economics from the other side: it counts search cost in "number of measurements" precisely because that "is a metric agnostic to the implementation of measurement and the overhead of search algorithm". *Fact (OpenTuner, PACT 2014, §3)*: its search and measurement modules "communicate exclusively through a results database used to record all results collected during the tuning process", and techniques "share results through the results database, so that improvements made by one technique can benefit other techniques". A store that discarded losing results would break exactly that sharing.

**Proposal — the store is evidence, not a memo, and its absence is never a correctness question.** The cache is an accelerator whose deletion changes nothing about what is compiled: ADR 0050's consequence list says "Generated Rust and binaries remain valid after whole-cache deletion." **The same property must hold for the tuning store and it must hold for a different reason.** Deleting the cache costs time; deleting the tuning store costs *ranking quality*, and the compiler must still emit a valid, explainable artifact. [Section 4](#4-the-fail-closed-story) is that guarantee.

### 2.7 The five properties, side by side

| Cache property (Fact, `expansion.rs:3-57`) | Transfers? | What the tuning store does (Proposal) |
| --- | --- | --- |
| Complete cache identity | **Transfers, widened** | The key adds an environment row, a protocol descriptor, and an oracle. Reuse scope moves *into* the key, inverting the cache's explicit non-property at `key.rs:60-66`. |
| Validation on every hit | **Splits** | Structural validation transfers verbatim. Semantic validation **inverts**: a cache hit is self-proving, a tuning hit is only unrefuted, and the separation test belongs to the consumer. |
| Immutable entries | **Inverts, at one level** | Observations are immutable and append-only; the derived verdict is replaceable. Evidence is immutable; conclusions are refutable. |
| Atomic publication | **Transfers unchanged** | One `create_new` temporary, validated through a separate descriptor, one `rename` — for a verdict, and for each observation, which is why appends need no new primitive. |
| Defined crash and race behaviour | **Rule transfers, target inverts** | Every failure is a typed miss. A cache miss falls open to redoing work; a tuning miss falls open to a *different authority*, so it must reach explain rather than only diagnostics. |
| *(no counterpart)* | **New** | Negative results are stored. |

## 3. The transfer model across shapes

The question — when does a result obtained for one shape apply to another — is the question parametric query optimization has been asking since 1992, and the answer this record reaches is the one that literature reached the hard way.

**Fact (Ioannidis, Ng, Shim, Sellis, VLDB 1992, abstract).** "Parametric query optimization attempts to identify several execution plans, each one of which is optimal for a subset of all possible values of the run-time parameters."

**Fact (adaptive-query-processing survey, §2.2.2).** "Despite the obvious appeal of parametric query optimization, there has not been much research in this area and the commercial adoption has been nearly non-existent. The bane of this technique is determining what plans to keep around: the space of all optimal plans is superexponential in the number of parameters considered." The same section records the two mechanisms that survived: validity ranges, where "if the values of the parameters are observed to be outside these ranges at the time of the execution, reoptimization is invoked", and progressive parametric query optimization, in which "the reoptimizer is called when error exceeds some bound (the Bounded implementation) or when there is no 'near match' among the set of possible plan configurations (the Ellipse implementation)".

**Measurement (Reddy and Haritsa, VLDB 2005, §1 and Fig. 2).** Over TPC-H queries on three commercial optimizers, plan diagrams "often appear similar to cubist paintings"; for Query 8 on one optimizer "no less than 68 plans cover the space in a highly convoluted manner". And the reduction result: that 68-plan diagram "can be 'reduced' to that shown in Figure 2(b) featuring as few as seven plans, without increasing the estimated cost of any individual query point by more than 10 percent". Their conclusion is that "current optimizers may perhaps be over-sophisticated in that they are 'doing too good a job', not merited by the coarseness of the underlying cost space".

**Fact (AutoTVM, §4).** "The key to transfer learning is to create a transferable representation that is invariant to the source and target domains. We can then share the cost model using the common representation across domains. Different choices of representations may have different levels of invariance." The mechanism is an additive split, `f(x) = f_global(x) + f_local(x)`, and the measured payoff is "a 2× to 10× speedup" on target workloads C7–C9 given 20,000–30,000 samples from source workloads C1–C6.

### The rule

**Proposal — Rule 1, and it is the whole answer.** *A measurement's only sanctioned route into selection is fitting a parameter whose domain is the machine, not the shape.* The analytic model is what generalizes across shapes; a measurement's job is to pin one of its constants. A table keyed by shape, mapping shapes to winning plans, is refused.

**Inference — the repository already did this and should be told that it was right.** The retained 2026-08-07 sweep (`spikes/program-planning/reduction-dispatch-crossover/`) measured 92 shapes and shipped exactly one scalar. Its calibration table describes its three parameters as "each a quantity of the machine and none of a strategy", and states the physics explicitly: "**The `max` is the whole of the model's physics and it produces the crossover instead of asserting it.** ... No parameter names a strategy and no strategy has a term of its own." The activated selector then dropped two of the three, keeping the one the mutation table showed carried the decision. **That is the transfer model.** Ninety-two shapes of evidence compressed into one number with no shape in it, and the shape-dependence recovered by an analytic form that was checked against held-out cells. Rule 1 states as a discipline what that sweep did as a practice.

**Why the alternative is refused, three ways.** The survey's superexponential-plan-space argument says a per-shape table cannot be complete. The plan-diagram measurement says a per-shape table is not *worth* being complete, because a 68-way partition collapses to 7 within 10%. And the sweep's own boundary note says a per-shape table would encode noise as structure: "**`parallel_threads` is determined to about a factor of four**", with the mutation table showing that quadrupling it leaves fit-set agreement unchanged and *improves* the held-out worst penalty from 1.81x to 1.20x. A table keyed at shape granularity would have memorized a contour whose position the evidence locates only to a factor of four.

**Proposal — Rule 2, the narrow exception, in the PPQO shape.** A future case may arise where no single machine parameter separates two implementations. The [flash-class capability record](../program-planning/flash-class-capability-set.md)'s axis 4 names the first identified candidate pair for which `CostComponent::ResourcePressure` would not be constant across candidates, and states that such a decision "turns on occupancy — the component that is `Unknown` for every plan"; it also records that no such pair is enumerable today, because the request boundary and fusion legality refuse a flash-shaped region earlier. When a case like it does arrive, a per-subject result is admitted **only** with a *declared validity region* over the shape space and a *declared tolerance*, and a subject outside the region is a **miss** that falls to the analytic model. It is never answered by the nearest stored region. The survey's "Ellipse" implementation is exactly a near-match rule, and near-match is admitted here only when the region and the tolerance are both declared by whoever took the measurement — never inferred from a distance metric the store invented. **Inference.** The reason is the one this repository states everywhere else: a nearest-neighbour answer is a confidently wrong answer with no way to tell it from a right one, which is what `resolve_work_items` already refuses to do for intermediate sizes ("two differently sized intermediates must not resolve to one of them", `frontier.rs:4576-4590`).

**Evidence gap, closed — Rule 2 unchanged, and now for a stated reason.** This paragraph originally named the construction of a validity range as something this record wanted and could not read. [`markl-pop-sigmod-2004`](sources/README.md#markl-pop-sigmod-2004) was subsequently retrieved and read; the row records the construction and the quotations below.

*Fact (Markl et al., SIGMOD 2004, §2.2).* A validity range is derived, not declared. It is a bound on an operator's input cardinality "such that if the range is violated at run-time, we can guarantee P is suboptimal with respect to the optimizer's cost model", computed as a by-product of pruning — when a surviving plan prunes an alternative, the optimizer solves for the cardinality at which the two cost functions intersect, by a modified Newton-Raphson iteration capped in practice at three steps. It is deliberately loose: "This range is defined conservatively, i.e., even within the validity range P may become suboptimal with respect to alternative QEP we do consider. This conservative definition is fine, since we only want to avoid needless re-optimization."

**Inference — Rule 2 stands, and the refusal to derive is now argued rather than merely cautious.** Three properties of the POP construction do not transfer. A POP range bounds where *the optimizer's own cost model* changes its mind, which is not where an observation of a machine stops applying — so deriving a measured result's region from Tiler's analytic model would bound the wrong quantity. POP's conservatism makes the range *wider* than the true optimality region, which is safe only because falling outside it triggers re-optimization, so a too-wide range costs POP a missed re-optimization and never a wrong answer; Tiler AOT-compiles one artifact with no recovery path, so a too-wide region means a stored result speaking for subjects it should not, which is the failure direction [section 4](#4-the-fail-closed-story) exists to forbid. And the derivation consumes the pruned alternatives and their cost functions at the moment of pruning, whereas Tiler discards alternatives after selection. Rule 2 therefore continues to require a region to be *declared*, and this record continues not to claim that this matches the POP construction — the difference is that it can now say why they differ.

**Proposal — Rule 3, the separation rule, promoted from analysis convention to store invariant.** A verdict may be recorded only for a subject whose alternatives are *separated*. The sweep's own definition: "A cell is **separated** when the gap exceeds two combined standard errors of the two medians", and its own reason for reporting unseparated cells apart rather than dropping them: "at a few hundred elements the whole plan costs less than one dispatch and the recorded order of three indistinguishable strategies is a coin toss". **Inference — this is the single most important rule in this record.** Without it a tuning store's dominant failure mode is not being wrong; it is faithfully recording coin tosses as preferences, in bulk, with full provenance, and then defending them on every subsequent compile. An unseparated comparison stores its observations and stores **no verdict**, and the consumer therefore falls to the analytic model — which is the same fail-closed direction as absence.

**Proposal — Rule 4, transfer never crosses an environment row.** *Fact (AutoTVM, §6.2):* the transfer evaluation forms its source domain from workloads C1–C6 and its targets from C7–C9 **within one hardware platform**, with the sample count stated per platform — "30000 samples in the TITAN X experiment and 20000 samples in the ARM GPU and ARM A53 experiments" — and the cross-device case is reported as its own separately labelled panel ("Mali GPU C1 C6 -> A53 CPU C7") rather than folded into the 2x-to-10x headline. **Inference.** So even the paper that makes transfer its contribution keeps the device boundary as a distinct, harder axis, and does not claim the headline speedup across it. *Fact:* the repository's own declaration path pins a measured cost row's validity at `TargetFactValidityScope::MeasuredEnvironment` specifically to stop it "widening into a portable claim" (`target.rs:2952-2974`). Since the environment row is part of the key ([section 2.1](#21-complete-cache-identity--transfers-and-must-be-widened)), a differing environment is a different key, and Rule 4 is enforced by construction rather than by policy.

**Proposal — Rule 5, no partial rankings.** `measured_scores` already refuses to rank a subset, and its doc comment gives the reason: "**Both refusals are all-or-nothing on purpose.** A comparison run over a subset would prefer whichever plan this derivation happened to understand, which is a preference for the compiler's own coverage rather than for the target's measured behaviour." Generalize it: if any alternative in a comparison lacks a valid, in-scope, separated verdict, the whole comparison declines. This is also why a store cannot silently mix a measured verdict for one candidate with an analytic estimate for another — that is a comparison across two model keys, which [section 0](#0-the-state-this-design-starts-from) records the frontier already refuses by name.

## 4. The fail-closed story

**Proposal — one sentence.** *The analytic model always answers; a measurement is only ever an additional later authority that must be present, valid, in scope, separated, and unrefuted, and if it is not any of those things the analytic model's answer stands unchanged and explain says which authority ranked the plan.*

**Fact — half of this is already true and already asserted.** `TargetCostRowResolution` distinguishes `Declared`, `Deferred`, and `Unknown`; `saturated_parallel_fold_steps`'s doc says `Unknown` "is an absence of preference and never a refusal: a consumer that treated it as a bound, a zero, or an infeasibility would invert the failure direction this row exists to avoid"; and `measured_scores` treats `Deferred` "exactly as silence, because a compile cannot wait for it". `select_non_dominated` records that the no-row path "is bit-identical to the one that existed before a cost row could be declared at all".

**Proposal — a tuning store adds four more silences, and every one of them is typed and none of them is a value.**

| Resolution | Meaning | Answer |
| --- | --- | --- |
| `Unknown` | No entry for this key. | Analytic model. *(exists)* |
| `Deferred` | The fact is declared at a later availability phase than the caller's. | Analytic model. *(exists)* |
| `OutOfScope` | An entry exists for this subject under a **different environment row**. | Analytic model. **Not a degraded hit — not a hit.** |
| `Unseparated` | Observations exist; the alternatives are inside each other's noise. | Analytic model. |
| `Refuted` | A later observation overturned the stored verdict and no replacement has been published. | Analytic model. |
| `Malformed` | The entry failed structural validation. | Analytic model, plus a typed report; the entry is quarantined, never trusted. |

**Proposal — the rule with no counterpart in the cache, stated on its own because it is the one a well-meaning implementer will break.** *There is no "last known good" measurement.* A cache that finds a corrupt entry redoes the work and gets the same answer; falling back costs only time. A tuning store that answered from a stale or out-of-scope entry would be preferring an unrefuted claim about a machine that is not this machine over a claim the compiler can still derive and check. **Inference.** The failure is asymmetric and that asymmetry is the whole argument: an analytic answer that is worse is *wrong by a factor and explainable*; a stale measured answer that is worse is *wrong by a factor and carries provenance saying it was measured*, which is strictly harder to catch. AGENTS.md's rule — "Prefer typed, explainable failure over a silently wrong fast path" — decides this without needing a new principle.

**Proposal — the artifact records which authority ranked its plan.** A plan selected by the analytic model and a plan selected by a measured verdict are different claims about why that artifact exists, and a consumer, a benchmark, or a later calibration must be able to tell them apart without re-running the compiler. This is the same obligation as the annotation half of [section 1](#1-where-measurement-enters), and it is the one place where the two decisions meet.

## 5. Statistical discipline for noisy GPU timings

The rules below are grounded in Hoefler and Belli (SC '15) and in the one measurement protocol this repository has actually executed. **Quotations of the twelve rules are verbatim from the digested byte stream.**

**Proposal — the protocol is part of identity, not part of the prose.** Two timings taken under different warm-up counts, repetition counts, interleaving policies, or amortization schemes are *different measurements of different things* and must not share a key. This is [section 2.1](#21-complete-cache-identity--transfers-and-must-be-widened)'s completeness property applied to the measurement rather than to the compilation, and it is exactly what **Rule 9** asks for — "Document all varying factors and their levels as well as the complete experimental setup (e.g., software, hardware, techniques) to facilitate reproducibility and provide interpretability" — made machine-readable instead of prose. **Rule 10** — "For parallel time measurements, report all measurement, (optional) synchronization, and summarization techniques" — is the same obligation for the timing instrument, and the repository's sweep already discharges it in prose by stating that its samples are wall clock across `commit()` and `wait_until_completed()` and "**this is not a GPU-busy measurement**".

**Proposal — warm-up is mandatory and its count is stored.** The retained sweep uses "Eight untimed submissions per alternative at each encode count" before any timed one. The number is not the point; storing it is, because a verdict taken after eight warm-ups and one taken cold are not comparable and nothing else records the difference.

**Proposal — repetition, interleaving, and rotation are required, and rotation is the part usually omitted.** The sweep's timed submissions are interleaved: "each of thirty rounds submits every alternative once, and the round's starting alternative rotates, so a thermal or scheduling drift lands on all three strategies alike instead of on whichever ran last." **Inference.** Without rotation, a monotone drift over the run is indistinguishable from a real difference between the last-measured and first-measured candidate, and no amount of repetition fixes it because the confound is in the ordering rather than in the count.

**Proposal — store the sample vector; never store only a summary.** **Rule 5:** "Report if the measurement values are deterministic. For nondeterministic data, report confidence intervals of the measurement." **Rule 8:** "Carefully investigate if measures of central tendency such as mean or median are useful to report. Some problems, such as worst-case latency, may require other percentiles." **Inference.** A store that kept only a median has thrown away the ability to answer any question its designer did not anticipate, including every tail question, and cannot recompute a separation test under a different tolerance. Keeping the vector costs kilobytes against a measurement that cost seconds.

**Proposal — no outlier is discarded.** This is stated as a rule rather than left to judgement because discarding is the default reflex. On a GPU an outlier is usually a *real* scheduling, residency, or thermal event, and removing it silently converts a robustness measurement into a throughput measurement. Instead, report a high quantile beside the median, which is what **Rule 8** explicitly contemplates. Where a single number is needed for ordering, use the median, and retain p90 so that a later reader can refute an ordering that holds only at the median. The sweep already does this — "Minimum, median, p90 and sample standard deviation are reported at both encode counts rather than a single number."

**Proposal — separation, not comparison of point estimates.** **Rule 7:** "Compare nondeterministic data in a statistically sound way, e.g., using non-overlapping confidence intervals or ANOVA." The sweep's two-combined-standard-errors gap test is an instance of this, and it is what [section 3, rule 3](#3-the-transfer-model-across-shapes) promotes to a store invariant.

**Fact, recorded as a weakness rather than repaired.** **Rule 6:** "Do not assume normality of collected data (e.g., based on the number of samples) without diagnostic checking." The retained sweep's separation test is built on standard errors of medians, which is a parametric shortcut, and no diagnostic check of the sample distributions is recorded anywhere in that spike. **Inference.** The repository's one executed measurement protocol currently fails Rule 6 and partially fails Rule 8 — it reports p90 but its *decision* rule uses only the median and a standard error. Neither invalidates the sweep's headline result, which turns on ratios of 50.7x and 0.56x that no distributional assumption could manufacture; both would matter at the margin, and the margin is exactly where the two held-out misses sit. This is named here so that a tuning store is not built on the assumption that the separation rule it inherits is distribution-free. A nonparametric replacement — bootstrap confidence intervals on the median, or a rank test — is the obvious repair and is not specified here because it is a measurement-protocol change and belongs with the protocol's owner.

**Proposal — ratios are reported beside absolutes, never instead of them.** **Rule 3:** "Use the arithmetic mean only for summarizing costs. Use the harmonic mean for summarizing rates." And the generalization Hoefler and Belli draw from Rule 1: "one should never report ratios without absolute values." The sweep complies, reporting per-plan microseconds beside every ratio. A stored verdict must do the same, because a ratio alone cannot be re-derived, re-scaled, or combined with a later observation.

**Proposal — an environment attestation is recorded, not assumed.** The sweep records host load averages before and after and states that "This run had the machine to itself". **Inference.** An unattested measurement on a shared host is not a weaker measurement; it is a measurement of an unknown quantity, and there is no way to tell from the numbers alone. The environment row therefore carries the attestation, and an observation taken without one is admissible as data and inadmissible as a verdict.

## 6. What this record does not decide

**A learned cost model.** The ticket names this a non-goal and this record honours it. **Inference — what would have to be true first**, stated so the deferral has a shape: a learned model consumes a corpus, and the corpus is the tuning store. Every property decided above — complete identity including the environment row, immutable observations, the separation rule, stored negatives — is a precondition for a corpus that could train anything, and every one of them is violated by the obvious shortcut of storing winners. So this record's position is that the store is worth designing *whether or not* a learned model ever arrives, and that deciding the model before the store would be deciding the cheap half first. The trigger is the same as [section 1](#1-where-measurement-enters)'s: a compilation mode that may touch a device.

**Whether Tiler ever ships several plans in one artifact.** This is parametric query optimization, it is what [section 1](#1-where-measurement-enters)'s post-hoc refinement would require, and it is a product expansion. Tom's. *Measurement (Cole and Graefe, SIGMOD 1994, §6), recorded to price the option rather than to decide it.* Their prototype shipped every potentially optimal plan in one access module and chose among them at start-up; for a ten-way join with eleven uncertain parameters "the difference in plan size is 14,090 versus 21 operator nodes", optimization time rose by under a factor of three, and the increase is attributed to branch-and-bound pruning becoming less effective once costs are allowed to be incomparable. **Inference.** The artifact-size cost of this expansion is real but is not the argument against it; the argument against it is that a choose-plan decision re-evaluates the *analytic* cost functions once the missing bindings arrive, so it varies when a cost-model parameter becomes known rather than admitting a measurement — which is the axis `AvailabilityPhase` already models, without the retention obligation. See [`cole-graefe-sigmod-1994`](sources/README.md#cole-graefe-sigmod-1994).

**The exact record shapes.** Four facets, two object kinds, and six resolutions are named above as *what must be distinguished*. Their spelling is a public boundary and is not proposed here.

**The nonparametric separation test.** Named as a gap in [section 5](#5-statistical-discipline-for-noisy-gpu-timings), owned by the measurement protocol rather than by this design.

## Sources and evidence gaps

Fourteen primary documents were obtained, digested, and read as extracted text; their exact references, retrieval URLs, SHA-256 digests, and what each is cited for are in [the source record](sources/README.md). Eleven were read before this record was first written. Two more — Markl et al.'s progressive optimization and Cole and Graefe's dynamic query evaluation plans — were retrieved afterwards, and they are exactly the two documents whose absence made two conclusions here thinner than the rest. **Both conclusions stand unchanged on the evidence that was missing.** The construction of a validity range in [section 3, rule 2](#3-the-transfer-model-across-shapes) is now argued rather than merely cautious: POP derives its ranges, and the three properties that make its derivation safe in a re-optimizing engine are the three Tiler does not have. The choice of the availability-phase ladder over a run-time choose-plan operator is now supported rather than unopposed: a choose-plan decision re-evaluates analytic cost functions when bindings arrive, so it addresses the same axis as `AvailabilityPhase` and adds an obligation to carry every alternative in the artifact.

**No document remains unread.** The fourteenth is Graefe and Ward's 1989 original, the origin of the choose-plan line, which this host could never fetch — every route terminated at a publisher bot wall — and which Tom supplied from a browser on 2026-08-07. Reading it **strengthens the availability-phase conclusion a second time and changes nothing else here.** The 1989 design's decision procedure is genuinely cheaper at start-up than its 1994 successor's, because it compares run-time bindings against break-even values computed at compile time rather than re-running cost functions. But it does not escape the obligation that is the actual argument against the line: the paper states that "the access module must also contain the support functions for all possible query evaluation plans", and it carries **no** optimality guarantee — that guarantee is 1994's contribution. So the origin has the same retention cost as its successor without the justification, and there is no earlier, cheaper form of choose-plan that would resolve a deferred cost row at a later availability phase without carrying alternatives. That was the one finding that could have made the line competitive with the ladder rather than a superset of it, and it is refuted. The [source row](sources/README.md#graefe-ward-sigmod-1989) carries the quotations, the provenance, and the settlement of two secondary characterisations this record's sources previously repeated at second hand. No claim in this record rested on the document either way.

The one measurement this record leans on is not its own. It is [the retained dispatch sweep](../../../spikes/program-planning/reduction-dispatch-crossover/README.md) of 2026-08-07, bounded to one profile, one contract, one program family, `f32`, and one host row, and every claim taken from it is bounded the same way.
