Current repository behavior:
  - `ExecutionEnvironment` is a single (profile, backend, representation, dtype_dispatch) tuple; hosts state it, the loader does not discover it.
  - `DecodedProgram::preflight` / `prepare` take one `&ExecutionEnvironment`. Selection is eligibility (pair + profile + dtype) then stable-priority guard walk; other-family variants contribute `FilteredVariant` rows and never reach guards.
  - Multi-family packaging works (`assemble_portfolio` + Metal selection-only members). Multi-family *preference* does not: a host can run only the family it stated; there is no typed allowed/required/fallback-only backend-family policy type.
  - Compiler side already binds ordered multi-contract preference into the request subject via `CompileRequest::preferring`; the loader has no analogue for multi-family willingness.
  - Composition parent is terminal with the family-policy remainder split to express, which depends on this decision. Exercise still requires Metal-or-CPU policy tests end to end.
