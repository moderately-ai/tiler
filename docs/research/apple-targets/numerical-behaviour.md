# Apple GPU f32 numerical behaviour

**Status:** bounded measurement on one host, one Mac GPU, one booted iOS Simulator, the offline `xcrun metal` toolchain, and the two runtime compilers those two execution environments load. Every value below is reproduced by a checked-in harness; every one except the exhaustive-only rows named in finding 19 is reproduced by the repository gate on every run. None of it is a portable guarantee about Metal, and the one thing this record establishes across families it establishes as a bounded one-host measurement rather than as a property of the families.

**Fact — this record's title is stale and the rename is a separate ticket.** The frontmatter title and heading still say `f32`; since finding 21 the record measures `f32` and `f16`, and since finding 24 it measures `bf16` as well. The title string is reproduced in four generated catalog blocks under `contracts/navigation` and in three prose citations under `contracts/decisions` and `contracts/artifacts`, none of which [widen-the-apple-numerical-probe-to-a-second-dtype](../../../tickets/widen-the-apple-numerical-probe-to-a-second-dtype.md) or [measure-the-apple-subnormal-flush-for-the-remaining-mature-dtypes](../../../tickets/measure-the-apple-subnormal-flush-for-the-remaining-mature-dtypes.md) holds a scope for, so renaming it here would have been a scope escape rather than a coherent edit. [rename-the-apple-numerical-record-past-one-dtype](../../../tickets/rename-the-apple-numerical-record-past-one-dtype.md) carries it with the scopes it needs. Read the title as naming the record's origin, not its extent.

**Probe date:** 2026-07-25 for findings 15 to 27, the widened matrix, and the second and third dtypes; 2026-07-24 for findings 1 to 14, on the same host row.

This record owns the measurements [ADR 0076](../../decisions/0076-declare-target-honourable-numerical-realizations.md) depends on. Before it existed those measurements lived only in the outcome of [prototype-metal-numerical-realization](../../../tickets/prototype-metal-numerical-realization.md) and in the ADR's own re-verification, taken by a hand-built Objective-C host that was never checked in. Nothing re-established them, and a hand-run measurement in this repository has already stopped being true within the hour once unrelated work changed the compiled source. The harness is [`spikes/apple-targets/numerical_probe.py`](../../../spikes/apple-targets/numerical_probe.py) with the dispatch host [`spikes/apple-targets/numerical_probe_host.m`](../../../spikes/apple-targets/numerical_probe_host.m); the assertions are [`spikes/apple-targets/test_numerical_probe.py`](../../../spikes/apple-targets/test_numerical_probe.py), which `scripts/check_repository.py` collects; and the retained values are [`results/2026-07-25-numerics-covering-xcode26.6-metal32023.883/record.tsv`](../../../spikes/apple-targets/results/2026-07-25-numerics-covering-xcode26.6-metal32023.883/record.tsv), the set the gate runs, with [`results/2026-07-25-numerics-exhaustive-xcode26.6-metal32023.883/record.tsv`](../../../spikes/apple-targets/results/2026-07-25-numerics-exhaustive-xcode26.6-metal32023.883/record.tsv) beside it for the rows only the exhaustive sweep produces. The schema `v3` record [`results/2026-07-24-numerics-families-xcode26.6-metal32023.883/record.tsv`](../../../spikes/apple-targets/results/2026-07-24-numerics-families-xcode26.6-metal32023.883/record.tsv) is retained as the previous row and is no longer the record any run is compared against.

**Fact — two case matrices, and why a record names which one it is.** The widened matrix costs more than the gate should pay on every run, so the harness assembles a `covering` set and an `exhaustive` one. The covering set keeps at least one case of every kernel, math mode, optimization level, contraction setting, and `-fmetal-math-fp32-functions` value, and every case a finding below cites; `TILER_APPLE_NUMERICS_EXHAUSTIVE` selects the full cross product on the widened axes. `probe.matrix` records which one produced a record and the comparison refuses to read one against a run of the other, because every case the two sets do not share would otherwise read as decay. A guard test that needs no toolchain holds the covering set to its coverage claim, so narrowing an axis is a test failure rather than a quieter record. **The boundary this leaves:** a row measured only under the switch is re-checked only when someone sets it. It is retained evidence with a reproducing command, not a gate-protected value, and it is labelled as such wherever a finding below rests on it.

Findings 1 to 7 and their disagreements with the values they reproduce were established by [check-in-apple-numerical-behaviour-probe](../../../tickets/check-in-apple-numerical-behaviour-probe.md) through the offline compilation path alone, for the macOS family only. Findings 8, 9, and 10, and the account of what replaces the emitted-IR guard layer, were added by [probe-metal-runtime-compilation-numerics](../../../tickets/probe-metal-runtime-compilation-numerics.md), which put the byte-identical source through `newLibraryWithSource:options:` as well and compares the two paths case by case. Findings 11 to 14, which carry every one of those measurements across `MetalPlatform`'s three artifact families and state whether the subnormal flush is Apple-wide or per-family, were added by [measure-numerics-across-apple-artifact-families](../../../tickets/measure-numerics-across-apple-artifact-families.md). Findings 15 to 19, which widen the operation vocabulary past multiply and add and close the `-fmetal-math-fp32-functions` and optimization-level boundaries this record used to carry, were added by [broaden-the-apple-numerical-probe-matrix](../../../tickets/broaden-the-apple-numerical-probe-matrix.md). Finding 20, which isolates input flushing on an add whose subnormal operand is not the output of a preceding multiply, was added by [extend-the-numerical-probe-to-an-additive-path-kernel](../../../tickets/extend-the-numerical-probe-to-an-additive-path-kernel.md). Findings 21 to 23, which widen the *dtype* and answer whether the subnormal flush is dtype-independent, were added by [widen-the-apple-numerical-probe-to-a-second-dtype](../../../tickets/widen-the-apple-numerical-probe-to-a-second-dtype.md); finding 21 is the one measurement in this record that refutes rather than refines something it previously carried. Findings 24 to 27, which add `bf16` — the dtype that discriminates between the two mechanisms finding 21 left undistinguished — were added by [measure-the-apple-subnormal-flush-for-the-remaining-mature-dtypes](../../../tickets/measure-the-apple-subnormal-flush-for-the-remaining-mature-dtypes.md). The retained record's directory name identifies the offline toolchain; its `environment.family.<name>.*` rows identify each family's SDK, emitted triple, execution environment, and the two compilers behind it.

**Fact — the case keys the widening added, and the ones it deliberately did not change.** A case key names its `-fmetal-math-fp32-functions` value only when that value is not the pinned `precise`, so every key recorded while the flag was fixed keeps its exact meaning and only the departing cases — whose keys end in `.fpfun-fast` — are new. `probe.default_fp32_functions` states the default the unsuffixed keys carry. The same rule carries the dtype: a kernel names its dtype in its own name only when that dtype is not `f32`, so the new keys are exactly the ones whose kernel ends in `_f16` or `_bf16` and every key any earlier finding cites keeps its exact meaning. `probe.default_dtype` states the default and `probe.dtypes` names every dtype measured. The record schema is `tiler.apple-numerical-behaviour/v6`.

**Fact — a recorded result is rendered at its own dtype's width.** Since schema `v5` a `case.*.results` row carries four hex digits for an `f16` kernel and eight for an `f32` one, and `probe.operands` became the per-dtype `probe.operands.f32`, `probe.operands.f16`, and now `probe.operands.bf16`. A reader may no longer assume every pattern in this record is 32 bits wide; the kernel name in the case key is what says which it is. **Two dtypes now share a width**, so the digit count no longer identifies the format either: `f16` and `bf16` rows are both four digits and only the kernel name distinguishes them, which is exactly why the same four digits `0080` mean a subnormal in one and a normal in the other.

**Fact — schema `v6` adds one row kind, because one device answered a question with a refusal.** `case.*.refusal` is present exactly when a family's device was asked to run a kernel and declined, which is a different fact from the family having no device at all. A case with no `results` row and no `refusal` row was never dispatched; a case with no `results` row and a `refusal` row was dispatched at and rejected, with the exact diagnostic recorded. `environment.family.<name>.device_bfloat_support` carries the per-family answer. Finding 26 is why this distinction exists.

## Which artifact family each finding covers

`tiler_metal::target::MetalPlatform` declares three families — `MacOs`, `IOsDevice`, and `IOsSimulator` — and `MetalTargetFacts::new` requires a caller to state `subnormal_arithmetic` for whichever one it is emitting for. The findings reach the three families unevenly, and the split is not incidental:

- **Fact — the compile side covers all three.** `air.compile.denorms_disable`, the fast-math licence spellings, and the surviving operation counts are read out of the emitted module, which needs no device. Findings 1, 4, 6, and 7's compile-side halves, and finding 11, hold for `MacOs`, `IOsDevice`, and `IOsSimulator` alike, and so do the compile-side halves of findings 15 to 27: the division rewrite, the fused call, the two-adds-into-one fold, the fp32-functions inertness, the optimization-level equality, the survival of the bare add under every math mode, and — findings 22 and 27 — the `f16` and `bf16` modules' declaration of `air.compile.denorms_disable` are each asserted for all three families.
- **Measurement — the device side covers macOS and the iOS Simulator, not an iOS device, and covers `bf16` on macOS alone.** A returned bit pattern is a property of the GPU that executed the kernel, so a family is dispatched only in its own execution environment. `MacOs` runs on the host GPU and `IOsSimulator` runs through `simctl spawn` on a booted runtime; `IOsDevice` runs nowhere, because this host has no iPhone or iPad attached. Findings 2, 3, 5, and 7's device-observable half hold for the two families that dispatch and are **unmeasured** for `IOsDevice`, and so do the device-observable halves of findings 15 to 23. Finding 21's dtype dependence is therefore measured on two families and inferred for none: for `IOsDevice` the *compile* side agrees and the arithmetic is unmeasured, exactly as for `f32`. **Finding 24 reaches one family only.** The iOS Simulator compiles and links every `bf16` module and then refuses to create a pipeline for it (finding 26), so `bf16` arithmetic is measured on the Mac GPU and is `Unknown` for both iOS families — refused for one, never asked for the other.
- **Fact — the simulator's GPU is the Mac's, and a simulator result is not evidence about a device.** `environment.family.ios-simulator.device_registry_id` is identical to the macOS one: the iOS Simulator dispatches on the host GPU under a different device name. That is exactly why finding 13 is a measurement about the simulator and not about iOS-device hardware, and why the device gap for `IOsDevice` is recorded rather than filled by loading its module on this Mac — which, finding 14 shows, the Mac will happily do.

## Evidence classification

This memo uses the four repository labels. **Fact** is supported by inspected source or primary documentation. **Measurement** is a direct observation tied to the exact environment and procedure below. **Inference** is derived from stated facts and measurements. **Proposal** remains to be accepted or tested.

## Measurement environment

**Measurement — the qualified row.** Apple M4 Max (`MTLCreateSystemDefaultDevice` reports `Apple M4 Max`, `registryID` 4294968621), macOS 27.0 build 26A5388g, arm64; Xcode 26.6 build 17F113. Three SDKs, one per family: `macosx` 26.5 build 25F70, `iphoneos` 26.5 build 23F81a, `iphonesimulator` 26.5 build 23F81a. One offline toolchain shared by all three SDKs: `Apple metal version 32023.883 (metalfe-32023.883)` and `AIR-LLD 32023.883 (metalfe-32023.883)`, resolved from the Xcode MetalToolchain asset. **Two runtime compilers, one per execution environment:** the macOS host loads `GPUCompiler.framework` build `metalfe-32023.921` (the same build the `MTLCompiler.framework` archive spelled as `Apple metal version 32023.921`), and the booted iOS Simulator — iOS 26.0 (26.0.1) build 23A8464, GPU reported as `Apple iOS simulator GPU` with the **same** `registryID` as the Mac — loads its own runtime `GPUCompiler.framework` build `metalfe-32023.830.1`. Findings 8 and 12 discuss the compilers; the shared registry ID is finding 13's boundary.

**Fact — the procedure.** Each probe kernel is generated in the Metal emitter's output shape, with every immediate written as an exact bit pattern through `as_type` — `as_type<float>(0x…u)` for `f32`, `as_type<half>(ushort(0x…u))` for `f16`, and `as_type<bfloat>(ushort(0x…u))` for `bf16`, the conversion being required because an unsuffixed integer literal is `uint` and `as_type` needs matching widths — so no decimal rendering stands between the stated constant and the compiled one, and no narrow constant is rounded twice on its way in. For each family it is compiled three ways from identical source bytes through that family's `--sdk` and `-target`: `xcrun --sdk <sdk> metal -target <family-target> -std=metal3.1 -O<level> -fmetal-math-mode=<mode> -fmetal-math-fp32-functions=precise -ffp-contract=<contract> -S -emit-llvm` for the emitted LLVM IR, the same command with `-c` for AIR, and `xcrun --sdk <sdk> metallib` to link. The targets are `air64-apple-macos13.0`, `air64-apple-ios16.0`, and `air64-apple-ios16.0-simulator`; `-std=metal3.1` raises each to the emitted triple recorded in `environment.family.<name>.emitted_triple`. A linked library is dispatched only for a family that has an execution environment, by a hand-written Objective-C host using `MTLCreateSystemDefaultDevice`, `newLibraryWithURL:`, `MTLResourceStorageModeShared` buffers, and one thread per output element, with `f32` bit patterns in and out. The host requires `MTLCommandBufferStatusCompleted` and a nil `commandBuffer.error` before reading the shared allocation back, and seeds the output buffer with a pattern no probe kernel can produce so an unwritten element is distinguishable from a written zero. One host invocation dispatches a whole per-family manifest so the iOS Simulator's roughly 290 ms `simctl spawn` launch is paid once rather than per case.

**Fact — the second procedure, added by [probe-metal-runtime-compilation-numerics](../../../tickets/probe-metal-runtime-compilation-numerics.md).** The byte-identical generated source is also compiled *in the dispatch host's own process* by `[device newLibraryWithSource:options:error:]` with an `MTLCompileOptions` whose `mathMode`, `mathFloatingPointFunctions`, `languageVersion`, and `optimizationLevel` are all set explicitly, and the resulting library takes the identical path to the GPU — same pipeline creation, same shared buffers, same terminal-status check, same readback. A difference between the two therefore cannot be an artefact of dispatching them differently. The host rejects an unrecognized option key or value with a usage exit rather than compiling with it defaulted, which the gate checks directly, because `mathFloatingPointFunctions` defaults to `Fast` and a silently ignored selection would make the record name a configuration the library was not built with.

**Fact — the operand vectors, one per dtype.** Every dispatch of an `f32` kernel uses one vector, so a single launch answers every question about that kernel: `00000001` (smallest positive subnormal), `00400000` (mid subnormal, whose double is the smallest normal), `007fffff` (largest subnormal), `00800000` (smallest positive normal, whose half is subnormal), `80400000` (negative mid subnormal), `80000000` (negative zero, which is not subnormal), `3eb97ef9` (an ordinary normal that reveals fusion), and `3f800000` (`1.0`, the execution witness for the scaling kernels).

An `f16` kernel uses a second vector whose eight entries occupy the same eight roles at `f16`'s own boundaries: `0001`, `0200` (mid subnormal, whose double is the smallest normal), `03ff`, `0400` (smallest positive normal, whose half is subnormal), `8200`, `8000`, `3555` (an ordinary normal), and `3c00` (`1.0`). Keeping the roles aligned is what makes a difference between the two records' results a difference in what the hardware did rather than in what it was asked, and it is why finding 21 can be stated as one sentence about a pair of kernels. One entry's role is deliberately not symmetric: halving the smallest subnormal rounds to zero in both formats, so the result-flush probe uses the smallest *normal* in both, and a returned zero from halving `0001` would be correct rounding rather than a flush.

A `bf16` kernel uses a third vector in the identical eight roles at `bfloat16`'s boundaries: `0001`, `0040` (mid subnormal, whose double is the smallest normal), `007f`, `0080` (smallest positive normal, whose half is subnormal), `8040`, `8000`, `3eab` (an ordinary normal), and `3f80` (`1.0`). **The arithmetic relation between this vector and the `f32` one is the whole reason the dtype was chosen.** `bfloat16` is exactly `f32` truncated to its high 16 bits, so `0040` widened is the `f32` pattern `00400000` and `0080` widened is `00800000` — the same two patterns the `f32` input-flush probe uses. Every `bf16` subnormal is therefore an `f32` subnormal, where every `f16` subnormal is an `f32` **normal**. Finding 24 is what that difference buys.

## Why a returned bit pattern is not, by itself, evidence

This is the load-bearing methodological point and it is encoded in the harness as a guard, not merely described here.

**Measurement — a relaxed mode can appear to honour a strict contract by deleting the arithmetic.** The emitter's `MultiplyThenAdd { scale 1.0, bias +0.0 }` shape computes an identity on every operand. At `-O2` the emitted module retains exactly one floating-point operation under `safe` — the `fadd` of `+0.0`, which cannot be removed without `nsz` — and **zero** under `relaxed` and under `fast`. Dispatched, it returns `00000000` for every subnormal operand under `safe` and returns every subnormal operand **unchanged** under `relaxed` and `fast`. Read from the returned patterns alone, the relaxed modes look like the ones that preserve subnormals. They are the ones in which no arithmetic ran.

**Measurement — counting operations in the emitted IR is necessary and not sufficient.** At `-O0` the same kernel under `relaxed` and under `fast` still carries **two** floating-point operations in the front end's LLVM IR, and the GPU nonetheless returns every operand unchanged, negative zero included. Something below the IR this harness can read — the AIR-to-ISA compilation the driver performs at pipeline-state creation — removed them. ADR 0076's account ("counting floating-point operations in the emitted LLVM IR explains it") is correct at `-O2` and incomplete at `-O0`.

**Fact — the guard the harness encodes.** `numerical_probe.subnormal_verdict` refuses to classify an observation as `preserved` or `flushed-to-zero` unless two conditions hold. First, the emitted module must contain at least one floating-point arithmetic instruction; `fcmp` is deliberately excluded, so a NaN test cannot stand in for a surviving multiply. Second, the same kernel in the same configuration must return its **execution witness**: a designated non-subnormal operand whose result differs from the operand exactly when the arithmetic ran. `multiply_two` witnesses on `3f800000 → 40000000`; the `scale 1.0, bias +0.0` kernel witnesses on `80000000 → 00000000`. A kernel that is an identity on every operand has no possible witness, `Kernel.witness` is `None` for exactly those, and every observation from them is classified `no-execution-witness` and is inadmissible. The remaining verdicts — `no-emitted-arithmetic`, `arithmetic-not-executed`, `witness-disagrees`, `unexpected-result` — each name a precise reason the observation proves nothing, rather than collapsing into a boolean.

**Inference — this is the same conclusion ADR 0076 draws, reached independently and strengthened.** Because a relaxation can delete the arithmetic, and because it can do so at a stage below the emitted IR, observing preserved subnormals from a compiled kernel is not evidence that a target preserves them. A target's numerical honourability must be a stated, versioned target fact. No amount of probing a kernel can substitute for it, and a design that tried would infer the wrong fact precisely under the modes least worth trusting.

**Fact — whether the operation was deleted or special-cased is not distinguished.** `x * 1.0f` at `-O0` retains an `fmul` in the emitted IR and returns every subnormal operand unchanged. Two explanations fit: the backend folded the multiply, or the hardware multiplier passes a denormal through when the other operand is exactly `1.0`. The harness does not separate them and does not need to; neither supports a claim about what arithmetic does, and the witness guard rejects the observation either way.

### What replaces a missing guard layer, on either side

A guard layer can be missing in two different situations, on opposite sides, and the data model keeps each absence distinguishable from a measurement rather than defaulting a field.

**Fact — layer 1 is unavailable on the runtime path, and the harness says so rather than substituting for it.** `newLibraryWithSource:options:` returns an opaque `MTLLibrary`; there is no emitted module to read. `Observation.operations` is therefore `None` for a runtime case and never `()`, because `()` asserts a *measured* absence of arithmetic while `None` records that the question could not be asked. `subnormal_verdict` skips layer 1 only for `None`, and the retained record omits the `case.*.float_operations` row for a runtime case entirely instead of writing an empty one, so no reader can mistake the two. A portable guard test pins that distinction on every gate run, including on a host with no Apple toolchain at all.

**Fact — layer 2 is unavailable for a family with no attached device, and that is the more dangerous absence.** `IOsDevice` compiles here but never dispatches, so it has an emitted module and no returned bit pattern. `Observation.results` is `None` for exactly those cases and never `()`, for the same reason `operations` is `None` on the runtime path: `()` would assert a dispatch that returned nothing. `subnormal_verdict` returns the distinct `no-device-observation` verdict before consulting anything else, `result_for` raises rather than inventing a value, and the record omits the `case.*.results` row. This is a distinct verdict rather than a reuse of `no-emitted-arithmetic` because the two say opposite things: one is a family whose compiler emitted no arithmetic, the other is a family whose arithmetic was never run. A portable guard test pins this `None` too.

**Inference — losing layer 1 is cheap and losing layer 2 is not.** Layer 2 is device-side and *sufficient* for "the arithmetic under test executed"; layer 1 is compile-side and merely *necessary*. Any observation layer 1 would reject emitted no arithmetic, so nothing ran, so the kernel returns its operands, so layer 2 rejects it as `arithmetic-not-executed`. The converse fails, and this harness measured it failing: at `-O0` layer 1 passed with two emitted operations and layer 2 was the layer that caught the deletion. So losing layer 1 on the runtime path costs only a compile-side cross-check and a distinct diagnostic. Losing layer 2 costs the admissibility decision itself: a compile-side-only observation can never be admissible evidence about arithmetic, which is why it can yield neither `preserved` nor `flushed-to-zero` under any operand pattern and gets its own inadmissible verdict instead of being classified by the layer it still has. This is the guarantee the ticket named as the one most likely to be dropped, and it is encoded in the data model rather than in prose.

**Fact — what the runtime path does instead, on every run.** A guard that never refuses anything is not a guard, so with only one layer left the harness must keep demonstrating that the layer still discriminates *on that path*: `test_the_runtime_guard_still_discriminates_when_a_toolchain_and_gpu_resolve` requires the trap kernel to be refused under `relaxed` and `fast` — on results whose unguarded reading is `preserved` — and admitted under `safe`, in the same process, in the same run.

**Measurement — one compile-side artefact survives, and it is corroboration rather than evidence.** Serializing the runtime-built pipeline into an `MTLBinaryArchive` and scanning the container recovers the compiler's version string and the presence of individual `air.compile.*` names. The container has no published layout and stores its strings concatenated without separators, so a scan can decide whether a given byte sequence is *present* but can recover neither the option set nor which strings the module attached to its `air.compile_options` node — which is exactly what the offline path resolves properly rather than substring-matching. Nothing in the admissibility guard consults it.

## The findings

Each is stated with the exact case key in the retained record, so a reader can locate the raw row in one step. Findings 1 to 10 were established on the macOS family and their case keys are written here without a family prefix for readability; in the schema `v3` record every key is prefixed by its family, so the macOS row for finding 1 is `case.macos.scale_two_bias_one.*.compile_options`. Findings 11 to 14 state their scope across families explicitly. Findings 11 and 12 establish that findings 1 and 8's compile-side facts hold with **identical bytes** for the two iOS families as well, so the unprefixed keys below are exact for macOS and, except where a finding says otherwise, reproduced for `IOsDevice` and `IOsSimulator` at their own prefixes.

### 1. `-fmetal-math-mode=safe` still disables denormals

**Measurement.** `air.compile.denorms_disable` appears in the emitted module's `air.compile_options` under `safe`, `relaxed`, and `fast` alike, at every `-ffp-contract` setting (`case.scale_two_bias_one.*.compile_options`). Under `safe` it appears alongside `air.compile.fast_math_disable`, and no emitted `fmul` or `fadd` carries a fast-math flag at `-ffp-contract=off` or `=on`. The strictest selection the offline driver offers therefore declares fast math disabled and denormals disabled in the same module.

**Measurement — the module flag is not a summary of the licences applied.** `air.compile.fast_math_disable` is also emitted under `relaxed`, where every floating-point operation carries `reassoc nsz arcp afn`. Only `fast` emits `air.compile.fast_math_enable`. An artifact-side reader that inferred the delivered realization from the module flag would read the opposite of the truth for `relaxed`, which is the measurement ADR 0076 item 4 relies on.

**Measurement — the exact flag sets, which are contraction-dependent.**

| math mode | `-ffp-contract=off` | `=on` | `=fast` |
| --- | --- | --- | --- |
| `safe` | (none) | (none) | `contract` |
| `relaxed` | `reassoc nsz arcp afn` | `reassoc nsz arcp afn` | `reassoc nsz arcp contract afn` |
| `fast` | `reassoc nnan ninf nsz arcp afn` | `reassoc nnan ninf nsz arcp afn` | `fast` |

### 2. Input flushing and result flushing are separable, and both occur

**Measurement.** An emitted `x * 2.0f` returns `00000000` for the operand `00400000`, where preserving the operand would give the *normal* value `00800000`. Because the exact result is not itself subnormal, this isolates **input** flushing (`case.multiply_two.*`). An emitted `x * 0.5f` returns `00000000` for the *normal* operand `00800000`, where the exact result is the subnormal `00400000`. Because the operand is normal, this isolates **result** flushing (`case.multiply_half.*`). Both hold at `-O0` and `-O2` and under `safe`, `relaxed`, and `fast`, without variation. Both kernels carry an execution witness that reports `executed` in every one of those twelve configurations, so each observation is admissible under the guard above.

### 3. The flush preserves the sign of zero

**Measurement.** `0x80400000 * 2.0f` returns `80000000`, not `00000000`, in every configuration of finding 2. ADR 0076 item 1 makes this load-bearing: a flush-to-zero behaviour that does not state which zero it produces cannot be checked against this hardware and cannot be reference-evaluated.

### 4. Materialization is unaffected

**Measurement.** A load-then-store kernel with no arithmetic returns `00000001 00400000 007fffff 00800000 80400000 80000000 3eb97ef9 3f800000` unchanged under `safe`, `relaxed`, and `fast`, and its emitted module contains zero floating-point operations (`case.materialize.*`). The limit is a property of arithmetic, not of materialization, which is what lets the Metal emitter record the obligation per arithmetic statement rather than per kernel.

### 5. The math mode changes a conforming result

**Measurement.** For the emitter's `MultiplyThenAdd { scale 1.0, bias +0.0 }` shape, the operand `80000000` returns `00000000` under `safe` and `80000000` under `relaxed` and `fast`, at both `-O0` and `-O2` (`case.scale_one_bias_zero.*`). IEEE-754 round-to-nearest requires the former, since `(-0.0) + (+0.0) = +0.0`.

### 6. Contraction changes a conforming result

**Measurement.** A multiply and an add written as two separate statements over `scale = 1.5`, `bias = 1.0` return the separately rounded `3fc58f9e` for the operand `3eb97ef9` under `-ffp-contract=off` and `-ffp-contract=on`, and the fused `3fc58f9d` under `-ffp-contract=fast` (`case.contraction_pair.safe.O2.contract-*`). The per-statement emission rule is therefore a measured defence against `on` and measurably not a defence against `fast`. The fusion is not visible in the emitted IR, which retains two operations carrying the `contract` flag under `=fast`; the pair is fused below that stage.

**Measurement — the NaN canonicalization is not a contraction barrier.** With the emitter's canonicalization interposed between the multiply and the add, the same operand returns `3fc58f9e` at every contraction setting including `=fast` (`case.contraction_pair_canonicalized.*`). This is not a defence: the identical source without the canonicalization does fuse under the same flags, so the absence of fusion here is a scheduling outcome on this toolchain row rather than a guarantee. `-ffp-contract=off` remains the only thing closing the case. This reproduces the caveat `prototype-metal-numerical-realization` recorded.

### 7. The trap

**Measurement.** `x * 1.0` retains zero floating-point operations at `-O2` under every math mode (`case.multiply_one.*.O2.*`). The `scale 1.0, bias +0.0` kernel retains exactly one under `safe` at `-O2`, an `fadd`, and zero under `relaxed` and `fast`. The surviving `fadd` is what flushes. The identical `nsz` licence that breaks signed zero in finding 5 also deletes the operation that would have flushed, so one mechanism produces both observations. The full statement of this finding, its `-O0` refinement, and the guard it forces are in "Why a returned bit pattern is not, by itself, evidence" above.

### 8. The offline and runtime compilers are different builds on this host

**Measurement.** `xcrun --sdk macosx metal --version` reports `Apple metal version 32023.883 (metalfe-32023.883)`, resolved from the Xcode 26.6 MetalToolchain asset mounted at `/private/var/run/com.apple.security.cryptexd/mnt/com.apple.MobileAsset.MetalToolchain-v17.6.109.0.6Dib3q`. A library compiled in process by `newLibraryWithSource:options:` and serialized through an `MTLBinaryArchive` embeds `Apple metal version 32023.921 (metalfe-32023.921)`; the runtime compiler ships with the OS rather than with Xcode. **Corrected by `measure-numerics-across-apple-artifact-families`:** this originally attributed that build to `/System/Library/PrivateFrameworks/MTLCompiler.framework` (`CFBundleVersion` 382.5), inferred from a framework present on disk with a matching version rather than from what the process loaded. The later per-family measurement read the loaded `dyld` images directly and found **no image whose path contains `MTLCompiler` loaded into either process**; the build is served by `GPUCompiler.framework`, as the qualified row above records. The build number and the OS-not-Xcode conclusion are unaffected — only the framework attribution was wrong (`environment.runtime_compiler` against `environment.metal_version`).

**Inference — this is what makes finding 9 worth having.** An agreement between the two paths is agreement between two separately built compilers, not one compiler invoked twice, so it is a stronger result than it would otherwise be. It is also the reason the two versions are recorded as separate environment fields: an artifact's recorded offline toolchain provenance does **not** identify the compiler that will compile a kernel through `newLibraryWithSource:`, and a future OS update can move one without moving the other. This is the axis along which the two paths are most likely to drift apart, and the retained record is what would notice.

### 9. Every case agrees across the two compilation paths

**Measurement.** All 40 macOS runtime cases — eight kernels across `MTLMathModeSafe`, `Relaxed`, and `Fast`, at both `MTLLibraryOptimizationLevelDefault` and `Size` — return bit patterns identical to their offline counterparts at `-O2`, for every operand in the vector (`comparison.macos.*`). No case diverges. Findings 2, 3, 4, and 5 therefore hold through runtime compilation exactly as through offline compilation: input flushing and result flushing both occur and are separable, the flush preserves the sign of zero, materialization is untouched, and `(-0.0) * 1.0 + (+0.0)` returns `00000000` under `mathMode = Safe` and `80000000` under `Relaxed` and `Fast`. Finding 7's device-observable half reproduces too: the trap kernel returns every operand unchanged under `Relaxed` and `Fast`, the unguarded reading of those results is `preserved`, and the guard refuses them. Finding 12 establishes that the iOS Simulator's 40 runtime cases agree the same way, on a *different* runtime compiler build.

**Fact — the comparison fails the gate rather than being rewritten.** Each `comparison.*` row is part of the retained record and is compared on every gate run whose environment row matches, alongside the case rows. A divergence appearing on this row would fail `test_the_two_compilation_paths_agree_case_by_case_when_a_toolchain_and_gpu_resolve` by name and kernel, not in aggregate.

**Fact — what agreement does not establish.** It is one host row and two specific compiler builds. It is not evidence that the two paths agree on another toolchain pair, and it does not make the offline build's declared realization *transferable* to a runtime-compiled kernel; it makes the two happen to coincide here. Finding 8 is the reason to keep re-measuring rather than to conclude the question is settled.

### 10. `MTLCompileOptions` exposes a different surface from the offline flag set

**Fact — the counterparts, enumerated by reading the complete `@interface MTLCompileOptions` in `Metal.framework/Headers/MTLLibrary.h` of macOS SDK 26.5.** `mathMode` (`MTLMathModeSafe`/`Relaxed`/`Fast`) corresponds exactly to `-fmetal-math-mode`; `mathFloatingPointFunctions` to `-fmetal-math-fp32-functions`, and it is pinned to `Precise` because its documented default is `Fast`; `languageVersion` to `-std`. `preprocessorMacros` has no offline selection in use here to correspond to.

**Fact — `-target` has no counterpart.** There is no target property. The runtime compiler targets the device and OS it runs on, so the offline `air64-apple-macos13.0` deployment floor has no runtime analogue and nothing was substituted for it.

**Fact — `-O0` has no counterpart.** `MTLLibraryOptimizationLevel` offers `Default` and `Size` only. Both are swept and neither changes any measured value. Finding 7's `-O0` refinement — two operations surviving into the emitted IR and still not executing — therefore has no runtime counterpart and remains an offline-only measurement.

**Fact — `-ffp-contract` has no counterpart, and what was measured instead of substituting one.** There is no contraction property. Rather than choosing an offline contraction row to compare against, each runtime case is compared against *every* offline contraction setting recorded for its kernel and mode, so a kernel on which contraction is unobservable yields a plain agreement and a kernel on which it is observable reports which offline setting the runtime path behaves like. **Measurement:** for the contraction pair over `scale = 1.5`, `bias = 1.0`, the runtime path returns the separately rounded `3fc58f9e` for the operand `3eb97ef9` at both optimization levels, matching offline `-ffp-contract=off` and `=on` and not the fused `3fc58f9d` of `=fast` (`comparison.contraction_pair.runtime.safe.*`, recorded as `agree-on-some`). The runtime default does not fuse this pair on this row.

**Measurement — a source-level pragma does control contraction, and was deliberately not used.** `#pragma METAL fp contract(off)` and `#pragma clang fp contract(off)` are both accepted without diagnostic by `xcrun metal -Wall -Werror -std=metal3.1` on this row and both remove the `contract` fast-math flag from the emitted IR under `-ffp-contract=fast`. It is a source-level control and not an `MTLCompileOptions` counterpart, and using it in the runtime probe would have changed the source bytes and destroyed the byte-identical pairing the whole comparison rests on. Recorded as the available mechanism, not adopted as a substitute.

### 11. The subnormal flush is an Apple-wide property on this row, not a per-family one

This is the finding [declare-metal-numerical-honourability](../../../tickets/declare-metal-numerical-honourability.md) needs, and it is the headline compile-side result across the three families.

**Measurement — every compile-side row is byte-identical across the three families.** For all 42 compiled cases, the emitted `air.compile_options` string set and the emitted floating-point operation list — opcode and fast-math flags — are **identical** across `MacOs`, `IOsDevice`, and `IOsSimulator`, at every math mode, optimization level, and contraction setting (`case.macos.*` against `case.ios-device.*` against `case.ios-simulator.*`, `compile_options` and `float_operations`). In particular `air.compile.denorms_disable` is emitted for every family under `safe`, `relaxed`, and `fast` alike, the finding-1 flag table holds unchanged for all three, and `x * 1.0` folds and `scale 1.0, bias +0.0` keeps exactly one `fadd` under `safe` for all three. The only per-family difference anywhere in the case rows is the runtime archive scan (`archived_options`), which is a device-side artefact and is `unavailable` for the iOS Simulator for the reason in finding 12 — no compile-side row differs.

**Measurement — the device-observable flush is identical on the two families that dispatch.** For every operand in the vector, `MacOs` on the host GPU and `IOsSimulator` on the booted runtime return **identical** bit patterns for all 82 dispatched cases (`case.macos.*.results` against `case.ios-simulator.*.results`). Input flushing, result flushing, the signed-zero-preserving flush, and the `(-0.0) * 1.0 + (+0.0)` divergence all reproduce identically. This is finding 13's measurement; it is stated here because it is the device-side half of the same conclusion.

**Inference — `MetalSubnormalArithmetic` can be one declared constant on this row, not a per-family field.** Nothing measured here distinguishes the families numerically: the flush is declared in the module identically and observed identically wherever it can be observed. So the subnormal-flush obligation is, on this bounded row, a property of the Apple toolchain rather than of the artifact family, and `MetalNumericalGap::SubnormalFlushInArithmetic` does not need to vary by family. Had `denorms_disable` been emitted for one family and not another, or the licence spellings differed, this is the finding that would have said so and forced the field to vary.

**Fact — what this does not establish.** It is one host, one offline toolchain build, one Mac GPU, and one iOS Simulator whose GPU is that same Mac GPU. It is not evidence that a **physical** iOS device flushes the same way — finding 13 is explicit that no iOS-device hardware was measured — and it is not evidence about another toolchain build or another GPU family. It says the three families' *emitted modules* agree here and the two *dispatchable* families' *results* agree here, and it says both are bounded one-host measurements the gate re-checks rather than properties of Metal.

### 12. Each family carries its own runtime compiler, and both agree with its offline path

**Measurement — the runtime compiler belongs to the execution environment, so it differs by family.** The offline `metal` driver is one binary (`metalfe-32023.883`) resolved by all three SDKs. The runtime compiler is whatever the execution environment loads: the macOS host process loads `GPUCompiler.framework` build `metalfe-32023.921` (finding 8's compiler, reported via the loaded image path and its build string in `environment.family.macos.runtime_compiler_build`), and the iOS Simulator process loads the simulator runtime's own `GPUCompiler.framework` build `metalfe-32023.830.1` (`environment.family.ios-simulator.runtime_compiler_build`). These are three distinct compiler builds across two dispatchable families. The image path is recovered from `dyld` rather than assumed: on this row no image whose path contains `MTLCompiler` is loaded into either process at all, even though that framework is present on disk, so a probe that matched only the expected name would have identified nothing.

**Measurement — every runtime case agrees with its offline counterpart, within each family.** No `comparison.*` row diverges, for either family (`comparison.macos.*` and `comparison.ios-simulator.*`, none `differ`). Because the comparison is derived per family, an agreement is agreement between that family's own offline and runtime compilers — for the iOS Simulator, between `metalfe-32023.883` and `metalfe-32023.830.1`, two builds that differ in both directions from the macOS pair. The four `agree-on-some` rows are the contraction pair on each family, where `MTLCompileOptions` cannot express `-ffp-contract` and the runtime default behaves like offline `off`/`on` and not `fast`; that is finding 10's measured axis, reproduced per family, not a divergence.

**Measurement — the iOS Simulator cannot serialize a binary archive, and the harness fails around it rather than into it.** `serializeToURL:` for a compute pipeline aborts the simulator process with `+[MTLLoader sliceIDForDevice:legacyDriverVersion:airntDriverVersion:] failed assertion 'Target device architecture is nil'`. Because that is an abort and not a returned error, the harness probes archive support in a one-entry batch of its own before any manifest that carries measurements, and records the exact abort as the reason `archived_options` is `unavailable` and `runtime_compiler` (the archive-embedded version string) is unrecovered for that family. The runtime compiler is still identified for the simulator, through the loaded-image build string above rather than the archive. On macOS the archive scan corroborates finding 1 for every math mode exactly as before.

### 13. The iOS Simulator dispatches on the Mac GPU, so it is not evidence about an iOS device

**Measurement.** `MTLCreateSystemDefaultDevice` inside the booted iOS Simulator reports device name `Apple iOS simulator GPU` and `registryID` 4294968621 — the **same** registry ID the macOS host reports for `Apple M4 Max` (`environment.family.macos.device_registry_id` equals `environment.family.ios-simulator.device_registry_id`). The simulator's Metal implementation is a software shim over the host GPU; the arithmetic that produced finding 13's results ran on the M4 Max.

**Inference — the simulator result is admissible as a simulator measurement and not as an iOS-device one.** It is a real and reproducible measurement of what the `IOsSimulator` artifact family delivers on this host, and it is worth having: the simulator uses a different runtime compiler (finding 12) and agreeing with the offline path there is a non-trivial result. But because the executing GPU is the Mac's, a claim about how an iPhone or iPad flushes subnormals cannot be read off it. The harness enforces the distinction structurally: `IOsDevice` is `Execution.NONE` regardless of anything on this host.

**Measurement — the device gap for `IOsDevice`, stated precisely with what would close it.** `IOsDevice` is compiled for all 42 cases and dispatched for none (`case.ios-device.*` carry `compile_options` and `float_operations`, no `results`; `environment.family.ios-device.execution` is `unavailable:` with the reason). Closing it requires dispatching the `air64-apple-ios16.0` metallib on a **physical** iPhone or iPad — Apple silicon, running iOS, connected to a host — through the same terminal-status-checked readback the other families use, on that device's own GPU. Nothing installable on this host substitutes for it; a simulator is explicitly not it, per this finding. Until then, ADR 0076's subnormal-flush claim is Fact for macOS, Fact for the iOS Simulator (on the Mac GPU), and Inference-from-compile-side-agreement-only for a physical iOS device.

### 14. The Mac runs a foreign family's module, which is the substitute this record refuses

**Measurement.** An `air64-apple-ios16.0` (`IOsDevice`) metallib compiled here loads and dispatches on the macOS host GPU without error, returning `00000000 00000000 00000000 01000000 80000000 80000000 3f397ef9 40000000` for the operand vector (`hazard.cross_family_load.ios-device_module_on_macos_gpu`). The load does not fail.

**Inference — this is exactly why the device gap is not closed this way.** The convenient way to "measure `IOsDevice`" would be to run its module on this Mac, and it works. It is refused because the GPU executing it is the Mac's, so its results are a fact about macOS running a foreign module, not about an iOS device. Recording the outcome under `hazard.` rather than `case.` keeps that reasoning checkable and keeps the refusal honest: the substitute is available and declined, not unavailable. The `hazard.*` row is part of the retained record and the gate compares it, so if a future OS ever started **refusing** the cross-family load, that change would be a finding rather than a silent drift.

### 15. Division flushes both dimensions, and a written power-of-two division is not one

**Measurement — a power-of-two divisor does not reach the device as a division.** `x / 2.0f` and `x / 0.5f` are emitted as a single `fmul` under `-fmetal-math-mode=safe` with `-ffp-contract=off`, which is the strictest selection the offline driver offers (`case.divide_by_two.safe.O2.contract-off.float_operations`, `case.divide_by_half.*`, `fmul` for all three families). A probe that isolated the flush on those divisors would be measuring the multiplier a second time under a division's name, so the flush is isolated below on divisors the rewrite cannot absorb.

**Measurement — a surviving `fdiv` flushes its subnormal input and its subnormal result.** `x / 0.375f` returns `00000000` for the operand `00400000`, whose exact quotient is the *normal* `00aaaaab`, isolating **input** flushing; `x / 3.0f` returns `00000000` for the *normal* operand `00800000`, whose exact quotient is the subnormal `002aaaab`, isolating **result** flushing (`case.divide_by_three_eighths.*`, `case.divide_by_three.*`). The negative operand `80400000` returns `80000000`, so finding 3's sign preservation holds on the division path too. Both kernels carry execution witnesses that report `executed` in every configuration, so each observation is admissible under the guard.

**Measurement — `arcp` substitutes a reciprocal multiply, and changed nothing here.** Under `safe` the emitted operation is `fdiv`; under `relaxed` and `fast` it is a single `fmul` carrying `arcp`. For every operand in the vector the returned bit patterns are **identical** across all three modes for both divisors. The licence permits a different result and on this row did not produce one for these two divisors; that is a bounded observation about two constants, not a statement that reciprocal substitution is value-preserving.

### 16. `-ffp-contract=off` is not a defence against an `fma` written in the source

**Measurement.** `fused_pair` carries the identical constants as `contraction_pair` — `scale = 1.5`, `bias = 1.0` — and differs from it in exactly one thing: the two statements are replaced by one source-level `fma`. For the operand `3eb97ef9` it returns the fused `3fc58f9d` at `-ffp-contract=off`, `=on`, and `=fast` alike, where the two-statement pair returns the separately rounded `3fc58f9e` at `off` and `on` (`case.fused_pair.safe.O2.contract-*` against `case.contraction_pair.safe.O2.contract-*`). The runtime path returns `3fc58f9d` too.

**Inference — this sharpens finding 6 rather than unsettling it.** The per-statement emission rule is a rule about what the emitter may *write*. `-ffp-contract=off` closes the case for a multiply and an add written separately; it has nothing to say about a fused operation the source asked for. An emitter that ever lowered a `MultiplyThenAdd` to `fma()` would deliver a contracted result under every contraction setting, and no compiler flag in this matrix would report it.

**Measurement — this is where the harness's own guard was found to be wrong, and the correction.** This front end lowers `fma(x, a, b)` to `tail call float @air.fma.f32(...)`. The harness's fused-intrinsic pattern named only the LLVM spellings `llvm.fma` and `llvm.fmuladd`, so it matched nothing and reported a kernel whose entire body is one fused multiply-add as containing **no floating-point arithmetic**. The verdict still failed closed — an empty operation list is `no-emitted-arithmetic` and inadmissible — but the *count* was wrong in the one direction a reader acts on, because a surviving operation reported as zero is indistinguishable from a deleted one, which is exactly the reading finding 7 rests on. `FUSED_INTRINSIC` now names both spellings and a gate assertion requires the fused kernel's operation list to be exactly `air.fma.f32`. The defect was latent for as long as the operation vocabulary was multiply and add: widening the vocabulary is what exposed it.

### 17. The relaxed math modes reassociate, and the earlier negative result is bounded, not general

**Measurement.** `(x + 2**-24) + 2**-24` returns the operand unchanged for `x = 1.0` when the parentheses are honoured, because `2**-24` is exactly half an ulp of `1.0` and each add is a tie that rounds to even; summing the two small terms first gives the exactly representable `1.0 + 2**-23 = 3f800001`. Under `safe` the emitted module keeps **two** `fadd`s and the device returns `3f800000`. Under `relaxed` and `fast` it keeps **one** `fadd` carrying `reassoc` and the device returns `3f800001` (`case.reassociation_chain.*`). The runtime path agrees at both `MTLLibraryOptimizationLevel` values.

**Fact — the guard carries this exactly as it carries a subnormal claim.** The unreassociated result *is* the operand, so a deleted chain and an honoured one return the same bits, and only the execution witness on a different operand — `00800000`, whose result `34000000` is the same under both association orders and under both flush hypotheses — separates them. `order_verdict` applies the identical two-layer guard as `subnormal_verdict`, because an observation whose arithmetic cannot be shown to have executed supports no claim about that arithmetic whatever the claim is about.

**Inference — what this does to the prior negative result.** `prototype-metal-numerical-realization` probed reduction reassociation over three fixtures and found no counterexample. That remains true of those fixtures and must not be read as "reassociation is unobservable here": a fourth shape, chosen so that association order changes the value by one ulp, is reassociated under `relaxed` and `fast` on this row. A bounded negative result over three fixtures is evidence that those three did not discriminate, not evidence about the licence.

**Inference — the consequence for a numerical contract.** A target profile that admits `relaxed` or `fast` cannot promise a reduction order, and this is the measurement that says so rather than an appeal to what `reassoc` means. Under `safe` the chain is evaluated as written on this row, for all three families' modules and both dispatchable families' devices.

### 18. `-fmetal-math-fp32-functions=fast` moves nothing this matrix measures

**Measurement.** For `multiply_two`, `multiply_half`, and `scale_one_bias_zero`, in every math mode, the `=fast` cases emit the identical `air.compile_options` set and the identical floating-point operation list as the `=precise` ones, and return identical bit patterns for every operand on both compilation paths (`case.*.fpfun-fast.*` against their unsuffixed counterparts). In particular the signed-zero divergence of finding 5 reproduces exactly: `(-0.0) * 1.0 + (+0.0)` returns `00000000` under `safe` and `80000000` under `relaxed` and `fast`, at `=fast` as at `=precise`.

**Fact — this closes a boundary this record used to carry.** `prototype-metal-numerical-realization` reported that the signed-zero divergence also reproduces under `=fast`; the flag was pinned to `=precise` here and nothing re-established it. It is now re-established by the checked-in harness, on both paths, for both dispatchable families.

**Fact — what it does not establish.** The flag selects the precision of the `f32` *function* implementations. Nothing in this matrix calls one: the vocabulary is multiply, add, divide, and a fused multiply-add. So this is a measurement that the flag is inert **for these operations**, which is the useful negative result, and it is no evidence at all about `sin`, `sqrt`, `rsqrt`, or any other function the flag actually governs.

### 19. `-O1`, `-O3`, and `-Os` behave like `-O2`; `-O0` is the sole outlier

**Measurement — exhaustive matrix.** Across `multiply_two`, `multiply_half`, `multiply_one`, and `scale_one_bias_zero`, in all three math modes, the emitted operation counts at `-O1`, `-O3`, and `-Os` are identical to `-O2` in every one of the twelve combinations, and no returned bit pattern differs at any of the five levels. `-O0` is the only level that differs, and it differs the way finding 7's refinement records: `multiply_one` keeps its `fmul` there and folds it at every other level, and `scale_one_bias_zero` keeps **two** operations there under `relaxed` and `fast` and **zero** at every other level (`case.*.O0/O1/O2/O3/Os.*` in the exhaustive record).

**Inference — the `-O0` refinement is about `-O0`, not about low optimization.** Finding 7's second layer exists because at `-O0` the front end emits arithmetic that a stage below it removes. That contrast is now measured to be confined to one level rather than to a range, so a reader cannot generalize it into "the emitted count is unreliable at low optimization levels". The guard's second layer is still necessary for exactly the reason it always was: `-O0` is a level a consumer may select.

**Fact — where this row lives.** The full twelve-combination sweep is in the exhaustive record and is re-checked only when `TILER_APPLE_NUMERICS_EXHAUSTIVE` is set. The covering set the gate runs carries `scale_one_bias_zero` under `safe` at all five levels, which is the kernel and mode where the level is known to move the count, so a change in the level's behaviour there fails the gate.

### 20. Input flushing on the additive path, measured rather than inherited from the multiplicative one

This is the finding [extend-the-numerical-probe-to-an-additive-path-kernel](../../../tickets/extend-the-numerical-probe-to-an-additive-path-kernel.md) owns, and it closes the one re-verified observation ADR 0076 named as not re-established by this record's harness.

**Measurement.** An emitted `x + 0x00800000` — a single add of `2**-126` with no multiply before it, so the operand reaching the add is the one the buffer supplied — returns `00800000` for the operand `80400000`, at `-O0` and `-O2`, under `safe`, `relaxed`, and `fast`, on both compilation paths and for both dispatchable families (`case.add_smallest_normal.*`). Preserving the operand would give `-2**-127 + 2**-126 = 2**-127`, the subnormal `00400000`. Every subnormal operand in the vector returns `00800000` for the same reason, and `80000000`, which is not subnormal, returns `00800000` too because `-0.0 + 2**-126` is `2**-126` whether anything flushed or not.

**Fact — a flush does not have to show up as a returned zero, and this is the case that shows it.** The flushed subnormal here is an *addend*, not the whole result, so the bias stands alone and the returned value is normal. `SubnormalProbe.flushing` is derived from the kernel by exact arithmetic under the substitution hypothesis rather than assumed to be a zero, which is what makes this probe expressible at all; before it, every probe's flushing candidate was a zero and a well-formedness test asserted so.

**Fact — the third outcome is kept distinct.** `00000000` would mean the operand survived the add and the *subnormal result* was flushed instead. That is a different mechanism from the one this probe isolates, so it classifies as `unexpected-result` rather than being folded into either candidate.

**Fact — this kernel is admissible where the trap kernel is not.** Adding a nonzero constant is an identity on no operand, so the `fadd` survives under `relaxed` and `fast` — it is present in the emitted module in all six configurations — and the execution witness `00800000 → 01000000` reports `executed` in all of them. The `scale 1.0, bias +0.0` kernel loses its arithmetic under exactly those modes (finding 7), so this is a *witnessed* additive-path observation under the relaxed modes, which that kernel cannot supply.

**Fact — the ADR sentence is reproduced, not corrected.** ADR 0076's re-verification records "an emitted `x + 0x00800000` returns `0x00800000` for the operand `0x80400000`, where preserving the operand would produce the subnormal `0x00400000`, confirming input flushing on the additive path", and notes that the harness did not re-establish it. It does now, with an execution witness, on this record's environment row. The ADR states the gap twice — in its `Measured evidence` bullet and in the subnormal-flush Measurement — and both are consequently stale. Repairing them belongs to whoever holds `contracts/decisions` and is carried by [retire-adr-0076-additive-path-caveat](../../../tickets/retire-adr-0076-additive-path-caveat.md).

### 21. The subnormal flush is not dtype-independent: `f16` preserves what `f32` flushes

This is the finding [widen-the-apple-numerical-probe-to-a-second-dtype](../../../tickets/widen-the-apple-numerical-probe-to-a-second-dtype.md) owns, and it is the only measurement in this record that refutes something the record previously carried rather than refining it.

**Measurement.** For every flush dimension this record isolates in `f32`, the `f16` kernel that isolates the identical dimension returns the **preserved** value, in all three math modes, on both compilation paths, and on both dispatchable families. Each pair differs in exactly one thing: the width of the format its constants and operands are spelled in.

| --- | --- | --- | --- | --- |
| input flush, multiply | `multiply_two` `00400000` | `00000000` | `multiply_two_f16` `0200` | `0400` |
| input flush, sign | `multiply_two` `80400000` | `80000000` | `multiply_two_f16` `8200` | `8400` |
| result flush, multiply | `multiply_half` `00800000` | `00000000` | `multiply_half_f16` `0400` | `0200` |
| input flush, additive path | `add_smallest_normal` `80400000` | `00800000` | `add_smallest_normal_f16` `8200` | `0200` |
| input flush, division | `divide_by_three_eighths` `00400000` | `00000000` | `divide_by_three_eighths_f16` `0200` | `0555` |
| input flush, division, sign | `divide_by_three_eighths` `80400000` | `80000000` | `divide_by_three_eighths_f16` `8200` | `8555` |
| result flush, division | `divide_by_three` `00800000` | `00000000` | `divide_by_three_f16` `0400` | `0155` |

Every `f32` column is the flushing candidate and every `f16` column is the exactly rounded preserving candidate, both derived from the kernel by `evaluate` rather than stated (`case.*_f16.*.results` against `case.*.results`).

**Fact — both verdicts are admissible, which is what makes this a measurement and not the trap.** Each `f16` kernel carries an execution witness on a non-subnormal operand, and it reports `executed` in every configuration: `multiply_two_f16` witnesses on `3c00 → 4000`, `multiply_half_f16` on `3c00 → 3800`, `add_smallest_normal_f16` on `0400 → 0800`, `divide_by_three_eighths_f16` on `3c00 → 4155`, and `divide_by_three_f16` on `3c00 → 3555`. So the guard admits these observations as `preserved` rather than refusing them as `arithmetic-not-executed`, and the returned subnormal is the output of arithmetic that demonstrably ran. This distinction is the whole content of finding 7 and it is why the `f16` result is not the same shape of mistake.

**Measurement — the two dtypes' modules are indistinguishable where a module can be read.** Under `safe`, `relaxed`, and `fast`, and for all three families, `multiply_two_f16` and `multiply_two` declare the **identical** `air.compile_options` string set and emit the identical opcode sequence (`case.macos.multiply_two_f16.*.compile_options` against `case.macos.multiply_two.*.compile_options`). `air.compile.denorms_disable` is present for both. Nothing on the compile side predicts the divergence; see finding 22.

**Fact — the mechanism is not distinguished *by this finding*, and finding 24 distinguishes it.** Two explanations fit everything in this finding: the hardware's `f16` arithmetic honours subnormals natively, or it evaluates at a wider internal precision where every `f16` subnormal is a normal and rounds once at the end. Nothing *here* separates them, exactly as finding 7's `x * 1.0f` does not separate a folded multiply from a hardware special case. The observable contract is the same under both, and a numerical contract is written against what a target delivers rather than against why. The separation arrived with a third dtype rather than a cleverer `f16` kernel: finding 24 measures `bf16` — whose subnormals are `f32` subnormals — flushing, which refutes the native-support explanation and leaves the wider-precision one accounting for all three dtypes.

**Inference — a declared subnormal-flush fact has to carry the dtype.** `MetalSubnormalArithmetic::FlushesToZero` is currently one target fact with no dtype. On this row it is true of `f32` arithmetic and false of `f16` arithmetic, so a consumer reading it for an `f16` kernel would be told a subnormal operand is unusable when it is in fact carried exactly — rejecting a plan that is correct, or declaring a numerical gap that does not exist. That is a contract consequence rather than a harness one, and it belongs to whoever owns `implementation/metal`; see "Consequences for the contracts" below.

**Fact — what this does not establish.** It is two dtypes agreeing on nothing, not a rule. `f16` preserving here said nothing about `bf16` — which has since been measured separately, and flushes (finding 24) — nor about any other format, nor about `f16` on another GPU family, another toolchain build, or a physical iOS device. The useful shape of the result is negative: it refutes dtype-independence, and one refuting pair is enough for that where no number of agreeing pairs would have established the positive. That reading is unchanged by finding 24, which is a third measurement and not a rule either.

### 22. The module-level declaration is not a summary of what the hardware does per dtype

**Measurement.** `air.compile.denorms_disable` appears in the emitted `air.compile_options` of every `f16` kernel here, under `safe`, `relaxed`, and `fast`, for `MacOs`, `IOsDevice`, and `IOsSimulator` alike — the same declaration, from the same compiler, that finding 1 records for `f32` (`case.*_f16.*.compile_options`). The arithmetic those modules then perform differs by dtype (finding 21).

**Inference — this is finding 1's second measurement again, on a new axis.** Finding 1 records that `air.compile.fast_math_disable` is emitted under `relaxed` while every operation carries `reassoc nsz arcp afn`, so the module flag is not a summary of the licences applied. Finding 21 shows the same flag failing in the other direction: `denorms_disable` is declared for a dtype whose subnormals are not disabled. An artifact-side reader that inferred the delivered realization from the module's `air.compile.*` names would be wrong about `f16` on this row — and would be wrong in the dangerous direction, believing a flush that does not happen and therefore accepting a reference evaluation that does not match the device. The declaration is a compile-side fact about what was requested; only a witnessed dispatch says what was delivered.

### 23. The guard still discriminates at the new width, which finding 21 depends on

**Measurement.** The `f16` trap kernel behaves exactly as its `f32` twin. `x * 1.0h` retains zero floating-point operations at `-O2` under every math mode. `scale_one_bias_zero_f16` retains exactly one `fadd` under `safe` at `-O2`, zero under `relaxed` and `fast`, and **two** at `-O0` under `relaxed` — the level finding 19 bounds the contrast to. Dispatched under `relaxed` and `fast` it returns every operand unchanged, its unguarded reading is `preserved`, and the guard refuses it as `arithmetic-not-executed`; under `safe` the same kernel is admitted (`case.*.scale_one_bias_zero_f16.*`, `case.*.multiply_one_f16.*`).

**Fact — why this matters more in `f16` than in `f32`.** In `f32` the admissible verdict is `flushed-to-zero` and the trap's unguarded reading is `preserved`, so the two are different words and a guard failure would be visible as a changed conclusion. In `f16` the admissible verdict *is* `preserved` — the same word the trap produces when nothing ran. A guard that stopped discriminating would therefore make finding 21 indistinguishable from a kernel whose arithmetic was deleted, and it would do so silently. The gate holds the `f16` trap kernel to the refusal and the `f16` flush kernels to their witnesses in the same run, which is what separates them.

**Measurement — the signed-zero divergence is dtype-independent, unlike the flush.** `scale_one_bias_zero_f16` returns `0000` for the operand `8000` under `safe` and `8000` under `relaxed` and `fast`, reproducing finding 5 exactly. So the two things `nsz` governs behave differently across the dtypes: the licence that breaks signed zero acts identically in both formats, and the flush the surviving `fadd` would perform does not exist in one of them. That is also the control on the `f16` trap kernel: the operation whose deletion the guard detects is the one whose *presence* produces `0000` here.

### 24. `bfloat16` flushes, which distinguishes the mechanism finding 21 could not

This is the finding [measure-the-apple-subnormal-flush-for-the-remaining-mature-dtypes](../../../tickets/measure-the-apple-subnormal-flush-for-the-remaining-mature-dtypes.md) owns.

**Measurement.** For every flush dimension this record isolates, the `bf16` kernel isolating the identical dimension returns the **flushed** value, in all three math modes, at `-O0` and `-O2`, and on both compilation paths. Each row differs from its `f32` twin in exactly one thing: the width of the format its constants and operands are spelled in.

| dimension | `f32` operand → result | `f16` operand → result | `bf16` operand → result |
| --- | --- | --- | --- |
| input flush, multiply | `00400000` → `00000000` | `0200` → `0400` | `0040` → `0000` |
| input flush, sign | `80400000` → `80000000` | `8200` → `8400` | `8040` → `8000` |
| result flush, multiply | `00800000` → `00000000` | `0400` → `0200` | `0080` → `0000` |
| input flush, additive path | `80400000` → `00800000` | `8200` → `0200` | `8040` → `0080` |
| input flush, division | `00400000` → `00000000` | `0200` → `0555` | `0040` → `0000` |
| input flush, division, sign | `80400000` → `80000000` | `8200` → `8555` | `8040` → `8000` |
| result flush, division | `00800000` → `00000000` | `0400` → `0155` | `0080` → `0000` |

Every `bf16` column is the flushing candidate, derived from the kernel by `evaluate` rather than stated (`case.*_bf16.*.results`).

**Fact — every verdict carries an execution witness reporting `executed`.** `multiply_two_bf16` witnesses on `3f80 → 4000`, `multiply_half_bf16` on `3f80 → 3f00`, `add_smallest_normal_bf16` on `0080 → 0100`, `divide_by_three_eighths_bf16` on `3f80 → 402b`, and `divide_by_three_bf16` on `3f80 → 3eab`. So each `flushed-to-zero` above is the output of arithmetic that demonstrably ran, and not a kernel whose operations were deleted. The trap kernel is held to its refusal in the same run (finding 27).

**Inference — this is the measurement that separates finding 21's two explanations, and it separates them decisively in one direction.** Finding 21 recorded two hypotheses that both fit every `f16` observation:

- **A, wider internal precision:** narrow-format arithmetic is evaluated at `f32` precision and rounded once at the end, with the `f32` flush of findings 2 and 3 governing. A predicts `f16` **preserves**, because every `f16` subnormal widens to an `f32` normal that nothing flushes. A predicts `bf16` **flushes**, because every `bf16` subnormal widens to an `f32` subnormal that the measured `f32` flush destroys.
- **B, native narrow subnormal support:** the hardware honours subnormals natively in narrow formats. B predicts both narrow dtypes preserve.

`bf16` flushes. **B is refuted** as a statement about narrow formats, and **A predicts both narrow dtypes correctly with no free parameter.** B survives only if weakened to a per-format claim — native subnormal support for `f16` and not for `bfloat16` — for which this record has no independent evidence and which A does not need. That is an Inference from two Measurements and not itself a measurement; what is measured is the three dtypes' behaviour, and what A buys is that one mechanism accounts for all of it.

**Fact — what this still does not distinguish, and what would.** A is not separated from "native `bfloat16` arithmetic that flushes at `bfloat16`'s own subnormal boundary", and no operand can separate them: a value is `bf16`-subnormal exactly when it is `f32`-subnormal, so the two hypotheses agree on every input this probe can supply. Double rounding cannot separate them either — `f32`'s 24-bit significand exceeds the 2p+2 = 18 bits that make a second rounding to `bfloat16`'s 8-bit significand innocuous, so **no single operation** can expose an `f32` intermediate. What would separate them is a *chain*: two `bf16` operations whose intermediate is rounded to `bf16` under one hypothesis and kept at `f32` precision under the other, with constants chosen so the two differ. That is a bounded follow-up and not a gap in this finding, which is about the flush.

**Fact — what this does not establish.** Three dtypes measured is not every dtype. `f64` where it exists and every integer and quantized format remain entirely unmeasured, and an unmeasured dtype must not be generalized from a neighbour — that is precisely the error finding 21 refuted. The positive claims here are per-dtype and each rests on that dtype having been measured.

### 25. The flush follows the exponent field, not the width

**Inference.** `f16` and `bf16` are both 16 bits wide and both carry `air.compile.denorms_disable`, and they behave oppositely. What differs between them is the exponent field: 5 bits in `f16` and 8 in `bf16`, the latter identical to `f32`'s. Every dtype measured here whose exponent range matches `f32`'s flushes, and the one whose exponent range is narrower than `f32`'s does not.

**Fact — this is a description of three measurements and not a rule for a fourth.** It is stated because it is the shape a reader will otherwise infer wrongly from "the two 16-bit formats disagree", and because it is what finding 24's hypothesis A predicts. A dtype whose exponent field is narrower than `f32`'s but which is not `f16` would test it; Metal exposes none on this row. Do not read it as licence to predict an unmeasured format.

### 26. A device can compile, link, and then refuse a module, and the two absences are different

**Measurement — the iOS Simulator will not run a `bfloat` kernel on this row.** Every `bf16` kernel compiles to LLVM IR, to AIR, and links to a metallib for `air64-apple-ios16.0-simulator` without a diagnostic, and its emitted module declares `air.compile.denorms_disable` exactly as the `f32` and `f16` modules do (finding 27's compile-side half). Dispatched, `newComputePipelineStateWithFunction:` then fails with `Compilation failed due to an interrupted connection: XPC_ERROR_CONNECTION_INTERRUPTED. This error occurred after multiple retries.` — on **both** the offline `library` path and the runtime `source` path. The same simulator runs every `f32` and `f16` kernel in the same invocation without complaint. Recorded as `environment.family.ios-simulator.device_bfloat_support` and, per case, as `case.ios-simulator.*_bf16.*.refusal`, and reproduced by the gate on every run.

**Measurement — the refusal is not about arithmetic, and this leg is a separate one-off probe rather than a gate-reproduced row.** The gate asks with `multiply_two_bf16` alone, so it cannot separate "no `bfloat` support at all" from "the type lowers and the arithmetic does not". [`spikes/apple-targets/bfloat_dispatch_probe.py`](../../../spikes/apple-targets/bfloat_dispatch_probe.py) asks the arithmetic-free kernel directly: `materialize_bf16`, whose whole body declares `bfloat` buffers and copies between them and which emits **zero** floating-point operations, is refused with the identical diagnostic. So the refusal is about the format and not about any operation on it.

**Fact — that leg needs a control, and the control is what makes it evidence.** A refusal observed after earlier faults could be the simulator's GPU compiler service degrading rather than a fact about `bfloat`. The probe therefore dispatches `materialize_f16` — the same 16-bit element width — **before and after** the `bfloat` attempts, and both dispatch successfully, returning all eight operands unchanged. On the run behind this finding the order and outcomes were: `materialize_f16` dispatched, `materialize_bf16` refused, `multiply_one_bf16` refused, `materialize_f16` dispatched. The probe exits nonzero when the trailing control fails, because such a run establishes nothing about `bfloat`. It is excluded from the gate because the refusal path costs minutes of `XPC` retries per case, and what the gate needs — that the simulator's `bf16` cases are refused and its `f32` and `f16` cases are not — the retained record already carries on every run.

**Fact — this is a boundary and not a fallback.** The harness asks each family once, before any measured case is dispatched, whether its device will create a `bfloat` pipeline at all; a family that refuses has its `bf16` cases left out of that family's manifest and recorded as refused, and every other dtype in the same family is measured exactly as before. A family that *accepts* the probe and then fails a real case is still a hard `ProbeFailure` that takes the run down, because that is a defect rather than a boundary. Nothing is retried, softened, or substituted.

**Inference — why the distinction is load-bearing rather than bookkeeping.** Before this, a missing `case.*.results` row meant one thing: the family had no attached device. It now means one of two things, and they are different measurements. `IOsDevice` was never asked — no iPhone is attached. `IOsSimulator` was asked and answered no. Collapsing them would let a future toolchain where the simulator started working look identical to today's record, and would let a genuine dispatch defect hide behind an absence. `Verdict::DEVICE_REFUSED_DTYPE` and `Verdict::NO_DEVICE_OBSERVATION` are separate members for exactly this reason, and neither is evidence about arithmetic.

**Fact — the cause is not diagnosed and is not guessed at.** `XPC_ERROR_CONNECTION_INTERRUPTED` is the simulator's GPU compiler service failing, which is a symptom rather than a cause. Whether the simulator runtime's `metalfe-32023.830.1` lacks `bfloat` lowering, whether the simulated GPU exposes no `bfloat` capability, or whether this is a defect in that runtime build is **unmeasured**. It is reproducible on this row and the exact diagnostic is retained; that is what the record claims and no more.

**Measurement — `bf16` on `MacOs` is therefore the only dispatched device row, and `bf16` is `Unknown` for both iOS families.** Finding 24's verdicts are macOS-only. For `IOsSimulator` the compile side agrees and the arithmetic is refused; for `IOsDevice` the compile side agrees and the arithmetic was never asked. Neither is evidence that `bf16` flushes there, and finding 11's "the flush is Apple-wide on this row" does **not** extend to `bf16` — it was measured for `f32` on two GPUs and for `bf16` on one.

### 27. The guard and the trap hold at the third width, in the direction `f16` did not test

**Measurement.** `air.compile.denorms_disable` appears in the emitted `air.compile_options` of every `bf16` kernel, under `safe`, `relaxed`, and `fast`, for `MacOs`, `IOsDevice`, and `IOsSimulator` alike, and `multiply_two_bf16` emits the identical opcode sequence and identical module options as `multiply_two` (`case.*_bf16.*.compile_options`). `x * 1.0` in `bfloat` retains zero floating-point operations at `-O2` under every math mode; `scale_one_bias_zero_bf16` retains exactly one `fadd` under `safe` at `-O2`, zero under `relaxed` and `fast`, and **two** at `-O0` under `relaxed`. Dispatched under `relaxed` and `fast` the guard refuses it as `arithmetic-not-executed`; under `safe` the same kernel is admitted and returns `0000` for the operand `8000`, reproducing finding 5.

**Fact — this is the control finding 24 needs, and it is a different control from finding 23's.** In `f16` the danger was that the admissible verdict and the trap's unguarded reading are the same word, `preserved`. In `bf16` they are different words again, as in `f32` — so the risk here runs the other way: a guard that had simply started refusing *everything* would make finding 24 unreachable rather than wrong, and that failure is invisible from the headline result alone. The gate therefore holds the `bf16` trap kernel to its refusal **and** the `bf16` flush kernels to their witnesses **and** the same trap kernel under `safe` to admission, in one run.

**Measurement — materialization is unaffected, which finding 24 depends on.** `materialize_bf16` emits zero floating-point operations and returns all eight operands unchanged, subnormals included. Without it, a `bfloat` buffer round trip that quietly normalized its values would produce the same zeros the arithmetic does, and finding 24 would not be attributable to the arithmetic.

## Where this record disagrees with the values it reproduces

**Measurement — `x * 1.0f` does not flush; the originating ticket says it does.** `prototype-metal-numerical-realization` records that "an emitted `x * 1.0f` returns `0x00000000` for the operand `0x00000001`". It does not, on this row: it returns `00000001`, unchanged, under `safe`, `relaxed`, and `fast` at both `-O0` and `-O2`. ADR 0076's re-verification already contradicted the ticket on exactly this point, and this record confirms the ADR against the ticket. The correction matters beyond bookkeeping: the ticket's `x * 1.0f` row was one of the three cited in support of "Apple GPU `f32` arithmetic flushes subnormals in every mode", and it is the one row of the three that proves nothing. The claim itself survives on the other two, which this record reproduces with execution witnesses.

**Measurement — the recorded fast-math flag spellings hold only at `-ffp-contract=fast`.** ADR 0076 records that "under `relaxed` each carries `reassoc nsz arcp contract afn`; under `fast` each carries `fast`", without naming a contraction setting. On this row those exact spellings appear only at `-ffp-contract=fast`. At `off` and `on` the spellings are `reassoc nsz arcp afn` and `reassoc nnan ninf nsz arcp afn`; the table in finding 1 gives all nine. Nothing in the ADR's argument depends on the spelling, so this refines the record rather than unsettling a conclusion. It is recorded because a future reader comparing a new toolchain against the ADR's text would otherwise see a spurious difference.

**Measurement — the emitted operation count is not the whole mechanism.** Stated in full above. ADR 0076's inference is correct at `-O2` and does not cover `-O0`, where both operations survive into the emitted IR and still do not execute. Finding 19 now bounds that: `-O0` is the only one of the five offline levels at which it happens.

**Retraction — this record's own Inference that the subnormal flush was dtype-independent is refuted, not refined.** Until finding 21 this record closed with: "`MetalSubnormalArithmetic` is declared once as a target fact. Every measurement behind it is `f32`. `air.compile.denorms_disable` is a module-level declaration, which is an argument that the flush is dtype-independent and not a measurement of it … until it runs, the declared fact's dtype independence is an Inference." The Inference was correctly labelled and is now measured to be **false** on this row. The argument behind it — that the flush is declared once per module — survives as a fact about the *declaration* and is retained as finding 22, which is exactly what the declaration turns out not to establish. No stated `f32` measurement changes: every `f32` case row reproduced byte for byte when the dtype axis was added, which is the check that separates a widened harness from a changed one.

**Retraction — this record's own operation counts were incomplete for a fused call, and are corrected.** Until finding 16 the harness's fused-intrinsic pattern named only `llvm.fma` and `llvm.fmuladd`. This front end spells the intrinsic `air.fma.f32`, so any kernel whose arithmetic was a source-level `fma` would have been reported as emitting **zero** floating-point operations. No finding published before this one used such a kernel, so no stated count is wrong; the claim being retracted is the implicit one that the operation count was complete for the operations a Metal module can contain. It was complete for multiply and add only. Both spellings are matched now and finding 16 asserts the fused kernel's list is exactly `air.fma.f32`, so the correction is checked rather than asserted.

## Measurement boundaries

**Fact — one row, now three families wide on the compile side and two GPUs wide on the device side.** One machine, one Mac GPU, one macOS build, one Xcode build, one offline Metal toolchain build, one MSL version (`metal3.1`). Three SDKs and three targets — `air64-apple-macos13.0`, `air64-apple-ios16.0`, `air64-apple-ios16.0-simulator` — are compiled; two execution environments — the Mac GPU and one booted iOS 26.0 Simulator whose GPU is that same Mac GPU — are dispatched. This closes the boundary the previous version of this record carried ("Nothing here is evidence about … iOS device or simulator artifacts") in one direction and only one: the *compile side* is now measured for all three families (finding 11) and the *device side* is measured for the iOS Simulator (finding 13). A **physical** iOS device is still unmeasured, by finding 13; another Apple GPU family, another toolchain build, another OS build, Catalyst, and any non-Apple Metal implementation remain unmeasured. The [artifact-compatibility record](artifact-compatibility.md) already establishes that "Xcode 26.6" is an insufficient toolchain identity, and findings 8 and 12 show it is doubly insufficient: it identifies neither runtime compiler, and the two dispatchable families load two *different* runtime compiler builds, each moving with its execution environment rather than with Xcode.

**Fact — three compiler builds, not one, and the record names all of them per family.** The offline driver `metalfe-32023.883` is shared by every SDK; the macOS runtime compiler is `metalfe-32023.921` and the iOS Simulator runtime compiler is `metalfe-32023.830.1` (finding 12). A per-family agreement between offline and runtime is therefore an agreement between two genuinely different builds, and the retained record's `environment.family.<name>.runtime_compiler_build` rows are what identify which build delivered each family's numbers.

**Fact — `-fmetal-math-fp32-functions` is swept, and only over operations it does not govern.** Both `=precise` and `=fast` are measured, on both compilation paths, and finding 18 records that neither the emitted module nor any returned bit pattern moves. The flag governs the precision of the `f32` function implementations and this matrix calls none, so the useful content is that it is inert for multiply, add, divide, and a fused multiply-add. `sin`, `sqrt`, `rsqrt`, and every other function it actually governs remain unmeasured.

**Fact — optimization levels.** Offline, all five of `-O0`, `-O1`, `-O2`, `-O3`, and `-Os` are measured; finding 19 records that only `-O0` differs. The four-kernel, three-mode sweep of the three new levels lives in the exhaustive record and is re-checked only under the environment switch; the covering set the gate runs carries all five levels for `scale_one_bias_zero` under `safe`. On the runtime path the whole surface — `MTLLibraryOptimizationLevelDefault` and `Size` — is measured, because that is all there is.

**Fact — the physical iOS device is the one measurement boundary this ticket did not close.** Finding 13 states it exactly: `IOsDevice` is compiled and its emitted module read (finding 11's compile-side half covers it), but no bit pattern from iOS-device hardware is measured, because none is attached. Closing it needs a physical Apple-silicon iPhone or iPad running iOS, dispatching the `air64-apple-ios16.0` metallib on its own GPU. The device-side subnormal-flush claim for a real iOS device therefore rests on compile-side agreement with the two measured families (finding 11) plus the fact that the flush is declared in the module identically — an Inference, not a Measurement, and labelled as such wherever it appears.

**Fact — one iOS Simulator runtime and device.** The simulator side is one runtime, iOS 26.0 (26.0.1) build 23A8464, on whichever device the harness deterministically selects. Another simulator runtime version could load another runtime compiler build, which is why the runtime, device, and its "booted-by-probe" provenance are recorded — the last two as non-qualifying, because a device UDID differs between hosts running identical software and whether this run had to boot the device says nothing about what it then computed.

**Fact — the iOS Simulator's runtime archive is unavailable, so its module-flag corroboration is absent.** Finding 12: `serializeToURL:` aborts the simulator process, so the archive scan that corroborates finding 1 on macOS has no counterpart on the simulator, and `archived_options` is `unavailable` for that family with the exact abort recorded. The simulator's runtime compiler is still identified, through the loaded-image build string rather than the archive.

**Fact — the runtime compilation path is measured, and only through its own surface.** Findings 8, 9, and 10 close the boundary this record previously carried, which is what `prototype-metal-numerical-realization` had reported and nothing re-established. What remains unmeasured there is what `MTLCompileOptions` cannot express: no `-target`, no `-ffp-contract`, and no `-O0`, each recorded in finding 10 rather than approximated. The per-operation fast-math flag list of finding 1 has no runtime counterpart at all, because the runtime path emits no readable module; only the module-level `air.compile.*` names are recoverable, and only as a presence test over an undocumented container.

**Fact — the runtime compile-side observations are containment tests, not resolutions.** Where the offline path resolves the `!air.compile_options` named metadata node and reports exactly the strings the module attached, the runtime path can only ask whether a given byte sequence occurs in a serialized `MTLBinaryArchive`. The two agree on this row for every math mode, but the runtime form cannot establish an option *set* and cannot establish attachment, and it is treated as corroboration everywhere in this record.

**Fact — the operation vocabulary is multiply, add, divide, and a fused multiply-add in `f32`, and multiply, add, and divide in `f16`.** Findings 15 to 17 widen the `f32` vocabulary past the multiply and add this record previously carried, finding 17 supplies the reassociation counterexample the earlier three-fixture negative result does not, and finding 20 closes the gap inside the previously claimed vocabulary — that every adding kernel added *after* a multiply, so no add ever took a subnormal operand straight from the buffer. What remains unmeasured is transcendental and other library functions in either dtype, and any multi-element reduction shape: the chain of finding 17 exposes reassociation within one thread over compile-time constants, which is the licence a reduction would be subject to, and it is not a reduction over a buffer, a threadgroup, or a subgroup.

**Fact — the `f16` vocabulary is narrower than the `f32` one, and deliberately so.** The `f16` kernels cover exactly what finding 21 needs: materialization, the multiply in both flush directions, a bare add whose subnormal operand comes straight from the buffer, a surviving `fdiv` in both flush directions, the identity multiply, and the trap. Contraction, a source-level `fma`, and reassociation have **no `f16` counterpart** here, so findings 6, 16, and 17 are `f32`-only measurements and nothing in this record says whether contraction or a `reassoc` licence behaves the same at the narrower width. They were left out because the ticket's question is the flush and each would have added a contraction or optimization axis to the gate for a question nobody has asked; the cost of closing them is a kernel each, and [widen-the-f16-operation-vocabulary-to-contraction-and-reassociation](../../../tickets/widen-the-f16-operation-vocabulary-to-contraction-and-reassociation.md) carries it with the trigger that would make it worth paying.

**Fact — three dtypes are measured and the rest are `Unknown`.** `f32` flushes, `f16` preserves, `bf16` flushes (findings 21 and 24). `f64` where it exists and every integer and quantized format remain entirely unmeasured. An unmeasured dtype must not be predicted from a measured one — that is the exact error finding 21 refuted, and finding 25's exponent-field description is offered as a summary of three measurements rather than a rule for a fourth. Any positive per-dtype claim needs that dtype measured. The harness takes a new dtype as a `Dtype` row plus its kernels rather than as a change to its shape.

**Fact — the mechanism behind the three results is narrowed but not closed.** Finding 24 refutes "the hardware honours subnormals natively in narrow formats" and leaves "narrow arithmetic is evaluated at `f32` precision, rounded once" fitting all three dtypes with no free parameter. It does **not** separate that from "native `bfloat16` arithmetic flushing at its own subnormal boundary": the two agree on every operand this probe can supply, because a value is `bf16`-subnormal exactly when it is `f32`-subnormal, and no single operation can expose an `f32` intermediate because 24 bits exceeds the 18 that make a second rounding to `bfloat16` innocuous. The experiment that would separate them is named in finding 24 — a two-operation `bf16` chain whose intermediate rounding is observable — and is not carried by any ticket, because nothing in the numerical contract depends on the answer. The contract is written against what the target delivers.

**Fact — `bf16` is measured on one GPU, and the iOS Simulator's refusal is a boundary with an exact diagnostic.** Finding 26: every `bf16` module compiles and links for all three families, and the simulator then fails pipeline creation with `XPC_ERROR_CONNECTION_INTERRUPTED` on both compilation paths. The refusal is measured to be about the *format* rather than any operation on it — the arithmetic-free `materialize_bf16` is refused too, with an `f16` control dispatching before and after — but that leg is a one-off probe, `spikes/apple-targets/bfloat_dispatch_probe.py`, and not a gate-reproduced row. Whether the cause is a missing `bfloat` lowering in the simulator runtime's `metalfe-32023.830.1`, an absent capability on the simulated GPU, or a defect in that runtime build is **unmeasured** and is not guessed at. Closing it needs either a simulator runtime that accepts the module or a physical iOS device; the second is the same boundary finding 13 already draws.

**Fact — the `bf16` vocabulary is the `f16` one, and a source-level `fma` is not available to it at all.** The `bf16` kernels cover exactly what finding 24 needs: materialization, the multiply in both flush directions, a bare add whose subnormal operand comes straight from the buffer, a surviving `fdiv` in both flush directions, the identity multiply, and the trap. Contraction and reassociation have no `bf16` counterpart for the same reason they have no `f16` one. **A fused kernel is different: it is not omitted but impossible at this width.** This front end has no `bfloat` overload of `fma` and no `air.fma.bf16`; `fma(bfloat, bfloat, bfloat)` returns `float`, and writing it emits `fpext bfloat to float`, `air.fma.f32`, and `fptrunc float to bfloat`. Such a kernel would measure `f32` arithmetic wearing `bfloat` operands, so finding 16 has no `bf16` counterpart that could be written, and that is a measured property of the front end rather than a scope decision.

**Fact — a row measured only under the exhaustive switch is retained evidence, not a gate-protected value.** The exhaustive sweep is selected by `TILER_APPLE_NUMERICS_EXHAUSTIVE` and its record is compared only when it is set, so a toolchain change that moved one of those rows would go unnoticed until the next exhaustive run. The covering set keeps at least one case of every kernel, math mode, optimization level, contraction setting, and fp32-functions value, and a portable guard test fails if it stops doing so; that bounds the exposure without removing it. Finding 19's twelve-combination sweep is the only finding here that rests on an exhaustive-only row, and its covering-set half is named in the finding.

**Inference — what the harness protects and what it cannot.** The harness fails the gate when a `case.*`, `comparison.*`, or `hazard.*` row diverges from the retained record on the same environment row, so a toolchain change that alters any measured value — including the cross-family load of finding 14 — is loud rather than silent. It cannot detect a change on a different row: when the environment differs, including a different simulator runtime or none at all, it announces the difference and declines to compare, because a different toolchain or runtime build legitimately produces different values and quietly accepting them would defeat the purpose.

## Consequences for the contracts

**Fact — what is already adopted.** `MetalTargetFacts::subnormal_arithmetic` in `tiler-metal` takes `MetalSubnormalArithmetic::FlushesToZero` as a required caller-stated fact with the measurement recorded on the type, and `MetalNumericalGap::SubnormalFlushInArithmetic` records the unrealizable obligation. Both were introduced by `prototype-metal-numerical-realization` on the strength of the measurements this record now owns.

**Proposal — whether honourability is declared once or per family, which finding 11 now answers.** [declare-metal-numerical-honourability](../../../tickets/declare-metal-numerical-honourability.md) asks whether `MetalSubnormalArithmetic` must vary by `MetalPlatform` family. On this bounded row it need not: finding 11 measures the subnormal flush declared identically in the emitted module and observed identically wherever it can be observed, across all three families' compile side and the two dispatchable families' device side. So the flush can be declared once as an Apple-toolchain property rather than three times as a per-family one, provided the declaration keeps the boundary finding 13 draws — that the physical-iOS-device leg rests on compile-side agreement (Fact) plus an Inference, not on a device measurement. Had a single family diverged, the type would have had to carry the flush per family; the seam for that is a strongly typed per-family field, and this record is the evidence that it can start as one constant with an explicit trigger to split it. That decision belongs to whoever holds `contracts/decisions`.

**Proposal — what ADR 0076 should cite.** ADR 0076 is `proposed`, and its `evidence` frontmatter currently names the Apple compatibility probe for that probe's own disclaimer, because no record about the numerical behaviour existed. It should name `tiler.research.apple-targets.numerical-behaviour` instead, keeping the compatibility probe only where the flag-acceptance row is meant. Its fifth open question, "Where the Apple numerical measurement should durably live", is answered by this record and the checked-in harness and can be closed. That edit belongs to whoever holds `contracts/decisions`.

**Proposal — what `docs/backends/metal.md` should record.** The Metal backend contract currently carries the compatibility probe's statement that the strict flag row "did not observe the numerical behavior these flags request". This record closes that gap in one direction and only one: the strict row is measured **not** to deliver subnormal preservation. It is measured to deliver a signed-zero-conforming result and a non-contracted result, which the same contract already treats as `MetalNumericalRequirement`s.

**Proposal — what the contracts should now say about the second compiler and the artifact families.** Findings 8 and 12 are the durable identity consequences, and finding 11 is the durable numerical one. Three edits follow, none of which this record's owner holds:

- `docs/backends/metal.md` (`contracts/artifacts`) should state that the AOT backend's toolchain provenance identifies the offline compiler only, and that a runtime-compiled kernel is compiled by a separate, separately versioned compiler whose identity is not part of the artifact's recorded provenance — and, from finding 12, that this runtime compiler belongs to the *execution environment*, so it differs between the macOS host and the iOS Simulator on one machine (`metalfe-32023.921` versus `metalfe-32023.830.1` here). It should record the measured cross-path agreement of findings 9 and 12 as a bounded per-family measurement on one host row rather than as a property of Metal, and say plainly that a delivered realization read off an offline build is not thereby true of a runtime-compiled one — it merely coincided here. It should also carry finding 11's result — that on this row the three families' emitted modules agree byte-for-byte and the two dispatchable families' results agree — as a bounded measurement, and finding 13's boundary that the iOS Simulator's GPU is the host's and no physical iOS device was measured.
- ADR 0076 needs no change to its conclusion. Findings 9, 11, and 12 support rather than unsettle it, and finding 8 strengthens its central argument: numerical honourability must be a stated, versioned target fact precisely because the compiler that delivers it is not always the one the artifact names. If ADR 0076 gains a sentence, it should be that the versioned target fact has to identify *which* compiler and *which* execution environment the realization was measured on, because a single Metal host resolves one offline compiler and two runtime ones. `repoint-adr-0076-evidence-at-the-numerical-record` holds `contracts/decisions` and should carry the citation there.
- `declare-metal-numerical-honourability` (`contracts/decisions`) can, on this row, declare the subnormal flush once rather than per family, per the honourability Proposal above and finding 11 — recording the physical-iOS-device leg as the explicit trigger that would reopen the question.

**Proposal — two consequences of the widened vocabulary that the numerical contract should carry, neither of which this record's owner holds.**

- Finding 16 is a constraint on the Metal emitter, not on a compiler flag. `docs/numerical-semantics.md` and `docs/backends/metal.md` (`contracts/foundation` and `contracts/artifacts`) treat `-ffp-contract=off` as the measured defence against contraction; it is measured to be that only for a multiply and an add emitted as separate statements. An emitter that lowered a `MultiplyThenAdd` to a source-level `fma()` would deliver a contracted result at every contraction setting, undetected by any flag in this matrix. The per-statement emission rule is therefore load-bearing rather than stylistic, and should be stated as a requirement on emission with finding 16 as its evidence.
- Finding 17 is a constraint on which math modes may be admitted where a reduction order is promised. A target profile that admits `relaxed` or `fast` cannot promise one on this row, because a two-add chain is measurably reassociated under both. Whoever owns the numerical contract should decide whether reduction order is a stated obligation and, if it is, whether admitting those modes is a feasibility rejection or a declared numerical gap in the sense `MetalNumericalGap` already uses.

**Proposal — the dtype question is settled, and it lands on a type this record does not own.** Finding 21 measures `MetalSubnormalArithmetic::FlushesToZero` to be true of `f32` arithmetic and false of `f16` arithmetic on this row, so a single dtype-free declaration cannot be correct for both. Finding 24 adds `bf16` as a third measured row that agrees with `f32`, so the per-dtype table the type needs now has three entries with a real measurement behind each. Two consequences follow, and neither belongs to `research/apple-targets`:

- `MetalTargetFacts::subnormal_arithmetic` in `tiler-metal` (`implementation/metal`) states the flush as one caller-stated fact with the measurement recorded on the type. It has to become a per-dtype statement, or the type has to name the dtype the fact applies to and reject a query about any other, because the current shape can only answer a question it was not measured for. Note which direction the error runs: an `f16` kernel read against the `f32` fact is told a subnormal is unusable when it is carried exactly, so the failure is an over-rejection or a spurious `MetalNumericalGap` rather than a wrong tensor — but a *reference* evaluation that flushes to match a device that does not would produce one. [carry-the-dtype-on-the-metal-subnormal-flush-fact](../../../tickets/carry-the-dtype-on-the-metal-subnormal-flush-fact.md) carries it, and can now declare `f32` and `bf16` as flushing and `f16` as preserving, each on the strength of a witnessed measurement. **Three cautions belong with those rows.** The `bf16` row is measured on `MacOs` only (finding 26), so a per-family split of that row is `Unknown` where the `f32` and `f16` rows are measured on two GPUs. Every dtype the table does not name must reject rather than default, because finding 24's whole content is that a neighbouring dtype predicts nothing. And the exponent-field pattern of finding 25 is a description of three measurements, not a rule the type may extrapolate with.
- ADR 0076's re-verification and its subnormal-flush Measurement are stated without a dtype, and its evidence bullet describes this record as owning "the on-device and compile-side measurements". Both remain true of `f32` and both now under-state their scope. Repairing them belongs to whoever holds `contracts/decisions`; the same ticket above names the ADR edit as its dependent, and no conclusion of ADR 0076 is unsettled by finding 21 — the ADR's central argument, that numerical honourability must be a stated versioned target fact rather than inferred from a compiled kernel, is *strengthened* by a case where the module declaration and the delivered arithmetic disagree.

**Proposal — finding 11's "declare the flush once" conclusion survives across families and does not survive across dtypes.** The two axes are independent and this record now answers them differently. Across `MacOs`, `IOsDevice`, and `IOsSimulator` the flush is declared and observed identically, so `MetalSubnormalArithmetic` need not vary by family (finding 11). Across `f32`, `f16`, and `bf16` it is observed to differ, so it must vary by dtype (findings 21 and 24). [declare-metal-numerical-honourability](../../../tickets/declare-metal-numerical-honourability.md), which asks the per-family question, should record both: one constant across families, one field per dtype, with the physical-iOS-device leg still the trigger that would reopen the family question.

**Proposal — a device that refuses a dtype is a capability question the physical contracts have no name for.** Finding 26 measures a family whose toolchain compiles and links a module its own device then declines to run. That is neither a compile-side fact nor a numerical one: it is a *capability* of an execution environment, and a planner that assumed "it compiled for this target, therefore it runs there" would be wrong on this row. Whoever owns the Metal target profile should decide whether per-dtype dispatchability is a stated target capability with a typed feasibility rejection, or whether it stays a runtime preflight failure. It is a real correctness seam — the failure is loud rather than silent here, which is the good direction, but it arrives after artifact production rather than before plan selection. This record does not hold that scope and names no ticket for it, because the choice is a genuine architectural one rather than a settled consequence.
